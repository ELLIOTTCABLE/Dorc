## Findings

- +SURE: Mature large Rust projects preserve difficult invariants with layered controls, not typing alone: compiler-denied defaults, explicit exception boundaries, point-of-use safety arguments, independent specialist review, and merge-commit testing. [B-chromium-rust-unsafe-build-rule-2026] [A-linux-rust-coding-guidelines-2026] [B-ferrocene-development-process-2026]
- +SURE: The review unit must include all code capable of violating an invariant, not merely the visibly dangerous operation; Ferrocene requires review and tests across the unsafe module and its clients. [B-ferrocene-handling-unsafety-2026]
- +SURE: Review approval must attach to exact bytes: Ferrocene invalidates prior approval after material changes and tests the exact merge commit that lands. [B-ferrocene-development-process-2026]
- +SURE: Scarce expertise scales better when architectural boundaries make exceptions mechanically visible and route them to the relevant owner; Chromium's target-level unsafe opt-in and rustc's file/team reviewer routing are concrete examples. [B-chromium-rust-unsafe-build-rule-2026] [B-rust-compiler-contribution-process-2026]
- +SURE: Rust's `expect`-over-`allow` mechanism provides a useful self-expiring-exception pattern: the compiler reports when an exception no longer matches reality, limiting silent policy residue. [A-linux-rust-coding-guidelines-2026]
- ~SUSPECT: Cargo Vet's most transferable idea is not dependency auditing itself but typed review evidence: named criteria, designated owners, in-tree records, incremental adoption, and CI refusal keep "reviewed" from collapsing into an unqualified trust bit. [A-cargo-vet-workflow-2026] [A-cargo-vet-audit-criteria-2026]
- +SURE: The Rust-specific prior art does not support a claim that types can encode arbitrary semantic security invariants. It supports concentrating semantic obligations at narrow APIs and exceptions, then binding human review and tests to those exact boundaries.
