**1. PRE-REGISTERED LESSONS**

Source register used before corpus exposure: [A-wadler-chi-2016] `homepages.inf.ed.ac.uk/wadler/papers/chi-sig-usability/chi-sig-usability.pdf`; [A-typescript-goals] `github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals`; [A-pep484] `peps.python.org/pep-0484`; [A-typed-racket-2017] `www2.ccs.neu.edu/racket/pubs/typed-racket.pdf`; [A-fish-design] `raw.githubusercontent.com/fish-shell/fish-shell/master/doc_src/design.rst`; [A-oils-faq-2023] `oilshell.org/blog/2023/03/faq.html`; [A-tc39-types-comments] `tc39.es/proposal-type-annotations`; [A-guido-reduce-2005] `artima.com/weblogs/viewpost.jsp?thread=98196`.

No lessons were added after corpus exposure.

1. A shell-adjacent gradual language must define the compatibility boundary as a user-visible contract: which plain-sh idioms remain plain sh, which idioms acquire analyzer meaning, and which future extensions are syntactically reserved. If that boundary is implicit or spread across folklore, real users will write code that accidentally becomes metadata or blocks future syntax.

2. “Looks like ordinary shell” is only ergonomic when the added meaning is locally visible. If a reader must know whole-program analyzer rules to tell whether `foo`, `foo.bar`, `VAR=value cmd`, or a trailing token is operational shell or language metadata, the notation has poor role-expressiveness and will hurt both admins debugging incidents and engineers reviewing libraries.

3. Gradual systems succeed by minimizing perturbation during migration, but every annotation must have a clear cost model: what it changes at runtime, what it changes only for tooling, and what failure mode occurs when it is absent, stale, or wrong. Hidden runtime effects or ambiguous absence semantics are adoption traps.

4. Added syntax should preserve progressive evaluation: a user should be able to run, lint, inspect, or partially author a script and get useful feedback before the whole dialect context is complete. Features that only make sense after global inference, naming discipline, or paired generated artifacts are high-risk.

5. Prefer a small number of orthogonal forms over many clever near-synonyms. If two spellings differ semantically, users need a short explanation and a visible cue; if they do not differ, one spelling should probably die before compatibility freezes it.

6. Namespaces and naming conventions are language features, not documentation details. If periods, prefixes, suffixes, or status-number ranges carry meaning, their grammar, ownership, collision behavior, and evolution path must be explicit from day one.

7. Machine-emitted code is part of the language surface. It should be readable, stable enough for users to recognize, and clearly separated from hand-authored code; otherwise users will debug, cargo-cult, or depend on accidental generator artifacts.

8. Diagnostics and refusal idioms are part of ergonomics, not just semantics. A dialect that asks users to encode uncertainty, refusal, or “not licensed” states must make those states easy to spell correctly, hard to confuse with ordinary failure, and easy to diagnose from plain shell execution.

9. Backwards compatibility does not merely preserve old code; it preserves old mistakes. Any “strawman” spelling that appears in examples, fixtures, stdlib candidates, or generated artifacts must be treated as potentially sticky and reviewed now for reserved syntax, deprecation path, and migration tooling.

10. For two-audience languages, the same notation must be evaluated separately under authoring, reading, debugging, and reviewing tasks. A spelling that is fine for a careful library engineer may be hostile to a rushed admin, and vice versa; good design should make the careful path more informative without making the scrappy path feel like a DSL tax.

11. The language should exploit substrate familiarity without inheriting substrate footguns unnecessarily. Reusing sh syntax is good when it lets existing scripts keep working or makes intent obvious; it is bad when it smuggles in quoting, scoping, exit-status, or command-substitution ambiguities for a new semantic purpose.

12. Escape hatches and future modes should be designed before first bulk authorship. If the dialect will need stricter checking, new annotation forms, or generated-code versioning, there must be an opt-in/version/mode story comparable to `__future__`, TypeScript compiler options, or Oils’ OSH/YSH split rather than ad hoc breaking changes.
