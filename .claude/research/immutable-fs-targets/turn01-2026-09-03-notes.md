## Findings

- +SURE that H1 SURVIVES for every read-only-root system I could reach a primary for, but the
  reason splits into two mechanisms that behave very differently: (a) read-only-root-plus-writable-
  tmpfs (OpenWrt [B-openwrt-filesystems-techref-2026], HAOS [A-haos-operating-system-architecture-2024],
  rpm-ostree [A-fedora-atomic-desktops-filesystem-2025], Flatcar [B-flatcar-faq-immutable-usr-2026],
  TrueNAS [A-truenas-developer-mode-readonly-root-2026]); and (b) EVERYTHING-writable-but-volatile,
  where the "read-only" system actually presents a fully writable root backed by RAM (Raspberry Pi OS
  overlay mode [A-raspi-config-overlayfs-source-2026], Alpine diskless
  [B-alpine-diskless-mode-wiki-2026]). Class (b) is the one the framing gets wrong: on a
  read-only Pi, `cat > /tmp/x` AND `cat > /root/x` both succeed; the writes just vanish on reboot.
- +SURE that the nowhere-writable set is narrower than {hardened containers, failure states}: it is
  essentially `readOnlyRootFilesystem: true` with no emptyDir mounted
  [B-k8s-security-context-readonly-root-2026] plus the failure states of Q2. No general-purpose
  distro or homelab appliance I reached ships with no writable path.
- +SURE that a DIFFERENT exclusion is much harder than filesystem writability, and it removes hosts
  from the population entirely: MikroTik RouterOS states in its own docs that because its SSH server
  does not support pseudo-tty for `ssh -T` / `ssh host command`, "it is not possible to send
  multiline commands via SSH" [A-mikrotik-routeros-ssh-no-multiline-2026]. The archetypal "weird
  homelab router" is not a fs-unwritable Dorc target; it is a non-target.
- +SURE that H4 is HALF TRUE and the half matters. dash never touches the filesystem for a
  here-document — `openhere()` uses `sh_pipe()`, i.e. `memfd_create()` above PIPESIZE and `pipe()`
  below, forking a writer child for the overflow case [A-dash-openhere-redir-source-2026]. busybox
  ash is the same shape, pipe-only with a forked writer above PIPE_BUF [ops-glue-residue:A-busybox-ash-source-2024].
  But bash uses a pipe ONLY when `shell_compatibility_level > 50` and the expanded document fits
  `HEREDOC_PIPESIZE`; otherwise it calls `sh_mktmpfd("sh-thd", MT_USERANDOM|MT_USETMPDIR, &filename)`
  and, on failure, prints "cannot create temp file for here-document"
  [A-bash-53-release-tarball-2025]. The pipe path arrived in bash 5.1. So a here-document in the
  artifact writes to the filesystem exactly on bash-as-sh below 5.1 (macOS /bin/sh is bash 3.2;
  RHEL8 is 4.4) — ALWAYS, at any size — and on bash >= 5.1 only above the build-measured pipe
  capacity.
- +SURE that bash's temp-dir search is a five-step ladder (`$TMPDIR`, `P_tmpdir`, `/tmp`, `/var/tmp`,
  `/usr/tmp`, then `"."`), gated by `file_iswdir` = `file_isdir && sh_eaccess(fn, W_OK) == 0`
  [A-bash-53-release-tarball-2025]. That is exactly the Q5 "`[ -w ]` lies" case: `sh_eaccess(W_OK)`
  passes on a directory that is full, quota-exhausted, or protected by `fs.protected_regular`.
- +SURE that Ansible has NO fallback ladder at all, contra the brief's "fallback ladder" framing.
  `_make_tmp_path` issues one `mkdir` against `remote_tmp` (default `~/.ansible/tmp`) and raises
  `AnsibleConnectionFailure` on any failure [A-ansible-action-make-tmp-path-source-2026]; the
  operator is expected to reconfigure `remote_tmp` by hand, which is literally what the error text
  says. The one machine-made choice is switching to `system_tmpdirs` (`[/var/tmp, /tmp]`) when
  becoming an unprivileged user [A-ansible-shell-common-options-2026].
- +SURE that ENOSPC on the staging directory is a first-class, separately-messaged failure inside the
  incumbent: `elif u'No space left on device' in result['stderr']` appears verbatim in Ansible's
  tmp-path error handling [A-ansible-action-make-tmp-path-source-2026]. Supports H2's "ENOSPC
  dominates" half from the tool side.
- ~SUSPECT that the ENOSPC half of H2 is WEAKENING on current Debian-family hosts: from Debian 13
  trixie `/tmp` defaults to tmpfs at up to 50% of RAM [A-debian-trixie-release-notes-issues-2025], so
  a full root filesystem no longer takes `/tmp` with it. The replacement failure is memory pressure,
  and a new hazard appears — systemd-tmpfiles now ages files out of `/tmp` after 10 days and
  `/var/tmp` after 30 on new installs.
- ~SUSPECT that `fs.protected_regular` is NOT a hazard for a private `mkdir -m 700` scratch dir: the
  kernel documents it as blocking `O_CREAT` opens of regular files "that we don't own in world
  writable sticky directories" [A-linux-sysctl-fs-protected-regular-2026]. It bites the shared-`/tmp`
  handoff (write as user, open as root), which is exactly Ansible's become-unprivileged path, not a
  freshly-created private directory.
- +SURE that the most explicit writable-scratch fallback ladder in the field belongs to Mitogen, and
  +SURE that Mitogen is NOT a no-filesystem story: it executes modules from RAM and avoids
  intermediary files, but "Temporary directories must exist to maintain compatibility with Ansible",
  and its interpreter tries nine paths in order until one is writable, ending at the current working
  directory [A-mitogen-ansible-tempfile-ladder-2026]. Even the RAM-only bootstrapper wants one
  writable directory.
- +SURE that vanilla Ansible may create up to six distinct temp paths per task, enumerated by a
  third party who reimplemented the layer [A-mitogen-ansible-tempfile-ladder-2026] — useful as the
  cost baseline that one-artifact-per-phase avoids.
- +SURE that the enterprise and appliance read-only-root mechanisms all name a writable-tmpfs list
  as part of the supported configuration, not as a workaround: RHEL's `/etc/rwtab` ships the literal
  line `empty /tmp` [A-rhel8-readonly-root-rwtab-2026]; Ubuntu Core's `writable-paths(5)` ships
  `/tmp none temporary none defaults` and states that anything unlisted is "by definition read-only"
  [A-ubuntu-core-writable-paths-manpage-2014]; systemd's own `ProtectSystem=strict` documentation
  says outright that "/tmp/ and /var/tmp/ will be writable" when `PrivateTmp=` is on
  [A-systemd-exec-protectsystem-privatetmp-2026]; and even Debian's DIY recipe opens by declaring
  which locations "must be writable" [B-debian-wiki-readonly-root-2026].
- ~SUSPECT that the H2 sub-claim "ext4 `errors=remount-ro` is the Debian default" is true only of
  the installer-generated fstab, not of the filesystem: e2fsprogs sets
  `EXT2_ERRORS_DEFAULT = EXT2_ERRORS_CONTINUE` in the superblock
  [A-e2fsprogs-ext2fs-errors-default-2026], and the kernel treats `errors=` as a mount option
  overriding that superblock value [A-kernel-ext4-admin-guide-options-2026]. Debian's own wiki
  recommends the `ro,errors=remount-ro` fstab line [B-debian-wiki-readonly-root-2026], which is the
  best evidence I have for the distro convention; I did NOT reach a primary from the installer
  itself. A related trap in the same kernel page: a plain `ro` ext4 mount still writes, because the
  journal is replayed; only `ro,noload` stops writes.
- +SURE that `noexec` on `/tmp` is a live, broadly-referenced hardening requirement (CIS plus DISA
  `SRG-OS-000368-GPOS-00154`, with CCEs for RHEL 8/9/10, SLE and Oracle Linux), and that a sibling
  rule imposes the same on `/var/tmp` [A-complianceascode-tmp-noexec-rule-2026]. +SURE that the
  consequence is narrower than it looks, because `noexec` blocks `execve`, not `open`: `sh /tmp/f`
  still runs on a `noexec` `/tmp`, while `chmod +x /tmp/f && /tmp/f` does not.
- +SURE that Docker treats writable-but-noexec scratch as ordinary: `noexec` is a documented
  `--tmpfs` option and the docs' own worked example is `--tmpfs /data:noexec,size=1024,mode=1777`
  [A-docker-tmpfs-mounts-noexec-2026].
- +SURE that the incumbents' behaviour under an unexpectedly-unwritable host is documented failure,
  not degradation. Ansible issue 25831 is precisely the H2 scenario — VMs whose root went read-only
  after a datastore failure, being probed to decide which to reset — and it fails with
  `mkdir: cannot create directory '/tmp/xxx': Read-only file system`, reporting the host
  UNREACHABLE; filed 2017 as a "feature idea", closed unfixed
  [B-ansible-issue-25831-readonly-root-2017]. salt-ssh has no memory-only mode at all: it "needs to
  upload a standalone environment to the target system", `thin_dir` defaulting to `/tmp/salt-<hash>`
  [A-saltssh-roster-thin-dir-2026]. cdist exposes only a knob, `-r REMOTE_OUT_PATH` / `remote_out_path`,
  "Directory to save cdist output in on the target host" [ops-glue-residue:A-cdist-manual-cli-reference-2026].
- +SURE for the Q6 counter-thesis at its strongest: Talos states flatly "Talos has no interactive
  shell and no writable filesystem", with no package manager and no mutable user space, managed only
  through an API; `talosctl copy` copies files FROM nodes and has no push counterpart
  [A-talos-for-linux-admins-no-writable-fs-2026]. In that class ssh-push is architecturally
  foreclosed, and the same is true from the other direction on RouterOS
  [A-mikrotik-routeros-ssh-no-multiline-2026].
- +SURE that POSIX itself constrains the slurp shape: for `$(…)`, "if the output ends with one or
  more bytes that have the encoded value of a <newline> character, they shall not be included in the
  replacement", and "If the output contains any null bytes, the behavior is unspecified"
  [ops-glue-residue:A-posix-2024-shell-language-2024]. ~SUSPECT (mechanism, not measured) that an
  `eval "$(cat)"`-shaped slurp additionally consumes stdin to EOF before evaluating, so the
  artifact's interior commands see a closed/EOF stdin rather than the remainder of the artifact —
  a different failure mode from the current pipe shape, not an absence of one.
- +SURE that the conventional writability probe is unreliable in exactly the ways the brief
  suspected, with two independent primaries: bash's own `file_iswdir` reduces to
  `file_isdir && sh_eaccess(W_OK)` [A-bash-53-release-tarball-2025], which cannot see ENOSPC,
  quota, or `fs.protected_regular`; and `findmnt`'s man page explicitly warns that "The default
  output, is subject to change… you should avoid using default output in your scripts"
  [A-findmnt-manpage-mount-options-2026], which condemns the `findmnt PATH | grep " ro,"` idiom that
  Raspberry Pi's own tooling uses [A-raspi-config-overlayfs-source-2026].
- -GUESS on population habit: I could NOT find a usable primary or even a decent secondary on
  whether homelabbers actually want ssh-push management of their read-only-fs hosts. Kagi's
  `site:reddit.com` results for this were uniformly off-target. The nearest real evidence remains
  the sibling round's OpenWrt collection [ops-glue-residue:A-ansible-community-openwrt-user-guide-2026], which proves
  demand for pushing to constrained routers but says nothing about writability.
