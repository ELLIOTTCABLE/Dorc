  separation is this front's main result. Of the eight best-evidenced effort artefacts I read, five
  are SH-SHAPED — an admin writes a shell script, ships it to the device, and the device runs it:
  Asuswrt-Merlin's ~20 named `/jffs/scripts/` hooks [A-asuswrt-merlin-user-scripts-hooks-2026],
  ghettoVCB's seventeen years of POSIX sh inside the ESXi shell
  [A-ghettovcb-esxi-shell-script-2025], Synology_HDD_db's 5,821-star bash script
  [A-synology-hdd-db-shell-script-2026], UniFi's `/data/on_boot.d` runner
  [B-unifi-common-on-boot-d-2026], QNAP's autorun processor
  [B-qnap-create-autorun-script-processor-2025]. Three are NOT-SH-SHAPED, and in each the effort went
  into reimplementing distribution in the device's OWN language or into an off-box API client:
  RouterOS Scripts [A-routeros-scripts-pull-distribution-2026], netmiko's per-vendor screen-scraping
  drivers [A-netmiko-screen-scraping-drivers-2026], Dell's own Redfish scripting library
  [A-dell-idrac-redfish-scripting-offbox-2026]. So the metric does two jobs at once: it finds the
  weird hosts, AND it says which of them are reachable in sh at all.
- +SURE that EVERY sh-shaped artefact on that list is a BOOT-HOOK re-invention rather than a push
  tool, and each one states the same reason: the change does not survive. QNAP's own wiki: "you
  cannot use the usual Linux methods for launching an application at startup: default config files
  are reset on every startup" [B-qnap-autorun-flash-config-partition-2021]. unifi-common exists to
  survive firmware upgrades [B-unifi-common-on-boot-d-2026]. Synology_HDD_db "would need to
  re-run ... after a DSM update" and its scheduled task exists for exactly that
  [A-synology-hdd-db-shell-script-2026]. ghettoVCB's cron-survival procedure ends in
  `/sbin/auto-backup.sh` writing config to `/bootbank`, and it warns `/tmp` logs "may not persist
  through reboots" [A-ghettovcb-esxi-shell-script-2025]. Merlin's scripts live on a JFFS flash
  partition gated behind an nvram flag [A-asuswrt-merlin-user-scripts-hooks-2026]. Read together:
  the scarce capability on this frontier is DURABILITY, not writability. The charter's
  `fs-durable` — which it notes cannot be tested, only intuited — is the thing all these people are
  fighting; `fs-write` is free almost everywhere.
- +SURE that the effort-invested set and the fs-unwritable set are close to DISJOINT. Not one
  sh-shaped effort artefact I read is on a host with nowhere to write. Every one of them writes: to
  `/jffs`, to `/data`, to `/tmp`, to a mounted flash config partition, to a `/share/CACHEDEVn_DATA`
  volume. This independently reproduces front-2's finding from a completely different direction — I
  selected on "somebody bothered", not on "read-only root", and still hit no nowhere-writable row.
- +SURE (Q9, front-2's most load-bearing gap) that ESXi's interpreter is busybox ash, from the
  maintainer's own captured terminal output rather than from vendor prose: `ps -c` shows the script

  OpenWrt.
- +SURE that VMware's OWN scripting doctrine for ESXi points OFF the box: the supported "run this
  against many hosts" pattern is a `#!/bin/bash` loop on one administration server calling
  `esxcli --config` per target with credentials in a per-host `.visdkrc`

  answer the same question in opposite directions; front-2's "break-fix framing" read

- +SURE (Q9, Synology) that bash is present and is the interpreter the largest community script
  actually uses — its troubleshooting table's first row is `/usr/bin/env: 'bash\r': No such file or
  directory` from CRLF line endings, which only happens if `#!/usr/bin/env bash` resolves — and that
  `sudo -s` reaches root over ssh [A-synology-hdd-db-shell-script-2026]. On `/bin/sh` specifically,
  the packaging framework's maintainers state "On DSM < 6 and SRM, /bin/sh is ash (BusyBox), not
  bash", with DSM 6+ described as behaving the way bash does, and note SRM still uses ash
  [B-synocommunity-dsm-srm-ash-binsh-2026]. Front-2's two contradicting secondaries are both right,
  about different versions.
- +SURE (Q9, QNAP) that the row is real and that its hazard is persistence, not the interpreter.
  bash, curl and sudo are all present — the documented install is `curl -skL ... | sudo bash`
  [B-qnap-create-autorun-script-processor-2025] — the login shell is busybox ash with `/opt/bin/bash`
  reachable via Entware, and QTS resets default config files on every startup, so persistence means
  mounting a raw flash config partition whose device path DIFFERS PER MODEL (`/dev/mtdblock4`,
  `mtdblock5`, `sdx6`, `sdc6`, `mmcblk0p5`, `mmcblk0p7`, `ubi2:config`, or on HAL machines
  `mount $(/sbin/hal_app --get_boot_pd port_id=0)6`) and, since QTS 4.3.3, flipping a Control Panel
  toggle [B-qnap-autorun-flash-config-partition-2021].
- +SURE (Q10) that sshd itself does NOT need a writable filesystem at session time, on the
  documentary evidence, though I could not close every sub-question. The privsep requirement is
  EXISTENCE and PERMISSIONS, not writability: `/var/empty` "should be empty, not shared with other
  system accounts and not readable or writable by the sandbox user", set up with mkdir/chown/chmod
  755 [A-openssh-readme-privsep-var-empty-2026]. And login records cannot break a session:
  `login_write()` calls whichever of syslogin/lastlog/utmp/wtmp/utmpx/wtmpx/wtmpdb handlers autoconf
  selected, DISCARDS every return value, and `return (0)` unconditionally
  [A-openssh-loginrec-write-nonfatal-2026]. So the failure mode in the field is not sshd refusing to
  serve; it is everything ELSE in a login — PAM session modules, the home directory, the login
  shell's own rcfiles — which I could not source, because Stack Exchange refused every fetch (see
  Failures).
- +SURE (Q11) that a file descriptor above 2 is NOT a portable return channel, and this is the
  sharpest constraint the question has. `sudo` "will close all open file descriptors other than
  standard input, standard output, and standard error when executing a command" BY DEFAULT; the
  escape `-C` refuses values under three and "the sudoers policy only permits use of the -C option
  when the administrator has enabled the closefrom_override option"
  [A-sudo-closes-fds-above-stderr-2026]. Stacked on front-2's FreeBSD finding that only
  `/dev/fd/0-2` exist under plain devfs [A-freebsd-fdescfs-manpage-devfs-only-2023], in-band framing
  on stdout or stderr is the only channel that survives BOTH a BSD appliance and a sudo boundary
  with no prior setup.
- ~SUSPECT (Q11) that the two framings worth stealing from are git's side-band and apt's Status-Fd,
  and that git's carries two design decisions a return channel wants. side-band-64k is a 4-byte
  pkt-line length plus a ONE-BYTE stream code — 1 pack data, 2 progress, 3 "fatal error message just
  before stream aborts" — and the progress channel is separately suppressible while "the sideband
  channel 3 is still used for error responses" [A-git-sideband-64k-stream-codes-2025]. apt's is the
  fd-named cousin: typed colon-separated records (`pmstatus`, `dlstatus`, `pmerror`, `pmconffile`,
  `media-change`), and notably the spec's own worked example writes to FD 2, not to a high fd
  [A-apt-status-fd-progress-protocol-2022]. For the reverse-HTTP shape the human floated, the
  existing prior art is cloud-init's phone_home module, already held by the sibling round
  [ops-glue-residue:A-cloudinit-phone-home-source-2026]; the in-band-on-stdout precedents are also
  already held there [ops-glue-residue:A-adb-shell-protocol-header-2026]
  [ops-glue-residue:A-k8s-remotecommand-v4-source-2026].
- +SURE (Q7) that the "no-shell OS" family is THREE tiers, not one, and only the third is genuinely
  shell-less. (a) SSH-AND-EDIT: Flatcar ships a socket-activated OpenSSH daemon, a `core` user with
  sudo, and a writable `/etc`; the documented day-2 procedure is to drop a snippet into
  `/etc/ssh/sshd_config.d/`, write a systemd drop-in, and `systemctl daemon-reload`
  [A-flatcar-customizing-sshd-day2-2026]. Fedora CoreOS is the same once booted, provisioning
  `ssh_authorized_keys` for a `core` user [A-fedora-coreos-ignition-first-boot-only-2026].
  (b) SHELL-BEHIND-A-LADDER: Bottlerocket has "no SSH server in a Bottlerocket image, and not even a
  shell", but control container → `enable-admin-container` → admin container (ssh, or
  `apiclient exec admin bash`) → `sheltie` yields a FULL ROOT SHELL on the host
  [A-bottlerocket-no-shell-sheltie-ladder-2026]. (c) NO-SHELL-AT-ALL: Talos, where the escape hatch
  is a privileged container built from an image the operator supplies

- +SURE that for the Ignition family the immutability constrains PROVISIONING, not ACCESS, and both
  projects say so in their own words. FCOS: "Ignition runs only once during the first boot of the
  system (while in the initramfs)" and the remedy for a wrong config is to "fix the configuration and
  re-deploy the instance from a fresh image" [A-fedora-coreos-ignition-first-boot-only-2026].
  Flatcar: "Since Butane Configs are only applied on first boot, existing machines will have to be
  configured in a different way" — and that different way is ssh-and-edit
  [A-flatcar-customizing-sshd-day2-2026]. The reprovision doctrine binds the DECLARATIVE surface; it

- +SURE that Bottlerocket's vendor states the escape hatch is a dead end for configuration, which is
  the sharpest available statement of the granule this round cares about: from `sheltie` "you can
  inspect and change even more as root, [but] Bottlerocket's filesystem and dm-verity setup will
  prevent most changes from persisting over a restart"
  [A-bottlerocket-no-shell-sheltie-ladder-2026]. A full root shell on a host where writes do not
  survive is precisely the `fs-write` yes / `fs-durable` no cell.
- +SURE that Talos's day-2 surface is a TYPED STRUCTURED MERGE against a running node, not a command
  push: `talosctl patch mc --nodes <ip> --patch patch.yaml`, with strategic-merge or JSON6902

  declarative-adjacent: relaxing `kernel.kptr_restrict` for a tracing tool is done by a machine-config

- +SURE (direct hit on this round's own question) that OpenWrt's IDIOMATIC multi-setting spelling is a
