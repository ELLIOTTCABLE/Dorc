## Findings

- +SURE that the H-shoe-in hypothesis is HALF WRONG, and the wrong half matters more than the right
  half. The Python precondition is real and Ansible states it in its own installation guide — the
  managed node "requires Python to run Ansible-generated Python code"
  [A-ansible-managed-node-requirements-2026] — and Ansible has conceded the no-Python tier
  ARCHITECTURALLY rather than fixed it: "Because the majority of network devices can not run Python,
  the Ansible network modules are executed on the Ansible control node"
  [A-ansible-network-modules-run-on-control-node-2026]. But the sh-only floor is NOT vacant ground:
  pyinfra states its target "need[s] nothing aside the SSH daemon running"
  [A-pyinfra-getting-started-target-precondition-2026] and its command builder really does wrap every
  command as `sh -c '…'` [A-pyinfra-make-unix-command-askpass-2026], and cdist makes the same claim
  [ops-glue-residue:B-cdist-why-2026]. Two siblings already occupy the interpreter floor.
- +SURE that the residual stranding is therefore NOT the interpreter — it is the FILE LANE and the
  LOGIN SHELL, and both are sourceable. pyinfra's file operations go through
  `get_file_transfer_connection`, which is SFTP by default or SCP by option, and raises "Unable to
  establish SFTP connection" when the subsystem is absent; the sudo path additionally shells out to
  `setfacl`, and rsync mode needs `rsync` on the target
  [A-pyinfra-ssh-connector-sftp-setfacl-2026]. Vanilla OpenWrt ships Dropbear with NO sftp-server
  [B-openwrt-sftp-server-dropbear-2026], which dropbear upstream confirms is not its to provide
  ("The sftp-server program is not provided by Dropbear itself")
  [A-dropbear-default-options-no-sftp-server-2026]. So on the single most archetypal weird homelab
  host, the sibling that claims sh-only cannot put a file until something else has already been
  installed over the network.
- +SURE that Ansible's precondition is TWO things, not one, and the second is the one that bites
  appliances: the managed node "also needs a user account that can connect through SSH to the node
  with an interactive POSIX shell" [A-ansible-managed-node-requirements-2026]. Three sourced rows
  deny exactly that while having a perfectly good ssh daemon: pfSense binds the `admin` account to
  the console menu as its shell (root is the account that is "not locked into the menu for its
  shell", and the observable symptom is scp failing with `Illegal option -t`)
  [A-pfsense-scp-root-menu-shell-2024]; Windows ships an in-box OpenSSH server whose DefaultShell is
  `cmd.exe` until a registry value says otherwise [A-microsoft-openssh-default-shell-cmd-2025]; and
  Junos/NX-OS put a network CLI in front of the shell
  [A-junos-start-shell-csh-sh-2023][A-cisco-nxos-feature-bash-shell-gated-2026].
- +SURE that pyinfra's own privilege path needs writable AND EXEC-able scratch, which is a second,
  independent stranding axis nobody advertises: `ASKPASS_COMMAND` mktemps a file under `$TMPDIR`,
  writes it with a here-document, `chmod 755`s it and hands the path to `SUDO_ASKPASS`
  [A-pyinfra-make-unix-command-askpass-2026]. That fails on a read-only root and on a `noexec` /tmp
  — and `noexec` on /tmp is a live hardening baseline [A-complianceascode-tmp-noexec-rule-2026].
  Whereas a `sh <file>` route survives `noexec`, because the shell reads rather than execs.
- +SURE that H-frontier-is-small SURVIVES, and the short list is genuinely short (see "The short
  list" below). Of the ~25 candidate rows the brief named, several turn out to be plainly ORDINARY
  writable Linux with OpenSSH and Python — Proxmox VE most emphatically, whose own installation
  chapter says it is "a complete Debian system" and that after boot "automation tools like Ansible
  can be used to further configure the installation" [A-proxmox-ve-debian-based-installation-2026] —
  and two are non-targets already settled by turn01 (RouterOS
  [A-mikrotik-routeros-ssh-no-multiline-2026], Talos [A-talos-for-linux-admins-no-writable-fs-2026]).
- +SURE that NOT ONE frequently-run host class I could reach a primary for is nowhere-writable. Every
  read-only-root row in the table pairs the read-only image with a RAM-backed writable layer by
  design: OpenBMC roots on read-only xz squashfs but overlays JFFS2 or UBIFS "over the entire
  filesystem space allowing all files and directories to be written", with tmpfs for /tmp and /run
  [A-openbmc-flash-layout-squashfs-overlay-2026]; ESXi puts scratch inside ESX-OSData and falls back
  to a ramdisk when that is absent [A-esxi-scratch-partition-ramdisk-2026]; Unraid boots "into a root
  RAM file system" so everything is writable and nothing outside /boot survives
  [A-unraid-root-ram-filesystem-2026]. This independently corroborates turn01 and is evidence
  AGAINST this round's own framing: the steady-state unwritable-scratch granule (G2-STEADY) is close
  to EMPTY among real homelab hosts. Its actual population is `--read-only` containers without a
  `--tmpfs` [A-docker-container-run-read-only-flag-2026], `readOnlyRootFilesystem` pods without an
  emptyDir [B-k8s-security-context-readonly-root-2026], and G2-FAILED.
- +SURE that the modal `/bin/sh` on this frontier is NOT dash, and the distribution matters for the
  heredoc hazard. bash-as-sh: macOS (indirected through `/var/select/sh`, which Apple documents the
  user may repoint at bash, dash or zsh) [A-apple-zsh-default-shell-varselect-2026] and NixOS
  (`environment.binsh` defaults to `bashInteractive`, with the option's own text warning "NixOS
  assumes all over the place that shell to be Bash") [A-nixos-environment-binsh-bash-default-2026].
  busybox ash: OpenWrt [B-openwrt-write-shell-script-ash-default-2025], Alpine
  [ops-glue-residue:B-alpine-shell-management-2026]. mksh with toybox utilities: Android, since Ice
  Cream Sandwich and Marshmallow respectively [A-aosp-shell-and-utilities-mksh-toybox-2026].
  FreeBSD `sh`: the whole BSD appliance family. So turn01's "here-document writes to disk exactly on
  bash-as-sh below 5.1" [A-bash-53-release-tarball-2025] lands on two of the most common developer
  targets, not on an exotic tail.
- +SURE that the `/dev/fd` micro-granule turn03 flagged is real on BOTH sides, and worse on Linux
  than expected. FreeBSD: "/dev/fd/0, /dev/fd/1 and /dev/fd/2 files are created by default when devfs
  alone is mounted. fdescfs creates entries for all file descriptors"
  [A-freebsd-fdescfs-manpage-devfs-only-2023] — so fd 3 does not exist without a separate mount, on
  FreeBSD and on pfSense/OPNsense/TrueNAS CORE/Junos beneath it. Linux: `/dev/fd` is normally just a
  symlink to `/proc/self/fd`, AND opening `/proc/self/fd/0` is a NEW open of the underlying inode
  governed by that inode's ownership — the man page's own worked example has an unprivileged process
  get `Permission denied` re-opening an inherited pipe by path while reading the descriptor itself
  works fine [A-linux-proc-pid-fd-manpage-devfd-2026]. An fd-named-as-a-path report sink must probe
  for existence AND survive the drop-privileges case.
- ~SUSPECT that the "appliance operators do not want push management" counter-thesis has real
  vendor-side support, though I found only one clean instance: Ubiquiti tells users the in-app Debug
  Console is the recommended way in and that it does "not recommend using SSH unless instructed by
  one of our Support Engineers", with ssh shipped DISABLED on consoles and ENABLED with generated
  credentials on network devices. (That source's MINT FAILED — see Failures — so this finding rests
  on a read I cannot cite by slug, and should be re-gathered before it is relied on.) The weaker
  cousins are pfSense shipping sshd disabled by default
  [A-pfsense-sshd-disabled-by-default-2025], ESXi shipping both shells off and framing them as
  break-fix-only [B-esxi-shell-ssh-enable-breakfix-2026], and Juniper stating flatly that it "does
  not provide support for operations in the shell" [A-junos-start-shell-csh-sh-2023].
- +SURE that the largest quantified population on this frontier is Home Assistant OS, and that its
  CHANNEL is the most hostile of any row. Measured: of 676,392 opted-in active installations,
  `installation_types` is os 538,919 / container 117,268 / supervised 7,709 / core 7,079, with the
  project stating opt-in is under a quarter of its userbase
  [A-home-assistant-analytics-installation-types-2026]. And port 22 reaches an add-on CONTAINER with
  limited privileges, not the host; host ssh is a separate daemon on port 22222 armed only by
  physically inserting a USB stick carrying an `authorized_keys` file on a partition labelled CONFIG
  [A-haos-host-ssh-port-22222-usb-2026]. Half a million appliances whose OS cannot be enrolled for
  push management without someone walking to the device.
- ~SUSPECT that the network-OS tier is NOT one tier and should not be conceded wholesale to G4.
  Junos exposes `start shell (csh | sh)` where sh is "a UNIX Bourne shell", gated on a shell or
  maintenance privilege level [A-junos-start-shell-csh-sh-2023]; NX-OS has bash behind a
  configuration feature that ships disabled (`feature bash-shell`, then `run bash`, landing as admin
  not root) and a dev-ops role that permits `python *` too
  [A-cisco-nxos-feature-bash-shell-gated-2026]; Arista EOS schedules `bash /mnt/flash/myscript.sh`
  and runs `.py` scripts from event handlers [A-arista-eos-cli-bash-event-handler-2026]. Three of the
  four big network vendors are G3-with-an-administrative-precondition, not G4. Only RouterOS is a
  true non-target [A-mikrotik-routeros-ssh-no-multiline-2026].
- -GUESS that the FreeBSD-derived appliance family carries a dated login-shell hazard: root's default
  shell became `sh(1)` only in FreeBSD 14.0 [A-freebsd-14-root-shell-sh-2023], so any appliance
  pinned to a 13.x-or-earlier base re-parses the remote command line through csh/tcsh, which quotes
  and splits differently. GUESS rather than SUSPECT because I did not source which base version any
  specific appliance (pfSense, OPNsense, TrueNAS CORE, Junos) currently pins.
- ~SUSPECT that OpenWrt is one edit away from being unreachable in a way no other row is: its own
  developer wiki warns that changing the root account's login shell away from `/bin/sh` gives "a good
  chance you will be unable to log in to your router via SSH", and that the default install is
  "very minimal" so coreutils are busybox applets unless separately installed
  [B-openwrt-write-shell-script-ash-default-2025]. Read against the collection that exists because
  OpenWrt cannot run the incumbent's payload language and is therefore written in ash, disabling fact
  gathering globally and installing coreutils-sha1sum and coreutils-base64 because the busybox
  applets do not suffice [ops-glue-residue:A-ansible-community-openwrt-user-guide-2026], this is the
  best-evidenced single row on the frontier.

## The short list (H-frontier-is-small, as produced)

Frequently run by homelabbers or small ops AND genuinely outside "ordinary writable Linux with
OpenSSH and Python". Eight entries, in rough descending order of how well-evidenced they are:

1. **OpenWrt** — busybox ash, no sftp subsystem, no Python, minimal PATH, tiny flash. G3a+G5-DP+G8.
2. **Home Assistant OS** — half a million measured installs; host channel requires physical USB
   enrolment; port 22 is a container. G5.
3. **Windows** — ordinary channel, zero interpreter until one is bootstrapped. G3c.
4. **Android via adb** — mksh + toybox, exec-API channel, no ssh. G3a+G5-DP.
5. **Network OS with a gated shell** (Junos · Cisco NX-OS · Arista EOS) — a real shell behind a CLI
   and, for NX-OS, behind a configuration feature that ships off. G3b+G6.
6. **BMCs** (OpenBMC family) — squashfs+overlay, busybox, tens of MB of flash. G8. Vendor BMCs
   (iDRAC/iLO) unverified.
7. **ESXi** — ssh off by default, break-fix framing, ramdisk scratch; interpreter unverified. G5+G8.
8. **Chrome OS** — cryptographically verified read-only rootfs, no network channel by default. G2+G5.

Ruled OUT of the frontier by evidence gathered this turn: Proxmox VE (ordinary Debian, its docs
point at Ansible), Unraid (everything writable, merely volatile), NixOS (bash-as-sh, writable /),
macOS (ordinary, modulo zsh login shell and bash-as-sh), OPNsense (Python present via configd),
Arista-once-past-the-CLI, TrueNAS SCALE (Python present via middleware). Ruled out as NON-TARGETS by
turn01: MikroTik RouterOS, Talos.

> [A-freebsd-fdescfs-manpage-devfs-only-2023]:§DESCRIPTION, §FILES (relevance: +1:SURE)
> The file-descriptor file system, or fdescfs, provides access to the per-process file descriptor
> namespace in the global file system namespace. The conventional mount point is /dev/fd.

> the process reading the directory. The files /dev/fd/0 through /dev/fd/# refer to file descriptors
> which can be accessed through the file system.

> ...

> still have permission bits and ownership information distinct from those of the /proc/pid/fd entry,

## Gaps (cells I could not source; each is a real hole, not an absence)

- **ESXi's interpreter.** Every secondary account says BusyBox ash, and turn01 already noted the
  Broadcom KBs are thin or login-walled. I reached the scratch and access-model primaries but found
  no first-party statement naming the shell. This is the single most load-bearing `?` in the table,
  because ESXi is a frequently-run small-ops host and its dialect decides whether it is G1 or G3a.
- **Synology DSM and QNAP QTS — entire rows.** Both vendors document how to ENABLE ssh and nothing
  about the userland behind it. Synology's developer guide covers the cross-compilation TOOLKIT's
  requirements (bash >= 4.1.5, python >= 2.7.3 on the DEVELOPER's machine) and explicitly tells you
  not to install it on the NAS, so it says nothing about the appliance. Secondary sources contradict
  each other on whether DSM's `/bin/sh` is busybox ash or a link to bash. Two of the most-owned
  homelab NAS platforms are therefore unmapped.
- **Population signals generally.** Only Home Assistant publishes measured install counts
  [A-home-assistant-analytics-installation-types-2026]. I found nothing primary-ish for OpenWrt,
  Proxmox, Unraid, TrueNAS, Synology or ESXi installed base. Turn01 recorded the same gap for habit
  evidence; I confirm it extends to raw population. A human-mediated pass (vendor investor material,
  Steam-hardware-survey-style datasets, distro popularity contests) is the way to close it.
- **iDRAC / iLO restricted shells** and **SteamOS** — not reached; deprioritised behind rows with
  larger populations.
- **`/proc` and `/dev/fd` presence per row.** I sourced the two MECHANISM primaries (FreeBSD fdescfs,
  Linux proc_pid_fd) but found no per-appliance statements. Every Linux row is ~SUSPECT-present and
  every FreeBSD-derived row is +SURE-limited-to-fd-0-2; neither is measured on a real device.
- **Which FreeBSD base version each BSD appliance pins**, which decides whether its root login shell
