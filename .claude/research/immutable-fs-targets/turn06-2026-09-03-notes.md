## Findings

- **+SURE that the premise of Q12 is false as stated: the memory route is NOT novel, and the
  ARGUMENT route in particular is what the incumbents actually do.** Three separate production
  orchestrators deliver their payload as an ssh command-line argument, base64-armored, and two of
  them say why in the code. Salt: "SSH_PY_SHIM is base64 encoded and formatted into the SSH_SH_SHIM
  string. This makes the python script 'armored' so that it can all be passed in the SSH command and
  will not need special quoting (which likely would be impossibe to do anyway)"
  [A-saltssh-shim-armored-in-ssh-command-2026]. Mitogen: `python -c '…exec(zlib.decompress(
  binascii.a2b_base64(sys.argv[1]),-15))' <base64>` [A-mitogen-boot-command-argv-payload-2026].
  Ansible-on-Windows: `-EncodedCommand <base64 utf-16-le>` behind
  `['PowerShell','-NoProfile','-NonInteractive','-ExecutionPolicy','Unrestricted']`
  [A-ansible-powershell-shell-encodedcommand-stdin-2026]. And outside orchestration the same shape
  is the single most-run install command on macOS —
  `/bin/bash -c "$(curl -fsSL …/install.sh)"` [B-homebrew-installer-bash-c-command-substitution-2026]
  and `sh -c "$(curl -fsSL …/install.sh)"` [A-ohmyzsh-installer-command-substitution-tty-2026].
- **+SURE that Salt states the argument-vs-stdin trade in exactly Dorc's terms, and lands on the
  OPPOSITE default**, with stdin named as the fallback for size: "The formatted SSH_SH_SHIM with the
  SSH_PY_SHIM payload is a bit big (~7.5k). If this proves problematic for an SSH command we might
  try simply invoking '/bin/sh -s' and passing the formatted SSH_SH_SHIM on SSH stdin"
  [A-saltssh-shim-armored-in-ssh-command-2026]. That is Dorc's current shape, described by a sibling
  as its own contingency plan.
- **+SURE that the ONE thing nobody does is `eval` a large sh body out of a shell VARIABLE.** Every
  argument-route instance above hands the payload to a fresh interpreter's `-c` / `-EncodedCommand`,
  never to `eval "$var"`. No source found does the latter. So H-slurp-is-novel splits: the
  *argument* half is common and well-priced; the *`a=$(cat); eval "$a"`* half really is unattested,
  and I found no stated reason against it — only the absence.
- **+SURE that the reason the incumbents' memory route is Python-shaped is stated by the incumbent
  itself, which supports H-slurp-is-novel-because-payloads-were-not-sh.** Ansible's become docs:
  "When pipelining is enabled, Ansible does not save the module to a temporary file on the client.
  Instead, it pipes the module to the remote Python interpreter's stdin. Pipelining does not work
  for Python modules involving file transfer (for example: copy, fetch, template), or for
  non-Python modules" [A-ansible-become-unprivileged-tmpfile-ladder-2026]. The memory route exists
  because the payload is one interpreter-readable blob; it fails exactly where the payload has to
  *become a file on the target*.
- **+SURE that there IS a hard stated technical reason the stdin route ships disabled, and it is not
  the filesystem — it is the pty.** Ansible's own config file: pipelining "can result in a very
  significant performance improvement when enabled. However this conflicts with privilege escalation
  (become). For example, when using 'sudo:' operations you must first disable 'requiretty' in
  /etc/sudoers on all managed hosts, which is why it is disabled by default"
  [A-ansible-pipelining-default-false-rationale-2026]. The full mechanism is in the abandoned patch:
  with `-tt` "ssh puts the tty into 'raw' mode (~ICANON), so there is no good way for the process on
  the other end to detect EOF on stdin", so `echo … | ssh -tt host "cat|python"` "hangs forever"
  [A-ansible-pr-13487-pipelining-requiretty-closed-2015].
- **+SURE that a SECOND orchestrator hit the identical wall and its own TODO names copy-then-exec as
  the only way out**: salt-ssh, in `_cmd_str()` immediately above the code that appends `-t -t`,
  carries "# TODO: if tty, then our SSH_SHIM cannot be supplied from STDIN Will # need to deliver
  the SHIM to the remote host and execute it there"
  [A-saltssh-shell-tty-blocks-stdin-shim-2026]. Two independent implementations, same conclusion,
  neither shipped a fix. NB this is a `-t` problem, not an fs problem: it only binds when something
  forces a pty.
- **+SURE that the pipelining fix was attempted with an END-MARKER protocol and abandoned as
  not-worth-it, not as impossible.** The patch fed the module through a sentinel-reading one-liner
  (`__EOF__<md5>`), worked, and was closed unmerged 17 months later by a core maintainer: "we're
  going to close this for now due to multiple issues with the above, and the fact that it's an issue
  that does not really seem to be impacting users much anymore. Pipelining has been around for over
  2 years, and it's well known and documented that requiretty needs to be disabled for it to work"
  [A-ansible-pr-13487-pipelining-requiretty-closed-2015]. Ten years on, the default is still False
  [A-ansible-pipelining-default-false-rationale-2026].
- **+SURE that H-pivots-walk-toward-files is HALF WRONG, and the counter-example is the biggest
  transport pivot in the incumbent's history.** Ansible built a side-channel daemon transport
  (fireball 1.2 → accelerate 1.3: temporary AES key, port 5099, 30-minute daemon, a UNIX socket
  under `$ANSIBLE_REMOTE_TEMP`), then walked it back to plain ssh: "Accelerated mode is deprecated.
  Consider using SSH with ControlPersist and pipelining enabled instead", because "If you can use
  pipelining, Ansible will reduce the amount of files transferred over the wire … Because less
  moving parts are involved, pipelining is better than accelerated mode for nearly all use cases"
  [A-ansible-accelerated-mode-deprecated-2017]. That pivot moved TOWARD stdin and AWAY from both
  files and a side channel.
- **+SURE of a second, cleaner counter-example: Kubernetes never built a file lane at all.**
  `kubectl cp` pipes tar through the exec channel, and the help text owns the cost: "# !!!Important
  Note!!! # Requires that the 'tar' binary is present in your container image. If 'tar' is not
  present, 'kubectl cp' will fail", with the manual equivalent printed as
  `tar cf - /tmp/foo | kubectl exec -i … -- tar xf - -C /tmp/bar` [A-kubectl-cp-tar-over-exec-stdin-2026].
- **+SURE that the strongest pivot TOWARD a structured side-channel is OpenSSH's own, and it broke
  compat deliberately.** scp switched to SFTP by default in 9.0 because the legacy protocol
  "performs wildcard expansion of remote filenames … through the remote shell. This has the side
  effect of requiring double quoting of shell meta-characters in file names … otherwise they could
  be interpreted as shell commands on the remote side", and the project refused bug-compatibility:
  "we … do not intend to introduce bug-compatibility for legacy scp/rcp"
  [A-openssh-9-scp-to-sftp-default-2022]. Cost: a permanent `-O` escape flag plus a new protocol
  extension (`expand-path@openssh.com`) to recover `~user`.
- **+SURE (Q16 root cause) that the login shell is not an incumbent quirk but sshd's contract.**
  `do_child()`: "/* Execute the command using the user's shell. This uses the -c option to execute
  the command. */ argv[0] = (char *) shell0; argv[1] = "-c"; argv[2] = (char *) command;"
  [A-openssh-sshd-session-login-shell-dash-c-2026], and the client flattens argv before sending:
  "If supplied, the arguments will be appended to the command, separated by spaces, before it is
  sent to the server to be executed" [A-openssh-ssh-manpage-command-flattening-2026]. Every
  login-shell abstraction in every tool descends from those two lines.
- **+SURE that the incumbents priced non-Bourne login shells and mostly REFUSED.** Bolt's option is
  `login-shell`: "Supported shells are sh, bash, zsh, dash, ksh, powershell. This option is
  experimental" — csh and fish absent, default `bash`, still experimental years later
  [A-bolt-transports-login-shell-tmpdir-2026]; its design issue scoped it as "We only need to
  support sh/bash for linux … The code should be written in such a way that we can add csh support
  without a further refactor however" [A-bolt-issue-813-shell-assumptions-2018]. Ansible kept only
  `sh`, `cmd`, `powershell` in core and EJECTED csh and fish to the `ansible.posix` collection in
  2020 (commit 829eb0f1, "Migrated to ansible.posix"); their in-collection docstrings read "When you
  have no other option than to use csh" [A-ansible-posix-csh-shell-plugin-2026] and "This is here
  because some people are restricted to fish" [A-ansible-posix-fish-shell-plugin-2026].
- **+SURE that Fabric went further and REMOVED its `sh -c` wrapper, on the ground Dorc's
  `ax-login-shell` is weighing**: "Non-sudo remote execution never truly required an explicit shell
  wrapper: the remote SSH daemon hands your command string off to the connecting user's login shell
  in almost all cases. Since wrapping is otherwise extremely error-prone and requires frustrating
  escaping rules, we dropped it for this use case" — while keeping manual wrapping for sudo "due to
  how the command string is handed off to the sudo program"
  [A-fabric-upgrading-shell-wrapper-removed-2026]. Directly opposed to pyinfra, which wraps
  everything as `sh -c '…'` [A-pyinfra-make-unix-command-askpass-2026].
- **+SURE of the concrete cost of supporting one non-Bourne shell, as code.** ansible-core's
  `ShellBase` builds every emitted command from per-family tokens — `_SHELL_SUB_LEFT/RIGHT`,
  `_SHELL_AND`, `_SHELL_GROUP_LEFT/RIGHT`, `_SHELL_REDIRECT_ALLNULL`
  [A-ansible-shell-mkdtemp-source-2026] — because csh needs `>& /dev/null`, `` "` `` / `` `" ``,
  and `env VAR=val` instead of a `VAR=val` prefix [A-ansible-posix-csh-shell-plugin-2026], and fish
  needs `; and` / `; or`, EMPTY group delimiters (so the umask-subshell trick in `mkdtemp` silently
  degrades), `set -lx`, and a wholly reimplemented `checksum()`
  [A-ansible-posix-fish-shell-plugin-2026].
- **+SURE that a wrong login shell breaks the FILE LANE first, in the field, today.** Terraform
  drives scp's far end through the login shell; on Windows with PowerShell as `DefaultShell` it
  fails with "Unexpected token '-vt' in expression or statement", and HashiCorp's documented answer
  is to change the target: "you must configure OpenSSH to run the commands with cmd.exe and not
  PowerShell. PowerShell causes file parsing errors because it is incompatible with both Unix shells
  and the Windows command interpreter" [A-terraform-issue-31423-powershell-scp-2022]. Open since
  2022.
- **+SURE that the copy-then-exec route's own handshake is a documented, high-traffic failure
  surface.** Ansible's `mkdir … && echo …` staging round-trip intermittently "returned empty
  string" on ordinary Linux; 15 reactions, 128 comments, two years to close
  [A-ansible-issue-13876-tmpdir-handshake-empty-2016]. The permission half of the same route is a
  five-rung ladder accreted over a decade (setfacl → chown → macOS `chmod +a` (2.11) →
  `ansible_common_remote_group` chgrp (2.10, deliberately unverified "because doing such a check
  would require another round-trip connection … which is a time-expensive operation") →
  `world_readable_temp`, flagged as "a potential security risk"), with a 2.1 compat break turning
  silent insecurity into a hard error [A-ansible-become-unprivileged-tmpfile-ladder-2026].
- **+SURE that copy-then-exec exists as a formal, pluggable ARCHITECTURE in one incumbent, with the
  seam cut exactly where cdist cuts it.** Rundeck splits delivery into two cooperating plugin
  services: "File Copier plugins transfer files and scripts from Rundeck to target nodes before
  execution. They work hand-in-hand with Node Executor plugins … the copier sends the file, the
  executor runs it", the copier's contract is "Must return the remote file path where the file was
  copied", and the executor then runs `ssh user@node '/tmp/rundeck-script-12345.sh'`. Built-in
  copiers are SCP, WinRM, and Stub; the docs' own worked custom example is an HTTP-upload copier
  whose executor line is `ssh node "curl -o /tmp/script.sh $downloadUrl && chmod +x … && …"` — the
  charter's floated controller-serves-over-HTTP shape, already a documented plugin pattern
  [A-rundeck-file-copier-node-executor-seam-2026].
- ~SUSPECT that the honest summary of the whole corpus is: **the file route is expensive and
  everyone pays it anyway, because the memory route cannot carry files.** Bolt has `tmpdir`,
  `script-dir`, `cleanup` and `copy-command` (default `["scp","-r"]`) on every transport and no
  in-memory mode at all [A-bolt-transports-login-shell-tmpdir-2026]; salt-ssh needs a thin dir
  [A-saltssh-roster-thin-dir-2026]; Ansible needs one per task
  [A-ansible-action-make-tmp-path-source-2026]; even Mitogen, the RAM-execution project, needs one
  writable directory [A-mitogen-ansible-tempfile-ladder-2026].
- ~SUSPECT (Q12, small but sharp) that **command-substitution delivery changes what the delivered
  script can observe about itself.** Oh My Zsh's installer carries the workaround in-tree: "The
  `[ -t 1 ]` check only works when the function is not called from a subshell (like in `$(...)` or
  `(...)`, so this hack redefines the function at the top level to always return false when stdout
  is not a tty" [A-ohmyzsh-installer-command-substitution-tty-2026]. Argument delivery also forces
  option-passing into extra argv (`sh -c "$(curl …)" "" --unattended`) or environment variables
  (`NONINTERACTIVE=1 …` [B-homebrew-installer-bash-c-command-substitution-2026]), because stdin is
  the terminal.
- -GUESS that the argument route's practical ceiling is comfortable rather than tight for Dorc-sized
  artifacts: Linux `MAX_ARG_STRLEN` is 128 KiB per single argument
  [A-linux-binfmts-max-arg-strlen-2026]; Salt calls ~7.5k "a bit big" and treats it as the point at
  which it would reconsider [A-saltssh-shim-armored-in-ssh-command-2026]; Mitogen tracks the number
  with a dedicated measurement script ("Optimized for minimum byte count after minification &
  compression. The script preamble_size.py measures this")
  [A-mitogen-boot-command-argv-payload-2026]. I did NOT find a first-party statement of OpenSSH's
  own exec-request size limit; treat that cell as unmeasured.
- ~SUSPECT (multiplexing, against which the charter holds a standing caution) that the one
  well-specified precedent carries a channel Dorc has not considered: Docker's non-tty stream is an
  8-byte frame header over ONE connection with FOUR ids — Stdin=0, Stdout=1, Stderr=2, and
  **Systemerr=3**, "errors originating from the system … returned as an error" whose arrival
  "terminates processing the stream" [A-docker-stdcopy-four-stream-multiplex-2026]. A dedicated
  in-band id for TRANSPORT failure, distinct from the payload's stderr. Recorded as priced prior art
  for the degraded cell only, not as a recommendation. Its frozen wart is instructive too: Stdin=0
  "is present for completeness and should NOT be used" but is still demultiplexed onto stdout for
  backward compatibility.
- --WONDER whether the in-band marker line is more standard than the round has assumed: salt-ssh
  emits a fixed 64-hex-character delimiter `RSTR` on BOTH stdout and stderr and documents a truth
  table of the four presence combinations, ending "RSTR in stderr, No RSTR in stdout: Undefined
  behavior" [A-saltssh-shim-armored-in-ssh-command-2026]. That is a working precedent for a marker
  protocol *and* an honest record of its unhandled cell.

## Hypothesis verdicts

- **H-slurp-is-novel-for-a-reason** — SPLIT, and the split matters. The *argument* form of the memory
  route is NOT novel (Salt, Mitogen, Ansible-on-Windows, Homebrew, Oh My Zsh) and its costs are
  documented: argv flattening through the login shell, escaping so hard that everyone base64-armors,
  a per-argument 128 KiB ceiling, and loss of the script's ability to see a tty. The *stdin* form is
  also not novel (Ansible pipelining) and its blocking reason is stated and specific: it is
  incompatible with a forced pty, hence with `requiretty` sudo. The genuinely unattested variant is
  `a=$(cat); eval "$a"` in a POSIX shell — and I found no stated reason against it, only silence.
  Decided by [A-saltssh-shim-armored-in-ssh-command-2026],
  [A-ansible-pipelining-default-false-rationale-2026],
  [A-ansible-pr-13487-pipelining-requiretty-closed-2015],
  [A-mitogen-boot-command-argv-payload-2026], [A-ansible-powershell-shell-encodedcommand-stdin-2026].
- **H-slurp-is-novel-because-payloads-were-not-sh** — SUPPORTED, in the incumbent's own words. The
  memory route was built for an interpreter blob and is documented as not working "for Python modules
  involving file transfer … or for non-Python modules"; Mitogen's whole first stage exists to get a
  *Python* interpreter running from RAM. Decided by
  [A-ansible-become-unprivileged-tmpfile-ladder-2026], [ops-glue-residue:A-mitogen-howitworks-2024],
  [A-mitogen-boot-command-argv-payload-2026].
- **H-pivots-walk-toward-files** — FALSIFIED as a general law; true only for the *file-transfer*
  sub-problem. Toward files/subsystems: OpenSSH scp→SFTP [A-openssh-9-scp-to-sftp-default-2022].
  Away from files and side channels: Ansible accelerate→pipelining
  [A-ansible-accelerated-mode-deprecated-2017]; Kubernetes never built a file lane
  [A-kubectl-cp-tar-over-exec-stdin-2026]; Fabric dropped recursive `put` and said a revival should
  use "an approach not involving intermediate files"
  [A-fabric-upgrading-shell-wrapper-removed-2026]. The reliable direction is not toward files — it is
  toward *fewer assumptions about the target*, which sometimes means a subsystem and sometimes means
  a pipe.

> [A-ansible-pr-13487-pipelining-requiretty-closed-2015]: PR body (relevance: Q12 — the full
> tty/EOF mechanism, and the end-marker fix that was never merged)

> Pipelining is disabled by default in Ansible because it conflicts with
> the use of sudo if 'Defaults requiretty' is set in /etc/sudoers (as it
> is on Red Hat) and su (which always requires a tty).
>
> We can (and already do) make sudo/su happy by using "ssh -t" to allocate
> a tty, but then the python interpreter goes into interactive mode and is
> unhappy with module source being written to its stdin, per the following
> comment from connections/ssh.py:
>
> ```
>     # we can only use tty when we are not pipelining the modules.
>     # piping data into /usr/bin/python inside a tty automatically
>     # invokes the python interactive-mode but the modules are not
>     # compatible with the interactive-mode ("unexpected indent"
>     # mainly because of empty lines)
> ```
>
> […] This works, but there's a problem: ssh will ignore -t if its input isn't
> really a tty. So we could open a pseudo-tty and use that as ssh's stdin,
> but if we then write Python source into it, it's all echoed back to us
> (because we're a tty). So we have to use -tt to force tty allocation; in
> that case, however, ssh puts the tty into "raw" mode (~ICANON), so there
> is no good way for the process on the other end to detect EOF on stdin.
> So if we do:
>
> ```
> echo -e "print('hello world')\n"|ssh -tt someho.st "cat|python"
> ```
>
> …it hangs forever, because cat keeps on reading input even after we've
> closed our pipe into ssh's stdin. We can get around this by writing a
> special __EOF__ marker after writing in_data, and doing this:
>
> ```
> echo -e "print('hello world')\n__EOF__\n"|ssh -tt someho.st "sed -ne '/__EOF__/q' -e p|python"
> ```
