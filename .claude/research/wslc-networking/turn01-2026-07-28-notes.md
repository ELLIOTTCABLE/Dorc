## Findings

- The prior agent was +SURE correct: as of 2026-07-28, `wslc.exe` (WSL container, public preview since 2026-06-29) is officially unsupported for invocation from inside a WSL distro at all — this is an open, unresolved Microsoft-filed feature request, not merely undocumented.
- Root architectural cause, confirmed directly by the feature's own PM: wslc containers run in a **separate, dedicated Hyper-V utility VM** from the shared VM that hosts all of a user's regular WSL2 distros (Ubuntu, Debian, etc). They do not share a kernel, a mount namespace, or (by extension) a network namespace/vswitch.
- wslc VM networking defaults to a mode called **"consomme"**: a user-mode NAT that terminates guest traffic as ordinary Windows-visible host sockets (via the OpenVMM `consomme` backend). Container ports published with `-p` are, by default, bound only to Windows loopback (`127.0.0.1`) — this is a per-user configurable default (`session.defaultBindingAddress` in `%LOCALAPPDATA%\wslc\settings.yaml`), not a hard limit.
- The wslc CLI/API source confirms per-port `BindingAddress` is caller-settable (Docker-style `-p <host_ip>:<host_port>:<container_port>` syntax), and the settings validator accepts any literal IPv4 address for the default — so `0.0.0.0` is a legal override, at least in principle. I found no direct report of anyone having done this specifically to reach a container from a *sibling* WSL2 distro (as opposed to from Windows itself).
- Regardless of which of wslc's two port-relay backends is used (`virtionet` default, or `wslrelay` — literally the same `wslrelay.exe` binary ordinary WSL2 NAT-mode distros use for their own localhost-forwarding), the relay target is always **Windows**, never a sibling WSL VM directly. So even the "wslrelay" backend does not create a WSL-to-WSL-VM bridge — it just changes how the container-VM-to-Windows leg is implemented.
- Net consequence: reaching a wslc container from WSL2 Ubuntu is not a wslc-specific problem once you get past "wslc must run from PowerShell" — it collapses into the generic, well-documented WSL2 question of "can Ubuntu-in-WSL2 reach a TCP listener bound on the Windows host?" That question already has two established answers: (a) default NAT mode — yes, via the Windows host IP as seen from WSL (`ip route show | grep default`), **provided** the service is not loopback-only-bound; (b) mirrored networking mode — yes via `localhost` directly, by design.
- However, (b) is presently unreliable: two open, detailed, very recent (2026-07-17 and 2026-07-22) bug reports show mirrored-mode loopback TCP handshakes failing/hanging on current Windows builds, one described as a regression from a 2026-07-15 Windows Update. Recommending mirrored mode as *the* fix right now carries real, current risk of hitting this.
- Confirmed (community, technically precise, unofficial-but-verifiable): `wslc run -p` published ports are reachable at `localhost` from Windows today. This nails down the Windows-side half of the chain; the WSL-side half (reaching that same port from a sibling Ubuntu distro via host-IP-after-rebinding-to-0.0.0.0, or via `netsh portproxy`) is my own inference from the architecture and cited primary sources, not something I found directly reported/tested by anyone.
- A separate, real usability problem independent of raw TCP reachability: even the *supported* Windows-side-invocation workflow has open bugs around bind-mounting WSL-filesystem paths into wslc containers (two VMs, no shared mount namespace, path-translation breaks), which matters if Dorc's book/oracle files need to be visible inside the container.
