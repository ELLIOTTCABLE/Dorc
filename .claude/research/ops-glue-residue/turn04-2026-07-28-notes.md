## Findings

### The headline: the language choice is not a taste axis, it is a capability axis

- **The incumbent's author designed Dorc's offline artifact, and his own payload language blocks it.**
  pyinfra issue 688 is Fizzadar sketching `pyinfra plan INVENTORY … | pyinfra apply -`, then naming
  the blocker himself: `python.call` callbacks would have to be *pickled*, behind an
  `--allow-unsafe-pickled-operations` flag `[A-pyinfra-issue-688-plan-apply-serialization-2021]`. In
  805 he restates the ambition: "creating a diff file that can then be moved somewhere else for
  execution — pyinfra needn't even be the tool doing the execution"
  `[A-pyinfra-issue-805-two-phase-retrospective-2022]`. The approval prompt shipped in v3
  `[A-pyinfra-changelog-2026]`; the transferable artefact never did, five years on. This is the
  single strongest positioning fact of the round: **when the plan is spelled in the target language,
  the plan is transferable by construction; when it is spelled in the controller's language, it is
  not — and the incumbent knows it.** +SURE. DESIGN-BEND: it re-grounds
  `dir-offline-compile-guard-artifact` and the splice-vector on a *structural* argument rather than
  a novelty claim.
- **cdist's manifests are sh that does not run.** Type invocations (`__package tree --state
  installed`) resolve through symlinks cdist plants in a private `bin/` dir and prepends to `PATH`,
  each pointing at a Python emulator that writes an object into a database
  `[A-cdist-manual-type-authoring-2026]`, `[B-cdist-source-config-dry-run-2019]`. So the closest
  sh-native prior art has **zero off-ramp**: run the manifest without cdist and you get
  `__package: command not found`. pyinfra's `deploy.py` has zero off-ramp for the same reason in a
  different language. Dorc's book running unchanged under `ssh host 'sh -s' <book.sh` is not a
  softer version of what they do; it is a property neither can have. +SURE.
- The three tools' *target-side floor is identical* — ssh + POSIX `/bin/sh`, nothing else
  (`[B-cdist-why-2026]`; pyinfra's own compatibility doc: "the only requirement on the remote side is
  shell access. POSIX commands are used where possible"). **Agentless floor is NOT a Dorc
  differentiator and must never be sold as one.** +SURE.

### pyinfra: what it actually ships, and how good it honestly is

- **Library breadth, counted not guessed:** 182 operations across 45 modules, 143 fact classes,
  10 connector entry points (`ssh`, `local`, `docker`, `podman`, `dockerssh`, `podmanssh`, `chroot`,
  `fake`, plus inventory-only `terraform` and `vagrant`), from 44 operation modules / 49 fact modules
  registered in `pyinfra-metadata.toml` `[A-pyinfra-metadata-registry-2026]`. 5,917 stars, MIT,
  pushed the day before this turn ran. Against Dorc's zero-stdlib reality this is a decade of work,
  and it is *not* the kind of thing a design decision closes. +SURE.
- **`--dry` does not show you commands, and cannot.** v3.0 "executes operations at runtime, rather
  than pre-generating commands" `[A-pyinfra-changelog-2026]`; the docs say `--dry` and
  `--debug-operations` "don't print the literal commands, because those aren't generated until
  execute time" `[A-pyinfra-using-operations-2026]`. The render is a three-column table —
  `Operation | Change | Conditional Change` with per-host counts `[A-pyinfra-cli-prints-source-2026]`.
  `--diff` (v3.5) adds *file-content* diffs only `[A-pyinfra-changelog-2026]`,
  `[B-pyinfra-issue-985-dry-run-diff-2023]`. To see shell you run `-vv` — at execute time, after
  consent. **pyinfra's plan is an operation×host change matrix; Dorc's plan is the user's own script
  with lines struck out. Different products, not different polish.** +SURE.
- **pyinfra has per-site "why nothing happened", hand-written, at `-v`.** `host.noop(description)`
  is called ~108 times across 24 operation modules — `host.noop("apt is already up to date")`,
  `host.noop(f"tap {src} already exists")` `[A-pyinfra-server-operations-source-2026]` (mechanism in
  `api/host.py`, gated on `state.print_noop_info`). This is elision-with-attribution shipping today,
  at *operation* granularity, as author-written prose, printed only at raised verbosity. It is real,
  and it is a smaller thing than Dorc's chain-with-labels. ~SUSPECT on the exact count (grep of
  `host.noop` call sites); +SURE on the mechanism.
- **pyinfra ships the author-vouch vocabulary and never wires it to behaviour.** `@operation(
  is_idempotent=False, idempotent_notice=…)` is declared on 57 operations; the decorator stores both
  as function attributes and **the only consumers repo-wide are `scripts/generate_operations_docs.py`
  and `scripts/generate_llms_txt.py`** `[A-pyinfra-operation-decorator-source-2026]`. An incumbent
  has the *exact* shape of an oracle's self-vouch — as documentation only. +SURE, verified by
  repo-wide grep excluding the declaring modules.
- **Privilege escalation is a solved, shipped, boring problem there.** `_sudo`, `_sudo_user`,
  `_sudo_password` (with prompt), `_use_sudo_login`, `_preserve_sudo_env`, `_su_user`,
  `_use_su_login`, `_su_shell`, `_su_password`, `_doas`, `_doas_user`, `_dzdo`, `_dzdo_user`, with
  the composition order documented as `doas -> dzdo -> sudo -> su`
  `[A-pyinfra-global-arguments-2026]`. Escalation can also be set as inventory data and as
  `config.SUDO` `[A-pyinfra-inventory-data-2026]`. +SURE.
- **Per-feature capability probing is shipped, phase-aware.** A fact may declare
  `requires_command()` (a binary that must exist) and `check_preconditions()` (returning a
  human-readable reason string). Failure is **silent during prepare** — "the binary may simply not
  be installed yet; a later operation will install it" — but **raised during execute from v4**
  `[A-pyinfra-api-facts-authoring-2026]`. This is `rul-capability-probing-per-feature` shipping in an
  incumbent, and the phase asymmetry is the same insight as Dorc's probe/apply fail-safe inversion.
  +SURE. The round's rule now has incumbent precedent to cite, not just turn C's openwrt evidence.
- Partial-apply is fleet-shaped, not state-shaped: `--limit` and `--exclude`, both repeatable, both
  matching host name / glob / group name `[A-pyinfra-cli-reference-2026]`. Nothing selects *by what
  has drifted* or *by what changed in git*. Confirms turn C's "partial-apply-by-STATE vs
  hand-declared phase flags" as the clearest value claim — now against pyinfra as well as k3s.
- Retry is first-class and richer than expected: `_retries`, `_retry_delay`, `_retry_until`
  (a callable inspecting `stderr_lines`), plus CLI `--retry`/`--retry-delay`
  `[A-pyinfra-global-arguments-2026]`. Bears on `dir-until-loop-glue-priority`: the incumbent's
  answer to flaky-command retry is a *controller-side* wrapper, which is exactly the
  O(retries)-connections shape turn C ruled against for waits. -0:SUSPECT that this generalises from
  retry to wait.
- Machine-readable plan exists: `--json` works with `--dry`, `debug-inventory`, `fact` and
  `--debug-operations` `[A-pyinfra-cli-reference-2026]`. So "a plan you can pipe" is *partly* solved
  upstream — as JSON metadata, never as executable material.

### cdist: the architecture Dorc is closest to, and the one that dead-ends

- **cdist's convergence check runs on the CONTROLLER, in sh, and signals "converged" by emitting
  nothing.** `gencode-remote` is a controller-side sh script that reads `$__object/explorer/*` and
  `$__object/parameter/*` and *prints* the target sh; `__package_apt/gencode-remote` literally does
  `if [ "$state_is" = "$state_should" ]; then … exit 0; fi` before any `echo`
  `[B-cdist-source-package-apt-gencode-2019]`. The engine sets `cdist_object.changed = True` iff
  either gencode emitted bytes `[B-cdist-source-config-dry-run-2019]`. **So the incumbent's
  tri-state answer is: converged = empty stdout from a generator, not any exit-code convention.**
  That is a fourth wild convention on top of turn C's three (systemd `ExecCondition` / GCP OS-policy
  / rinstall) — and it is *not portable to the target side*, because target code only exists when
  there is something to do. The missing shared primitive remains missing. +SURE.
- **cdist's dry run runs the explorers and the generators and withholds only the execution.** `-n`
  is documented as "Do not execute code" `[A-cdist-manual-cli-reference-2026]`; the implementation
  guards only `run_code_local` / `transfer_code_remote` / `run_code_remote`, and logs
  `Processing <object>` **only for objects that generated code**
  `[B-cdist-source-config-dry-run-2019]`. So cdist *does* narrow the dry-run listing to changing
  objects — genuine attention narrowing, at object granularity — and the generated shell is written
  to `$__object/code-remote` in the out-dir but never shown. +SURE.
- **cdist's whole receipt substrate already exists and has no query product on top.** The per-host
  local cache holds: every global and per-type explorer's output, `code-local` / `code-remote`
  (present only if something was generated), per-object `stdout/` and `stderr/` for manifest,
  gencode and code, the `messages` file, `typeorder`, and per-object `state`. Upstream states the
  cache "is one way only … cdist does not use stored data for future runs" (6.0.4 `cdist-cache.rst`;
  the CACHE PATH PATTERN section of `[A-cdist-manual-cli-reference-2026]` corroborates the layout).
  Raw dumps, no explanation chain, no provenance labels, no `why`. -0:SUSPECT that the 2019 doc is
  current; +SURE on the contents as of 6.0.4.
- **cdist ships no templating engine, and its documented practice is a heredoc in an sh script.**
  First-party: "create the template as an executable file like `files/basic.conf.sh` … use `cat <<
  eof` (here document) … and use standard shell variables"
  `[B-cdist-best-practice-templating-2019]`. Dorc's deliberate absence of templating is therefore
  *precedented*, not a gap. (Lint gem, kin to turn C's `{1..N}` finding: the doc's own example writes
  `$SERVERNAME_access.log`, which expands the undefined `$SERVERNAME_access`. A first-party doc ships
  a broken template.) +SURE.
- **cdist has no privilege story at all; it connects as root.** `__remote_exec: ssh -o User=root`,
  `__remote_copy: scp -o User=root`, overridable only by replacing the whole transport with
  something that "must behave as if it were ssh" `[A-cdist-manual-cli-reference-2026]`, corroborating
  turn B's `[A-cdist-manual-remote-exec-copy-2026]`. The only `sudo` in cdist's docs concerns which
  *humans* may invoke cdist on a gateway host `[B-cdist-best-practice-templating-2019]`. +SURE.
- **cdist has no per-host data.** Its inventory is tag-only and has been in `--beta` for years:
  "Tags have no values, as tags are just tags" (6.0.4 `cdist-inventory.rst`; beta status confirmed
  live at `[A-cdist-manual-cli-reference-2026]`). No `group_data`, no `host_vars`. Branch-on-facts is
  the *only* mechanism, done in the manifest against `$__global/explorer/os` etc. — which is,
  notably, exactly the idiom turn C found dominant in the wild. +SURE.
- **Type breadth:** 153 types, 20 global explorers, 122 type-level explorer scripts across 78 of the
  153 types (6.0.4 tree). ~15 of the types are `__install_*` — partitioning, mkfs, fstab, bootloader
  — because cdist has a whole second `install` mode. +SURE for 6.0.4; -1:GUESS for 7.0.0.
- **Staleness, graded honestly:** PyPI's latest is **7.0.0, uploaded 2022-07-31**
  `[A-cdist-pypi-release-record-2022]`; the readable GitHub mirror's newest branch tops out at
  **6.0.4, 2019-11-19**; `code.ungleich.ch` is down (human-confirmed). The live manual at
  `www.cdi.st` is the only current first-party surface and it matches the 6.0.4 tree line-for-line on
  every document I cross-checked `[A-cdist-manual-type-authoring-2026]`,
  `[A-cdist-manual-preos-2026]`. **Treat cdist as an architecture to learn from, not a moving
  competitor.** +SURE.
- Incidental, worth a line somewhere: `cdist scan` is an ICMPv6 discovery daemon that finds hosts on
  an interface and reconfigures them periodically `[A-cdist-manual-cli-reference-2026]`. Nobody else
  in the corpus has "the tool finds its own inventory by pinging the link."

## pyinfra's self-admitted limitations (from its own tracker and docs)

- "The whole two-stage deploy mechanism has consistently provided complexity over the last 7(!)
  years" — the creator `[A-pyinfra-issue-805-two-phase-retrospective-2022]`.
- Operation ordering is derived from **line numbers via stack inspection**, with named failure modes:
  loops and context processors produce DAG cycles requiring `host.loop`; `preserve_loop_order` is
  called "counter-intuitive" `[A-pyinfra-issue-805-two-phase-retrospective-2022]`,
  `[B-pyinfra-2x-deploy-limitations-2023]`.
- `assume_present` — the hint that suppresses a stale check — is "a real pain and a massive gotcha"
  per the creator; he would "absolutely love to remove" it (same source).
- Dry-run fidelity is admitted as unfixable-in-general: collecting facts at execution time "may
  break" the promise that the proposed change count matches the executed count; his mitigation
  sketch was to print "up to X" commands (same source).
- Fact errors are all-or-nothing: a non-zero fact command marks the host **failed** unless
  `_ignore_errors` is passed, and facts that silently return defaults for a missing command "will
  raise an error during the execution phase" in v4 `[A-pyinfra-using-operations-2026]`,
  `[A-pyinfra-api-facts-authoring-2026]`.
- Interdependent operations remain the named structural limitation
  `[B-pyinfra-2x-deploy-limitations-2023]`.
- File diffs took from 2023-05 to 2025-09 (v3.5) to land, driven by a user's prototype, with users
  citing the absence as blocking Ansible migration `[B-pyinfra-issue-985-dry-run-diff-2023]`.
- *Not* found: any issue thread about fleet-scale performance degradation. Four search framings
  (`slow`, `performance`, `scaling`, `many hosts`) surfaced only connection flakiness and import
  overhead. Report as "no evidence found", never as "no such problem". -1:GUESS.

## cdist PreOS vs turn A's channel work

cdist is the only tool in this round's corpus with a first-party day-zero story, and **it answers a
different question than turn A's channels do.** `cdist preos ubuntu … -B -C -k ~/.ssh/id_rsa.pub -p
/preos/pxe-ubuntu` debootstraps a minimal OS, cdist-configures it (installing your authorized key via
`__ssh_authorized_keys`), and emits a PXE boot directory; then "it can be accessed through ssh, i.e.
it can be further installed and configured with cdist" `[A-cdist-manual-preos-2026]`,
`[A-cdist-manual-cli-reference-2026]`.

The consequence for `dir-offline-compile-guard-artifact`: **even the closest sh-native prior art
answers day-zero by MANUFACTURING the ssh precondition rather than by compiling convergence into the
boot payload.** cdist never puts a guarded artifact into user-data, `%post`, or an installer hook; it
builds a bootable OS whose only job is to make the normal transport work. That strengthens turn A's
adjudication ("the cell is empty of convergence machinery, not of channels") from a *different*
direction than the cloud-init/Ignition evidence: it is not merely that nobody ships convergence into
the payload — the strongest sh-native contender deliberately routes around the payload entirely, at
the cost of requiring DHCP, TFTP, and physical/virtual PXE control.

Second-order note for the strawmen: cdist's `install` mode (~15 `__install_*` types —
`__install_mkfs`, `__install_partition_msdos`, `__install_bootloader_grub`, `__install_fstab`,
`__install_reboot`, …) is the same type machinery pointed at a chroot on a PreOS-booted machine. It
is the incumbent's version of the pivot — and it does the pivot by *rebooting into a controlled
environment first*, which is turn C's INVERSE wait shape, shipped.

## Gap-closers

### cloud-init `phone_home` — the reverse pivot

`PER_INSTANCE` frequency (once per instance, not every boot). It HTTP-POSTs a form body to a URL that
may be templated on the instance id (`{{ v1.instance_id }}`, or `$INSTANCE_ID` via the url-params
render). Default payload `all` = `instance_id`, `hostname`, `fqdn`, **and the three ssh host public
keys** (`pub_key_rsa`, `pub_key_ecdsa`, `pub_key_ed25519`), each read from `/etc/ssh/*.pub`; missing
values are posted as the literal string `N/A`. Retry: `tries` defaults to 10, implemented as
`retries=tries-1, sec_between=3`. **Total failure is logged and swallowed** — boot is never blocked
`[A-cloudinit-phone-home-source-2026]`.

Design consequence, and it is a real one: this is the *only* mechanism anywhere in the round's corpus
that carries **host identity from the new machine back to the controller**, and it does so with no
authentication and no delivery guarantee. It is the concrete answer to turn C's opportunity note
("the controller MINTED the machine — identity could be bound at creation instead of punted"): the
incumbent primitive for that exists, is per-instance, is best-effort, and is a plain POST. Anything
Dorc builds on it inherits "the endpoint is unauthenticated and anyone who can reach it can lie" —
the same trust cell as `StrictHostKeyChecking=no`, merely relocated. ~SUSPECT that this is worth
designing against now; +SURE on the mechanics.

### GitLab CI — turn C's DEAD verdict CONFIRMED

"The shells don't have any configuration options." The supported set is exactly `bash`, `sh`,
`powershell`, `pwsh`; selection is per-*runner* in `config.toml`, not per-job; and the job's `script:`
lines are baked into a generated script that also does `git clone`, cache restore and artifact upload
before the whole thing is piped to `/bin/bash --login` `[A-gitlab-runner-shells-2026]`. **There is no
GitHub-Actions-style per-job interpreter override.** The only seat is "call `dorc` as a command",
which exists everywhere and is not an inside-seat. DEAD stands. +SURE.

### Jenkins — turn C's DEAD verdict REFUTED (narrowly)

The official `sh` step reference states verbatim: *"An interpreter selector may be used, for example:
`#!/usr/bin/perl`. Otherwise the system default shell will be run, using the `-xe` flags"*
`[A-jenkins-durable-task-sh-step-2026]`. So `sh script: '#!/usr/bin/env dorc-run\n…'` is a
**first-party documented custom-interpreter seat**, structurally identical to the GitHub Actions
`shell: dorc-run {0}` seat the charter already calls the strongest API-adjacent one.

Against the charter's two-conjunct discriminator: (a) **holds for long-lived agents** — Jenkins
workspaces persist under `AGENT_ROOT/workspace/JOB_NAME` and are not wiped unless asked, and the
classic pet-agent deployment re-runs `sh` blocks against a machine that accumulates state; it does
*not* hold for ephemeral containerised agents. (b) **holds unconditionally** — `sh` is a raw escape
hatch with `-xe` and nothing else; Jenkins provides no check/idempotence machinery for its contents.

Verdict: **ALIVE-narrow, gated on agent longevity** — the same shape as the k8s
initContainer-on-a-PV cell. Two warts for any strawman: the shebang must be at the very first byte
(Groovy triple-quoted strings routinely indent it and silently break the selector — a widely-reported
failure mode), and adopting a custom interpreter discards Jenkins's default `-xe`, so trace and
errexit become the interpreter's problem. +SURE on the doc; -0:SUSPECT on how often the
long-lived-agent case is the real one.

## What the writing phase must know (handoff — this is the last gathering turn)

1. **Reframe the value claim away from "we explain skips" and toward "we strike lines from your own
   text, and the receipt is interrogable later."** pyinfra's `host.noop` and cdist's changing-objects-
   only dry run both do a weaker version of the first half. Nobody does the second half, and nobody
   *can* do the source-text half.
2. **The offline artifact's argument is now structural, not novel-cell.** Lead with issue 688: the
   incumbent designed it and his payload language blocked it. That is a much sturdier foundation for
   `dir-offline-compile-guard-artifact` and `dir-splice-vector-fragment-mode` than "the cell is
   empty."
3. **Concede four axes explicitly and in the README**: library breadth, templating, per-host/group
   inventory data, and privilege-escalation *mechanism*. Conceding them cheaply buys credibility for
   the axes that are genuinely distinct, and each has a clean "use pyinfra" line above.
4. **Do not claim the agentless floor.** All three tools sit on ssh + POSIX sh. Turn B's `kBOOT`
   axis is where Dorc's floor claim actually lives; it is a different claim and must be worded so it
   cannot be misread as "we're more agentless."
5. **Copy pyinfra's privilege surface, then note the part nobody has.** The `_sudo`/`_su`/`_doas`/
   `_dzdo` matrix with a documented composition order is the mature answer and it corroborates turn
   C's `$SUDO`-prefix trichotomy. What no incumbent has is any model of what escalation does to the
   *analysis* — that is the Dorc-shaped half of the open sudo gap.
6. **The tri-state rc row is now four-wide, and cdist's entry is instructive**: silence-from-a-
   generator is elegant and *cannot* cross the wire. Use it as the argument for why the oracle rc
   contract has to be a target-side convention.
7. **Jenkins moves from DEAD to ALIVE-narrow** (long-lived agents only); GitLab stays DEAD. If the
   inside-strawmen slots are still open, Jenkins `sh` with a shebang is a cheap second exhibit
   alongside the k8s initContainer book — same shape, different ecosystem, first-party documented.
8. **cdist is prior art, not competition** (last release 2022-07, canonical repo offline). Cite it
   for architecture — controller-side sh generators, sh-heredoc templating, per-object explorers —
   without positioning against it as a live alternative.
9. **Two numbers to keep honest in any prose**: pyinfra 182 operations / 143 facts; cdist 153 types /
   142 explorer scripts. Dorc's stdlib is zero. Any "gradual enhancement" story has to survive being
