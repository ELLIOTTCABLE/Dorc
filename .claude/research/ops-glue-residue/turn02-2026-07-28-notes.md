## Findings

### The capability lattice is real, and two unrelated projects wrote it down

- adbd's own source contains a 2x2 table proving **exit-code visibility and stdout/stderr separation are
  INDEPENDENT capabilities**, and that a PTY forecloses separation even when the framing protocol is
  present [A-adb-shell-service-source-2026]. Docker states the same law from the other side: separation
  exists only via 8-byte framing and is lost entirely under a TTY [A-docker-engine-api-swagger-2026].
  Dorc's floor triple {byte-clean stdin, separate stderr, non-echoing} is not three arbitrary asks; it is
  one coherent cell of a lattice two unrelated projects independently discovered.
- **adb and Kubernetes each shipped a v1 that lost the exit code, then bolted on a framed side-channel to
  get it back.** adb: `kIdExit` in shell-protocol v2, feature-negotiated via `kFeatureShell2`, with an `-x`
  opt-out that disables rc AND separation together [A-adb-shell-protocol-header-2026],
  [A-adb-commandline-shell-2026]. Kubernetes: v4 "adds support for exit codes on the error stream through
  the use of metav1.Status instead of plain text messages" [A-k8s-remotecommand-v4-source-2026]. Dorc's
  in-band stdout sentinel is the same move — arrived at in v1 rather than v2, which is the cheap win.
- Docker is worse than both: the exit code is not in the stream at all and needs a **second out-of-band
  request** to exec-inspect [A-docker-engine-api-swagger-2026].
- No prior art was found for Dorc's specific refusal to trust channel rc. cdist aborts on explorer exit
  codes [A-cdist-manual-explorer-model-2026]; rset propagates `WEXITSTATUS`; judo returns 1/2/111;
  pyinfra computes success as `exit_code in _success_exit_codes` [A-pyinfra-connectors-api-2024]. That is
  weak evidence of novelty and equally weak evidence of unnecessity — it should not be read as validation.

### Ansible's connection contract, and the two things plugins do when a capability is missing

- Contract confirmed at source: `_connect`, `exec_command(cmd, in_data, sudoable) -> (rc, stdout, stderr)`,
  `put_file`, `fetch_file`, `close`, plus capability flags `has_pipelining`, `has_tty`,
  `supports_persistence`, `module_implementation_preferences` [A-ansible-connection-base-2026]. `in_data`
  IS the pipelining seam — the payload fed on stdin.
- **The `aws_ssm` hypothesis is confirmed and is stronger than suspected.** SSM has no `put_file`, so the
  plugin mandates an S3 bucket, `curl` on the target, egress to S3 from *both* ends, and a
  controller-minted presigned URL passed over the exec channel — "required even for modules which do not
  explicitly send files (such as the `shell` or `command` modules), because Ansible sends over the `.py`
  files of the module itself, via S3" [A-ansible-aws-ssm-connection-2026]. It inherits a documented
  plaintext-secret-in-S3 hazard as a direct consequence.
- The **second** strategy is more radical and under-discussed: for network appliances Ansible gave up on
  the target entirely. `NetworkConnectionBase` sets `_remote_is_local = True` and delegates
  `exec_command`/`put_file`/`fetch_file` to a `local` connection [A-ansible-connection-base-2026]. So the
  two incumbent answers to a capability-poor channel are **synthesise the capability out-of-band** or
  **relocate the work to the controller**. Within the pipe class there is a third:
  `ssh_transfer_method: piped` synthesises file transfer out of `exec_command` alone via `dd if=` / `dd of=`
  [A-ansible-ssh-connection-source-2026] — **a duplex-pipe-only channel can carry files.**
- The capability Dorc treats as floor is the one Ansible ships **disabled**: `pipelining` defaults to
  `false` because it conflicts with `become` unless `requiretty` is removed from sudoers
  [A-ansible-ssh-connection-docs-2026]. The source shows why:
  `if not in_data and sudoable and use_tty: args = ('-tt', ...)` — the incumbent forces a TTY *only when it
  is not feeding stdin* [A-ansible-ssh-connection-source-2026]. Stdin-fed payload and TTY are mutually
  exclusive there too. Dorc's floor is Ansible's pipelining mode made mandatory.
- Ansible's own floor-below-the-floor is Dorc's normal mode: `raw` "requires no Python on the remote as it
  passes the command directly into the connection string" [A-ansible-raw-module-2026]. Its stated limit
  matters: non-UTF-8 output "must be encoded to avoid issues. One option is to pipe the output through
  `base64`" — **Ansible does not promise a byte-clean return path.**

### Why each floor sits where it does

- Mitogen's floor requires Python because the payload *is* Python: a zlib+base64 first stage handed to
  `python -c`, which forks to recover stdin and feeds `mitogen.core` source to a re-exec'd interpreter
  [A-mitogen-howitworks-2024]. Not a transport choice — the consequence of being a Python-object RPC
  system. What it genuinely proves is the *channel* claim: everything after bootstrap rides one duplex
  pipe under a 26-byte header {magic, dst_id, src_id, auth_id, handle, reply_to, length}.
- Mitogen also validates the driver-seam shape: fourteen connection methods (buildah, docker, podman, lxc,
  lxd, jail, kubectl, setns, su, sudo, doas, ssh, local, fork) all reducing to *spawn a local subprocess
  whose stdio is a duplex pipe*, composable via `via=` chaining [A-mitogen-api-connection-methods-2024].
- cdist states its floor plainly: "a ssh server running and a posix compatible shell (/bin/sh)", no agent,
  no high-level language, "does not require to open up an additional port", target never connects back
  [B-cdist-why-2026].
- salt-ssh is the sharpest agentless-but-not-thin case: "Python is required on the remote system (unless
  using the `-r` option to send raw ssh commands)", and the documented bootstrap for a Python-less host is
  a raw sh call [A-saltstack-salt-ssh-docs-2026]. Same shape as Ansible's `raw`: **every heavy tool keeps a
  thin-sh escape hatch, and that escape hatch is Dorc's front door.**
- pyinfra's contract is `run_shell_command -> (success: bool, CommandOutput)` plus `put_file`/`get_file`/
  `rsync`, with `_stdin`/`_timeout`/`_get_pty` as control arguments [A-pyinfra-connectors-api-2024] — so
  pyinfra *does* depend on faithful rc where Dorc does not. A concrete difference in assumed floor.

### pyinfra is the closest shipping analogue to probe/plan/apply, and it documents the trap

- Five stages splitting into prepare (gather facts read-only, diff, compute `will_change`, **no mutating
  commands sent**) and execute (re-evaluate, run lock-step, all hosts finish operation N before any starts
  N+1) [A-pyinfra-deploy-process-2026]. That is probe → plan → apply, shipping today, on a heavier floor.
- Upstream documents the staleness trap explicitly, and it is the poison-wall problem in another guise: a
  fact branched on in deploy code reflects **pre-deploy** state. Their fix is `_if=` — defer the check to
  execution time. That is the elide-vs-guard cut, and their answer is "guard"
  [A-pyinfra-deploy-process-2026]. Independent confirmation the cut is forced, not a Dorc quirk.

### The thin-sh family splits 4-to-1 against the stdin pipe — and the dissenter's reason is security

- cdist, judo, drist and `remotely` all **copy to disk then execute by path**: cdist's `transfer()` shells
  out to `__remote_copy` (scp) and `run_script()` then invokes `/bin/sh -e <remote-path>`
  [B-cdist-python-transport-source-2016]; judo's `pushFiles` shells out to `scp -r`
  [A-judo-transport-go-scp-exec-2022]; drist rsyncs a tree then executes the copied script
  [A-drist-solene-official-manpage-2026].
- **Only rset pipes to the remote interpreter's stdin by default, and it implements both paths as named
  siblings in one file** — `ssh_command_pipe` vs `ssh_command_tty` [A-rset-execute-c-pipe-vs-tty-2026].
  Its stated reason is *confidentiality*, not performance: "Scripts embedded in pln(5) files are normally
  piped to the interpreter over SSH, minimizing the types of information that is written to temporary
  files", under a threat model where rset does not trust the hosts it manages
  [A-rset-scriptedconfiguration-overview-2026].
- **The cost of the stdin channel, stated by someone who hit it: if you spend stdin on code, the code can
  never read stdin.** rset's `-t` exists solely for that ("Allow TTY input by copying the content of each
  label to the remote host instead of opening a pipe to the interpreter")
  [A-rset-manual-page-options-2026]. judo pays the same price and converts it to doctrine: fd 0 is closed
  before the script runs, on the argument that programs which unexpectedly want input should fail
  immediately rather than hang for minutes [A-judo-readme-design-refusals-2022].
- **A third option exists in the wild and may be the one Dorc wants**: the maintained drist fork uses the
  stdin channel as *transport* while materialising a file before executing —
  `ssh host "cd $tmp && cat - > $tmp/f && chmod u+x $tmp/f && exec sh -c $tmp/f" < script`
  [A-johnkaul-drist-shell-reimplementation-2025]. One connection, no scp/rsync, no target-side rsync
  dependency, and the executing shell's own stdin stays free.
- cdist's `--remote-exec`/`--remote-copy` is far cruder than "pluggable transport" implies, and
  deliberately: the scripts must impersonate ssh and scp **positionally**, including scp's `host:path`
  syntax and IPv6-in-brackets [A-cdist-manual-remote-exec-copy-2026]. Every shipped non-trivial transport
  does string surgery on its own argv. A stringly-typed seam: trivially extensible, trivially wrong — but
  it bought chroot, schroot, sudo, local-loopback and URI dispatch with zero engine changes.
- **cdist's stated regret is connection count.** "As cdist makes many connections to each host successive
  connections can be sped up by…" — ControlMaster bolted on in v4.0.0, inheriting sshd's `MaxSessions 10`
  as a hard concurrency ceiling; and the controller's own `/bin/sh` had to be swapped to dash for speed
  [A-cdist-manual-best-practice-connection-cost-2026]. The source shows why: one `remote_exec` **per
  explorer**, repeated per object in stage 3 [B-cdist-python-transport-source-2016],
  [A-cdist-manual-execution-stages-2026]. One-artifact-per-phase is a direct answer to precisely this.
- A recurring, independently-rediscovered failure mode across the family: **environment marshalling.**
  cdist prepends `export K=V;` to the command string and breaks outright if the login shell is csh (hence
  `CDIST_REMOTE_SHELL`) [B-cdist-python-transport-source-2016]; judo shells out to `env(1)`
  [A-judo-transport-go-scp-exec-2022]; `remotely` hand-rolls four layers of backslash escaping and still
  ships a quoting bug [C-remotely-bash-ssh-library-2020].
- Eric Radman already wrote down and rejected the naive strawman: `ssh 10.5.5.1 < configure-wordpress.sh`
  appears on a slide labelled "Oversimplification", failing on "install configuration files" and "apply
  part of a config"; the modularisation attempt adds "performance degrades with each module". His answers
  were ControlMaster reuse, a staging directory, and `rinstall(1)` — a utility that "Exit `0` only if file
  was installed or changed" [B-radman-minimalist-scripted-configuration-2021]. Worth reading in full: he
  is the closest thing this niche has to a design document, and he argues against the naive form of Dorc's
  transport while landing on a refined version of it.
- Two of the five named kin are out of frame: `sshdo` is an SSH forced-command authoriser
  [C-sshdo-command-authorisation-2018]; `bashible` is a *local* bash DSL with no transport, bash-only and
  GNU-coreutils-bound [B-bashible-local-bash-dsl-2015].

### Exec-API channels: the hard caps, and the asymmetry that bends artifact design

- **The truncation caps run in opposite directions.** AWS keeps the **first** 24,000 characters of stdout
  and first 8,000 of stderr [A-aws-ssm-getcommandinvocation-api-2026]; Azure classic keeps the **last**
  4,096 bytes [A-azure-action-run-command-linux-2025]. An in-band completion sentinel on stdout survives
  AWS only if total output stays under the head cap, and survives Azure only if it is emitted **last** and
  the tail stays under 4 KB. The two demand opposite artifact designs.
- **Not one of the six exec-API channels streams output through its own API.** AWS returns nothing until
  terminal state; Azure classic reports only final status
  [A-azure-run-command-overview-compare-2026]; Azure managed and Proxmox are polled
  [A-proxmox-cli-qm-exec-source-2026]; GCP returns nothing at all. Every "live" story is a side-channel to
  a different service (CloudWatch, append blobs, GCS) or a client-side poll. An artifact assuming the
  controller sees progress as it happens is wrong on all six.
- **Azure classic reports no exit code whatsoever** — `RunCommandResult` is an array of
  `InstanceViewStatus`, a type with no numeric field anywhere in its definition
  [A-azure-rest-action-runcommand-2026]. On that channel Dorc's in-band status is *required*, not merely
  defensive: there is nothing else to read.
- **Session Manager cannot satisfy Dorc's three assumptions simultaneously.** `Standard_Stream` gives
  stdin but through a PTY where `plugin.stdin = plugin.stdout = ptyFile` (echo on, streams merged);
  `NonInteractiveCommands` gives separated pipes but sets `plugin.stdin = nil` — **no stdin at all**
  [A-amazon-ssm-agent-shell-unix-source-2026]. No mode is byte-clean, fd-separated and stdin-capable at
  once. The agent also states Session Manager "supports UTF-8 encoding only".
- **GCP has no genuine run-command primitive, and the negative is stronger than "use SSH".** The nearest
  thing caps inline scripts at **1024 characters**, returns output only via a file the script writes
  itself, and redefines exit codes as a compliance tri-state where 100 = in-desired-state, 101 = not, and
  **a script exiting 0 is an error** [A-gcp-os-policy-proto-googleapis-2026]. Google's own worked example
  tells you to `gcsutil cp` results out [A-gcp-os-policies-guide-2026]. Startup-script metadata carries
  256 KB but runs at boot and surfaces output only on the VM [A-gcp-startup-scripts-linux-2026].
- **Proxmox is the best-behaved of the six by a wide margin** — the only channel reporting `exitcode` AND
  `signal` AND explicit `out-truncated`/`err-truncated`, and the only one with a genuine in-channel file
  pair (60 KiB write / 16 MiB read) [A-proxmox-api2-qemu-agent-source-2026]. Underneath, QGA takes whole
  stdin up-front as base64 `input-data`, populates output only after exit, and caps capture at 16 MiB in 4
  KiB chunks [A-qemu-qga-qapi-schema-2026].
- Proxmox's stdin cap is documented inconsistently — **1 MiB on the CLI path, 64 KiB on REST** — because
  the CLI calls the Perl helper directly and enforces its own `die`
  [A-proxmox-cli-qm-exec-source-2026], [A-proxmox-api2-qemu-agent-source-2026]. A 16× artifact-budget
  difference decided by which path you use.
- libvirt is a passthrough, not a channel: the complete `libvirt-libvirt-qemu` function list contains no
  guest-exec entry point [A-libvirt-qemu-module-api-2026], and the project states the route "is
  unsupported" [B-libvirt-wiki-qemu-guest-agent-2026].
- Two size caps echo turn A's console findings without being about consoles: adb's pre-shell-v2 command
  string capped at `MAX_PAYLOAD_V1 = 4 * 1024` [A-adb-commandline-shell-2026], and Azure's 4,096-byte
  output tail [A-azure-action-run-command-linux-2025]. 4 KB keeps reappearing as a channel quantum.

### Cross-host sequencing spellings (Q6, reservation evidence only)

- Ansible spells it `delegate_to` + `serial`, and the load-bearing detail is attribution: facts gathered by
  a delegated task "are assigned by default to the inventory_hostname (the current host), not to the host
  that produced the facts" unless `delegate_facts: true` [A-ansible-delegation-docs-2026]. Direct prior-art
  hit on the attribution-scope re-entry trigger: the incumbent grew an explicit opt-in the moment one play
  addressed two hosts.
- Fabric spells it as a task-major loop with `execute()` as the escape hatch, and names what the simplicity
  buys: it "enables shell script-like logic where you may introspect the output or return code of a given
  command and decide what to do next", explicitly contrasted against "tools which push the multi-host
  functionality down to the individual function calls" [B-fabric-execution-model-2016].
- DeHaan named the same property as push's irreducible advantage over pull: "you can do THIS on that
  machine, hop over there and do THAT… This is where pull based tools typically break down"
  [A-dehaan-pull-mode-announcement-2012]. That is `ack-pivot-must-support` stated by the incumbent's
  founder as the reason push survives.

### The pull/local-mode escape hatches keep the runtime and remove only the server

- None of ansible-pull / chef-solo / chef-zero / puppet apply lowers the interpreter floor by one
  dependency. `ansible-pull` re-execs `ansible` and `ansible-playbook` from its own bindir with `-c local`
  and an explicit `ansible_python_interpreter=sys.executable` [A-ansible-pull-cli-source-2026];
  `chef-client -z` boots a real in-memory HTTP server and talks to it over loopback
  [A-chef-client-local-mode-docs-2026]. They lower the *coordination* floor, not the reach floor.
- jpmens, contemporaneously: pull mode "invalidates" the managed-nodes-need-nothing property, and
  push-bootstrap is "impossible if SSH from manager to nodes is forbidden"
  [B-jpmens-ansible-pull-floor-2012].
- **Puppet formally retracted its escape hatch**, past tense and by name: standalone "is challenging to
  maintain and secure" [A-puppet-architecture-standalone-2026]. Chef removed the original engine
  (`--legacy-mode` "Removed in Chef Infra Client 14") [A-chef-solo-ctl-options-2026] for consolidation:
  "there are simply too many ways to run the Chef Infra Client"
  [B-chef-solo-legacy-removal-issue-2020].
- The sharp edges Chef bolted around were **analysis** problems, not transport problems: no search, no
  data bags, and recipes forced to fork on `if Chef::Config[:solo]` — the escape hatch had bifurcated the
  user's own source code [B-chef-solo-to-zero-blog-2014]. Directly relevant to the one-file-works-
  everywhere claim: a two-dialect split is the failure mode to avoid.
- Bolt is agentless only for the degenerate case: `apply_prep` "runs the `puppet_agent::install` task to
  install the agent" the moment you want the declarative model [A-bolt-apply-manifest-blocks-2026].
- At first boot with no inbound connectivity all three cloud-init paths **install the tool first**:
  `cc_ansible` installs then raises if absent [A-cloudinit-cc-ansible-source-2026]; `cc_chef` needs six
  dirs, a rendered `client.rb`, a mandatory `server_url` and validation PEM, curl-pipe-sh of the omnibus
  installer, then daemonizes against a server [A-cloudinit-cc-chef-source-2026]; `cc_puppet` runs
  `puppet agent --test` — **`puppet apply` does not appear in the industry-standard masterless-shaped
  regime at all** [A-cloudinit-cc-puppet-source-2026].
- Puppet carries run status **out-of-band** in a bit-flag exit code (0/1/2/4/6, 6 = changes + failures) —
  the channel Dorc declines to trust — and accepts a pre-compiled catalog **on stdin**
  [A-puppet-apply-manpage-2024]. Both Ansible and Chef independently reinvented jittered scheduling
  (`--sleep`, `--splay`): inverting to pull moves the thundering herd from controller to artifact source,
  it does not remove it [A-ansible-pull-cli-docs-2025].

## Lane-survival table (Q5 — analysis, grounded in the sources above; NOT itself a cited finding)

Classes: **DP+F** duplex pipe with a file side-channel · **DP** duplex pipe only · **RR** request/response
exec · **OS** one-shot payload (no return path). Lanes: **probe** (round-trip: ship probe artifact, read
structured results back) · **report** (artifact-side scratch-file drain; needs only that the artifact's own
stdout comes home intact) · **apply** (ship apply artifact, in-band sentinel carries `$?`) · **live**
(`142` per-leaf diagnostic files + FIFO fast-lane).

| Class | Members (evidence) | probe | report | apply+sentinel | live topology |
|---|---|---|---|---|---|
| **DP+F** | ssh (`sftp`/`scp`/`piped` [A-ansible-ssh-connection-source-2026]); Proxmox qga (`file-read`/`file-write` [A-proxmox-api2-qemu-agent-source-2026]) | ✅ | ✅ | ✅ | ✅ — the only class where `142` works as designed |
| **DP** | `docker exec`, `kubectl exec`, `adb shell` (v2), Mitogen-style spawned pipes [A-mitogen-api-connection-methods-2024] | ✅ | ✅ | ✅ | ⚠️ degraded — no file side-channel, so per-leaf files must be *synthesised* over the pipe (the `dd` trick [A-ansible-ssh-connection-source-2026]) or multiplexed in-band with framing (adb/k8s prove framing works); FIFO fast-lane loses its point |
| **RR** | SSM Run Command, Azure classic + managed, Proxmox `qm guest exec`, qga `guest-exec`, GCP OS-policy `exec` | ⚠️ conditional — payload must fit the in-cap (AWS 64 KB doc; GCP **1024 chars** kills it outright); results must fit the out-cap and survive head-vs-tail truncation | ⚠️ **the lane most at risk** — a drain is exactly the high-volume case the caps punish; AWS 24 K head / Azure 4 K tail / GCP structured-output-only | ⚠️ sentinel survives only if placed on the surviving *side* of truncation: **last** for Azure, **first-24 K-window** for AWS. Azure classic makes it mandatory (no rc at all) | ❌ — no streaming on any of the six; poll-only or after-exit-only |
| **OS** | cloud user-data / startup-script / boothook; installer hooks; Packer-style provisioner (turn A); AWS Session Manager `NonInteractiveCommands` (stdin is `nil` [A-amazon-ssm-agent-shell-unix-source-2026]) | ❌ — no return path, so no probe round-trip; this is turn A's "compiled guard artifact" cell and the reason nothing can elide there | ❌ locally; only via a side-channel the artifact itself opens (GCS/journalctl/serial) | ⚠️ artifact runs, but the sentinel has nowhere to land — completion must be inferred from the world, not reported | ❌ |

Consequences worth carrying into the knob entry:

1. **The lane that breaks first under channel degradation is the report lane, not apply.** Apply needs a
   few bytes home; report needs many. Every RR channel's cap is sized for human-readable output, not for
   an artifact-side drain. If the report lane is load-bearing, RR channels need an explicit
   overflow story (their own: S3, append-blob, GCS) — which is precisely the `aws_ssm`-needs-S3 shape.
2. **Probe survives everywhere a return path exists at all**, and dies exactly where turn A already
   located the boundary (OS class). No new territory is lost; the boundary is the same one.
3. **The DP→DP+F gap is bridgeable and the bridge is already prior art** (`dd` over exec; adb/k8s framing).
   The `142` live topology is the only commitment that genuinely *needs* DP+F, and even there the
   degradation is "synthesise files over the pipe", not "impossible".
4. **Head-vs-tail truncation is the single most artifact-shaping external fact found this turn.** It is
   not a capability but a *placement* constraint on the sentinel, and the two major clouds disagree about
   which end is safe.
