# turn 5 — 2026-07-28 11:16:07 CDT

Remit: the large, expensive mistakes in pyinfra's and cdist's own record — breaking
changes, major-version transitions, reversals, abandonments, open sores. Inventory and
explanation only; no mapping onto Dorc.

## Findings

- pyinfra's central mistake is the **two-phase (generate-then-execute) deploy model**, which the
  maintainer kept for ~9 years and then explicitly renounced: "the disadvantages and confusion of
  the current execution strategy outweigh the advantages" — the direct cause of the v3 rewrite.
  +SURE [A-pyinfra-issue-805-maintainer-comments-2024]
- The v3 rewrite **did not actually retire the two-phase model** — it moved *command generation*
  to runtime while keeping a per-host *prepare* pass over the deploy file for ordering. Every
  user-visible gotcha the v2 docs listed under "Limitations" survives verbatim in the 3.10 docs
  under the softer heading "When does this matter?". +SURE
  [A-pyinfra-deploy-process-3x-doc-2026] vs [B-pyinfra-2x-deploy-limitations-2023]
- pyinfra's **operation-ordering mechanism has been rebuilt four times** (best-effort guess →
  `state.when`/`state.limit` context managers → AST compilation of the deploy file → line-number
  ordering → DAG), and each rebuild retracted the previous release's user-facing advice. +SURE
  [A-pyinfra-changelog-0x-branch-2020], [A-pyinfra-changelog-2x-branch-2024]
- pyinfra has a **stated semver contract** (majors only for breaks, deprecation warnings on the
  prior major) and has broadly honoured it — four majors in ten years, each with a migration
  page. +SURE [A-pyinfra-compatibility-upgrade-guide-2026]
- cdist has **no comparable contract**: seven majors, and its canonical upgrade guide's newest
  entry is still "Updating from 3.0 to 3.1" (2014). 4.0.0, 5.0.0, 6.0.0 and 7.0.0 shipped with
  no migration notes at all. +SURE [A-cdist-upgrade-guide-latest-2022]
- cdist's headline 4.x features — provisioning, PreOS, install types — were announced in 2014,
  shipped years late (install merged 4.4.0 in Dec 2016; PreOS only in 6.0.0, Oct 2019), and the
  `install` command was **still gated behind `--beta` in the final 7.0.0 release, eight years
  later**. Inventory (2017), archiving (2017), `scan` (2020) and the Python integration API
  (2017) are likewise still beta/unstable in 7.0.0. +SURE [B-cdist-speech-4x-preview-2014],
  [A-cdist-manual-cli-reference-2026], [A-cdist-sdist-7-0-0-2022]
- Two cdist 4.x promises never shipped at all: configuration history & rollback, and the
  "configuration as a service" webapp. +SURE (promise) / ~SUSPECT (never-shipped, argued from
  absence across the full changelog) [B-cdist-speech-4x-preview-2014]
- pyinfra has **deleted three connectors it shipped**: `@ansible` (0.11–2.x, removed in 3.0 as
  "broken"), `@mech` (0.12–2.x, gone by 3.x), `@winrm` + all Windows ops/facts (0.14–2.x, evicted
  to `pyinfra-windows`, whose README still says "This repo is NOT ready for production").
  +SURE [A-pyinfra-changelog-0x-branch-2020], [A-pyinfra-windows-plugin-readme-2026]
- cdist by contrast has deleted essentially nothing: exactly **one** type removed between 6.0.4
  and 7.0.0 (`__pf_apply`), against twenty added; five deprecation markers carried, none acted
  on. Its cost is accretion, not eviction. +SURE [A-cdist-sdist-7-0-0-2022]
- cdist's upstream forge (code.ungleich.ch) is **unreachable** as of this turn; the last release
  is 2022-07-31; Debian's package is **orphaned** and carries unforwardable patches.
  +SURE [B-debian-tracker-cdist-orphaned-2026]
- pyinfra's oldest open issues run to 2018 and 133 are open; notably `#653` (force an operation
  despite cached facts, 2021) is **still open after** the v3 rewrite that was meant to fix
  exactly that class. ~SUSPECT (that #653 is genuinely unaddressed rather than merely untriaged)
  [B-pyinfra-open-issues-oldest-2026]

## pyinfra: chronological breaking-change inventory

### v0.2 (2016) — first deprecation wave
Lowercased inventory group names; `yum.upgrade`→`yum.update`; `pip_virtualenv_packages` and
`npm_local_packages` facts collapsed into argument-taking variants. Bought: consistency and
parameterised facts. Cost: silent renames across every inventory file.

> [A-pyinfra-changelog-0x-branch-2020]:"# v0.2" (relevance: +1:SURE)
> To-be-breaking changes (deprecated):
> + Switch to lowercase inventory names (accessing `inventory.bsd` where the group is defined as `BSD = []` is deprecated)
> + Rename `yum.upgrade` -> `yum.update` (`yum.upgrade` deprecated)
> Internal changes:
> + Operations now `yield`, rather than returning lists of commands

### v0.4 (2018) — whole CLI replaced; connectors introduced
Entire command grammar replaced (`pyinfra INVENTORY deploy.py`), `@`-prefixed connectors
introduced, `@deploy` decorator added, `docopt`/`termcolor` swapped for `click`. Legacy CLI kept
"for the next few releases" and finally removed in v1.0. Bought: a coherent CLI and non-SSH
targets. Cost: every invocation, script and CI job rewritten.

### v0.5 → v0.7 → v0.8 (2018–2019) — the ordering reversal, the most expensive self-inflicted churn
The clearest build-then-abandon cycle in either project, across three releases:

1. **v0.5** told users that plain `if` statements produce "imbalanced operations" and to rewrite
   them as `state.when(...)` / `state.limit(...)` context managers, with a large warning printed
   at runtime linking to the docs.
2. **v0.7** shipped an AST compiler over the deploy file's top-level scope, which made that
   advice *wrong* — and said so in the changelog.
3. **v0.8** threw the compiler away entirely for a new ordering scheme.

> [A-pyinfra-changelog-0x-branch-2020]:"# v0.7 / Internal changes" (relevance: +1:SURE)
> + pyinfra now compiles the top-level scope of deploy code, meaning if statements no longer generate imbalanced operations
>     * This means the recommendations to use `state.when` in place of conditional statements is invalid
>     * Updated the warning shown, now once, with a link
>     * Compiling can be disabled by setting `PYINFRA_COMPILE=off` environment variable

> [A-pyinfra-changelog-0x-branch-2020]:"# v0.8" (relevance: +1:SURE)
> + Completely new operation ordering:
>     * different args *will not* generate imbalanced operations!
>     * no more deploy file compile needed

Users who took the v0.5 advice rewrote working Python into context managers for one release,
were told in v0.7 the rewrite was unnecessary, and in v0.8 the machinery behind both was
replaced. `state.limit`/`state.when`'s successors (`hosts`/`when` global args) were then
*removed* in v1.0.

### v0.5 (2018) — hooks broken by an unrelated refactor, then deprecated
> [A-pyinfra-changelog-0x-branch-2020]:"# v0.5" (relevance: +1:SURE)
> + **Hooks broken**: no longer loaded from deploy files, only from `config.py`, due to changes from `0.4` (removal of `FakeState` nonsense)

Deprecated outright in v0.13. A feature broken as collateral damage, then killed rather than
repaired — ~SUSPECT that this reflects low usage rather than inability to fix.

### v0.10 → v2.2 — `preserve_loop_order`, added and retired
`State.preserve_loop_order` shipped in v0.10 to work around loops executing out of order under
line-number ordering; the v2.2 DAG made it unnecessary and it was removed. A four-year-lived
workaround for a mechanism that was itself later replaced.

> [A-pyinfra-changelog-2x-branch-2024]:"# v2.2" (relevance: +1:SURE)
> The main feature of `2.2` is the switch to **using a DAG to generate operation order**. This mostly replaces line-number ordering (still used to tie-break) and means hacks such as `state.preserve_loop_order` are no longer required!

### v1.0 (2020) — the great rename
Bought: a stable, consistent public API worth committing to. Cost: essentially every operation
call site touched. `name` was overloaded as the first positional argument (a `set`!) and became a
global keyword; `files.*` args `name`→`path`, `destination`→`dest`; `server.*` `name`→
`user|group|cron_name|key|path`; `git.repo` `source`→`src`, `target`→`dest`;
`interpolate_variables` default flipped `True`→`False`; deprecated `hosts`/`when`/`op` global
args, `python.execute`, `add_limited_op` and the legacy CLI all removed.

> [A-pyinfra-changelog-1x-branch-2022]:"# v1.0 / Breaking changes" (relevance: +1:SURE)
> + Deprecate using `set` as the first/name argument for operations
> + Rename `files.*` arguments (`name` -> `path`, `destination` -> `dest`)
> + Change default of `interpolate_variables` from `True` -> `False`
> + Remove deprecated legacy CLI suppot

Also v0.15: `pyinfra.modules` → `pyinfra.operations`, back-compat shim kept through v1 and
removed in v2.

### v1.1 (2020) — a silent semantic change inside a minor
The yum/dnf "version join" separator changed from `-` to `=`, because package names may contain
`-`. Shipped in a *minor* despite changing the meaning of existing `name-version` strings.

> [A-pyinfra-changelog-1x-branch-2022]:"# v1.1 / Notable change" (relevance: +1:SURE)
> The `yum.packages` and `dnf.packages` operations have _changed_ their "version join" string value - both package managers use `-` to join name + version while allowing `-` in the name. This leads to ambiguous behaviour for packages containing dashes, as such the version join value has been changed to `=`

### v1.4 (2021) — magic facts replaced by explicit imports
`host.fact.apt_sources` → `host.get_fact(AptSources)`; CLI `pyinfra INV fact apt_sources` →
`pyinfra INV fact apt.AptSources`. Bought: third-party facts, arguments to facts, and global
arguments on facts ("previously impossible"). Cost: every fact reference and every fact-fetching
CLI invocation rewritten. Notably the changelog admits the migration shipped incomplete:

> [A-pyinfra-changelog-1x-branch-2022]:"# v1.4" (relevance: +1:SURE)
> This is not yet standard across the project and will be updated in subsequent releases.

### v1.5 (2021) — AST-extracted config replaced by a config object
`SUDO = True` at the top of a deploy file had been read by parsing the AST; replaced by
`from pyinfra import config; config.SUDO = True`. Bought: config values that can be computed and
that work across multiple deploy files. Cost: the old spelling deprecated then removed in v2.
The second time pyinfra retreated from AST inspection of user code.

### v2.0 (2022) — Python 2 dropped, deploy directory removed
> [A-pyinfra-changelog-2x-branch-2024]:"# v2.0" (relevance: +1:SURE)
> Breaking: **the "deploy directory" concept has been removed** - everything now executes from the current working directory which removes the ambiguous magic v1 used to pick a deploy directory. A new `--chdir` CLI flag has been added

The changelog explicitly warns this "may affect scripts or CI workflows currently setup" and
gives a before/after invocation. Also removed in 2.0: `host.fact.X`, the `init.*` operations,
`--facts`/`--operations`/`--debug-data` CLI flags, jinja2 parsing of string arguments, the
`Windows` prefix on Windows facts, `config.MIN_PYINFRA_VERSION`, `branch`/`create_branch` on
`git.worktree`, and `pyinfra.api.connectors` → `pyinfra.connectors`. Non-existent host data
began raising `AttributeError`.

### v3.0 (2024) — the two-phase renunciation
Bought (claimed): "fixes an entire class of bugs and confusion", plus a typed internal API, a
real connectors API, and CLI approval prompts. Cost, as listed by the project:
`_use_sudo_password`→`_sudo_password`; `@deploy` must now be *called* as `@deploy()`; `@winrm`
and all `windows*` operations/facts removed; the Ansible inventory connector removed as broken.

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1704036523, 2023-09-03 (relevance: +1:SURE)
> I'm convinced, it has become clear the disadvantages and confusion of the current execution strategy outweigh the advantages.
> To remedy this I am proposing that pyinfra v3 will switch to executing operations and facts live.

## pyinfra: the retrospective in full (the highest-value maintainer voice)

Issue #805 (opened by a *user*, May 2022) asked plainly what the two-phase split buys. The
maintainer's reply is a long, honest defence-then-concession, and is worth reading whole.

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1120166570, 2022-05-07 (relevance: +1:SURE)
> Because facts were loaded in parallel (2.a), each iteration of 2 got quicker and quicker as most/all facts were pre-cached for the current host. This is why facts were(are) gathered before execution.

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1120166570, 2022-05-07 (relevance: +1:SURE)
> Unfortunately I don't think we can avoid this without breaking operation execution flow, particularly where there are multiple code paths for different hosts involved in a deploy. The line/stack ordering enforces "correct" ordering - except loops and context processors. The general assumption being that deploy files are generally "simplified Python" consisting of operation calls, conditional statements and functions. I'm not a fan of this gotcha and would be keen to investigate alternatives!

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1120166570, 2022-05-07 (relevance: +1:SURE)
> I would absolutely love to remove this [`assume_present`], it's a real pain and a massive gotcha. v2 makes it entirely possible to do by having operations (re)collect facts at execution time. The only drawback is the list of changes pre-execution may not be correct; ie if you do a dry run deploy first you expect the number of commands proposed to match those executed, and collecting facts at execution may break this.

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1120166570, 2022-05-07 (relevance: +1:SURE)
> The whole two-stage deploy mechanism has consistently provided complexity over the last 7(!) years, but has also enabled writing almost-normal Python code to generate operations that execute in a similar way to tools like Ansible. I've yet to encounter something that wasn't possible (but have seen things not possible in other tools).

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1120166570, 2022-05-07 (relevance: +1:SURE)
> Today pyinfra seems to be a hybrid of a Ansible/SaltStack-like mostly-state-base ddeployment tool and Fabric/Parallel-SSH command execution tool. This is definitely both an advantage in terms of high flexibility but also a disadvantage because it comes with some gotchas that make it "almost like Python" at times.

The user's counter-list of what the split costs — worth keeping because the maintainer did not
dispute any item, only the proposed replacement:

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1131434383, 2022-05-19 (relevance: +1:SURE)
> I think it important to answer that because this split comes at the great cost of:
> - not being able to react dynamically to output and exit code of operations.
> - having things like preserve_loop_order and assume_present
> - not supporting some native python constructs with loops, context manager, exceptions
> - having to develop some specific features to workaround it like dynamic facts

The one thing the maintainer defended to the end was **cross-host lock-step ordering**, which is
what forbids running the deploy file straight through per host:

> [A-pyinfra-issue-805-maintainer-comments-2024]:comment 1125350055, 2022-05-12 (relevance: +1:SURE)
> The problem with doing this is it breaks a number of scenarios in which the order across multiple costs is essential. Really anything involving a control / worker node setup. [...] There are many similar examples of this where operations on one node must complete before operations on another. The operation order as it currently exists handles this.

Earlier, the same limitation stated flatly:

> [A-pyinfra-issue-710-nested-ops-2022]:comment 979835126, 2021-11-26 (relevance: +1:SURE)
> the issue here is calling an operation during execution - ops can only (currently) be generated before any execution starts. [...] This error is confusing and useless and I'd like to update it to reference the actual issue here

## pyinfra: what v3 actually bought — and did not

The v3.10 documentation still describes a five-stage run with a **prepare** stage that executes
the deploy file once per host:

> [A-pyinfra-deploy-process-3x-doc-2026]:"How pyinfra Works" (relevance: +1:SURE)
> 3. **Prepare** — run the deploy code once per host to establish operation order and detect which operations will change each host

> [A-pyinfra-deploy-process-3x-doc-2026]:"Why all this matters: ordering" (relevance: +1:SURE)
> This is why **deploy code always runs before any host is mutated**, and why a fact branched on in Python (`if host.get_fact(File, ...):`) reflects pre-deploy state rather than the running state at that point in the file.

The identical nginx-default-site example that v2 filed under "Limitations" appears in the v3
docs under "When does this matter?"; the `host.loop` cycle-error section is carried across
near-verbatim. What changed is the *remedy*: v2 said add `assume_present=install_nginx.changed`;
v3 says pass `_if=remove_default_site.did_change`. -GUESS: the rename of the section is the more
telling artifact — the same defect, reframed from limitation to idiom.

> [B-pyinfra-2x-deploy-limitations-2023]:"Limitations / Interdependent operations" (relevance: +1:SURE)
> The major disadvantage to separating the deploy into two phases comes into effect where operations rely on each other - i.e. the changes of one operation will affect a later operations facts.

Users noticed the mismatch between the v3 changelog's claim and the v3 docs:

## cdist: chronological breaking-change inventory

cdist's versioning is *not* semver and there is no stated contract. The migration guide is the
only place breaks are collected, and it stops in 2014.

- **1.0.0 (2011-03-07)** initial release, implemented in shell.
- **1.1.0 (2011-03-16)** — `__file` split into `__file`/`__directory`/`__link`; `--type` removed
  from `__file`. Every manifest touching files rewritten.
- **1.3.0 (2011-03-20)** — every type's `gencode` renamed to `gencode-remote`.
- **1.6.0 (2011-04-06)** — `__package_apt --preseed` removed in favour of a new type;
  `--state deinstalled|uninstalled` normalised to `removed`.
- **1.7.0 (2011-05-10)** — global explorer `hardware_type` renamed to `machine`.
- **2.0.0 (2011-09-16)** — **the core rewritten from shell into Python**; Python ≥3.2 required on
  the source host; `cdist-deploy-to` / `cdist-mass-deploy` replaced by `cdist config [-p]`;
  `__self` → `__object_fq` then `__object_name`. The single largest transition in the project.

> [A-cdist-changelog-mirror-6-0-4-2019]:"2.0.0: 2011-09-16" (relevance: +1:SURE)
> 	* __self replaced by __object_fq (Nico Schottelius)
> 	* Rewrote cdist in Python (Nico Schottelius)

- **2.1.0 (2012-12-09)** — the big type-API purge, staged over five `pre` releases: `--state`
  restricted to `present`/`absent` across all package/process types; several parameters became
  boolean (`--parents`, `--recursive`, `--default`); `__addifnosuchline`/`__removeline` replaced
  by `__line`; `__ssh_authorized_key` superseded by `__ssh_authorized_keys`; `__user --groups`
  removed in favour of `__user_groups`; the `conf` directory moved to `cdist/conf` with a
  **manual** migration; `__autofs*` types deleted "(no maintainer, no users)".

> [A-cdist-upgrade-guide-latest-2022]:"Updating from 2.0 to 2.1" (relevance: +1:SURE)
> * The **conf** directory is now located at **cdist/conf**.
>   You need to migrate your types, explorers and manifests
>   manually to the new location.
> * The types **__autofs**, **__autofs_map** and **__autofs_reload** have been removed
>   (no maintainer, no users)

- **2.2.0 (2013-07-12)** — the singleton object-id dropped, changing dependency syntax from
  `require="__type/singleton"` to `require="__type"`. The guide's migration advice is a
  self-admittedly untested `sed`:

> [A-cdist-upgrade-guide-latest-2022]:"Updating from 2.1 to 2.2" (relevance: +1:SURE)
> You can probably fix your configuration by running the following code
> snippet (currently untested, please report back if it works for you):
> find ~/.cdist/* -type f -exec sed -i 's,/singleton,,' {} \;

- **3.0.0 (2013-12-24)** — the `changed` attribute of objects removed, replaced by the messaging
  subsystem. Last entry in the upgrade guide bar one.
- **3.1.x (2014)** — `__ssh_authorized_keys` began managing pre-existing keys, not just
  cdist-added ones. The final migration note ever written.
- **4.0.0 (2016-05-04)** — headline items are "Types: Remove bashisms in scripts" and
  `CDIST_REMOTE_COPY/EXEC`. No migration entry. Note that the *stated purpose* of 4.x from the
  2014 talk — provisioning and install types — did **not** ship in 4.0.0; it was merged in
  **4.4.0 (2016-12-03)** as "Merge install feature from 4.0-pre-not-stable".
- **5.0.0 (2019-05-05)** — headline items are the forge migration to code.ungleich.ch and
  promoting `-j/--jobs` out of beta. No migration entry; no obvious break.
- **6.0.0 (2019-10-01)** — headline is "Core: Add preos functionality". A *feature*, in a major.
  No migration entry.
- **7.0.0 (2022-07-31)** — a pure type-and-explorer release: one new type, several apt fixes, an
  explorer rewrite. No core change, no migration entry, no deprecation removal. ~SUSPECT that
  cdist bumps major on essentially arbitrary grounds; +SURE that whatever the grounds, they are
  nowhere written down.

Only one type was actually removed across the whole 6.x→7.0 span:

> [A-cdist-sdist-7-0-0-2022]:docs/changelog "6.7.0: 2020-07-28" (relevance: +1:SURE)
> 	* Delete deprecated type: __pf_apply (Darko Poljak)

and five deprecation markers were left standing in 7.0.0 (`__apt_key_uri`, `__locale`, plus
parameter-level markers on `__apt_key`, `__debconf_set_selections`, `__letsencrypt_cert`), the
deprecation machinery itself having been added only in 5.1.0/5.1.2 (2019) — eight years in.
