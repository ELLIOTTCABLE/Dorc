## Authoritative frame

Microsoft meta-principles + Golden Rule [A-microsoft-pragmatic-rust-2026]: guidelines admitted only if
they affect {safety, COGS, maintenance}, "a majority of experienced (3+ years) Rust developers would agree",
and are "reasonably comprehensible to Rust novices (4+ weeks)"; "must" vs "should"; "it is the spirit that
counts, not the letter ... you should not blindly follow a guideline if ... doing so would violate its
underlying motivation." (Directly licenses the conductor's why-first stance.)

Rust API Guidelines checklist axes [A-rust-api-guidelines-2024]: Naming (C-GETTER no get_ prefix,
as_/to_/into_ conversions by cost, C-ITER), Interoperability (C-COMMON-TRAITS eagerly derive
Debug/Clone/Eq/Ord/Hash/Display/Default; C-CONV-TRAITS From/TryFrom/FromStr), Predictability, Flexibility,
Future-proofing (C-STABLE public deps stable, C-NON-EXHAUSTIVE, sealed traits), Documentation (C-CRATE-DOC,
C-EXAMPLE, C-QUESTION-MARK examples use ? not unwrap, C-FAILURE document Errors/Panics).

M-* index highlights [A-microsoft-pragmatic-rust-2026 / -ai / -resilience / -libs-ux]:
- Libs/UX: M-SIMPLE-ABSTRACTIONS (service types must not nest type params on their own volition, max 1 deep),
  M-AVOID-WRAPPERS (no Arc/Rc/Box/RefCell in public APIs), M-NO-PRELUDE, M-BALANCED-MODULES,
  M-ERRORS-CANONICAL-STRUCTS (error = situation struct w/ Backtrace + cause + helper methods; simple crate =
  one `Error` type), M-INIT-BUILDER, M-ESSENTIAL-FN-INHERENT, M-DONT-LEAK-TYPES.
- Libs/Resilience: M-MOCKABLE-SYSCALLS, M-INTEGRATION-TESTS (public-API tests under tests/, prefer
  integration over unit when equivalent), M-STRONG-TYPES (strongest type earliest; PathBuf not String),
  M-STRONG-TYPES-GUARD (centralize invariants), M-NO-GLOB-REEXPORTS, M-LOG-NOT-PRINT.
- Correctness: M-PANIC-IS-STOP (panic != exception; never communicate upstream), M-PANIC-ON-BUG (detected
  bug/contract violation = panic, NOT an Error type), M-UNSAFE (needs reason, avoid), M-UNSOUND.
- Universal: M-SMALLER-CRATES (err toward more crates -> compile time), M-STATIC-VERIFICATION (clippy +
  rustfmt + cargo-audit/hack/udeps + miri as check-in gates; concrete [lints.rust] set), M-SHORT-NAMES,
  M-WEASEL-WORDS, M-PUBLIC-DEBUG, M-PUBLIC-DISPLAY, M-LINT-OVERRIDE-EXPECT (#[expect] not #[allow]).
- Docs: M-FIRST-DOC-SENTENCE (one line ~15 words), M-MODULE-DOCS, M-CANONICAL-DOCS.
- Project: M-LATEST-EDITION, M-MSRV, M-CARGO-WORKSPACE, M-CRATES-FLAT-FOLDER.

Verbatim (M-PANIC-ON-BUG) [A-microsoft-pragmatic-rust-2026]: "when an unrecoverable programming error has
been detected, libraries and applications must panic ... no `Error` type should be introduced or returned
... Contract violations ... are programming errors and must therefore panic ... a function `parse(&str)`
clearly must return a `Result`."

Verbatim (M-MOCKABLE-SYSCALLS) [A-microsoft-rust-resilience-2026]: "Any user-facing type doing I/O, or sys
calls with side effects, should be mockable ... file and network access, clocks, entropy sources and seeds
... should not perform ad-hoc I/O, i.e., call read(foo.txt) ... should not offer MyIoLibrary::default()
constructors." (Mock controllers returned via tuple (Self, MockCtrl), gated behind a test-util feature.)

Verbatim (M-AVOID-WRAPPERS) [A-microsoft-rust-libs-ux-2026]: "generic wrappers and smart pointers like
Rc<T>, Arc<T>, Box<T>, or RefCell<T> should be avoided in public APIs ... these might even be
impossible to resolve once multiple crates disagree about the required type of wrapper."

## Error handling consensus

- thiserror for libraries (typed, matchable), anyhow for applications (context chains) — near-universal.
  [C-rustlang-forum-ai-rust-2025], seed rules err-thiserror-lib / err-anyhow-app [C-leonardomso-rust-skills-2026].
  Microsoft nuance: prefer canonical error STRUCTS with Backtrace over sprawling enums; M-FROM-ERROR for `?`.
- Never `.unwrap()`/`.expect()` in library/production paths except genuine invariants; `?` propagation;
  document a `## Errors` section (C-FAILURE). [A-rust-api-guidelines-2024], seed err-* / anti-unwrap-abuse.
- mitsuhiko [B-mitsuhiko-api-learnings-2023]: "Errors deserve attention just as much as your other types ...
  Implement std::error::Error ... Implement source() ... Try to avoid panics."

## Practitioner "tasteful" norms (library-author heuristics)

mitsuhiko [B-mitsuhiko-api-learnings-2023]: golden path + good defaults; "Less is More / More API = More
Problems"; "Hide the Onion but create the Onion" (layered, expose outer first); "I avoid traits unless I know
abstraction over implementations is necessary ... You can always add traits later"; Debug on all public types;
avoid Display unless custom primitive; "Copy/Clone once granted, impossible to take away"; avoid clever
lifetimes/self-referential (self_cell).

rodriguez pit-of-success [C-rodriguez-pit-of-success-2025]: progressive disclosure (core/generic/prelude
layers in one crate); make dangerous ops syntactically obvious (set_no_expiration_danger_acknowledged(),
feature v1_public_insecure); default() = the SAFE constructor, new() = opt out of validation; honest
fallible return types so `?` marks the fallible calls.

killercup (DATED 2016) [B-killercup-elegant-apis-2016]: generous inputs (&str/&[T] not &String/&Vec,
Into<Option<T>>, AsRef, IntoIterator); derive the usual traits; FromStr over string-taking ctors; "please
don't overdo Deref — not inheritance". AGE CAVEAT: written pre-impl-Trait-stable; "may become easier once
impl Trait is stabilized" is now moot; verify per 2024 edition.

## Simplicity / anti-over-engineering (counter to idiomatic-maximalism)

matklad Concrete Abstraction [B-matklad-concrete-abstraction-2020]: "If in every x.blag() the x is either
Blorg, or Gonk, but never a T (each usage is concrete), you don't need this abstraction ... replace a
trait with two inherent methods ... 'is this abstraction used exclusively concretely?' ... If 'Yes!', then the
abstraction can be replaced by ... simpler, shorter, and more direct" (rust-analyzer case: +999,-1123 diff).

corrode Be Simple [B-corrode-be-simple-2024]: "Simplicity is prerequisite for reliability" (Dijkstra);
"Generics Are A Liability" (monomorphization cost, viral signatures, 'we might need it in the future' trap);
"Use generics sparingly. The thinking should be 'this is generic functionality' instead of 'I could make this
generic.'"; good abstractions "click"; BUT "simple software does not mean 'good-enough-for-now' ... compile-time
invariants and making illegal states unrepresentable ... add real safety without adding accidental complexity."

Effective Rust Item 20 [B-effective-rust-optimize-2024]: "Making an allocation or copy operation visible
rather than hidden isn't a good reason to optimize it away, especially if that happens at the expense of
usability ... you don't have to treat Rust's smart pointers as a last resort" (i.e. `.clone()`/`Arc` are fine).

daymare abstraction addiction [C-daymare-abstraction-addiction-2025]: "the ecosystem has an abstraction
addiction ... you hit 'Go to Definition' and ... free falling through ten layers of traits, macros, and
generics"; nalgebra vs glam; "building for someone who doesn't exist"; "keep 'Go to Definition' useful";
"the community shows up to tell you that if you don't over-complicate it, you're writing unidiomatic Rust."

atwood (contrarian ballast) [C-atwood-rust-lisp-denial-2026]: monomorphization-by-default bloats binaries
and becomes load-bearing in public APIs (serde), turbofish/'a are C++ residue, proc-macro stack = homoiconicity
denied. Tangential to a small crate; useful only as breadth.

## LLM-authored Rust: named failure modes (complaint corpus)

HN top comment [D-hn-llm-rust-verbose-2025]: "The rust produced by LLMs is quite bad. It's overly verbose
(misses combinators) and often subtly wrong (swallows errors on result types when it shouldn't). A single
errant collect or clone call can destroy your performance and LLMs sprinkle them for no reason. Unless you are
experienced in rust, you have zero ability to catch the kind of mistakes LLMs make." COUNTER in same thread:
"I'd say it's on par with other languages then ... LLM are roughly 95% correct."

Rust forum (kornel + experienced) [C-rustlang-forum-ai-rust-2025]: "hallucinated dependencies, models trained
only on old versions of libraries"; "sometimes you get noob code with .clone() and .unwrap()"; "paint
itself in a corner with poorly designed structs, nearly duplicate enums"; "invariably change unrelated code";
"the more I prompt for fixes the worse it gets"; COUNTER: "T / V > 100 ... it's not a big deal if it's fairly
obvious to detect the BS solutions."

rulesync [D-rulesync-ai-rust-rules-2025] (commercial, structured): "excessive cloning to satisfy the borrow
checker ... using unwrap() everywhere ... overly complex lifetime annotations when restructuring would be
simpler ... fighting the ownership model with Rc<RefCell> when a simpler architecture would work ... traits
that look like Java interfaces — large, kitchen-sink abstractions with 10+ methods ... holding a MutexGuard
across an .await ... tests that under-utilize Rust's testing capabilities."

Microsoft first-party naming [A-microsoft-rust-ai-guidelines-2026]:
- M-RUST-SHAPED: "any striking technical similarity between Rust and { C#, Java, Python, ... } implementations
  is indicative of deeper architectural problems; a throw_if_null() never makes sense."
- M-NO-META-DESIGN-DOCUMENTATION: "Agents frequently produce sections that describe how a change was designed,
  'why we picked X over Y' essays, and design journals inside user-facing documentation" + literal self-report
  rule-compliance tables. "describes process, not behaviour, and goes stale."
- M-TAUTOLOGICAL-TESTS: "Agents frequently produce tests that re-state the expected value from the same logic
  the code under test uses ... Such tests pass by construction, provide virtually no value."

Institutional corroboration: the Rust project itself moved to restrict low-effort LLM contributions (3000+
Zulip msgs) [C-socket-rust-llm-policy-2026]; leadership-council #273 "No low-effort contributions" — explicitly
"not intended for AI-assisted contributions that have been thoroughly self-reviewed" [B-rust-council-low-effort-2026].
