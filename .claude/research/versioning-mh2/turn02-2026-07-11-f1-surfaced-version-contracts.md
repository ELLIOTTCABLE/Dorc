## Findings

- f1-fd1 +SURE: Hickey's Spec-ulation is the single closest structural match to `vers1-position-surfaced-contract` — he derives, live, that the artifact/package version massively over-specifies actual need: the *real* dependencies are the function-to-function calls, so a consumer "does not need X/Z" that the dependency tree lists. The thing you depend on is a property of the consumed call-set, not the package. That is Dorc's "package version DERIVED from the set of versioned callsites actually consumed," stated by a primary author in 2016. [B-hickey-spec-ulation-2016]
- f1-fd2 +SURE: Hickey's positive prescription IS the OCaml-prime-convention promoted to law — the written source the charter hoped existed. Change is not a thing; it is *growth* (accretion: provide more / relaxation: require less / fixation: fix) or *breakage* (require more / provide less / reuse a name for something else). Any breakage = "a new thing" = "MIGHT JUST AS WELL CHANGE THE NAME" → `foo-2` in the same namespace, or a new namespace. Semver's MAJOR means "you might be screwed" and is useless because it smashes all levels together. This is precisely "semver dies in favor of per-signature version marks," argued from first principles. [B-hickey-spec-ulation-2016]
- f1-fd3 +SURE: Go Semantic Import Versioning is the largest *shipped* instance of surfacing the version at the callsite — the major version lives in the import path (`my/thing/v2`), so every `import` types the contract-version it consumes, and the "import compatibility rule" enforces accretion-within-a-name (same law as f1-fd2). But the derivation runs *opposite* to Dorc: SIV makes the AUTHOR mint a new name per breaking change; Dorc wants the CONSUMER's package-version derived from consumed callsites. Same law, inverted agency. [A-cox-siv-2018]
- f1-fd4 +SURE: Go MVS is the "build's version derived from the consumed requirement-set" prior art the charter named: the build list is the reachable set from the consumer keeping newest-required-version; the goal is "high-fidelity" (as close as possible to what the author built against); only minimum versions are ever declared (the accretion assumption again). Related to, not identical with, Dorc's "highest version that includes the consumed callsites" — MVS derives *from declared requirements*, Dorc would derive *from actual consumption*. [A-cox-mvs-2018]
- f1-fd5 +SURE: The sharpest counter-thesis to any derive-identity-from-API design is Bourgon's "SIV is unsound": deriving identity from API-compatibility "strips authors of authority"; he argues "the version as expressed by the author is the core truth, and API compatibility is an emergent property of that truth. SIV's model is precisely backwards." Plus a hard limit Dorc inherits: API-compat "can't even be discovered, in the P=NP sense." This is the direct warning that a derived-version engine fights author intent, and that mechanical compat is undecidable — keep it best-effort. [B-bourgon-siv-unsound-2020]
- f1-fd6 +SURE: ELF/glibc symbol versioning is the literal per-symbol callsite-bound version mark at massive scale — `foo@v1` (non-default/hidden) vs `foo@@v2` (default), a `.gnu.version` table parallel to the symbol table, and undefined references that carry the exact version they linked against. Mechanism proof that per-signature version marks scale to libc. [B-maskray-symversioning-2020]
- f1-fd7 ~SUSPECT: Symbol versioning's author-side UX is genuinely loathed, as the charter suspected. MaskRay (an ld.lld maintainer) repeatedly flags the design: "these rules are not documented," "I strongly believe it is an issue in GNU ld but the maintainer rejected [the PR]," and several bare "this behavior is strange." The author must hand-maintain version scripts, and the forward-compat trap (build against new glibc → binary breaks on older glibc via `memcpy@GLIBC_2.14`) makes binaries non-portable across distros and time. Author-side pain ≈ mechanism value. [B-maskray-symversioning-2020][C-steam-symversioning-2021]
- f1-fd8 +SURE: Unison is the purest "intent compiles to hash" — each definition is the hash of its AST with all dependencies inlined *as hashes*; names are separately-stored metadata, "pointers to addresses in [an] immutable address space" whose contents "are forever unchanging." Dependency conflicts and diamond deps are "just not a thing" (multiple versions coexist by hash); type-preserving edits auto-propagate to callers, type-changing edits generate a to-do list, code never enters a "broken" state. This is `vers1-position-surfaced-contract`'s endgame (canonical form = opaque key) already shipped. [A-unison-big-idea-2021][B-unison-lwn-2024]
- f1-fd9 +SURE: Why nobody else shipped Unison's model — it is all-or-nothing. The payoff only lands when the WHOLE program is content-addressed: no stable FFI, no reuse of any text-based tooling (Share, browser, formatter all rebuilt from scratch), code isn't human-diffable in git, and it is still pre-1.0 after ~12 years of work. The Dorc lesson is a fence, not a template: content-addressing's benefits are real but demand discarding the surrounding ecosystem — the exact opposite of Dorc's redline that scripts "can be effortlessly re-used after abandoning Dorc." [B-unison-lwn-2024]
- f1-fd10 +SURE: Mechanical API-diff versioning is real and works, and its ceiling IS Dorc's undershoot. Elm auto-computes the API diff and *forces* the version number (`elm bump`/`elm diff` reject a wrong version at publish) — yet the maintainer's own issue concedes "type signatures [are] far from a precise specification… a change in the type signature is breaking, but the converse [does not] hold": behavioral breakage is invisible to the diff. cargo-semver-checks generalizes the mechanism (SemVer is "so hard… no mere mortals can uphold it"; 1-in-6 of the top-1000 Rust crates has violated it) but likewise only sees mechanical API *shape*, never runtime semantics. Deriving a version from a mechanical diff is achievable and useful — and structurally blind to exactly the semantic rot Dorc most fears. [C-elm-typesig-2020][B-predrag-semver-rust-2024]
- f1-fd11 +SURE (CENTRAL FILTER verdict): Across the entire front the versioner is the author of the versioned thing — glibc maintainers version glibc's own symbols; Unison authors mint their own hashes; Elm/Go/Rust authors version their own APIs; COM authors own `IFoo→IFoo2`. Every source UNDERSHOOTS Dorc's third-party-describer need. Only two affordances lean third-party at all: (a) Unison's names-as-separate-metadata (a third party can bind *its own* name to someone else's hash without touching the hash), and (b) mechanical diff tools (cargo-semver-checks, `elm diff`) that externalize the compat verdict from author-declaration to tool-derived fact. Neither models a *description that rots independently of the described tool*. The third-party-describer variant of surfaced version-contracts is, as far as this pass reached, genuinely unoccupied — a finding worth banking as much as any positive lift. [B-hickey-spec-ulation-2016][A-cox-siv-2018][A-unison-big-idea-2021][B-maskray-symversioning-2020][C-codecraft-com-immutability-2013]
- f1-fd12 ~SUSPECT: COM interface immutability (`IFoo`/`IFoo2`, each semantic change = a new IID) is the enterprise-scale instance of "never mutate, only add a new name," and the codecraft retrospective documents its real failure mode: in messy multi-party development the immutability is constantly *cheated* — "a security vulnerability forces us to start encrypting the string we return," silently changing semantics without a new IID — so consumers "cannot know when that threshold has been passed." That is Dorc's rot problem appearing even in a first-party world (author redefines behavior under a stable name), and it strictly worsens under third-party description. Corroborates that name-immutability alone does not stop semantic drift; you also need a *comparison/verification* layer (leads toward f4). [C-codecraft-com-immutability-2013]

## Citations

> [B-hickey-spec-ulation-2016]:§"Dependency Truth (code)" (relevance: +SURE)
> These are the _actual_ dependencies, right? Code that needs to run needs other code in order to work. That is the truth. … We do not need X. Right? ralph foo calls ricky foo. It never calls ricky bar, and ricky bar was the only thing that needed X. So this is already like not great. Our dependency tree is not really reflecting our actual needs.

> [B-hickey-spec-ulation-2016]:§"Growing/Breaking Your Software" + §"Which Name?" (relevance: +SURE)
> Accretion + provide more … Relaxation + require less … Fixation + bash bugs
> So calling it change is just not useful. We need to talk about one of two things. It either grew or it broke. There is growth and there is breakage.
> MIGHT JUST AS WELL _CHANGE THE NAME_
> Essentially, we are going to be able to say: this spec is incompatible. … And if it is, I want to see a new function. And in Clojure you have two ways to do that. You can stay in the same namespace and you can have foo-2.

> [A-cox-siv-2018]:§import-compatibility rule + §Semantic Import Versioning (relevance: +SURE)
> If an old package and a new package have the same import path, the new package must be backwards compatible with the old package.
> But when it's time to add v2, instead of redefining the meaning of the now-stable `my/thing`, we give it a new name: `my/thing/v2`. … I call this convention *semantic import versioning*.
> the import compatibility rule pushes a small amount of additional work onto package authors, and all users benefit.

> [A-cox-mvs-2018]:§Algorithm 1 + §Low-Fidelity Builds (relevance: +SURE)
> Construct the rough build list for M by starting an empty list, adding M, and then appending the build list for each of M's requirements. Simplify the rough build list to produce the final build list, by keeping only the newest version of any listed module.
> It also produces *high-fidelity builds*, in which the dependencies a user builds are as close as possible to the ones the author developed against.
> a dependency requirement gives only a minimum version, never a maximum version or a list of incompatible later versions.

> [B-bourgon-siv-unsound-2020]:§"Impact on the ecosystem" (relevance: +SURE — the counter-thesis)
> In SIV, versions are modeled so that API compatibility is considered the fundamental "thing", the authoritive truth that defines identity. … But API compatibility isn't and can't be precisely defined, nor can it even be discovered, in the P=NP sense. … Consequently, SIV's model of versioning is precisely backwards. The version as expressed by the author is the core truth, and API compatibility is (or isn't) an emergent property of that truth. SIV strips authors of this authority.

> [B-maskray-symversioning-2020]:§Representation + §Linker behavior (relevance: +SURE)
> Symbol versioning provides a way to maintain backward compatibility without changing `DT_SONAME`.
> Defined versioned symbols have two forms: `foo@@v2`, the default version. `foo@v2`, a non-default version (hidden version).
> GNU ld uses indirect symbols to represent versioned symbols. There are complicated rules, and these rules are not documented.
> I strongly believe it is an issue in GNU ld but the maintainer rejected [PR ld/27210].

> [C-steam-symversioning-2021]:issue body (relevance: ~SUSPECT — thin but real downstream pain)
> Compiling against a library with GNU symbol versioning on recent glibc/linux distros will produce binaries which will break on not-that-old glibc/linux distros. I don't know if it is an upstream symbol versioning bug, or it is by design and done on purpose.

> [A-unison-big-idea-2021]:§"The big idea" + §"No dependency conflicts" (relevance: +SURE)
> While we've given this function a human-readable name … names are just separately stored metadata that don't affect the function's hash.
> Names are like pointers to addresses in this space. We can change what address a name points to, but the contents of each address are forever unchanging.
> In Unison, definitions are referenced by hash (and the names are just separately stored metadata), so dependency conflicts and the diamond dependency problem are just not a thing.

> [B-unison-lwn-2024]:§"Drawbacks" (relevance: +SURE — the why-nobody-shipped-it answer)
> Unison doesn't even have a stable foreign-function interface (FFI) that could be used to wrap libraries written in other languages. Because of this, existing Unison programs need to reimplement a lot of functionality that is already present in other languages.
> Since Unison code is not stored as text files, but rather as a database, the community can't really reuse existing tooling. Tools like Unison Share must be written from scratch.

> [C-elm-typesig-2020]:issue #2099 body (relevance: +SURE — the API-diff ceiling)
> we should recognize that type signatures far from a precise specification. It is true that a change in the type signature is breaking, but the converse doesn't necessarily hold.
> Your elm.json says the next version should be 4.0.0, indicating a MAJOR change to the public API. This does not match the API diff given by: `elm diff 3.1.0` — This command says this is a PATCH change, so the next version should be 3.1.1.

> [B-predrag-semver-rust-2024]:§overview (relevance: +SURE — mechanical-derivation feasibility + human infeasibility)
> semantic versioning in practice is so hard that no mere mortals can uphold it. *None of us* are good enough to do it on a consistent basis.
> 1 in 6 of the top 1000 Rust crates has violated semantic versioning at least once, frustrating both users and maintainers alike.

> [C-codecraft-com-immutability-2013]:§"Immutability and Versioning" + §"Evolution Isn't Always Forward" (relevance: ~SUSPECT)
> Current thinking on interface versioning calls for an interface to be immutable; each change to its semantics … should cause a change to the interface number/name/guid.
> A security vulnerability forces us to start encrypting the string we return from a function. … Over time the assumptions about semantics attached to an interface accumulate enough drift that it is impractical to ever treat an `IWidget9` as an instance of `IWidget2`. How does Sally know when that threshold has been passed by Bob?
