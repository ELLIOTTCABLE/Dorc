## §2 — The human's design positions (HUMAN-TYPED this session; the new durable material)

- vers1-position-surfaced-contract: versioning is NOT necessarily hidden from the user. The
  human's long-standing pre-Dorc language concept: make version a surfaced, substrate-level
  *contract element* between any two users, peer to name and type-signature — every callsite
  types an explicit version of the contract it consumes (`do_thing@2(arg1, arg2)`), the
  engine intersects *granularly* (per-callsite, not per-package); the "package version" you
  want is *derived*: the highest version that includes the set of versioned callsites you
  actually consume. Authors get complete freedom to change any part of a contract at any
  point; semver dies in favor of per-signature version marks (the OCaml prime-convention,
  promoted from idiom to checked contract).
- vers1-position-rot-asymmetry: the Dorc shift of that idea targets *oracle rot*: ALL code in
  this language is ~10× more rot-prone than a normal ecosystem, because essentially nothing is
  first-party — it is always an interested third party describing someone else's tool. The
  author-of-the-thing-versioned ≠ author-of-the-version-description, which the human flags as
  the critical *undershoot* dimension for prior art (most prior art may assume they're the
  same party; its lessons then cap out below our need).
- vers1-position-two-domains: the shape probably *cannot* be globally-version-specific,
  because there are two separate version-domains, only one of which is rot:
  1. **oracle-version** — the oracle-author's own work ages (rot; the tether problem);
  2. **described-tool-version** — a best-effort author writing an up-to-date oracle *today*
     must describe an entire chronology *in-situ*: handle Python v2 AND v3 at once.
  The latter almost certainly must descend granularly INTO the oracle body — arms/paths (at
  minimum) become version-annotatable — because sixteen un-D.R.Y. siblings
  (`python__v2.5.1__disturbs()`, `python__v2.5.2__disturbs()`, …) are unacceptable. "How to
  sh-spell this" is the critical analysis dimension; explicitly future-turn work.
- vers1-position-inline-pins: pinning under serious consideration as *inline emission
  directly into the otherwise-human-managed file* — the Homebrew pattern (hashes live inline
  in the human-written descriptor code), with tooling to auto-insert/update them — NOT a
  separate lockfile-kind artifact.
- vers1-position-silence-gate (self-declared STRAWMAN; SHARPENED same-session, this
  refinement supersedes the first cut): extend silence-licenses-nothing to versioning —
  but per-FEATURE, with different features on opposite poles, never one global pin.
  version1 / version2 / unversioned are live, separate, *maintained* classifications — a
  lattice that never collapses. Specifically the *sharp-knife* features — the ones that
  travel elision-licenses (the survival tier) — are suspected to bear a third enablement
  requirement, growing the existing double opt-in {oracle-buyin, admin-buyin} to
  {oracle-buyin, admin-buyin, explicit-version-match}: a growth of pre-existing
  limitations, not a new limitation. *Self*-blast-radius features (general
  self-elision-when-converged, not traveling-elision) can/will probably continue
  gradual-enhancement, taking the mildly-dangerous route of
  version-silence-means-correctness (human explicitly not married to that half).
- vers1-position-comparison-keyed: any such gate would have to be *comparison-keyed*, not
  hash-keyed — hash-keying is too broad a brush and kills value across the broad class of
  situations where hashes churn; the wanted window is mid-narrow, something purl/semver-shaped.
  No specific plan yet.
- vers1-position-promise-names: the sibling block-settle work independently hit the
  `__version`-is-plausible-and-innocent collision problem; the lean there is gently toward
  slightly-odd names, AND toward encoding *promises* into names — e.g. `kind__reaches()` has
  evolved to `kind__disturbance_only_reaches()`, surfacing the dangerous exclusion-set nature
  of the promise in "only" so it can't be cargo-culted accidentally. If a version-specific
  role ever exists, the human's gentle lean is something like `cmd__version_described()` —
  but per vers1-position-two-domains, the shape is probably not globally version-specific.
- vers1-position-larger-than-axis: the human gently-but-strongly suspects versioning is
  *larger* than an axis/context of the entity algebra being settled in `270:block-settle`
  (not certain; strongly suspicious).

## §3 — Conductor synthesis (derived, UNACKED; certainty-marked)

- vers1-fd-inline-pins-thread-koob: ~SUSPECT the inline-pin position *strengthens* kOOB
  standing versus any lockfile design: pins spelled in-band, in the sh the human already
  manages, tool-*maintained* but human-*owned*, thread the no-sidecar-configuration redline
  that a lockfile artifact would strain. It introduces one genuinely new interaction lane —
  Dorc tooling writing into human-managed files — which has healthy prior art (Homebrew's
  bump tooling, nixpkgs update-scripts, `cargo add`) and one standing house precedent to
  reconcile with: strip-fidelity (whatever is emitted must erase cleanly with `dorc strip`).
- vers1-fd-dispatch-is-value-plane: ~SUSPECT the described-tool-version domain
  (vers1-position-two-domains item 2) largely reduces to machinery that already has owners:
  a tool's version is a *value-carrying probe fact* (the `an-ide-value-layer` row —
  `nginx@1.24` — which TODO-ADDTL already couples to MH2), and in-body version-dispatch is
  ordinary sh branching on a captured value — `case "$(python --version)" in 2.*) …` — which
  is exactly the read-value lane (`270:block-context` capture fold) plus the orphaned
  case-scrutinee arm-resolution precision item (TODO-ADDTL read-value residue). Per-arm
  annotation precedent exists (`24G` typed emission: trailing marks on arms). What does NOT
  reduce: the comparison key — case-globs compare strings; version *windows* need
  EVR/semver-shaped comparison. Which leads to:
- vers1-fd-compare-is-kind-owned: ~SUSPECT version-comparison semantics are *kind-owner
  knowledge* — dpkg-EVR vs semver vs PEP 440 is per-ecosystem, exactly the per-KIND family's
  species (`resolve()`/`reaches()` precedent), and the founding `.version-compare` verb
  finally has a natural home that didn't exist in 2026-05: a per-KIND role, not per-TOOL.
  Also coheres with no-join-across-managers: comparison only ever *within* a kind.
- vers1-fd-lockin-ledger (updated from the prior turn's four; the deliverable):
  1. **coordinate-seam** (TIME-SENSITIVE — live in `270:block-settle` NOW): see §4 relay.
  2. **unmarked-oracle reading pin**: the `rul24M-rungs-default` precedent (future machinery
     never re-reads unmarked functions) applies to version-silence. The two poles were
     RECONCILED same-session by the sharpened silence-gate position — they are
     per-feature-TIER, not rivals: self-blast-radius tiers read version-silence as
     correctness (the prior-turn conductor lean, scoped down to that tier);
     traveling-license tiers withhold the sharpest knife until explicit-version-match (the
     strawman, scoped down likewise). What remains pin-work: the tier-boundary itself
     (which features sit on which pole) and the typed ruling — still owed before
     `block-stdlib` authors ~40 oracles and the field trial invites outside authorship.
     One ruling now; unretractable drift later.
  3. **capture-at-authoring**: no future tether can recover a world that was never recorded —
     oracles published before grounding-capture exists have permanently lost their origin
     context. The inline-pin position sharpens this: the *authored file itself* carries the
     grounding, so the capture discipline (and its emission grammar) is what must exist before
     the corpus accretes; `an-oracle-ref-sha` and git metadata are the free floor.
  4. **role-name namespace**: converged with the sibling work's odd-names/promise-names lean;
     candidate future version-role names should ride the existing munge-reservation lint's
     reserved set (superset-reserve now; the recognition surface is permanent and
     unversionable per rul24M-version-comment).
- vers1-fd-fences (standing law adjacent to any traveling-pin design; surfaced, not objected):
  rec-5 (probe-TAPE write-only, never re-ingested — welded) · kSTATE parked with the human's
  hostile-host rider (state from one host affecting another = security vector) · the
  wall-clock-keyed verdict classes are the first hermeticity test-cases "any content-key
  design must survive" (KNOBS kSTATE note) — an intent-to-hash compilation IS a content-key
  design, so they transfer wholesale. The sharp lane-crossing: pins *harvested from a host*
  (TOFU first-contact) entering the authored/trusted plane re-activate the hostile-host
  rider; pins authored/committed by humans ~SUSPECT thread it cleanly.

> *non-foreclosure* is warranted for the deferred versioning layer (MH2 — deferred, but

> candidate shapes, and only the non-foreclosure is asked for, no mechanism: (i) room for a
> grounding/version qualifier segment on coordinates — same species as the context-qualifier,
> marking "this coordinate, as-of version-window V / world-key W"; (ii) the weaker property
> that a kind's canonical form is not welded to *flat, human-legible, timeless name-string* —
> the `resolve()` content-address endgame (canonical form = opaque key) and version-qualified
> canonical forms should both remain representable someday. The failure being priced: if the
> algebra bakes "coordinate = kind × timeless-name [× context-qualifier]" into transfer
> functions, footprint intersection, and probe keying, a later version/epoch qualifier forces
> a second whole-corpus re-key — the exact author-once mistake this block exists to avoid.
> Caveat, from the human directly: versioning is gently suspected to be *larger* than an
> axis/context of this algebra — it spans two distinct version-domains (the oracle's own age
> vs the described tool's in-body version-chronology) — so if reserving it as an axis feels
> like it distorts the algebra, treat that instinct as evidence *for* the larger-than-an-axis
> reading and report it back rather than forcing the fit.

## §5 — Prior-art review-round charter (DRAFT; dispatch pending human ack)

Central filter, applied to every source (from vers1-position-rot-asymmetry): does this prior
art assume the versioner IS the author of the thing versioned? If yes, its lessons *undershoot*
— grade the finding accordingly and hunt for the third-party-describer variant.

Fronts:
- **f1-surfaced-version-contracts** — per-callsite/per-symbol versioning in the wild: ELF/glibc
  symbol versioning (`memcpy@GLIBC_2.14` — literally callsite-bound version marks at massive
  scale, including its author-side UX pain); Unison (content-addressed definitions; names as
  metadata over hashes — the purest intent-compiles-to-hash language); Go MVS (build's version
  derived from the consumed requirement-set — related to, not identical with, the
  highest-including-consumed-callsites derivation); COM interface immutability; Elm's
  enforced API-diff versioning; cargo-semver-checks. Include failure modes: why symbol
  versioning is loathed by maintainers, why nobody else shipped Unison's model.
- **f2-inline-pin-emission** — machine-maintained pins inside human-authored artifacts:
  Homebrew formulae (inline sha256 + livecheck/bump tooling — the named exemplar), nixpkgs
  fetcher hashes + update-scripts, pre-commit autoupdate, `go.mod`/`go.sum` and
  manifest-vs-lock splits *as the contrast case*, pip hash-pinning in requirements files.
  Focus: authoring UX, drift/update workflows, merge-conflict behavior, what the human reads
  vs what the machine owns — not hash mechanics.
- **f3-in-body-chronology** — one body describing many tool-versions (the
  described-tool-version domain): autoconf's feature-not-version doctrine (the canonical
  counter-tradition: probe capabilities, never key on versions — a live design-alternative
  for Dorc oracles, not just background); browser feature-detection vs UA-sniffing hindsight;
  Ansible module version-guard idioms; python-six/compat-shim structure; sh-native comparison
  primitives (`dpkg --compare-versions`, `sort -V`) as spelling prior-art.
- **f4-comparison-keys** — the mid-narrow window shapes: purl, dpkg/RPM EVR, PEP 440, semver
  ranges, OSV/vuln applicability-windows (the closest existing "which claim applies to
  version V" machinery — claims authored by third parties about others' software, passing the
  central filter).
- **f5-rot-governance** (light) — freshness/rotation semantics only: TUF's freshness model,
  Debian buildinfo/reproducible-builds' grounding records. Explicitly not transport security.

Exclusions (fenced): transport-verification mechanics (vers1-scope-out-transport) · hash
algorithm choice · registry design (no-registry is welded) · secrets (quarantined pending an
Opus-only round, per TODO) · anything corpus-sizing/H2SaLS-shaped (standing fence).

Method: interactive-research idiom — graded sources (source-IDs, sources.json), main-context
adjudication; subagents only for fan-out gathering; raw load-bearing sources get read into
main context after the fan-out.
