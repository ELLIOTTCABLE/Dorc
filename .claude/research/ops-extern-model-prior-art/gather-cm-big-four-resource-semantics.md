# gather-cm-big-four-resource-semantics — Puppet, Chef, Salt, Ansible as prior art for a resource model over ops externs

Lane 3 of ten. 311 read at `63e49f29` (git rev-parse --short HEAD at start). All grades `graded-by: subagent`.

## Findings

- Counter-thesis largely CONFIRMED for identity: all four key a declaration by a per-type string (Puppet `(type, title)` plus `(type, uniqueness_key)`; Chef `"type[name]"`; Salt the ID label plus a `name` string; Ansible nothing at all across tasks). None compares two declarations by what they reach; canonicalisation is lexical and type-local at most (Puppet file strips trailing slashes and runs `File.expand_path`, never resolving symlinks or mounts). +SURE [A-puppet-resource-catalog-duplicate-alias-code-2026] [A-puppet-file-type-path-munge-autorequire-code-2026] [A-chef-resource-set-lookup-code-2026] [A-salt-highstate-id-and-name-declaration-2026] [A-ansible-builtin-file-module-code-2026]
- The four split on what a duplicate MEANS, and the split is itself a finding: Puppet treats an equal key as one thing and refuses the catalog; Chef (since 13) treats equal names as "entirely separate" resources and admits it "makes it impossible to safely deliver notifications to the right resource"; Salt's documented idiom for two states on one file is to give them different IDs and the same `name`; Ansible has no catalog. Only Puppet detects anything, and only string-equal keys. +SURE [A-puppet-core-lang-resources-uniqueness-2026] [A-chef-deprecation-resource-cloning-chef3694-2026] [A-salt-highstate-id-and-name-declaration-2026]
- The best refuted-shape witness in the lane: Puppet's own tracker diagnoses "the File type assuming that the path is a unique identifier (namevar), while that's not true when Mounts are involved ... there are actually two /x directories", and the fix was to revert an autorequire, not to model the mountpoint vs mounted root. A 311 §3.3 routing mutation (a mount) that a string-keyed model cannot express. +SURE [A-puppet-pup6397-mount-path-not-unique-2016]
- The strangers case (311 §1.2, two mSchemes into one mSort unknown to the engine) is explicitly conceded by Puppet maintainers: after moving package identity to `[name, provider]` (Puppet 4.0), "a composite key does not provide an airtight guarantee of uniqueness" because `yum` and `rpm` "manage the same pool of packages" and implicit vs explicit default provider still collide undetected. Lindberg: deciding whether two references are the same "without resolving against the actual resource type — that is a really really bad idea". +SURE [A-puppet-pup1073-composite-package-namevar-2013]
- Puppet has an explicit, named punt: a type may declare itself non-isomorphic ("an isomorphic name is the identity of a resource"); `exec` and `tidy` do, and the catalog then skips the uniqueness-key alias and all collision checks for them. This is the closest thing in the big four to 311's "absent warrant": a per-type declaration that equal names license nothing. +SURE [A-puppet-type-rb-isomorphism-autorelation-code-2026] [A-puppet-resource-catalog-duplicate-alias-code-2026]
- Puppet's autorequire IS the most any of the four did toward a cross-sort may-read / entailment table, and it is small, type-author-declared, create-order-only, and resolved by string lookup in the catalog: file → nearest managed ancestor directory, link target, owner user and group BY NAME (numeric uid/gid skipped); exec → cwd, absolute paths scanned from command/onlyif/unless by regex, user by name; package → responsefile, adminfile, absolute source; user → groups, roles. It adds an edge only "if puppet is managing both ends". Declared by the TYPE author (the 311 mSort owner), never by the provider or user. ~SUSPECT on completeness (mount/cron/ssh_authorized_key/host now live in separate modules, not read). [A-puppet-file-type-path-munge-autorequire-code-2026] [A-puppet-type-rb-isomorphism-autorelation-code-2026] [B-puppet-specifications-resource-types-2017]
- What autorequire does NOT cover, per Puppet's own tracker: it is ensure-blind (ancestors autorequired "regardless of whether it is ensured present or absent", so deletes cycle, unresolved since 2014); mount ↔ mountpoint could not be expressed and was reverted; it carries ordering and optional refresh only, never "this write changes that fact". +SURE [B-puppet-pup2451-autorequire-absent-cycle-2014] [A-puppet-pup6397-mount-path-not-unique-2016]
- "What a write reaches" is, in all four, hand-written user speech about CHANGE EVENTS, not about referents: Puppet notify/subscribe (refresh on any change, once per run), Chef notifies/subscribes by `"service[blah]"` string, Salt watch/onchanges/listen fired by a non-empty `changes` dict with the watcher's `mod_watch` as the refresh action (author of the WATCHING state module declares it), Ansible handlers (not pulled). None lets an mSort owner declare "writing K entails may-write of L". +SURE [B-puppet-core-lang-relationships-2026] [B-chef-rfc058-before-notification-whyrun-2015] [A-salt-requisites-doc-2026]
- Salt's reference mechanism conflates label and referent: requisites "match on both the ID Declaration and the name parameter", so a state whose `name` equals another's ID resolves to itself ("Recursive requisite found"; reopened as a feature, stale-closed), and `require_in` silently dropped an edge when an ID in another state type matched the name (fixed 2021). +SURE [B-salt-issue-5667-name-treated-as-id-2013] [B-salt-issue-59922-requisite-in-id-name-conflict-2021]
- Puppet's own maintainers litigated the committee-law problem (311 §3.5) and answered it with exclusive ownership: two Forge modules that each need `Package['foo']` cannot coexist; the "constraints" proposal (a module stating a need about a resource it does not own) never shipped; the ticket is open since 2014. +SURE [A-puppet-pup1968-duplicate-resources-forge-modules-2014]
- Canonicalisation phase matters and Puppet gets it wrong: `File['/tmp/test/']` yields a uniqueness key with the slash at compile and without it after `to_ral`, so two resources for one path pass compilation and crash at apply. ~SUSPECT that this generalises (single unresolved ticket). [B-puppet-pup6770-uniqueness-key-trailing-slash-2016]
- The natural key per type is itself contested: Puppet `host` keyed by hostname cannot express `127.0.0.1` and `::1` both named `localhost`; IP is also insufficient; closed Won't Fix. Line-structured config entries (item 40-shaped) have no stable key in Puppet's model. +SURE [B-puppet-pup1928-host-key-not-unique-2014]
- Nearest thing to a declared mScheme `resolve()`: the Puppet Resource API `canonicalize` hook (provider normalises values; `get`'s output must be a fixpoint, checked under `--strict`). It is value normalisation within one type and provider, never cross-type. Resource API explicitly does not support several providers for one type, and floats but never built "definitions [that] declare (partial) equivalence to other definitions (ala apt::package is a package)" — the unbuilt 311 `:yields`. +SURE [A-puppet-resource-api-specification-2023]
- Chef's `identity` is for reporting and for seeding `load_current_value` ("correlated across Chef runs"), never for collision; the lookup key is the declared name. Chef's `provides` is DSL-name dispatch ("the last class to load wins"; RFC 107 adds locking), not package-alias identity. +SURE [A-chef-resource-rb-identity-provides-code-2026] [B-chef-rfc107-resource-map-locking-2018] [A-chef-rfc056-load-and-converge-2015]
- Noop/check-mode faithfulness, in their own words: Salt "Test mode does not predict if the changes will be successful or not"; Ansible "Check mode is just a simulation. It will not generate output for tasks that use conditionals based on registered variables" and modules that lack support "report nothing and do nothing"; Ansible's file module warns in check mode "Create user up to this point in real play"; Puppet noop suppresses refresh and only logs "what would have happened". All four simulate per resource with no model of prior simulated writes. Chef :before and Salt prereq both TRUST a per-resource dry run as a prediction of change. +SURE [A-salt-writing-state-modules-return-contract-2026] [A-ansible-checkmode-diffmode-doc-2026] [A-ansible-builtin-file-module-code-2026] [B-puppet-core-lang-relationships-2026] [B-chef-rfc058-before-notification-whyrun-2015] [A-salt-requisites-doc-2026]
- Ansible's one in-module identity heuristic coincides with 311 §1.5's evidence: `get_state` calls a path with `st_nlink > 1` "hard". It also folds PermissionError into "absent" (GOTCHAS unreachable-is-not-absent) and compares hard links by `st_ino` alone (no `st_dev`). `follow=yes` writes mode/owner through a symlink to the target, documented only in prose. +SURE [A-ansible-builtin-file-module-code-2026]
- Absence semantics: Resource API "If a requested resource is not listed in the result, it is considered to not exist"; Chef `current_value_does_not_exist!` separates absent from unset. Analogue of 311's existence cell as the mParent-Catalog entry. -GUESS on how useful beyond vocabulary. [A-puppet-resource-api-specification-2023] [A-chef-rfc056-load-and-converge-2015]
- The RFC/proposal repositories are nearly silent on identity: Salt SEPs contain nothing on state semantics beyond sub-state returns; ansible/proposals contains nothing on resource identity, and its whole-collection-write thread ("state: pure") was pushed out of core into roles; Chef RFCs treat identity only as property plumbing; Puppet's litigation lives in Jira, not in puppet-specifications or the ARM/puppet-rfc repo. +SURE for Salt and Ansible repo listings; ~SUSPECT for Puppet ARMs (listed, not read). [C-ansible-proposal-71-pure-state-squashing-2017]
- Origin evidence: Kanies's 2006 design statement treats an element as "a kind of named hash" needing only "the element type and the element name". Identity beyond (type, name) was never in the design. ~SUSPECT as evidence of intent (it is a pitch, not a spec). [B-kanies-puppet-next-generation-cm-2006]

### Counter-thesis verdict

Largely confirmed. Identity: a string key per type, with Puppet the only one that even detects equal keys, and Puppet's own maintainers conceding the strangers case and the path-is-not-a-referent case in writing. Write reach: hand-written change-event edges in all four; Puppet autorequire is the one type-author-declared cross-type table, and it covers create-order among managed resources found by exact name (parent dir, owner, group, cwd, command path, package files, user groups), nothing about what a write changes, nothing ensure-aware, nothing through mounts or symlinks, and nothing for unmanaged ends. Refutation of the "string key only" half comes only from two narrow places: Puppet's per-type isomorphism flag (a declared "equal names license nothing") and the Resource API's `canonicalize` fixpoint. Neither crosses types.

### Breadth against the 47 items

Modelled as a first-class type/state in at least one of the four (core or first-party module), by name only: 1–2 (service), 3/6/44/45 (file content; Augeas/ini_setting modules outside core), 5 (file mode), 14–16 (package ensure / version / mark hold), 17–20 (user shell/uid/groups/password), 19 (group members), 23 (mount options), 28 (cron), 30 (host/hostname via modules), 33 (cert files only), 36 (Puppet `alternatives` module, Salt `alternatives`), 39 (ssh_authorized_key), 40 (file line), 43 (package provider pip/gem), 11–13 (Salt `sysctl.present`, Puppet via modules), 21–22 (Salt `network.managed`), 24–26 (docker/k8s modules), 27 (DNS provider modules), 29/31/41 (firewall modules), 32 (Salt `mount.swap`), 34–35 (selinux/timezone modules), 42 (DB modules), 46–47 (Salt `lvm`, Puppet `lvm` module). -GUESS on module coverage: I did not read the module docs; this is from type names in the read sources and general knowledge.

Unmodelled or modelled only as opaque text in all four: 4 (InvocationID), 7 (inode/hardlink identity as such — only Ansible's `state: hard`), 8 (xattr), 9–10 (git config scope / resolved chain), 25 (container health), 37–38 (process environment), and any item whose value depends on the observer (311 §2.8). None of the four models an item's cells, only a resource's properties.
