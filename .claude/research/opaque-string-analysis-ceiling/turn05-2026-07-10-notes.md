## opaques5-proposal1-context-axes-kind-sensitivity (the candidate holistic shape)

The answer opaques4-question1-holistic-transform seems to want, assembled from the
grounding (status: PROPOSAL, ~SUSPECT overall; each leg cited):

1. A context is a point moved along a small set of AXES: {user, fs-root, env, host, …}.
   A WRAPPER's oracle (per-TOOL, argv-keyed — it alone knows its own flags) declares
   which axes its tail moves and to what: sudo moves user(+env-scrub unless -E); chroot
   moves fs-root; ssh moves host (someday-never per ruling-host-someday-never); nice
   moves nothing.
2. Whether a moved axis CHANGES a coordinate's referent is KIND knowledge, not wrapper
   knowledge: package is user-invariant (dpkg db is system-global) but fs-root-SENSITIVE
   (a chrooted dpkg reads a different database); crontab is user-SENSITIVE; file is
   user-invariant (post-expansion paths are absolute) but fs-root-sensitive-WITH-MAP
   (the rebase). So each KIND declares, per axis: invariant / sensitive-with-map /
   sensitive (no map). Silence = the conservative floor: cross-boundary pairs get NO
   identification — may-alias for disjointness tests (demote, safe) AND no
   must-alias for establishment-flow (facts don't discharge outer requirements through
   an undeclared boundary — walls, safe). Monotonic: every declaration only ADDS
   identification, in exactly the 24F §3a degrade-direction.
3. The engine composes mechanically: a coordinate crossing a boundary that moved axis A
   consults the kind's A-sensitivity: invariant ⇒ identity bridge (same cell both
   sides); sensitive-with-map ⇒ apply the owner's map (oracle-authored sh, probe-lane,
   riding resolve()'s exact rails — host-run, CanonicalCoord-minting, may-alias on
   failure); sensitive ⇒ no bridge (floor). Wrapper nesting = axis-move composition;
   site verdict = weakest cell, as in the turn-3 composition rule.

Why this is plausibly NOT over-abstraction (the 24G §3 graduation-test logic): each leg
is keyed to the one party that knows it — wrappers know their argv/axes, kind-owners know
their referent-stability — and each leg has live traffic across maturities (sudo's
env-scrub is static; the chroot fs-map is BORN dynamic, realpath-under-root). The
"opaque transform over resolver-surface-area" of note-fsview-dovetail lands as the
sensitive-with-map cell: a kind-owner's context-map is a sibling of resolve() — same
probe-lane, same trust tier, same failure direction — parameterized by the context.

- opaques5-finding8-track-vs-forbid (+SURE): the literature offers exactly TWO stances on
  cross-boundary aliases (cutpoints — objects reachable from inside a passed region AND
  from outside, bypassing the interface): TRACK them (POPL05: freeze cutpoint-labels at
  entry, thread through, invert at return — pays in PRECISION collapse when multiple
  aliases coexist, "two lists with shared tails will be handled very conservatively") or
  FORBID-and-DETECT them (SAS05: cutpoint-free programs; detect at each call, halt
  otherwise — buys per-procedure-bounded cost and REUSABLE heap-modular summaries).
  Practice converges on forbid-and-guard too: Bazel makes the boundary sound by
  ENUMERATING what crosses (declared inputs, known outputs), never by rewriting; Nix
  guarantees referential integrity only WITHIN one canonical root. proposal1 is squarely
  the forbid-and-guard family (undeclared crossing ⇒ no identification ⇒ may-alias/wall;
  sensitive-with-map = the enumerated legitimate crossing) — the family the literature
  says is the cheap, modular one. [A-rinetzky-local-heaps-2005] §3/§5.3;
  [A-rinetzky-cutpoint-free-2005] §1/§2.2; [B-bazel-sandboxing-2026];
  [A-nix-store-path-2026].
- opaques5-finding9-dorc-has-a-bottom (+SURE, structural advantage): SAS05 must HALT on a
  detected cutpoint (shape analysis has no fallback); Dorc's analog is DEMOTE-toward-run
  — the "just run the line" bottom always exists, so forbid-style designs cost us VALUE,
  never soundness or termination. This is why the may-alias floor is affordable for us
  where the PL literature had to choose between tracking machinery and program-class
  restrictions.
- opaques5-finding10-rebase-unsound-confirmed (+SURE — closes half of
  opaques5-open3): BOTH literatures independently call naive coordinate
  string-substitution unsound. Nix: relocating a store object by string-replacing the
  store-dir "is in general not enough… as this may render executables unusable by
  invalidating their internal offsets or checksums" (embedded self-references the rewrite
  can't see); POPL05's whole apparatus exists because the naive rename fails under
  outside aliases. So proposal1's static-prefix-rebase rung for fs-root maps is
  officially the cheap-but-wrong rung (internal symlinks = our embedded self-references);
  the honest ladder is enumerated-bridge ⊑ in-context-map ⊑ may-alias floor.
  [A-nix-store-path-2026] Store-Directory; [A-rinetzky-local-heaps-2005] §3.
- opaques5-finding11-bindmount-cutpoint-confirmed (~SUSPECT): bind-mounts (and their
  docker-volume cousins) are the cutpoint-analog proper — within-context aliasing minted
  by mount state, invisible to any per-boundary bridge. The literature's two answers map
  to: track (label the shared referent — expensive, precision-collapsing) or
  detect-and-degrade (probe-lane mount read ⇒ may-alias within the fs kind ⇒ demote).
  Given finding9, detect-and-degrade is the obvious Dorc lean; recorded as the
  opaques5-open4 disposition-lean, not settled.
- opaques5-finding12-content-address-endgame (-GUESS, cross-ref only): Nix's
  content-addressing divorces identity from coordinates entirely — the deep endgame of
  resolve() (canonical form = content hash, location-independent). Ties directly to
  TODO-ADDTL's MH2 binary-content-hash grounding gate; noted for whenever MH2 unparks,
  not for this round.

> [A-rinetzky-local-heaps-2005]:§3 Def 3.1 (relevance: +1:SURE)
> "A cutpoint for an invocation of function p is a heap-allocated object that … is:
> (i) reachable from a formal parameter of p (but not pointed-to by one) and (ii)
> pointed-to by a pending access path that does not pass through any object that is
> reachable from one of p's formal parameters."

> [A-rinetzky-cutpoint-free-2005]:§2.2 (relevance: +1:SURE)
> "The fact that the invocation is cutpoint-free guarantees that the only references
> into the local heap are references to objects referenced by an actual parameter."

> boundaries." / "It is in general not enough to replace the store directory string in
