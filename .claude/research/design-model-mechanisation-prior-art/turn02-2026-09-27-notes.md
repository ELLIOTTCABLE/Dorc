# turn 2 — 2026-09-27 11:38:42 CDT

Subagent turn, front-single-artifact-prose-and-checks. The question: is there a standard format for one authoritative artifact that holds mechanically checkable claims and normative-but-untestable claims together, with the untestable residue tracked toward zero? Secondary: what people do instead, and how the prose-to-check seam is kept honest.

## Findings

- No standard single-artifact format exists that is both mechanically analysable and carries a typed notion of evidence for untestable claims. A peer-reviewed 2015 survey says so directly: existing dependability-case languages are either logic-based and analysable with no notion of evidence, or claim-and-evidence notations that no tool can analyse [A-ernst-dependability-case-language-2015]. Nothing found since closes that gap in a maintained, general tool.
- The nearest research instance is one Alloy artifact built as a checked safety case (CAV 2016), described in [A-pernsteiner-safety-case-pluggable-checkers-2016]:
   - The system model S and property P are Alloy. Each component property is guarded by an uninterpreted `evidence[tool, args, kind]` predicate. The checker runs the named tool, fills in the predicate, and asks Alloy whether S ∧ ¬P has a counterexample.
   - Claims no tool can check use an "expert evidence" kind: a prose document with the expert's name and a date, and the tool checks only that it exists.
   - Sufficiency of evidence is explicitly left to manual audit.
   - Trying to attach evidence to every claim exposed a modelling error: the relay the model named did not exist.
   - The extension never reached mainline Alloy; a 2024 practitioner is still asking for it [C-alloy-discourse-dependability-cases-2024].
- Standards bodies, where they mechanise at all, give each normative prose sentence a stable in-prose ID and keep the check (or the recorded refusal to check) in a separate artifact keyed by that ID:
   - Vulkan tags every valid-usage sentence with a VUID. The validation-layer script computes the percentage of spec VUIDs checked in code and tested in tests. It has a consistency mode that fails on IDs present in code or tests but undefined in the spec [A-khronos-vvl-validation-stats-2026].
   - A reasoned register of about 658 VUIDs that "are not possible to validate", each with a why-comment, is kept beside the checks. The coverage script counts that register as layer source, so declared-uncheckable IDs sit inside the "checked" percentage rather than a separate bucket [A-khronos-vvl-unimplementable-validation-2026][A-khronos-vvl-validation-stats-2026].
   - Drift control is a spec-side rule: a semantic change to a valid-usage sentence must retire its VUID so a new one is minted. Exempt: non-semantic edits, and sentences not yet implemented in the layers [A-khronos-vulkan-vuid-style-guide-2026].
- RISC-V has two separate things, and neither is a checked single artifact:
   - Its Alloy memory model sits inside the ISA manual as pasted listings in an appendix that declares itself "commentary; all normative material is provided in" the main body [A-riscv-isa-manual-mm-formal-2026]. A grep of the Makefile and the ISA build workflow at the same commit found no Alloy step (observation, not a registered source).
   - Its live mechanism is `norm:` anchors on normative prose (one tag equals one rule), extracted into a norm-rules JSON [A-riscv-normative-rules-tagging-2026]. The record has no status or check-linkage field [A-riscv-norm-rules-schema-2026].
- A literate model format exists, but none of the tools read the prose:
   - Alloy Markdown: the Analyzer reads `.md` files with fenced `alloy` blocks directly [B-alloy-docs-markdown-2023]. One practitioner says shared, maintained models are "almost always" written this way, with every run and check in one final fence [C-alloy-discourse-tell-a-story-2026]. No production literate-Alloy artifact was found; the canonical example repo's instance pastes analyzer output as unchecked text tables and records assumptions as facts left commented out for the reader to toggle [B-alloytools-webattack-literate-model-2026].
   - Quint (lmt tangling) [A-quint-literate-specifications-2026] and the Ethereum executable spec [A-ethereum-consensus-specs-md-to-spec-2026] work the same way: only code fences (and, for Ethereum, constant tables) become the spec, and the prose is ignored.
   - Ethereum adds two small seam checks: a class definition must match its enclosing heading, and mainnet constants in the Markdown must equal the YAML configs. A `<!-- eth_consensus_specs: skip -->` comment excludes the next element [A-ethereum-consensus-specs-md-to-spec-2026].
- Proof-assistant literate documents are the one family where the tool reads references from prose into formal entities, and where the unproved residue is a machine census:
   - Isabelle document antiquotations type-check formal terms inside `text` blocks, which gives "some degree of consistency-checking between the main body of formal text and its informal explanation".
   - Isabelle `sorry` taints the derivation as an oracle, reportable per theorem by `thm_oracles`. `oops` records a proof attempt that makes no claim [A-isabelle-isar-reference-manual-2026].
   - Lean tracks sorryAx and every other axiom transitively per declaration, queryable with `#print axioms` [A-lean-reference-axioms-2026]. The build-log sorry-warning count is not a census, because warnings can be suppressed [C-anastasia-wsc-blaster-readme-2026].
- The Lean blueprint is the closest living practice to "one authoritative prose artifact, residue driven to zero". It has many production users (sphere eversion, liquid tensor experiment, PFR, FLT) [A-massot-leanblueprint-readme-2026]. How it works:
   - LaTeX statements carry `lean` links, `uses` edges, `notready` flags and author-asserted `leanok` claims, rendered as a coloured dependency graph whose goal is all-green [A-massot-leanblueprint-readme-2026][B-tao-pfr-blueprint-tour-2023].
   - The seam is only half mechanical. `checkdecls` checks that the named declarations exist [A-massot-leanblueprint-readme-2026]. `leanok` is set by hand after the proof compiles [B-tao-pfr-blueprint-tour-2023]. A lint for "sorry in Lean but marked leanok" was proposed, not built in [B-leanblueprint-issue-absorb-functionality-2023].
   - Formalisation surfaced a hypothesis missing from the prose, and the fix went back into the prose [B-tao-pfr-blueprint-tour-2023].
- Requirements-traceability tools all keep prose as the authority and give every item a stable ID. Each has a way to mark items that need no machine coverage, and a drift trigger. They differ in whether the drift trigger is mechanical:
   - OpenFastTrace: normative items sit inline in ordinary Markdown. `Needs:` declares which artifact types must cover an item; an item with no `Needs` is terminating (no coverage owed) [A-openfasttrace-writing-a-specification-2026]. A revision number in the ID voids all coverage links on semantic change [A-openfasttrace-concepts-and-terms-2026]. A forward notation records "read, deliberately handed down" [A-openfasttrace-delegating-coverage-2026].
   - Doorstop: a `normative` flag, and content fingerprints for review. Per-link parent fingerprints flag suspect links when the parent changes, and sha256 pins sit on referenced test files [A-doorstop-item-reference-2026].
   - StrictDoc: user grammars can require a `VERIFICATION: MultipleChoice(Review, Analysis, Inspection, Test)` field, and there is code-marker and JUnit coverage. STATUS affects only a statistics screen [A-strictdoc-user-guide-2026].
   - sphinx-needs: build-failing filter rules over requirement objects [A-sphinx-needs-configuration-2026].
- The systems-engineering answer to untestable requirements is a per-requirement verification method: analysis, demonstration, inspection (which includes inspection of documents), or test. Results go in a compliance matrix, with waivers [A-nasa-se-handbook-product-verification-2023]. StrictDoc's grammar example mirrors this [A-strictdoc-user-guide-2026].
- duvet is the most complete typed discharge register found:
   - Code comments quote the spec sentence verbatim, so the quote must match the spec text. Types: implementation, test, implication (correct by construction), exception with a reason, todo with a tracking issue, and spec (a requirement without RFC 2119 words) [A-awslabs-duvet-annotations-2026].
   - The whole coverage state is a checked-in snapshot that CI diffs, so any change in what is covered, or how, fails until re-approved [A-awslabs-duvet-reports-2026].
- The OASIS Test Assertions Model (an OASIS Standard, 2012) is the one ratified format found for binding a normative source (quoted or referenced, with version ids) to a boolean predicate:
   - The predicate's expression language is declared in a `language` attribute, so it may be formal, and the assertion carries a prescription level.
   - It lives beside the spec, not in it.
   - It says test cases only indicate fulfilment and "cannot generally be considered as a formal proof".
   - Writing assertions early is meant to surface statements "which require excessive or impractical resources for testing" [A-oasis-test-assertions-model-2012].
- Counter-thesis at production scale: Cedar keeps two artifacts. The Lean model is the specification, with proofs over it; Rust production code is differentially tested against the model; unmodelled parts (the parser) get property tests. It is "unclear what properties we could prove about a parser model" [A-disselkoen-cedar-verification-guided-2024].
   - The seam check is honest about its gaps: an anti-trophy table lists the bugs it missed and why, including a non-termination bug that only the proof effort found [A-disselkoen-cedar-verification-guided-2024].
- The two production Alloy seam checks from turn01, read in full:
   - silo's sigil check is exact string-set equality of `[SILO-...]` tags between `specs/*.als` and `src/*.rs`, failing on either difference [B-gadget-silo-sigil-validator-2026]. The tags sit on individual pre/post clauses of transition predicates and in assertion doc-comments, and the model comments record why an invariant is an assertion rather than a fact (a fact would make it unfalsifiable) [B-gadget-silo-job-shard-model-2026]. The check is purely syntactic.
   - emilia's "F-numbers" are comment labels only. Several checked assertions restate a fact verbatim (A6 = F17, A7 = F19, A9 = F23, A13 = F29), so those checks cannot fail, and fact F30's body (`sa.human in Entity`) holds for every instance [C-emilia-protocol-relations-model-2026].
- How the seam fails in practice, at field level [A-cleland-huang-traceability-trends-2014]:
   - Trace links go stale on change, and tools respond by marking them suspect, so "it is not uncommon to see an industrial trace matrix populated with a high percentage of suspect links".
   - FDA submissions showed trace data created just before certification.
   - Human link vetting is wrong about 25% of the time; delta-only review cuts effort but lowers quality.
   - WPT shows the lightweight end: tests carry `rel=help` spec links, and coverage is assessed by browsing directories [A-wpt-css-metadata-2026][A-wpt-making-a-testing-plan-2026].
