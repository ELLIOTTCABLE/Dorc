## Findings

- Validate before you verify: the book's workflow is declare, run an empty command at once,
  iterate instances, add facts as instances show problems, and only then check assertions; after
  any fact change, run again to be sure the facts still admit non-trivial instances, because a
  check yields "no counterexample" for an inconsistent model too
  [A-practicalalloy-structural-modeling-2026]:65-88,1120-1144.
- A labelled command with an empty block, `check no_partitions {}`, checks `true`, never finds a
  counterexample, and is named as a false-confidence trap [A-practicalalloy-commands-2026]:96-100.
- A plain `fact` binds only the initial state of a trace; signature facts and declaration
  multiplicities hold in every state [A-alloytools-language-reference-2025]:791-809,882-907,
  1059-1062; [B-alloydocs-time-2026]:38-47.
- A quantifier over a mutable set written outside `always` is evaluated in the initial state, which
  turned a real assertion trivially true [A-practicalalloy-mutable-toplevel-signatures-2026]:124-148;
  [A-practicalalloy-protocol-design-2026]:817.
- `util/ordering` forces an exact and non-empty scope on its parameter; runs go trivially
  unsatisfiable and checks trivially valid [A-practicalalloy-ordering-2026]:105-142;
  [B-alloydocs-ordering-2026]:31-41.
- Scope arithmetic: the overall scope binds top-level signatures only; `one` signatures consume
  their parent's scope; when every extension but one is scoped the last one gets the remainder,
  which can be zero and silently empty a command [A-practicalalloy-commands-2026]:130-191;
  [A-alloytools-language-reference-2025]:1345-1379.
- The book's own scar: an event whose effect contradicted itself in a one-node ring never fired
  although its guard held; three checks stayed green because the fairness premise used the wrong
  enabledness; only a `run` for exactly one node exposed it. Their rule: exhaustively validate
  with runs before trusting checks, above all for liveness
  [A-practicalalloy-protocol-design-2026]:1102-1127.
- `in` is subset, not membership; a `lone` singleton passes vacuously when empty. `iden` ranges
  over `univ`, so `iden in R` is wrong for reflexivity. `none` is unary, so `R = none` is an arity
  error for a binary `R` [A-practicalalloy-relational-logic-2026]:287-302,655-657.
- Multi-variable `one` and `lone` are not the nested form, and quantified variables are not
  distinct unless `disj` is written, which applies per group [B-alloydocs-expressions-and-constraints-2026]:253-311;
  [A-practicalalloy-relational-logic-2026]:213.
- Analyzer options change verdicts: recursion depth is treated as a fact, prevent-overflows makes
  an obviously false check pass, allow-warnings gates execution; the book says a model whose
  outcome depends on an option is bad practice [A-practicalalloy-recursion-2026]:131-152;
  [A-practicalalloy-integers-2026]:350-366; [B-alloydocs-analyzer-2026]:18-84.
- Integers are atoms, bounded by a bitwidth the overall scope does not touch, two's complement;
  `+` is union and `-` is difference; overflow wraps; arithmetic over a set sums it, so
  `sum File.size` deduplicates [A-practicalalloy-integers-2026]:50-56,105-125,210-261,300-321.
- Declaration constraints on predicate and function parameters are conjoined only when the
  predicate is run directly and ignored when it is invoked; they are documentation
  [A-alloytools-language-reference-2025]:519-527,1271-1274.
- Subtype disjointness holds over all states; a mutable signature extending a static one is
  necessarily static (a warning) [A-alloytools-language-reference-2025]:697-717.
- Frame conditions: any mutable relation an event does not mention changes freely; an effect
  spelled as inclusion (`n.id in n.outbox'`) instead of equality leaves the rest of the set free
  [A-practicalalloy-behavioral-modeling-2026]:204-216; [A-practicalalloy-protocol-design-2026]:367-383.
- Without a stuttering event a model that runs out of actions has no infinite trace at all, which
  shows up as a run with no instances rather than an error
  [A-practicalalloy-behavioral-modeling-2026]:336-350; [A-practicalalloy-protocol-design-2026]:483-495.
- Fairness written as a fact taxes every safety check; keep it a predicate used as a premise; a
  guard is not always the enabled condition [A-practicalalloy-fairness-2026]:116-164.
- Test instances: the some/disj idiom (existential disjoint variables per signature, every
  signature and field pinned to unions of them, a sufficient scope); never singleton signatures for
  test atoms, since they then exist in every instance and break symmetry; negative instances as
  unsatisfiable runs; `expect 0`/`expect 1` on commands, noting `expect 1` disables symmetry
  breaking; a counterexample exported as a predicate becomes a regression test
  [A-practicalalloy-testing-instances-2026]:41-53,70-132,213-288.
- Bounded checking returns the shortest counterexample; default horizon 10 steps; `1.. steps` is
  unbounded and needs NuSMV or nuXmv; the book's order is bounded first, unbounded to raise
  confidence [A-practicalalloy-behavioral-modeling-2026]:784-821; [A-alloytools-alloy6-release-notes-2025]:24-35.
- Inductive-invariant checking needs init and transitions as predicates rather than facts, is
  two orders faster, and reports counterexamples from unreachable states for non-inductive
  invariants [A-practicalalloy-inductive-invariants-2026]:36-110,126-179.
- Record-like signatures for messages need a generator axiom and a uniqueness predicate, and a
  scope too small for the messages a trace needs makes runs unsatisfiable and checks vacuous;
  messages as tuples analysed an order of magnitude faster [A-practicalalloy-protocol-design-2026]:1407-1484,1707-1711.
- Alloy Markdown mode requires a YAML header (`---` ... `---`) as the first lines of the file
  before any fenced block is read [B-alloydocs-markdown-2026]:13-23.
- Hong et al.: o3-mini and DeepSeek R1 asked for twenty distinct formulas per toy property got
  between 1 and 19 of 20 right; syntax errors ran as high as 14 of 20; supplying a reference
  formula did not reliably help; one round of error feedback fixed the syntax errors; the paper's
  thesis is that the Analyzer makes every output immediately checkable
  [B-hong-llms-writing-alloy-formulas-2025]:p2,p9,p12-14.

## Report

### 1. The workflow the first-party sources teach

Practical Alloy's method is uniform across its chapters. Declare the signatures, add an empty
`run example {}` before writing any constraint, execute it, and read instances with `New`; the
instances are what reveal missing constraints, and each fact is introduced in response to an
instance that exhibited a problem [A-practicalalloy-structural-modeling-2026]:65-88,518-528,760-806.
The empty run doubles as the consistency probe: "If no instance is returned then the assumptions
are inconsistent and most likely our specification of the system is buggy"
[A-practicalalloy-structural-modeling-2026]:86-88. The language reference states the same in its
semantics: a model without core instances "is inconsistent, and almost certainly erroneous", and a
predicate with no instances "is likewise inconsistent, and is unlikely to be useful"
[A-alloytools-language-reference-2025]:296-300. Only after the instances look right does the book
write assertions, and it closes its first case study with the warning that a check yielding no
counterexample "may be valid" only, that inconsistent or trivial-instance facts make any assertion
pass, and that the correct move after the last fact change is to run again "to make sure the
specification is still consistent and admits non-trivial file systems"
[A-practicalalloy-structural-modeling-2026]:1120-1144.

Symmetry breaking is part of the method: iterating `New` returns each non-isomorphic instance once,
so validation by iteration is tractable, and different solvers return the same set in a different
order [A-practicalalloy-structural-modeling-2026]:135,148-157. Iteration needs an incremental
solver; Lingeling refuses [A-practicalalloy-model-finding-2026]:291-296.

Abstraction advice recurs: use the simplest structure that fulfils the need, avoid integers and
strings unless arithmetic is required, model identifiers as uninterpreted atoms with an explicit
order where comparison is needed [A-practicalalloy-protocol-design-2026]:137;
[A-practicalalloy-type-system-2026]:349-387; [A-practicalalloy-integers-2026]:6-18. The protocol
chapter shows abstraction as an analysis lever, removing an `Id` signature, an `Elected` signature
(replaced by a derived function over the past), an `outbox`, and finally message atoms, each
change cutting states or atoms and making checks faster [A-practicalalloy-protocol-design-2026]:962-1100,1586-1711.

Validation of behavioural models leans on the visualizer's four exploration buttons, with `New
Fork` singled out as the main tool: it changes only the transition at the focused state, so a
scenario is reached by forking step by step, and "no more satisfying instances" on a fork proves
no other event is enabled there [A-practicalalloy-behavioral-modeling-2026]:486-600. The written
form of the same validation is the scenario `run` (section 9 below).

### 2. Vacuity, inconsistency, and false confidence

Every source that touches analysis lists a way a command passes for the wrong reason.

- Inconsistent facts: any assertion checks green; the remedy is the empty run
  [A-practicalalloy-structural-modeling-2026]:1131-1144; [B-alloydocs-predicates-and-functions-2026]:185-200
  ("A fact is *always* considered true by the Analyzer. Any models that would violate the fact
  are discarded instead of checked").
- The labelled empty check: `check no_partitions {}` labels a command with an assertion's name
  and checks the empty constraint, "possibly leading the distracted user to a false sense of
  confidence" [A-practicalalloy-commands-2026]:96-100. An anonymous assertion cannot be checked
  at all, since a check must name it [A-alloytools-language-reference-2025]:1073-1075.
- `util/ordering` makes its parameter's scope exact and non-empty, "making run commands
  trivially unsatisfiable or check commands trivially valid"; a three-atom Even/Odd model has no
  instance at the default scope and one at four [A-practicalalloy-ordering-2026]:105-142. Hillel
  Wayne: "be careful when using ordering as part of an assertion: the assertion may pass because
  of the implicit constraint" [B-alloydocs-ordering-2026]:31-41. The protocol chapter drops
  `util/ordering` for a hand-written order precisely so smaller configurations are still checked
  [A-practicalalloy-protocol-design-2026]:965-980.
- Missing stuttering: once every node has initiated and nothing else may happen, "our command
  will return no trace" because traces must be infinite [A-practicalalloy-protocol-design-2026]:483-495.
- Prevent-overflows: with the option on, `check big_files { all f: File | f.size > 10 }` finds no
  counterexample at bitwidth 4 because 10 is unrepresentable; "a false sense of security"
  [A-practicalalloy-integers-2026]:350-366.
- Scope too small for the scenario: `bad_all_initiate` needs four messages and the default scope
  has three, so the Analyzer reports no trace; "This can also lead to a false sense of safety from
  check commands, since a limited set of messages may reduce the valid traces explored"
  [A-practicalalloy-protocol-design-2026]:1475-1484.
- The all-but-one extension rule: `run dirs_3 { some File } for 3 but 3 Dir` yields nothing
  because `File` receives the leftover of `Object`'s scope, which is zero
  [A-practicalalloy-commands-2026]:179-191.
- The one-node ring: the effect on `n.succ.inbox` and on `n.inbox` contradict when `n.succ = n`,
  so `process` "cannot actually occur (is not truly enabled) even if its guard is true"; the
  fairness premise, written from guards, therefore excused the deadlock and
  `at_least_one_leader_fair` passed. "It is very easy to make such subtle mistakes while
  specifying, and introduce inconsistencies in our model, and to avoid them we should always
  exhaustively validate our specification before checking our assertions. This is specially true
  for liveness properties. Ideally, we should have different run commands to check the
  consistency of different scenarios" [A-practicalalloy-protocol-design-2026]:1102-1127.
- Inductive checks over unreachable states: a preservation check for a true-but-non-inductive
  invariant returns a counterexample whose states no trace reaches; the book warns against
  answering that with a reachability run "as the command would run for a long time"
  [A-practicalalloy-inductive-invariants-2026]:150-179.
- Recursion depth: a recursive function past the option's depth "just fails silently by returning
  an empty relation", and `util/natural` past its scope "will just yield an empty set (without any
  kind of error or warning)" [A-practicalalloy-recursion-2026]:46-51,131-152.
- Trivially-true assertions from initial-state evaluation: `all f: File | always (...)` with a
  mutable `File` quantifies over the empty initial `File` [A-practicalalloy-mutable-toplevel-signatures-2026]:124-148;
  the same point about `Elected` [A-practicalalloy-protocol-design-2026]:817.
- Alloy's own checks that cannot fail: Hillel Wayne flags that a `check` whose constraint the
  facts already state cannot fail (the emilia specimen of turn02 is the field instance); no
  first-party source offers a mechanism for it.

### 3. Scopes, bounds, and horizons

The language reference gives the rules; the book gives the traps.

- Default scope 3 for every top-level signature; `for N` changes the default; `for N but ...`
  overrides listed signatures; a list with no default must cover every top-level signature; the
  specification must be consistent (one bound per signature), complete (every top-level bound),
  and uniform (a bounded subsignature needs a bounded ancestor)
  [A-alloytools-language-reference-2025]:1345-1358,1406-1413; [A-practicalalloy-commands-2026]:207-213.
- Implicit bounds: an abstract signature with no bound takes the sum of its subsignatures'; with
  a bound and all-but-one subsignature bounded, the last takes the difference; a `one` signature
  is bound 1 [A-alloytools-language-reference-2025]:1359-1372. The book's corner: extension scopes
  raise the parent's, so `for 3 but 3 Dir, 3 File` gives `Object` six
  [A-practicalalloy-commands-2026]:170-178; the Analyzer's log reports the scopes actually used and
  the verbosity option explains how [A-practicalalloy-commands-2026]:192-205.
- Subset signatures take no scope; bound them by a cardinality constraint in the command
  [B-alloydocs-commands-2026]:175-190; [A-alloytools-language-reference-2025]:1317-1321. Relations
  take no scope either [B-alloydocs-commands-2026]:141-149.
- `exactly` is allowed for static signatures only; scopes on a mutable signature apply to
  top-level ones only; a scope on a mutable signature counts the atoms appearing in any state of
  the trace, not per state [A-alloytools-language-reference-2025]:1321-1331,1374-1379;
  [A-practicalalloy-mutable-toplevel-signatures-2026]:30.
- Conflicts with multiplicity are errors: a `one` signature must have scope 1, `lone` at most 1,
  `some` at least 1; enumeration signatures cannot be scoped [A-practicalalloy-commands-2026]:163-167.
- `Int`'s scope is a bitwidth including the sign bit; it is untouched by the overall scope and
  must be set explicitly; the default 4 gives -8..7 [A-alloytools-language-reference-2025]:1333-1343;
  [A-practicalalloy-integers-2026]:313-321.
- `seq` has its own scope, default 4; `add` and `insert` on a full sequence silently drop; the
  Int bitwidth must be wide enough for the seq bound or the Analyzer refuses
  [A-practicalalloy-sequences-2026]:63; [B-alloy-analyzer-help-seq-2026]:59-66,140-155.
- `steps`: `for M .. N steps` bounds the lasso length including the looping transition; `for N
  steps` is `1 .. N`; default 10; `for 1.. steps` is unbounded and needs a complete model checker,
  and "should therefore preferably be executed to check assertions on small models and only when
  checking with a bounded time horizon does not find counterexamples anymore"
  [A-alloytools-alloy6-release-notes-2025]:24-31; [A-alloytools-language-reference-2025]:1381-1404.
- Cost: "The difficulty of the analysis increases with scope in a quicker than linear fashion"
  [B-alloy-analyzer-help-analyses-2026]:87. Bitwidth is expensive for the same reason
  [A-practicalalloy-integers-2026]:339-344. A field of arity n may need on the order of two to the
  n-squared booleans; a 5-ary field is representable only under 74 atoms
  [A-practicalalloy-protocol-design-2026]:1758; [A-practicalalloy-nary-relations-2026]:57-62.
- The Analyzer's log reports primary vars (one per free tuple in a relation's bounds), vars and
  clauses, which is the readout of problem size [A-practicalalloy-model-finding-2026]:274-280.
- Decomposed solving: `batch`, `parallel` (splits by signature and field dependencies, good for
  satisfiable problems, possibly slower for unsatisfiable checks), `hybrid`
  [A-alloytools-alloy6-release-notes-2025]:37-43. SAT4J is the default and "rarely the fastest"
  [A-practicalalloy-model-finding-2026]:282-291.

### 4. Language-semantics traps stated by the sources

Relational core.

- Everything is a relation; scalars are singleton unary relations; there is no function
  application, and `x.f` outside the domain of `f` is empty, so `x.f = y` with scalar `y` is
  simply false [A-alloytools-language-reference-2025]:317-346.
- `in` is subset. With `Root` declared `lone`, `Root in Dir` is true when `Root` is empty; the
  membership form is `some Root and Root in Dir` [A-practicalalloy-relational-logic-2026]:287-302.
- `iden` is over `univ`; reflexivity on `A` is `(A <: iden) in R`; `none` is unary, so `R = none`
  is an arity error for binary `R`, and `no R` is the idiom [A-practicalalloy-relational-logic-2026]:655-657;
  [A-alloytools-language-reference-2025]:1499-1508.
- `*r` includes `iden` and is therefore mutable when `univ` is; Hillel Wayne's advice: use `*`
  only immediately before a join [B-alloydocs-sets-and-relations-2026]:360-373;
  [A-alloytools-language-reference-2025]:1591-1593.
- Transpose and closures are binary-only; composing two ternaries gives a quaternary; projection
  is by comprehension or `util/ternary`'s `select13` [A-practicalalloy-nary-relations-2026]:219-270;
  [B-alloydocs-sets-and-relations-2026]:329.
- Dot binds tighter than box: `a.b[c]` is `(a.b)[c]`; implication and `;` associate right; the
  binary temporal connectives are non-associative; `else` binds to the closest `implies`
  [A-alloytools-language-reference-2025]:212-265; [B-alloytools-quickguide-alloy4-syntax-2025]:71-93.
- The temporal unary operators sit with logical negation, above the binary logical operators, so
  `always (A or B)` needs its parentheses, as does a macro body such as `always (eventually (ev))`
  [A-alloytools-language-reference-2025]:235-247; [A-practicalalloy-behavioral-modeling-2026]:156;
  [A-practicalalloy-macros-2026]:174.
- Override `++` is defined for higher arity and keys on the first column only
  [A-alloytools-language-reference-2025]:1620-1624; [B-alloydocs-sets-and-relations-2026]:404-428.
- `=` is never overloaded: on sets of integers it compares sets, while `=<` and `>=` sum their
  operands first, so `S =< T` and `S >= T` can both hold with `S != T`
  [A-alloytools-language-reference-2025]:1784-1803; `1.eq[1 + Root]` is true where `1 = 1 + Root`
  is false [A-practicalalloy-integers-2026]:223-225.
- `let` is non-recursive and can shadow a global, retrievable with `@`
  [B-alloydocs-expressions-and-constraints-2026]:39-44.

Quantifiers.

- `all x, y: A | P` is `all x: A | all y: A | P`, but `one x, y: A | P` is not the nested form;
  the book gives a three-tuple relation where the flat form is false and the nested form true
  [A-practicalalloy-relational-logic-2026]:213; [A-alloytools-language-reference-2025]:1936-1966.
  Wayne's truth table and rule of thumb: "use only some and all when writing multiple clauses"
  [B-alloydocs-expressions-and-constraints-2026]:285-311.
- Variables drawn from one set are not distinct: `all x, y: A | x.rel != y.rel` is false whenever
  `A` is inhabited; `disj` applies only to a group quantified over the same set, so in
  `all disj x, y: A, w, z: B` the pair `w, z` may coincide [B-alloydocs-expressions-and-constraints-2026]:253-283;
  [A-practicalalloy-relational-logic-2026]:213.
- Higher-order quantification is accepted by the grammar and solved only when Skolemizable: an
  outermost `some` over a relation in a `run`, an outermost `all` or `no` in a `check`; the other
  way round is refused, and the evaluator never accepts it [B-alloydocs-expressions-and-constraints-2026]:318-345;
  [A-alloytools-language-reference-2025]:359-370,1967-1970; [B-alloy-analyzer-help-analyses-2026]:51-60.
- `no` and `some` are "considerably more useful than one and lone" in practice
  [B-alloydocs-expressions-and-constraints-2026]:137-138.

Declarations, facts, and the temporal asymmetry.

- A signature fact is `fact { always all this: S | F2 }`, with fields rewritten to `this.f`;
  `@f` suppresses the rewrite; inside a signature fact a field of another atom must be reached as
  `y.@entries` [A-alloytools-language-reference-2025]:791-809; [A-practicalalloy-signature-facts-2026]:15-89;
  [B-alloydocs-predicates-and-functions-2026]:218-243. Implicit facts are inherited by subsignatures
  [B-alloydocs-signatures-2026]:542.
- A field declaration constrains `this.f` in every state, not `f`; its default multiplicity is
  `one`, so `x: X` is a scalar [A-alloytools-language-reference-2025]:882-907,558-571. The book's
  house rule is to write every multiplicity explicitly, even `one`
  [A-practicalalloy-structural-modeling-2026]:390-393.
- A plain fact "is a constraint that holds in the initial state of every instance"; `fact init {
  no f }` binds state zero and `fact behaviors { always (...) }` binds all
  [A-alloytools-language-reference-2025]:1059-1095.
- Declaration constraints on parameters are used when a predicate is run directly and ignored when
  invoked: "You should therefore not rely on such declaration constraints to have a semantic
  effect; they are intended as redundant documentation" [A-alloytools-language-reference-2025]:519-527,1271-1274.
  The `seq` help says the same of `seq` in a parameter declaration [B-alloy-analyzer-help-seq-2026]:51-56.
- Type signatures are disjoint "over all states of any instance": an atom never moves between
  top-level or sibling signatures across time; hence a mutable signature extending a static one
  is static, with a warning [A-alloytools-language-reference-2025]:697-717;
  [A-practicalalloy-mutable-toplevel-signatures-2026]:31.
- With a mutable top-level signature, `univ` and `iden` are mutable [A-practicalalloy-temporal-logic-2026]:25;
  [A-alloytools-alloy6-release-notes-2025]:22.
- The prime operator distributes over subexpressions, static factors unchanged: `(s.m)'` is
  `s.(m')`; `*r` must first be expanded to `^r + iden` [A-alloytools-language-reference-2025]:1644-1669.
  This is why the frame macro must be `x = (x)'` and not `x = x'`
  [A-practicalalloy-macros-2026]:125-131.

Types and overloading.

- Three error classes: arity, disjointness (an expression that is always empty, including
  override of disjoint relations), redundancy (a union member that can never contribute); "Error
  messages reporting that an expression is ill-typed are never spurious"
  [A-alloytools-language-reference-2025]:372-421. The book calls the second class irrelevance
  warnings, refused by default and enabled under Allow warnings; "in general irrelevance warnings
  are most likely specification errors made by the user"; write `none` when an empty relation is
  intended; declaring disjoint subsets with `extends` rather than `in` plus facts is what makes
  the warning fire [A-practicalalloy-type-system-2026]:87-122.
- Overloaded fields, functions and predicates resolve by the whole enclosing expression, arity
  included; the systematic fix for an ambiguous field is `S <: f`, "not a special casting syntax"
  [A-alloytools-language-reference-2025]:423-453; [B-alloytools-quickguide-alloy4-syntax-2025]:171-181.
  Two subset signatures with overlapping types may not declare a same-named field
  [A-alloytools-language-reference-2025]:783-789.
- Casts: `X + 3` parses as `int[X] + 3` because the Int-to-int cast is preferred as cheaper
  [B-alloytools-quickguide-alloy4-syntax-2025]:183-196.

Lexical.

- Backslash and backquote are forbidden characters; `$`, `%`, `?` are reserved; hyphen is an
  operator and never part of an identifier; identifiers may contain underscore and, after the
  first character, digits; a numeric literal may not start with zero; smart quotes are not the
  prime mark [A-alloytools-language-reference-2025]:3-51.
- The Alloy 6 reserved words, with `event`, `modifies`, `enabled` and `invariant` reserved but
  unused; the new symbols are the single quote and the semicolon, and an old model using either
  as an identifier breaks [A-alloytools-language-reference-2025]:67-123; [A-alloytools-alloy6-release-notes-2025]:115-123.
- Three namespaces (modules; signatures, fields, paragraphs and bound variables; command names);
  bound variables may shadow each other and field names [A-alloytools-language-reference-2025]:127-140.
  Predicates and functions can share a name and are disambiguated syntactically, which the event
  idiom exploits [A-practicalalloy-event-depiction-2026]:253-254.
- Comments are `--`, `//`, and non-nesting `/* */`; a fact's name may be a string
  [A-alloytools-language-reference-2025]:32-34; [B-alloydocs-predicates-and-functions-2026]:202-208.

### 5. Integers

- `Int` is always present in `univ`; its atoms are the two's-complement integers of the bitwidth;
  "integers are atoms, bounded, and interpreted in binary" is the book's three-point summary
  [A-practicalalloy-integers-2026]:38-56; [B-alloydocs-sets-and-relations-2026]:38-43.
- `1+2` is `{1,2}` and `1-1` is `{}`, without warning; arithmetic is `plus`, `minus`, `mul`,
  `div`, `rem` (or `fun/add` and kin), and comparison operators; an arithmetic operand that is a
  set is summed first, so `(1+2).plus[3]` is 6 and `(1+1).plus[3]` is 4; a set with no integer
  atom is a type error [A-practicalalloy-integers-2026]:105-225; [B-alloydocs-sets-and-relations-2026]:155-169.
- `sum File.size` undercounts when two files share a size; the `sum f: File | f.size` quantifier
  is the correct total [A-practicalalloy-integers-2026]:238-261.
- Overflow wraps in analysis (the book's instance sums three sizes to -4 under a capacity of 4);
  Hillel Wayne states that an overflowing predicate is declared false in analysis but wraps in the
  evaluator; the language reference says an instance requiring a larger bitwidth "will not be
  considered by the analysis" [A-practicalalloy-integers-2026]:300-311;
  [B-alloydocs-sets-and-relations-2026]:102-106; [A-alloytools-language-reference-2025]:1339-1343.
  Two of these three statements are not the same claim; which holds for Alloy 6.2 under the
  default options is unverified here (-1:GUESS that the book, being newest, describes the current
  default). A skill should say "do not depend on either" rather than pick.
- The book's remedy is a fact bounding sizes by `div[max, #File]` so that no instance overflows,
  rather than the prevent-overflows option [A-practicalalloy-integers-2026]:323-337.
- `#` counts tuples of any arity; a relation of arity three is one element for `#`, for `one`, for
  `lone` [B-alloydocs-expressions-and-constraints-2026]:140; [A-alloytools-language-reference-2025]:1700-1707.
- `util/natural` encodes naturals as atoms bounded by their own scope, with `inc` past the scope
  silently empty; the depth example needs scope six on `Natural` for depth five
  [A-practicalalloy-recursion-2026]:40-51,236-240.
- Comparison of atoms is better done by a total order on a plain signature than by integers, and
  the protocol chapter writes that order by hand to escape ordering's exact scope
  [A-practicalalloy-type-system-2026]:374-380; [A-practicalalloy-protocol-design-2026]:965-980.

### 6. Signatures, subsets, enumerations, ordering, modules

- `extends` gives disjoint subsignatures; `in` gives overlapping subsets, possibly of a union of
  unrelated signatures, possibly by `=`; subset signatures carry fields, inherit their parents',
  and cannot themselves be extended [A-practicalalloy-subset-signatures-2026]:11-18,146-206;
  [B-alloydocs-signatures-2026]:406-467.
- `abstract` without extensions "has no effect" and "is likely an indication that the model is
  incomplete" [A-alloytools-language-reference-2025]:739-745; [B-alloydocs-signatures-2026]:487.
- `one sig` extensions are the enumeration idiom; `enum` is the same plus a total order in
  declaration order [A-practicalalloy-enumerations-2026]:22-47,145-148. Because `enum` imports
  ordering, two enums make `first` ambiguous and a namespace is needed
  [B-alloydocs-signatures-2026]:580-592; ordering opened twice needs `as` aliases
  [B-alloydocs-predicates-and-functions-2026]:133-150.
- A record signature's scope caps how many distinct value combinations can exist; the permission
  example needs the overall scope raised to 4 before two objects can differ
  [A-practicalalloy-enumerations-2026]:115-140.
- `util/ordering`: exact scope, non-empty (`first` and `last` always one atom), atoms named in
  order by the visualizer, `next` clashes with `util/integer`'s `next` in the evaluator (qualify
  as `ordering/next`), one instantiation per signature, and an auxiliary singleton atom
  `ordering/Ord$0` remains in `univ` [A-practicalalloy-ordering-2026]:9-10,55,105-142;
  [A-practicalalloy-modules-2026]:369-378; [B-alloydocs-ordering-2026]:22.
- Modules are found by file name only, relative to the main file's directory or the library
  directory; the `module` header's path affects resolution; opening a module twice with different
  parameters gives one module under two names and needs aliases; a parametrized module cannot add
  fields to its parameter signature (the singleton-auxiliary idiom, which `util/ordering` itself
  uses); `private` hides names but the atoms stay in `univ`; commands inside a parametrized module
  treat the parameter as an arbitrary signature; a parameter may be marked `exactly`
  [A-practicalalloy-modules-2026]:24-36,98-138,188-237,331-382; [A-alloytools-language-reference-2025]:591-644;
  [B-alloytools-quickguide-alloy4-syntax-2025]:109-146. The `open` search order is installation
  directory first, then relative inference [B-alloy-analyzer-help-analyses-2026]:63-68.
- The utility modules shipped: boolean, graph, integer, natural, ordering, relation, sequniv,
  ternary [B-alloy-analyzer-help-seq-2026]:69-72 names sequniv; the full list is in the
  Analyzer's util help page (read, not registered).
- Booleans: model as an `in` subset ("the standard way"), or a `lone` field over a singleton;
  `util/boolean` "is generally not recommended" (alloydocs techniques/boolean-fields, read in full,
  not registered).

### 7. Higher-arity relations

- Ternary fields as `Name -> Object` remove auxiliary record atoms from the universe, can carry
  multiplicities in the declaration (`Name -> lone Object`), and are navigated with dot joins that
  need parentheses because `n.d` would be arity zero [A-practicalalloy-nary-relations-2026]:40-66,135-161.
- The sweet spot: a few ternaries improve readability and performance; "relations with arity
  higher than 3 are very rarely useful"; too many higher-arity relations "can become unmanageable"
  and slow [A-practicalalloy-nary-relations-2026]:57-66,299-306.
- Messages as tuples in a mutable ternary `inbox: Type -> Node` made `at_most_one_leader` an
  order of magnitude faster than message signatures, at the cost of padding with an `Empty`
  singleton when payloads differ in arity [A-practicalalloy-protocol-design-2026]:1595-1620,1707-1758.
- Multirelation multiplicities `A m -> n B` and their sixteen readings are tabulated by Wayne,
  with the note that `one -> one` is unsatisfiable unless the sets have equal size
  [B-alloydocs-signatures-2026]:295-370; the book's bestiary names the nine standard shapes
  [A-practicalalloy-bestiary-2026]:62-137.

### 8. Recursion, functions, and Analyzer options

- Predicates and functions may not recurse; the Recursion depth option unrolls at most three
  times, is off by default, returns `none` silently past the depth, and makes "the outcome of a
  command ... dependent on an Analyzer option, which in general is a bad practice in Alloy where
  models are expected to be self-contained"; the book keeps it disabled and uses a memoization
  field with a fact [A-practicalalloy-recursion-2026]:62-172; [B-alloydocs-analyzer-2026]:54-84
  ("The recursion depth is treated as a 'fact'").
- A parameterless function is a constant set, appears in instances as `$name`, and can take
  closure [B-alloydocs-predicates-and-functions-2026]:95-104; the book uses this for derived
  relations that the visualizer shows and that formulas may read [A-practicalalloy-event-depiction-2026]:67-104.
- Function invocation is textual inlining, not a join: no lifting over sets, possibly higher
  order [A-alloytools-language-reference-2025]:1140-1189.
- Options that change results: Allow warnings, Prevent overflows, Recursion depth, Skolem depth
  ("the maximum depth of alternating universal-vs-existential quantifier"), solver choice
  [B-alloydocs-analyzer-2026]:14-38; the GUI help lists the same set (read, not registered).
- Unsat core needs MiniSat with core, absent on Windows by default; the Core granularity setting
  "is not strictly increasing in terms of information" [B-alloydocs-analyzer-2026]:95-121.
- The Kodkod problem for a command can be recorded and inspected [A-practicalalloy-model-finding-2026]:100-119.

### 9. Test instances, scenarios, and regression

- The problem: atoms cannot be named in a specification; a distinguished atom needs a singleton
  signature [A-practicalalloy-relational-logic-2026]:71-73.
- The wrong solution: singleton signatures per test atom, because "such signatures will now exist
  in all instances of the model, regardless of the executed command" and "it would break the
  symmetry" [A-practicalalloy-testing-instances-2026]:41-53.
- The idiom: `some disj d0, d1: Dir, disj f0, f1: File, ... { Root = d0  Dir = d0 + d1  ...
  entries = d0->e0 + ... }` with a scope large enough; forcing every signature equal to the union
  of its variables excludes stray atoms; `disj` must be repeated per group; too small a scope
  makes the command "trivially inconsistent" [A-practicalalloy-testing-instances-2026]:70-132.
- Negative instances are the same shape and must be unsatisfiable; `expect 1` and `expect 0`
  document the intent and the Analyzer reports agreement; `expect 1` turns symmetry breaking off
  for that command [A-practicalalloy-testing-instances-2026]:213-263; [A-practicalalloy-commands-2026]:244-254.
- A counterexample can be exported from the visualizer as a predicate in exactly this idiom and
  kept as a negative regression test after the fix [A-practicalalloy-testing-instances-2026]:275-288.
- Scenario runs for traces: the configuration by some/disj, then per-state constraints joined by
  `;` (lowest precedence, `p;q` is `p and after q`); a pinned prefix still admits every
  continuation until `always` closes it; families of scenarios by under-specification;
  event-oriented encoding `upload[f]; share[f, t0]; ...; always stutter` is briefer but hides the
  concrete values when events are non-deterministic [A-practicalalloy-scenarios-2026]:23-266;
  [A-alloytools-alloy6-release-notes-2025]:62-85.
- Named `run` and `check` over a reusable predicate or assertion make several scopes of one
  property cheap to write; a run of a parametrized predicate quantifies the parameters
  existentially and shows them as skolems [A-practicalalloy-commands-2026]:40-92.
- A generator predicate (every combination of a record's fields exists) plus a uniqueness
  predicate make explicit-message models explorable; kept as predicates for runs, optionally
  promoted to facts once the scope is known to be large enough; a mutable `Message` signature was
  tried and was "more difficult and analyses less efficient" [A-practicalalloy-protocol-design-2026]:1407-1473,1556-1559.

### 10. Behavioural modelling

The book's transition-system idiom, with the traps it names.

- State: `var` on signatures and fields; mutable subsets of static signatures (`var sig uploaded
  in File`) or mutable top-level signatures, whose scope counts atoms over the whole trace and
  whose atoms can never move to another top-level signature [A-practicalalloy-behavioral-modeling-2026]:42-60;
  [A-practicalalloy-mutable-toplevel-signatures-2026]:29-32.
- Initial state: a fact with no temporal operator; Alloy has no `init` keyword; with meta
  signatures `all v: var$ | no v.value` writes it once [A-practicalalloy-behavioral-modeling-2026]:99-114;
  [A-practicalalloy-meta-2026]:175-182.
- Events: one predicate each, guard then effect then frame conditions; `always (some f | ... or
  ... or stutter)` as the transitions fact; the disjunction and existential choose the event
  non-deterministically [A-practicalalloy-behavioral-modeling-2026]:122-156,188-216.
- Effects as equalities: `n.outbox' = n.outbox + n.id` and not `n.id in n.outbox'`, which "would
  allow identifiers other than n.id to be freely removed or added"; every other node's field
  needs its own frame condition; "if nothing is said about a particular mutable relation then its
  value can change freely" [A-practicalalloy-protocol-design-2026]:337-383. Pointwise and
  pointfree effect styles are equivalent and a matter of taste; the pointfree `inbox' = inbox -
  n->i + n.succ->(i & n.^next)` encodes a conditional addition by intersection with a possibly
  empty set [A-practicalalloy-pointwise-effects... see the pointfree passage at
  A-practicalalloy-protocol-design-2026]:1156-1182.
- A guardless event holds trivially when its effect is already true, which reads as "nothing
  happened" in a trace; a history guard is one temporal operator (`historically n.id not in
  n.outbox`) where other languages need a phase field [A-practicalalloy-protocol-design-2026]:428-478.
- Stuttering: a predicate of frame conditions only, in the transitions disjunction; it makes
  composition with other specifications possible and guarantees every finite behaviour extends
  to an infinite trace; without it deadlocked prefixes vanish from the analysis
  [A-practicalalloy-behavioral-modeling-2026]:322-365.
- Safety by `always P`; nested `always` and `after always` for "from then on"; `releases`; the
  double prime for two states ahead; liveness by `eventually`; liveness needs fairness, and the
  book's first fairness fact is `always eventually empty` [A-practicalalloy-behavioral-modeling-2026]:642-777.
- Fairness discipline: a fairness fact "is imposed for all the traces of the system. So even for
  the verification of safety properties the solver has to take them into account, which can slow
  down the verification procedure significantly"; keep it a predicate and check `fairness implies
  property`; weak fairness is `always ((always enabled[A]) implies always eventually A)`, strong is
  `(always eventually enabled[A]) implies always eventually A`, unconditional is `always
  eventually A`; the enabled condition is usually the guard but not when the body existentially
  quantifies over a set that may be empty [A-practicalalloy-fairness-2026]:104-203;
  [A-practicalalloy-protocol-design-2026]:859-910,1556.
- Past operators: a formula is interpreted at state zero, so `historically` at top level
  collapses to the present and `before` is false at state zero; past operators are useful only
  under a future operator; they add succinctness (exponentially), not expressiveness
  [A-practicalalloy-temporal-logic-2026]:230-240.
- Traces are infinite lassos; the small-model property guarantees a lasso witness whenever any
  trace satisfies the constraint; finite-trace semantics was rejected because `not after P` and
  `after not P` would diverge [A-practicalalloy-temporal-logic-2026]:252-256.
- Bounded model checking returns the shortest counterexample or witness; the protocol example's
  minimal election is eight states [A-practicalalloy-protocol-design-2026]:643-651.
- Inductive invariants: `init` and `next` as predicates and `traces { init  always next }` as
  the premise of every temporal assertion; `init implies inv` at 1 step and `(inv and next)
  implies after inv` at 2 steps; a hundred times faster than the unbounded check; not all
  invariants are inductive; strengthening by a known inductive invariant; "finding inductive
  invariants is notoriously hard" [A-practicalalloy-inductive-invariants-2026]:36-204.
- Derived state instead of stored state: `Elected` as a function by comprehension over `once
  (before n in n.inbox and n not in n.inbox)`, removing a mutable signature and every effect on
  it [A-practicalalloy-protocol-design-2026]:1022-1049.
- Meta signatures `sig$`, `field$`, `var$`, `static$`, with `value`, `parent`, `fields`,
  `subfields`, activated by any mention; generic stutter `all v: var$ | v.value = v.value'`,
  generic frame `all v: var$ - uploaded$ | ...`, a run that populates every mutable element
  [A-practicalalloy-meta-2026]:57-218.
- Event depiction: an `enum Event`, one derived relation per event by comprehension
  (`{ e: Upload, f: File | upload[f] }`), a union `events` function; `always some events` as the
  transitions fact; `check at_most_one_event { always lone events }`; no performance penalty and
  fewer variables than existentially quantified predicate calls [A-practicalalloy-event-depiction-2026]:64-261.
- Macros: untyped textual expansion, lexically scoped, curried, cryptic errors, "rather
  discouraged"; the two sanctioned uses are `let unchanged[x] { x = (x)' }` for frame conditions
  of any arity and constraint schemas such as `let fair[ev] { always (eventually (ev)) }`, both
  needing their parentheses [A-practicalalloy-macros-2026]:9-46,123-174; [B-alloytools-quickguide-macros-2025]:13-19.
- Sequences: `seq` only in fields; `util/sequniv` is auto-imported; a sequence is `seq/Int -> A`
  over a prefix of the non-negative integers; `first` from sequniv collides with a signature named
  `first` (qualify `this/first`); a bounded queue model showed the protocol fails when the queue
  is smaller than the ring [A-practicalalloy-sequences-2026]:15-63; [A-practicalalloy-protocol-design-2026]:1792-1854.
- The legacy explicit-`Time` idiom (ordering on a Time signature, `Page -> Time` fields, a trace
  fact) with its own traps: an incomplete trace lets unmentioned actors do anything; ordering
  makes the ordered signature exact; no deadlock, liveness or fairness reasoning
  [B-alloydocs-dynamics-2026]:11-187. Alloy 6's `var` replaces it [B-alloydocs-time-2026]:7-31.

### 11. Skolemization

- Kodkod Skolemizes outermost existentials in a run and outermost universals in a check into free
  relations named `$command_var`, visible in instances and the evaluator, customizable in themes;
  this is what lets some higher-order quantifications run; it adds no expressiveness (a subset
  signature would do) but keeps the quantifier local to the assertion; a non-Skolemizable
  higher-order quantification is an error [A-practicalalloy-model-finding-2026]:319-386;
  [A-practicalalloy-testing-instances-2026]:152-176. The reference: whether existentials inside
  universals are Skolemized depends on user preferences [A-alloytools-language-reference-2025]:1306-1309.
- The Analyzer's help: a non-reducible higher-order declaration "will always take a significant
  amount of time and memory unless the scope is very, very small, since every combination must be
  enumerated. Thus, the Alloy Analyzer will not attempt to solve such a formula"
  [B-alloy-analyzer-help-analyses-2026]:51-60.

### 13. The Hong, Jiang, Fu and Khurshid experiment

### 14. Style rules the book states

- Prefer the English operators (`and`, `or`, `implies`, `iff`, `not`) for readability
  [A-practicalalloy-structural-modeling-2026]:551-559.
- State every field multiplicity explicitly, even `one` [A-practicalalloy-structural-modeling-2026]:390-393.
- The navigational style (few quantifiers, joins to reach related sets) is the common one;
  pointwise is verbose; pointfree is "a nice intellectual challenge" that often yields formulas
  "very difficult to understand", and not every formula converts [A-practicalalloy-structural-modeling-2026]:850-949.
- Name assertions and keep them in `assert` blocks for maintainability; named commands ease
  multiple scopes [A-practicalalloy-structural-modeling-2026]:986; [A-practicalalloy-commands-2026]:40-49.
- Keep the constraint under check out of the assumptions: `Elected` deliberately not declared
  `lone` because at most one leader is the property, not a premise
  [A-practicalalloy-protocol-design-2026]:253.
- Document expected outcomes on commands with `expect` rather than comments
  [A-practicalalloy-commands-2026]:244-254.
- Comments inside predicates label guard, effect and frame lines; every fact carries a one-line
  English restatement above its formula (throughout the book's listings).
- Configuration (static) versus state (mutable) is the first split to make when modelling a
  protocol; verification quantifies over all configurations up to scope, which "is not possible
  in some competing model checkers" [A-practicalalloy-protocol-design-2026]:42-54,761-764.

### 15. Bearing on assay and 30Z (conductor's read, unreacted; not a ruling)

- +SURE the twin-per-check posture (`30Z` 2.4) is the first-party posture too, stated as the
  empty run and the re-run after fact changes (section 1). The first-party sources add three
  vacuity sources the praxis document does not yet list: the labelled empty check, ordering's
  exact scope, and a stuttering-less deadlock that makes a whole book unsatisfiable.
- ~SUSPECT `30Y` § 1.1's claim that a person can open a spec in the Analyzer's Markdown mode
  without assay: alloydocs says the file must begin with a YAML header, and the 30Z document form
  begins with a heading. A five-minute test with the pinned jar settles it.
- ~SUSPECT the book-fixture encoding question is live: assay pins named atoms as `one sig` per
  line and per introduced name; the book's idiom for exactly that job is some/disj inside the
  command, with the stated objections that singleton signatures leak into every command and break
  symmetry. Inside a per-book module the leak is contained; the symmetry cost is not. Worth a
  strawman measurement, not a ruling.
- -GUESS `expect 0`/`expect 1` on generated commands would let the Analyzer itself report a
  lock mismatch, but `expect 1` disables symmetry breaking and the report would duplicate the lock.
- +SURE the quiet-traps habit in `30Z` § 3 can grow from these sources without inventing
  anything: `in` as subset, `iden` over `univ`, plain facts binding state zero only, a quantifier
  over a mutable set outside `always`, declaration constraints ignored on invocation, the
  all-but-one scope remainder, `abstract` without extensions, option-dependent outcomes, and the
  `(x)'` parenthesization.
- -GUESS the parse lint (`30Y` § 2.6, fourth item) earns its place on the Hong numbers alone:
  syntax errors were the largest failure class for one model, and one feedback round cleared them.
