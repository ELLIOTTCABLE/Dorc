# turn 1 — 2026-09-27 11:27:18 CDT

Subagent turn covering two briefs:
- task-1: a web scout on mechanising prose relational models, and on iterated LLM critique;
- task-2: a filter for production open-source projects that actively use Alloy.

Method for task-2:
- about 30 `gh search code --extension als <keyword>` sweeps collected about 275 candidate repos;
- `gh api` supplied stars, language, creation date, commit counts, `.als` paths and per-file commit history;
- evidence files were read at pinned SHAs.

Facts marked (api) come from `gh api` observations, not from a registered source.

## Findings
- The strongest production Rust user found is gadget-inc/silo, a job queue on object storage built by Gadget. It keeps two Alloy 6 models under `specs/`. CI runs a separate path-filtered verification job per model. A CI step on every PR checks that each `[SILO-*]` sigil in the Alloy models matches a Rust comment, and the reverse. This is the only mechanical model-code sync check found [B-gadget-silo-ci-alloy-jobs-2026]. The repo also steers coding agents with a rule file scoped to `*.als` [B-gadget-silo-alloy-agent-rule-2026].
- Several models per project, one per component, is common. Explicit shared vocabulary between them is rare:
   - silo: 2 models (job_shard, coordination), each standalone, both importing only `util/ordering` (api).
   - kimberlite: 4 standalone modules (api).
   - emilia: 5 standalone modules (api).
   - kiri: 5 standalone modules; three of them are design alternatives, PlanA/B/C (api).
   - fspec: 3 standalone modules (api).
   - Only pta-standards shows a shared-base pattern. A shared `core/formal/inventory.als` is opened by five per-method booking models. `balance_equation` is opened by the report models. Format-specific models live in per-format directories (api). The same repo has strong slop signals; see its entry.
   - Orange's Cloudnet-TOSCA-toolbox shares a `TOSCA.als` + `LocationGraphs.als` + generic `map[VALUE]` base across per-TOSCA-version profiles. These are generated, not hand-written (api).
   - OpenAADL/ocarina layers `meta/contract` → `lib/property` → `lib/data_structure` → `contract/*`, a 2016 fossil (api).
- Scaling across components over time is observable in only a few repos, each within one year:
   - silo added `coordination.als` about 2 months after `job_shard.als` (2025-12 → 2026-01), and both kept changing until 2026-04/05 (19 and 7 commits) (api).
   - emilia added models between 2026-03 and 2026-07 (api).
   - axios added a second model in 2026-07 (api).
   - No repo shows multi-year growth of a model set. Every older (pre-2023) user found is a single-model or single-burst fossil.
- CI gating of model edits was found in:
   - silo (per-model path filter) [B-gadget-silo-ci-alloy-jobs-2026];
   - kimberlite (PR-blocking; pinned jar + SHA-256; a scope-5 "quick" variant in CI and a scope-10 run off-CI) [C-kimberlite-formal-verification-ci-2026];
   - pta-standards (all `.als` files on model-touching PRs; its runner may not fail on counterexamples) [C-pta-standards-run-alloy-ci-2026];
   - emilia-protocol (custom runner that fails on a counterexample or a vacuous `run`) [C-emilia-protocol-run-alloy-doc-2026];
   - kiss-cache (a Nix flake check running `alloy6 exec`; the repo itself is rejected on the bar) (api).
   
   One counter-pattern: axios keeps its model check manual-dispatch only [C-axios-model-check-workflow-2026].
- Two repos use the model as a regression record of real bugs:
   - Mic92/nixbot's scheduler model maps predicates onto named Python functions, and its comments name the production bugs each assertion caught [B-nixbot-scheduler-alloy-model-2026].
   - aws-cdk's IAM merge model records a counterexample Alloy found that reversed a belief [B-aws-cdk-iam-policy-merging-alloy-2022].
- Standards bodies keep Alloy models as executable companions to prose specs:
   - Khronos Vulkan memory model: 1 model plus about 90 litmus tests. A Makefile diffs SAT/UNSAT results against reference results. No CI was found [A-khronos-vulkan-memory-model-readme-2019] [A-khronos-vulkan-alloy-litmus-makefile-2019].
   - The RISC-V ISA manual embeds an Alloy RVWMO model in `src/unpriv/mm-formal.adoc`; the file has commits into 2026 (api; not fully read, not registered).
- Several large projects hold one-time design artifacts with no CI and no designated owner:
   - lnd: 1 model, 2024, written after an off-by-one bug [B-lnd-alloy-models-readme-2024].
   - aws-cdk: 1 model, 2022, referenced from the implementing TypeScript file (api) [B-aws-cdk-iam-policy-merging-alloy-2022].
   - AdaCore gnatcoverage: 14 `.als` files in `tools/gnatcov/misc/models`, last touched 2021 (api).
   - OpenHarmony ark_runtime_core: 4 files in `verification/models`, last touched 2022 (api).
- A designated owner for models was found only in pta-standards' CODEOWNERS: `*.als` and `**/formal/` go to `@pta-standards/formal-maintainers` [C-pta-standards-codeowners-formal-2026]. That repo is also the only one with an ADR choosing Alloy over TLA+ for relational fit [C-pta-standards-alloy-over-tlaplus-adr-2026].
- Several 2025-2026 Alloy adopters show LLM-era signals: kimberlite, pta-standards, emilia, kiri and fspec (AI-assistant commit trailers, bot-authored bursts, one or two contributors). Their governance mechanisms are real files, but their durability is unproven.
- Name collision: the Rust "alloy" crates (alloy-rs, the Ethereum library) are unrelated and were excluded. So were `.als` files that are Ableton Live sets or mIRC alias scripts.
