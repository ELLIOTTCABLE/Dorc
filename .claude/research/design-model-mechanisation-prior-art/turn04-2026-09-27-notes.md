# turn 4 — 2026-09-27 12:53:29 CDT

Subagent turn, front-fundamental-unit-across-tiers. The question: in the analyzer's referent, sibling, and inspiration projects, what artifact (if any) stays constant across their correctness tools and evolution stages; which tiers consume it; whether it predates the implementation; how drift between it and the tiers is controlled; and whether a formal-proof tier reuses the implementation tier's suite. Counter-thesis sought equally: projects with no shared unit, and refinement projects whose constant is an abstract state rather than an example.

## Findings

- Where a proof tier consumes the implementation tier's suite, it does so the same way every time: an executable is extracted from the proof-side definitions and run under the ordinary test runner. The theorems themselves never consume the examples.
   - WasmCert-Coq's extracted interpreter runs the official `.wast` suite, vendored as a submodule, in CI, and is expected to pass all core tests [A-wasmcert-coq-readme-2026].
   - WasmCert-Isabelle splices its extracted OCaml definitions into a fork of the reference interpreter, i.e. the verified definitions are driven by the spec-test script runner [A-wasmcert-isabelle-readme-2026]; the README does not itself say the suite is run.
   - Sail: an OCaml emulator extracted from the generated Isabelle model of CHERI-MIPS runs the CHERI test suite, explicitly as end-to-end validation of the Sail-to-Lem-to-Isabelle translation, chosen instead of proving the translation correct [A-armstrong-sail-isa-semantics-2019].
   - The suite in these cases validates the *definitions* the proofs are about (the statement side), not the proofs.
- Refinement projects hold no example unit across tiers; the constant is an abstract state machine plus a state relation.
   - seL4: three layers (abstract spec, executable spec, C) related by forward-simulation theorems; concrete programs appear only at design time, running user code (a subset of the Iguana OS) on a Haskell-prototype-plus-QEMU-derived simulator. Use by student projects and the x86 port found 16 implementation defects; verification found 144 more [A-klein-sel4-formal-verification-2009].
   - KEVM: one K semantics, two backends, two units. The concrete (LLVM) backend runs the community Ethereum Test Set; the symbolic (Haskell) backend discharges separate proof specifications. The proof tier inherits the vectors' confidence only through the shared definition [A-kevm-evm-semantics-readme-2026].
- The held-constant input splits three ways by where its verdict lives:
   - Verdict stored in the unit: wast assertions [A-webassembly-reference-interpreter-readme-2026]; Oils per-shell expected stdout and status [A-oils-var-op-test-spec-file-2026]; goblint per-line annotations [A-goblint-developer-testing-guide-2026]; SV-COMP `expected_verdict` per property [A-sv-benchmarks-readme-2026]; tree-sitter expected trees [A-tree-sitter-writing-tests-2026]; smoosh's scripts with expected output and exit status [A-greenberg-smoosh-executable-posix-semantics-2020].
   - Verdict computed by an executable reference, per configuration:
      - RISC-V ACT: the Sail model, configured to match each device, computes the expected signature, which is compiled into the test [A-riscv-arch-test-readme-2026].
      - Ethereum consensus: the executable pyspec, run in generator mode, emits the vectors [A-ethereum-pyspec-readme-2026].
      - SibylFS: test scripts carry no expected result at all; the model decides whether each observed trace is allowed [A-ridge-sibylfs-oracle-testing-posix-fs-2015].
   - No verdict: Csmith programs have "no ground truth"; majority vote across compilers decides [A-yang-csmith-finding-bugs-c-compilers-2011].
- Stored verdicts routinely carry per-implementation qualifications rather than a single answer. Four shapes of qualification:
   - Oils: every case has a default expectation plus OK / N-I (not implemented) / BUG overrides per shell. A BUG annotation is kept as a comment when a shell fixes the bug [A-oils-var-op-test-spec-file-2026].
   - goblint: separates the analyzer's expected answer from the concrete semantics, and tags which property each annotation checks. `UNKNOWN!` checks soundness; `UNKNOWN` marks intended imprecision; `TODO` records a precision improvement not yet made [A-goblint-developer-testing-guide-2026].
   - Ethereum consensus: an absent post-state means "must reject" [A-ethereum-consensus-operations-format-2026].
   - SV-COMP: records the violated subproperty for a `false` verdict [A-sv-benchmarks-readme-2026].
- Shell lineage, specifically:
   - smoosh:
      - Its own unit is a short script paired with expected output and exit status, run unchanged against the semantics and seven shells.
      - CoLiS's interpreter passed 8 of those 161 tests.
      - Of the Open Group POSIX suite's 494 tests, 31 are "untestable" and checked by hand at certification; 44 are locale-dependent and marked unresolved or unsupported.
      - smoosh was written in Lem so that one implementation would extract to OCaml for execution and to Coq for proof. No proof consumes the suite [A-greenberg-smoosh-executable-posix-semantics-2020].
   - Oils:
      - It derives its spec from an automated survey of other shells. A case must be green or annotated on every other shell before OSH implements it; releases gate on an allowed-failure count [B-oils-spec-tests-wiki-2026].
      - The same files run against the Python implementation and its C++ translation [A-oils-spec-readme-2026].
   - CoLiS gives every seam its own unit and oracle [A-becker-colis-platform-maintainer-scripts-2022]; there is no single cross-tier artifact:
      - parser vs dash on 7.4M archived scripts (95% agreement);
      - CoLiS semantics vs sh on a construct-covering script suite;
      - interpreter vs inductive semantics by 245 Why3 verification conditions;
      - utility specs vs real commands by extracting a model, building the filesystem, running the command.
   - SibylFS is the POSIX-filesystem cousin from the smoosh/Sail group [A-ridge-sibylfs-oracle-testing-posix-fs-2015]:
      - Scripts carry no expected results; the model is the oracle.
      - Coverage is measured over the model (98%). Test equivalence classes are mechanically checked for "at least one test case for each logically-possible combination".
      - Model and suite co-evolve in a stated "virtuous circle".
      - The Lem model also renders to HOL4 and Isabelle, where two sanity theorems were proved independently of the suite.
- Whether the unit predates the implementation varies:
   - Predates:
      - Test-first by rule or feature: tree-sitter [A-tree-sitter-writing-tests-2026] and Oils [B-oils-spec-tests-wiki-2026].
      - Before any client: Ethereum consensus vectors (generated from the executable spec) [A-ethereum-consensus-test-formats-2026].
      - Before any device: RISC-V ACT tests, with expected values computed by the reference [A-riscv-arch-test-readme-2026].
      - Independent of every verifier: SV-COMP tasks [A-sv-benchmarks-readme-2026].
   - Follows the implementation:
      - Kubernetes conformance tests are promoted only after running two weeks, and the prose Conformance Document is generated from their comments [A-kubernetes-conformance-tests-guide-2026].
      - Nix language tests are characterisation goldens of a former version [A-nix-manual-running-tests-2026].
- Drift control, as found:
   - Regeneration of stored verdicts from current implementation output, one flag away: tree-sitter `-u` [A-tree-sitter-writing-tests-2026], Nix `_NIX_TEST_ACCEPT=1` [A-nix-manual-running-tests-2026], goblint `dune promote` for cram tests [A-goblint-developer-testing-guide-2026]. This is characterisation: the implementation writes the verdict.
   - A rule that maintenance edits must not change the intended verdict [A-sv-benchmarks-readme-2026].
   - Generation of vectors or expected values from an executable spec [A-ethereum-pyspec-readme-2026] [A-riscv-arch-test-readme-2026].
   - Versioning per release branch, with a review board gating promotion, demotion, and any change to a conformance test [A-kubernetes-conformance-tests-guide-2026].
   - A manifest in each vector duplicating its path identity so vectors travel intact [A-ethereum-consensus-test-formats-2026].
- Units accrue renderers:
   - Wasm: `.wast` to JS to Web Platform Tests [A-webassembly-test-suite-readme-2026].
   - SV-COMP: programs re-rendered as Horn clauses [A-sv-benchmarks-readme-2026].
   - Kubernetes: a test's RFC 2119 comment rendered into the Conformance Document [A-kubernetes-conformance-tests-guide-2026].
   - Nix: one set of JSON test data checked by the (de)serialisation tests and by the JSON Schema that generates manual pages [A-nix-manual-running-tests-2026].
   - Sail: one source rendered to C/OCaml emulators and Isabelle/HOL4/Coq definitions [A-armstrong-sail-isa-semantics-2019].
- Where the unit is shared across implementations, disagreement is triaged, not auto-resolved. The strongest form is RISC-V ACT's five-way triage, each kind routed to a different repository [A-riscv-arch-test-readme-2026]:
   - device error;
   - test error;
   - missing configuration parameter;
   - reference-model error;
   - specification ambiguity.
  Validation runs also surfaced defects in the specs and suites themselves:
   - smoosh found ten bugs in the POSIX test suite and typos in the POSIX specification [A-greenberg-smoosh-executable-posix-semantics-2020];
   - SibylFS queries led to POSIX issues recorded and resolved on the Austin Group tracker [A-ridge-sibylfs-oracle-testing-posix-fs-2015];
   - CoLiS's suite exposed a dash nonconformity with POSIX [A-becker-colis-platform-maintainer-scripts-2022];
   - Sail's work fed fixes back to the RISC-V prose spec and to Spike [A-armstrong-sail-isa-semantics-2019].
- A verified implementation treated as one voter among many: six CPU-years of Csmith found CompCert wrong-code bugs only in its unverified front end and in an under-specified PowerPC immediate width, none in the verified middle end [A-yang-csmith-finding-bugs-c-compilers-2011].
- Product siblings show no cross-tier unit.
   - The only tier is the field:
      - Terraform provider acceptance tests drive a real binary against real infrastructure [A-hashicorp-terraform-acceptance-tests-2025].
      - Ansible's integration tests are "Tests for playbooks, by playbooks", one target per module [A-ansible-integration-tests-guide-2026].
   - Nix follows the implementation with characterisation goldens [A-nix-manual-running-tests-2026].
   - Kubernetes is the exception: a cross-vendor unit, but one that graduates (e2e to conformance) and demotes, the opposite of a never-graduating witness [A-kubernetes-conformance-tests-guide-2026].
