### structural — 4

**`rw-btree-iteration-crashes-charon`.** `BTreeMap`/`BTreeSet` are not merely
unmodelled. Charon dies typechecking std's own `impl Iterator for
alloc::collections::btree::map::Iter`, inside `alloc`, before emitting anything:

```
error: Type error after transformations:
       Mismatched trait clause:
       expected: TraitClause0_1: (alloc::collections::btree::map::Iter<'a, K, V>: Iterator<&'a T>)
            got: {impl#88}<'a, K, V>: Iterator<alloc::collections::btree::map::Iter<'a, K, V>, (&'a K, &'a V)>
 --> /rustc/library/alloc/src/collections/btree/map.rs:1732:1
```

Any `for (k, v) in &map` reaches it — deleting `MapL::iter` alone changed
nothing. This is worth flagging precisely because it is *not* the expected
"unsupported type, opaque axiom" outcome: it is a frontend crash in a
dependency you did not write, and the diagnostic points into `alloc`, not into
your code. +SURE on the observation; ~SUSPECT it is a charon bug rather than a
deliberate refusal, given the shape of the message.

The substitute is a sorted `Vec` with hand-written merges:

```rust
// before
pub struct Powerset<T: Ord + Clone>(pub BTreeSet<T>);
fn join(&self, other: &Self) -> Self {
    Powerset(self.0.union(&other.0).cloned().collect())
}
// after
pub struct Powerset<T: Ord + Clone>(pub Vec<T>);   // sorted, deduped BY HAND
fn join(&self, other: &Self) -> Self {
    let mut out: Vec<T> = Vec::new();
    let (mut i, mut j) = (0usize, 0usize);
    while i < self.0.len() { /* ...index-walked merge... */ }
    Powerset(out)
}
```

The real cost is not the loop. It is that `spike/CLAUDE.md`'s `inv-determinism`
("Never iterate a `HashMap`/`HashSet` where order is observable —
`BTreeMap`/sorted vecs") currently gets *the ordered-collection half of its
guarantee from the type*. After this rewrite the sortedness is an unchecked
invariant on a `Vec`. `MapL`'s no-⊥ canonical form was always hand-maintained,
so that half is unchanged; the set/map ordering half is newly on the honour
system.

**`rw-maplattice-becomes-assoc-vec`.** `BTreeMap<K, V>` → key-sorted
`Vec<(K, V)>`; `get`/`insert` become linear walks. Same class as above.

**`rw-option-borrow-split-into-two-passes`.** `if let Some(v2) = other.0.get(k)`
held a borrow into `other` while `out` was being built. `Option` itself is
modelled fine; the *borrow shape* is what Aeneas is sensitive to, so this split
into a `has_key` presence test plus a by-value `get`. Mechanical to write,
structural in effect: it doubles the scan.

**`rw-vecdeque-becomes-vec-plus-cursor`.** No deque in the model. The FIFO
discipline is load-bearing for `inv-determinism`, so it cannot degrade to a
stack; the honest substitute is a `Vec` plus a never-rewinding read cursor,
which makes the worklist grow without bound across a run. Fine for a
translation probe, **not** a shape the real solver could ship. This is the one
rewrite that would need genuine design work rather than transcription.

### mechanical-local — 6

**`rw-closure-returning-slice-aborts-aeneas`.** The `flows_to` closure returned
`&[usize]` borrowed from `graph`:

```
[Error] Can't end abstraction 18 as it is set as non-endable
Source: 'lattice/src/lib.rs', lines 491:23-496:9
Compiler source: interp/InterpBorrows.ml, line 1203
```

Lifting it to a free function `fn flows_to<G: Graph>(graph: &G, direction:
Direction, v: usize) -> &[usize]` fixes it outright. Note what this is *not*: it
is not "closures are unsupported". The `transfer: impl Fn(usize, &L) -> L`
parameter three lines above survived untouched (§b). The trigger is a closure
whose *return* borrows from its capture.

**`rw-vec-macro-becomes-push-loop`.** `vec![L::bottom(); n]` expands through
`alloc::vec::from_elem` + `Clone`, unmodelled. Push loop.

**`rw-range-collect-becomes-loop`.** `(0..n).collect()` → seed loop.

**`rw-for-over-slice-becomes-index-walk`.** `for &w in flows_to(v)` → indexed
`while`. Iterator *chains* were never the issue here; there are none in this
tier. `for` over a slice is.

**`rw-debug-assert-deleted`.** `debug_assert!(w < n, "…{w}…{n}")` — the
format-string machinery is unmodelled. It is a no-op in the release build charon
compiles anyway, so this loses a real diagnostic and no semantics. Worth
recording as a genuine (small) loss rather than a syntax fix.

**`rw-static-str-literal-hoisted-to-const`.** Found in the §4 idiom census, not
in the algebra tier, but it is the sharpest single finding in the round. A
function *returning a `&'static str` literal inline* aborts Aeneas
("There should be no bottoms in the value"). The same literal bound to a named
`const` translates perfectly. Four-way classification, one lenient run
(`spike-aeneas/strings/`):

| spelling | outcome |
|---|---|
| `fn f() -> &'static str { "lit" }` | **`sorry`** |
| `const SLUG: &str = "lit"; fn f() -> &'static str { SLUG }` | `ok SLUG`, clean |
| `fn f(s: &str) -> usize { s.len() }` | `core.str.Str.len s`, clean |
| `fn f() -> &'static [u8] { b"lit" }` | **`sorry`** |

`const SLUG` extracts as `@[global_simps, irreducible] def SLUG : Str := toStr
"systemctl.oracle.sh:12"` — exactly what you want. So this is a one-line
mechanical fix, *provided you notice*. Which brings us to the sharp part.

### The silent-degradation hazard, and why the tasks are shaped as they are

Under Aeneas's default (non-`-abort-on-error`) mode, `return_literal` above did
not fail. It emitted:

```lean
def return_literal : Result Str := do
  sorry
```

A `sorry` typechecks. Anything proved downstream of it is vacuous, and Lean's
warning is one line in a 1700-job build. The probe's `mise run translate` task
therefore carries `charon --error-on-warnings` and `aeneas -abort-on-error`, and
`translate:lenient` exists only to enumerate failures in one pass — never to
judge whether an extract translated. Both current extracts are at **zero
`sorry`**. `-GUESS` that this is the single most important process rule for any
team adopting Aeneas: a green build proves nothing without a `sorry` census.

## b. What translated cleanly, zero changes

This is the more surprising half of the result. Everything below came through
untouched, and most of it came through *legibly*:

- **The `Lattice` trait**, including its defaulted `leq` method. Becomes a Lean
  `structure` whose fields are the operations, with the supertrait dictionaries
  as extra fields:
  ```lean
  structure lattice.Lattice (Self : Type) where
    corecloneCloneInst : core.clone.Clone Self
    corecmpEqInst : core.cmp.Eq Self
    bottom : Result Self
    join : Self → Self → Result Self
    meet : Self → Self → Result Self
    leq : Self → Self → Result Bool
  ```
- **`BoundedLattice: Lattice`** — the supertrait becomes a `LatticeInst` field.
  The `Powerset`-has-no-⊤ asymmetry that `lattice.rs` encodes by *withholding*
  the `BoundedLattice` impl survives: there simply is no
  `Powerset.Insts...BoundedLattice` in the output.
- **The combinators**: `Flat` → a real `inductive`; `Product A B` → `A × B`;
  `Powerset T` → `Vec T`; `MapL K V` → `Vec (K × V)`.
- **Blanket/conditional impls**: `impl<A: BoundedLattice, B: BoundedLattice>
  BoundedLattice for Product<A, B>` translates as a function from the two
  component dictionaries to the product one.
- **The generic `solve<G: Graph, L: Lattice>`**, whole. Two trait dictionaries
  as parameters, nothing monomorphised, nothing hand-instantiated.
- **`impl Fn(usize, &L) -> L`** — a type parameter plus a
  `core.ops.function.Fn T2 (Std.Usize × L) L` dictionary, invoked as
  `coreopsfunctionFnT2PairUsizeSharedLLInst.call transfer (v, t)`. **No
  de-closuring was required.** (The brief anticipated this being a problem; it
  was not.)
- **The slice-returning `Graph` API**: `succ : Self → Std.Usize → Result (Slice
  Std.Usize)`. Slice-returning trait methods are fine; it was the *closure*
  returning a slice that broke.
- **`Direction`, `Solution<L>`** — enum and struct, verbatim shapes.
- **Derive macros** — `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `Default`,
  `PartialOrd`, `Ord`, `Hash` all translate. They are also most of the output
  volume: of 2095 generated lines, the great majority are `Insts.CoreFmtDebug`,
  `Insts.CoreCloneClone`, `Insts.CoreCmpPartialEq*`, `Insts.CoreCmpEq`. Dropping
  `#[derive(Debug)]` alone would remove two of the six external axioms.
- **`PhantomData`** (from the idiom census) — `def core.marker.PhantomData (T :
  Type) := Unit`, and the mint extracts as `ok { payload, _tier := () }`. The
  phantom *index* stays a real Lean type parameter, so `Claim ObservationTier P`
  and `Claim VouchTier P` remain distinct types. `claim-tier-gating` survives
  translation.
- **Uninhabited marker enums** — `inductive ObservationTier where`, no
  constructors. Correct.
- **`Option`**, `usize`/`u32` arithmetic, nested `match`, early `return`.

Two clean-translation results that are *losses* rather than wins, and belong in
the census as much as in this section:

- **The sealed-trait fence evaporates.** `mod sealed { pub trait Sealed {} }` +
  `pub trait Tier: sealed::Sealed {}` becomes `structure sealed.Sealed (Self :
  Type) where` — an **empty structure**. In Lean anyone writes
  `sealed.Sealed MyType := {}` and mints a fourth tier. The seal is a Rust
  *visibility* device and Lean privacy does not reconstruct it. Any Lean-side
  reasoning that leans on "these three are the only tiers" must re-establish it
  as an explicit hypothesis or an inductive.
- **Interned newtypes evaporate.** `struct SelectorId(u32)` → `@[reducible] def
  SelectorId := Std.U32`, and likewise `KindId`. They are definitionally equal
  to each other and to raw `U32`, so `selector_covers` will happily accept a
  `KindId` in Lean. `core/CLAUDE.md`'s `selector-chokepoint` is a Rust-side
  guarantee only.
- **`May<L>`/`Must<L>` evaporate the same way** — `def lattice.May (L : Type) :=
  L` and `def lattice.Must (L : Type) := L`, both `@[reducible]`. The *instances*
  still differ (`Must`'s join really is `L`'s meet), so the operations stay
  correct, but the types are interchangeable. `inv-must-may` — "only a `Must`-grade
  fact may license a replacement; the reverse does not compile" — is a Rust-level
  guarantee that does not survive into Lean. On the current design this is
  containable (the licensing decisions live in Rust, above the algebra), but it
  is exactly the kind of thing that would be assumed to carry over.

## c. The Lean output, and what proving against it feels like

**Readability: better than expected.** Here is `Flat::join`, one of the two
places the ⊤-saturation rule lives, side by side in spirit:

```lean
def lattice.Flat.Insts.LatticeLatticeLattice.join
  {T : Type} (corecloneCloneInst : core.clone.Clone T) (corecmpEqInst : core.cmp.Eq T)
  (self : lattice.Flat T) (other : lattice.Flat T) : Result (lattice.Flat T)
  := do
  match self with
  | lattice.Flat.Bottom =>
    lattice.Flat.Insts.CoreCloneClone.clone corecloneCloneInst corecloneCloneInst
      corecmpEqInst other
  | lattice.Flat.Elem a =>
    match other with
    | lattice.Flat.Bottom => …clone… self
    | lattice.Flat.Elem b =>
      let b1 ← core.cmp.impls.PartialEqShared.eq corecmpEqInst.partialEqInst a b
      if b1 then let t ← corecloneCloneInst.clone a
                 ok (lattice.Flat.Elem t)
            else ok lattice.Flat.Top
    | lattice.Flat.Top => ok lattice.Flat.Top
  | lattice.Flat.Top => …
```

Four things degrade it, in rising order of importance:

1. **Or-patterns are expanded.** `(Flat::Bottom, x) | (x, Flat::Bottom)` becomes
   a full 3×3 nested match. Semantics preserved, symmetry lost to the eye.
2. **Names are long and doubled.** The crate is `lattice` and so is the module,
   so everything is `lattice.lattice.Flat`; instances are
   `Insts.LatticeLatticeLattice`.
3. **`&mut` becomes a lens pair, and reorders the read.** In `solve`:
   ```lean
   let (_, index_mut_back) ← alloc.vec.Vec.index_mut … state w
   let b1 ← alloc.vec.Vec.index … queued w
   if b1 then let state1 := index_mut_back t1
              ok (cont (state1, queued, work, e1))
   ```
   The write-back closure is obtained *before* the unrelated read and applied at
   the end. This is Aeneas's whole trick and it is sound, but it is the point
   where line-by-line correspondence with the Rust stops.
4. **Everything is in `Result`, and loops become state tuples.** `solve`'s inner
   loop body carries `(state, queued, work, head, rounds)` through a
   `ControlFlow` return type. Any proof about the solver is a proof about that
   5-tuple's invariant.

**Stating and proving the laws.** I wrote `spike-aeneas/lattice/lean-proj/Laws.lean`
by hand and built it. The result is sharp:

The Rust doc-comment's very first law, `⊥ ⊔ a = a`, is **not provable as
stated**. The extraction of that arm is `cl.clone other`, and `cl.clone` is a
field of an opaque record. Aeneas's model of Rust's `Clone` carries no law
saying a clone returns its argument, and its model of `Eq` is literally

```lean
structure core.cmp.PartialEq (Self : Type) (Rhs : Type) where
  eq : Self → Rhs → Result Bool
  ne : Self → Rhs → Result Bool := fun self other => do ok (not (← eq self other))
structure core.cmp.Eq (Self : Type) where
  partialEqInst : core.cmp.PartialEq Self Self
  assert_fields_are_eq (_ : Self) : Result Unit := .ok ()
```

— no reflexivity, no symmetry, no transitivity. `solve`'s stated precondition
3, "`L`'s `Eq` is **semantic**", has nothing on the Lean side to appeal to.

Supply the missing lawfulness as explicit hypotheses and the proofs are *short*:

```lean
def LawfulClone {T} (cl : core.clone.Clone T) : Prop := ∀ x : T, cl.clone x = ok x

theorem join_bot_left {T} (cl : core.clone.Clone T) (eq : core.cmp.Eq T)
    (hcl : LawfulClone cl) (a : Flat T) :
    Flat.Insts.LatticeLatticeLattice.join cl eq Flat.Bottom a = ok a := by
  unfold Flat.Insts.LatticeLatticeLattice.join Flat.Insts.CoreCloneClone.clone
  cases a <;> simp [hcl _]
```

`join_bot_left`, `join_bot_right`, and `join_idem` (which additionally needs
`LawfulEq`) all go through in one `unfold` plus one `cases <;> simp`. Axiom
report:

```
'LatticeLaws.join_bot_left'  depends on axioms: [propext]
'LatticeLaws.join_bot_right' depends on axioms: [propext]
'LatticeLaws.join_idem'      depends on axioms: [propext, Quot.sound]
```

No `sorryAx`, and none of the six `FunsExternal` axioms. Axiom-clean.

**So the tax is the glue, not the proof.** Roughly: for each generic seat, each
derived instance, you carry a "this dictionary is lawful" hypothesis that the
extraction cannot give you and that nothing checks against the Rust. That
hypothesis is a **new trusted-base entry**, and it is the honest answer to
"versus hand-written definitions": a hand-written Lean `Flat` would have
`join ⊥ a = a` by `rfl`, with no hypothesis and no trusted base. What the
extraction buys instead is that the theorem is about *the actual shipped Rust*,
not about a model of it someone transcribed. That is the entire trade.

Two further honesty notes:

- **Aeneas's own Lean library contains `sorry`s** —
  `Aeneas/Std/Slice.lean:363`, `:586`, `Aeneas/Std/StringIter.lean:12`, `:15`.
  They are warnings in every build. Anything proved through those declarations
  is not proved. ~SUSPECT they are in corners the algebra tier does not touch
  (my three laws are axiom-clean, which is evidence but not proof for a larger
  effort).
- **Six external axioms** in `FunsExternal_Template.lean` for the algebra tier —
  `Vec::remove`, `usize::saturating_mul`, tuple `PartialEq::{eq,ne}`, and two

## e. jxl-proofs

`AeneasVerif/jxl-proofs` is the flagship non-crypto example, and its shape is
instructive out of proportion to its size.

- **It translates ONE entry point, not a crate.** The Makefile runs
  `charon cargo --preset=aeneas --start-from="jxl::entropy_coding::ans::_::read"`.
  That flag ("translate these items and anything they refer to") is the scoping
  mechanism, and it is how they keep the surface tractable.
- **It is tiny.** `Funs.lean` 9.2 KB, `Types.lean` 1.8 KB, `FunsExternal.lean`
  1.8 KB, `Proofs.lean` 8.3 KB. My algebra-tier `Funs.lean` is 2095 lines /
  ~65 KB — **roughly seven times** the flagship example's generated body, from
  two small files. That is a sobering calibration on what "an Aeneas-sized
  verification target" currently means.
- **Proof-to-code is about 1:1 by bytes** (8.3 KB of proofs against 9.2 KB of
  generated code), and that is for panic-freedom and data-structure invariants,
  not functional correctness.
- **Re-extraction is a manual merge, every time.** Their own documented bump
  procedure: "Remove the `lean` directory · setup and build a lake project ·
  extract · **Manually merge and restore content (using `git status` and
  `git diff`)** · make sure the project builds before committing." Proofs and
  generated definitions live in the same tree and are reconciled by hand on
  every toolchain or source bump. Both sides are pinned by exact commit files
  (`aeneas-commit`, `jxl-rs-commit`) with a `test-commits` target that checks
  them.
- **The proof idiom is Aeneas-specific automation**, not vanilla Lean:
  `progress*`, `scalar_tac`, `bv_tac`, `grind_pattern [agrind]`. Much of
  `Proofs.lean` is overflow plumbing (`and_lt1`, `or_lt2_usize`,
  `times_zero_or_1`) forced by the `Result` monad making every arithmetic
  operation fallible. They also hand-write `deriving instance Inhabited` for
  generated types, and carry a helper whose comment reads "avoids `progress*`
  being blocked because of an automatically-inserted coercion that is not
  recognized by the implementation of `progress*`".

The tax profiles differ: jxl pays an **arithmetic-overflow** tax; Dorc's algebra
tier would pay an **opaque-instance** tax (§c). Both are structural, neither is
the tax you would predict from reading the Rust.

## f. Verdict

**The within-discipline rewrite for this algebra tier is small — call it a
day's work, not a rewrite.** +SURE: ten changes, none of them a wall, over 439
lines, and the type-level architecture (traits, generics, the `impl Fn`
parameter, the sealed/phantom devices, the `Must`/`May` dual) needed no
concession at all. +SURE the pipeline works end to end and the output
typechecks; +SURE three lattice laws are provable against it, axiom-clean.

Three qualifications, in descending confidence:

- +SURE **the door is currently ajar, not open, and one hinge is real design
  work**: the `VecDeque` substitute is not shippable. Everything else I did is
  something the kernel could simply adopt.
- ~SUSPECT **the type-level guarantees do not cross the boundary, and this is
  the finding most likely to be mis-assumed.** Sealed traits become empty
  structures; newtypes become `@[reducible] def`s; `Must`/`May` become the same
  type. Any Lean-side argument that leans on `inv-must-may`,
  `claim-tier-gating`, or `selector-chokepoint` must re-establish it from
  scratch. Aeneas verifies *behaviour*, and Dorc's kernel spends a great deal of
  its correctness budget on *unrepresentability*, which is exactly the part that
  does not translate.
- -GUESS **the cost is not the translation, it is the standing maintenance.**
  jxl-proofs's manual-merge bump loop, against a charon that pins an exact
  rustc nightly and an aeneas that pins an exact charon, is the ongoing bill.
  For a project whose own doctrine is "this spike is disposable", adopting a
  toolchain whose upstream cadence is a *daily nightly release* is a commitment
  worth pricing separately from the rewrite.

### Top three disciplines to adopt now, to keep the door open

1. **`disc-no-ordered-std-collections-in-the-kernel`.** `BTreeMap`/`BTreeSet` are
   the only hard blocker found, and they crash the *frontend*. Move the algebra
   tier's containers behind a thin internal abstraction now — sorted `Vec` +
   `Vec<(K,V)>` with the ordering invariant asserted in a test rather than
   assumed. This is also the one that costs something today
   (`inv-determinism`'s type-carried half), so it deserves a decision rather
   than a drive-by.
2. **`disc-hoist-static-literals-to-consts`.** Every `&'static str` (and
   `&'static [u8]`) literal returned by reference is either an abort or, worse,
   a silent `sorry`. Naming them as `const`s is free, is better Rust anyway, and
   removes an entire failure class. Pairs with: **never trust a lenient
   translation — census `sorry` count on every run.**
3. **`disc-keep-borrows-out-of-closure-returns-and-option-holds`.** Two of the
   three Aeneas-side aborts were borrow-shape, not feature-support: a closure
   returning a slice borrowed from its capture, and an `if let Some(v) =
   other.get(k)` holding a borrow across a mutation of a sibling. Both are
   already mild code smells; making them house style costs nothing and removes
   the failure mode where Aeneas dies inside its own OCaml with a stack trace.

Honourable mentions, cheaper but lower-value: prefer index loops to `for`-over-
slice in the kernel (`rw-for-over-slice-becomes-index-walk`); consider whether
`#[derive(Debug)]` earns its place on kernel algebra types (it is two of six
external axioms and a large share of generated volume).

### tc-shaped judgment calls — FLAGGED, not resolved

- **`tc-nested-mise-config-vs-root`.** I put the probe's toolchain in a nested
  `spike-aeneas/mise.toml` rather than the repo root, diverging from the sibling
  Lean spike's placement. Rationale is real (the `rust` pin shadows the
  workspace compiler) but the divergence is a call an orchestrator should ratify,
  as is whether a throwaway research toolchain belongs in `mise install` at all.
- **`tc-ubi-backend-is-deprecated`.** mise 2026.7.3 warns that the `ubi:` backend
  is deprecated in favour of `github:` (removal in 2027.1.0). I used `github:`;
  the sibling's root-level `ubi:leanprover/elan` will need the same migration.
  Not mine to change.
- **`tc-determinism-invariant-moves-to-honour-system`.** Replacing
  `BTreeSet`/`BTreeMap` with sorted `Vec`s moves half of `inv-determinism` from
  the type system to an unchecked invariant. In the probe that is free; in the
  kernel it is a real trade against `spike/CLAUDE.md`'s explicit "never iterate
  a `HashMap`/`HashSet` where order is observable — `BTreeMap`/sorted vecs".
- **`tc-must-may-unrepresentability-does-not-translate`.** `inv-must-may` says
  the `May → Must` direction "does not compile". In Lean, `May L` and `Must L`
  are both `L`. Whether that matters depends on where licensing decisions live;
  it is a cross-cutting call, not a component one.
- **`tc-worklist-shape-needs-real-design`.** The `Vec`+cursor substitute for
  `VecDeque` leaks. Anyone adopting this must design the FIFO properly rather
  than inherit my probe's shape.
