# turn 7 — 2026-08-23 19:31:27 CDT

Front: `front-write-ordering`. When is the durable record written relative to the mutations it explains?

## Findings

- **The canonical pattern is Lampson and Sturgis's *intentions*, and its guarantee is one-directional.** Write-ahead buys "no effect exists without a record of the intent to cause it". It does NOT buy "a record implies the effect happened". Every downstream property — recovery, resumption, reconciliation — is built on the first half, and the prediction hazard is the unavoidable price of the second.
- **The canonical pattern's atomicity boundary is a single durable write, and the intent set may be arbitrarily large and written incrementally before it.** Lampson and Sturgis are explicit: the intentions set may be any size, but the commit that makes it authoritative "must be the result of a single Put action", and until that Put the intentions have no effect. That is the durability-boundary criterion, stated in 1979, and it validates the human's criterion in the source.
- **The pattern's guarantee does not survive the trip to another machine.** Gray classifies effects on the far side as *real actions* — cannot be undone, must be deferred until after commit, must be *named so duplicates are discarded*, and must be *restartable*. An arbitrary remote shell command satisfies none of the three. Even AWS gives a caller-token dedup contract on an enumerated subset of its own mutating operations and nowhere else. What survives the trip is: "we know what we meant to do"; what does not survive is "we know whether it happened".
- **Shipped systems overwhelmingly write more than one record per invocation, and the splits are temporal, not taxonomic.** Kubernetes audit emits per execution stage; sudo writes an accept record then optionally an exit record plus a per-session directory of streams; ansible-runner writes one numbered immutable file per event; Salt writes one intent record plus one outcome record per target; yum writes an intended-set file then appends a completed line per element. Every one of these splits at a moment, not at a kind.
- **The one place fail-closed is defensible is exactly the pre-mutation record, and shipped systems scope it there deliberately.** Kubernetes' `blocking-strict` fails the whole request only when audit fails *at the RequestReceived stage* — the pre-mutation one. Terraform halts the apply when a mid-run state write fails but goes best-effort at the end. Nobody fails an operation because the post-hoc record could not be written, because that is incoherent: the mutation already happened.
- **sudo is the closest shipped analogue and it splits the failure policy by record class, not by one global rule.** `ignore_logfile_errors` on (summary record failing does not stop the command), `ignore_audit_errors` on (same), `ignore_iolog_errors` **off** (the detailed session transcript failing *does* terminate the command). And it is genuinely write-ahead: "a command may only be run after the log file entry is successfully written."
- **The availability counter-thesis is real, documented, and has already forced a shipped retraction.** auditd's `space_left_action` lost its `halt` option upstream because "halting the system at this stage could lead to unintended consequences and is considered a bad action" — precisely the three-in-the-morning objection, conceded by the maintainers. The remaining fail-closed actions were pushed to the last two stages.
- **A recording facility taking down the thing it records is not hypothetical.** AWS traced a customer incident to the default blocking container log driver: with the sink unreachable, the buffer fills, the application blocks, the container freezes. The documented middle is buffer-to-local-disk, which is the exact resource a broken-store operator lacks.
- **The prediction hazard has a shipped verdict against it, in the harshest possible form.** yum, on failing to write its transaction journal, *deletes the journal* and continues, on the stated reasoning that "having incomplete transactions is probably worse than having nothing". A partial intent record is treated as more dangerous than none, because the recovery tool acts on it.
- **The composed read surface fails exactly as feared, and there is a shipped example with the author's confession in a comment.** yum's recovery reader joins intended-set against completed-set by subtraction; when the intended-set file is missing it returns an empty remainder — indistinguishable from "nothing left to do" — with the comment "something is wrong, here, probably need to raise _something_". The same reader raises a hard error on a malformed line. One damage class reported as fact, the other smoothed into a plausible answer.
- **Composition also degrades completeness detection into a heuristic.** auditd states outright that it cannot guarantee the records making up one event occur atomically or in order, so its reader maintains a list-of-lists and falls back on a two-second timeout to decide an event is finished. A single logical event spread over several records in a shared stream has no construction-time coherence left to recover.
- **Resumption-from-record is a real privilege boundary, and there is a 2026 CVE where it broke.** In CRIU, a process inside the container being checkpointed can influence what gets written into the image; on restore, the spoofed credentials become live authority — elevated capabilities, zeroed identifiers. This is the read-back-is-report-only rule validated by a working exploit, not a theory.
- **Terraform shows the safe form of a prediction record: bind it to the world-version it was computed against, and refuse if that moved.** The plan file carries the prior state snapshot with lineage and serial; before applying, both are compared and two *distinct* refusals are emitted — wrong lineage versus stale. Kubernetes does the same with `observedGeneration`.
- **Kubernetes' intent/observation split is the most worked-out and it forbids the writer of one from touching the other.** `spec` is intent, `status` is "the most recent observations of actual state"; PUT and POST MUST ignore status; a separate subresource exists so controllers can write status without writing spec. Different authorization scopes for each.
- **Emit an explicit Unknown rather than nothing.** Kubernetes requires controllers to apply their conditions "the first time they visit the resource, even if the `status` is Unknown", and absence of a condition reads as Unknown. Logfire's shipped "pending spans" do the same for tracing: emit an eagerly-marked record if the operation has not finished within a second, and let the real record supersede it.
- **Write-at-the-end loses the record precisely when it is most wanted, and the people who own that model say so.** The OpenTelemetry maintainers are exploring a span-start/update/end event model specifically because a record emitted only on completion is lost when the process dies.
- **A per-invocation artifact whose home is unmanaged gets abandoned regardless of forensic worth.** Ansible's `.retry` file — its only resumption aid — was disabled by default in 2.8 for clutter, no default save path, shell-completion interference, and needing an ignore-file entry. Approved in a public core meeting.
- **The terminator's absence is the crash signal, and shipped systems use it that way.** ansible-runner: "If the playbook runs to completion without getting killed, the last event will always be the `stats` event." This corroborates the design's existing terminator unit at no extra cost.
- **Readability and security are NOT in tension for the ordering decision itself** — writing earlier neither adds nor removes any disclosure. They ARE in tension at Terraform's last-ditch fallback, which dumps raw secret-bearing state to the terminal, and at sudo's I/O log, which the manpage admits stores typed passwords unencrypted.

### The canonical pattern and its atomicity boundary

> [A-lampson-sturgis-intentions-1979]:§7 Transactions (relevance: +1:SURE)
> First, record the information necessary to do the writes in a set of intentions, without changing the data stored by the system. The last action taken in this phase is said to commit the transaction.
> Second, do the writes, actually changing the stored data.
> If a crash occurs after the transaction is committed but before all the changes to stored data have been done, the second phase is restarted.

> [A-lampson-sturgis-intentions-1979]:§7 Transactions (relevance: +1:SURE)
> To preserve the atomic property, the writing of the intentions set must itself be atomic. … This change is the point at which the transaction is committed. It must be atomic, and hence must be the result of a single Put action. The intentions set may be of arbitrary size, but it must be represented in such a way that its existence has no effect on the file data until this final Put has been done.

> [A-lampson-sturgis-intentions-1979]:§4.4 Simple, compound and restartable actions (relevance: +1:SURE)
> During crash recovery it is usually impossible to discover whether a particular action has completed or not. Thus, we will frequently require that S be restartable, by which we mean that Qcrash implies P … Notice that atomic does not imply restartable.

> [A-lampson-sturgis-intentions-1979]:§8.2 Ordering of actions (relevance: -0:SUSPECT)

## What I did not pursue, and why

- **Common Criteria FAU_STG.4 itself.** Search surfaced it repeatedly as the standards basis for "prevent auditable events if the trail cannot be written", but the Part 2 document is a 300-page PDF and the auditd manpage states the same doctrine in one sentence from a shipped implementation's maintainer. I did not read the standard and therefore make no claim about its exact wording. If the round later wants the normative citation, that is a cheap follow-up.
- **dpkg's `/var/lib/dpkg/updates` journal.** yum's two-file journal gave the same shape with better-commented source and a cleaner failure story. Adding dpkg would be corroboration, not new information.
- **etcd/Raft's persist-before-apply.** It is the same rule as write-ahead logging in a setting where the "action" is a local state-machine transition, so it does not touch the remote gap, which is the crux.
- **ARIES.** Same reason. Gray 1981 and Lampson-Sturgis 1979 carry the argument this front needs; ARIES refines recovery efficiency, not the ordering question.
- **The `phase`-versus-`conditions` history in Kubernetes** beyond the one paragraph on deprecation. Interesting for report design, not for ordering.
- **A quantified field study of orphaned resources after interrupted runs.** I looked; what exists is forum threads and vendor recovery articles, and the source of record is already covered by Terraform's own error prose. I did not want to register discussion-board material as evidence for a cost claim.
