# turn 8 — 2026-08-23 20:05:41 CDT

Front: `front-cleanup-without-a-daemon`. Retention and clearing for a one-shot tool that is not a daemon.

## Findings

- **The human's lean survives, but its stated reason does not.** "One-shot tools do not do housekeeping during unrelated invocations" is factually false — git, cargo, Homebrew, Gradle-without-a-daemon and the Go toolchain all do, and three of them added it deliberately after user complaints. The variable that actually separates the tools that delete unbidden from the tools that refuse is not daemon-ness. It is **reconstructibility**.
- **The rule the corpus actually supports: a tool may delete on its own initiative exactly what it can recreate.** Cargo deletes locally-recreatable data after 1 month and re-downloadable data after 3; Gradle splits its six retention categories on "can be recreated locally or downloaded from a remote repository" (7 days versus 30); Go trims a build cache that is pure derivation but does not trim the module cache; git prunes only *unreachable* objects; journald auto-removes only *archived* files. Not one automatic cleaner in the corpus deletes an unreconstructible primary record. The tools that hold unreconstructible records — restic, borg — require an explicit command every time. A whylog is unreconstructible by construction, and front 7 made half of it a record of *intent* that no later run can re-derive. So the lean is right for this store and wrong as a claim about tool shape, and it should be re-grounded on reconstructibility.
- **The concrete harm case exists and is recent.** A detached background `git gc`, spawned by one command, mutated the shallow file under a *later* command in the same job, producing `fatal: shallow file has changed since we read it`. The most-used checkout automation on GitHub has set `gc.auto=0` for years to prevent exactly this — and that opt-out silently stopped working in git 2.54.0 when the default maintenance strategy was renamed from `gc` to `geometric`. **An opt-out a version bump can silently invalidate is not an opt-out.**
- **If an automatic mode is ever added, the corpus prescribes its exact shape, and every element is a scar.** Throttle on a persisted stamp written *before* the work (Go had to move the write earlier to stop concurrent CI invocations all trimming at once, issue #76314); take an exclusive lock and *silently skip* if it cannot be had (cargo); never detach; grace period longer than the worst-case timestamp slop (Go subtracts an extra hour to cover its own mtime imprecision); and suppress cleaning entirely when the tool is in a degraded mode (cargo disables GC under `--offline`, because you may need what you would delete). Three tools independently converged on a ~24-hour throttle.
- **Cleaning at the *start* of a run is the worst of the three options and should be ruled out outright.** It delays what the operator asked for, it runs before the run's own record exists, and under front 7's ordering it would run before the pre-mutation publication — so a cleaner that fails or fills the disk can abort a run the operator wanted. Go cleans in `Close()` at process exit; Gradle without a daemon cleans "in the foreground after the build session". Both chose the end.
- **Grace periods are not an optimisation; under an undetectable concurrent sibling they are the entire mechanism, and git says candidly that they are not sufficient.** Git keeps any object newer than two weeks and admits the mitigations "fall short of a complete solution, so users who run commands concurrently have to live with some risk of corruption (which seems to be low in practice)". Go states the same thing as an *interface invariant*: "a cache trim from one process should not delete an OutputID from disk that was recently Get or Put from another process. As a rule of thumb, don't trim things used in the last day."
- **Our grace must exceed the longest plausible run, not the longest plausible pause.** A decision document published at t and its outcome at t+45min means any grace shorter than a long multi-host run can delete a decision whose outcome is about to be written. This is a Dorc-specific number that no prior-art constant covers.
- **A retention policy is an attack surface, and count-shaped policies are the vulnerable ones.** Restic documents the attack in its own manual: against an append-only repository, an adversary who can only *add* snapshots injects one decoy per retention window, and the next honest `forget --keep-weekly 3` deletes every legitimate snapshot. Their prescribed mitigation is to use duration-shaped selectors (`--keep-within`) rather than count-shaped ones. Dorc's threat model already concedes host-influenced record bytes; "keep the last N runs" hands a compromised host a way to push the incriminating run out of the store.
- **Deleting records does not give back the enumeration cost.** Directory compaction on the ext family is an offline `e2fsck -D` pass on an unmounted filesystem; online unlinking never shrinks the directory. So a big flat store is paid for permanently once incurred, and retention cannot undo it. Go's answer is to pre-shard: `Open` eagerly creates all 256 subdirectories before storing anything.
- **Enumerate first, then delete — never interleave.** Go reads all names from a subdirectory and closes it before removing anything, "in case removing files invalidates the file offset in the directory scan", and only removes entries whose names match the expected suffixes, leaving anything it does not recognise alone.
- **Judge age from a timestamp that survives ownership and permission churn.** Salt had to switch its cleaner from ctime to mtime because a package upgrade's `chown -R` over the cache reset ctime on every entry, making pre-upgrade jobs look freshly created and blocking cleanup entirely (#68351). File-sync and restore-from-backup do the same thing to timestamps.
- **The abandonment case is squarely about the working directory, not about forensic value.** The accepted Ansible proposal names four killers verbatim: directory-listing noise, shell-completion interference in the working directory, the version-control ignore burden "which may not always be remembered until after a commit has been performed", and a feature whose usage "may not be widely know". All four are properties of writing into the cwd. None apply to a per-user state directory. There is a fifth killer Ansible did not hit: **being deletable by somebody else's policy**.
- **There is a specified home for this store and it is neither config, nor data, nor cache.** `$XDG_STATE_HOME` (v0.8, 2021) exists for "state data that should persist between (application) restarts, but that is not important or portable enough to the user that it should be stored in `$XDG_DATA_HOME`", explicitly including "actions history (logs, history, recently used files, …)". That is a description of the whylog store. The cache directory is defined as "non-essential", which licenses anyone to delete it; the runtime directory is defined as subject to periodic clean-up with a documented six-hourly keepalive to survive it.
- **Handing cleanup to a generic reaper is a real option on exactly one of three platforms, and it has teeth.** `systemd-tmpfiles` has a per-user drop-in path and a user timer, respects BSD locks when removing, has `--dry-run`, and refuses `--purge` without an explicit config file "for safety reasons". It also deleted a long-running program's lock files after ten days, breaking its locking semantics (a new lock file is a different inode, so mutual exclusion silently fails); upstream closed that as working-as-intended in under two hours. A generic reaper does not know your invariants and cannot be told them.
- **"Off" cannot mean "creates nothing" when the identity has a second consumer — and today ours does not.** Salt's `prep_jid` creates the per-job directory with `makedirs` and treats failure as "someone else is using it, get a new jid"; with `nocache` set it *still* creates the directory and writes a marker file inside it. That is load-bearing because the job identity is spoken to minions. Dorc's document token, today, protects only the store's own namespace — so if nothing is written there is no namespace to protect and "record nothing" can mean "create nothing". That stops being true the instant the identity crosses a wire, which is front 9's decision.
- **Incomplete is a report class, not a retention class, and the corpus leans hard toward keeping orphans longer rather than shorter.** Restic's checker reports leftovers of an interrupted run as an anomaly and immediately classifies them "uncritical", leaving them until an explicit prune; and the leftovers of a crashed backup are *load-bearing for resuming it*. Journald renames a corrupted or uncleanly-closed file to a `~` suffix and starts a new one rather than deleting. Salt is the counter-pole: it deletes incomplete entries with no age check at all, and had to add a timestamp check at the outer level after racing its own writer (#29286).
- **Key deletion as retention: NIST recognises it and then rules us out on two preconditions, in its own words.** Cryptographic erase requires that no sensitive data was ever stored on the medium in plaintext (our plain-projection fallback writes exactly that, into the same store), and "should not be trusted on ISM that have been backed up or escrowed unless the organization has a high level of confidence regarding how and where the keys were stored and managed outside of the ISM" (our key is a file in the per-user config directory, i.e. in every backup and every dotfile-sync). The recommended key-sanitization technique is zeroization and *all copies* must be sanitizable — which front 5 already established we cannot do.
- **NIST also settles the deletion-audit question in passing**: a sanitization record must state, among ten items, "how the ISM handles error conditions that prevent the CE operation from fully completing … determine whether the CE operation can report success or failure to the user". A deletion record that cannot say whether the deletion completed is not a record.
- **Readability and security are NOT in tension for sharding, for a deletion ledger, for duration-shaped selectors, for refusing an empty policy, or for choosing the state directory.** Every one of those is strictly better on both axes. They ARE in tension for retaining orphan decision documents indefinitely, which is simultaneously the highest-value firefighting artifact and the most adversary-useful class in the store.
- **The counter-thesis's sharpest form is internal, not borrowed.** Under front 7, a failed pre-mutation publication fails the run. A store that fills the disk therefore stops the operator from operating. Unbounded growth is not untidiness; it is a mechanism by which the record-keeping subsystem takes the tool offline.
- **The counter-counter is that believed retention can be worse than none.** Deletion does not reclaim enumeration cost, does not reach backups (the regulator says so explicitly), does not reach sync clients, and does not obliterate the medium. An operator who believes "I set retention to fifteen days" is *more* misled than one who knows nothing is deleted.

### Delegating cleanup to the platform: the offer and the price

### Keeping the store out of backups and indexes — and why not to

> [A-cachedir-tag-specification-2019]:§The Problem (relevance: -0:SUSPECT)
> The contents of a cache directory tends to change frequently even when the user is merely browsing or viewing files, which confuses incremental backup or synchronization software into seeing many frequent "false changes" in the directory tree
> The files in a cache directory are often named very cryptically … Seeing thousands of such meaningless filenames scroll past during operations that traverse a user's home directory is annoying at best, and may confuse or frighten inexperienced users.

> [A-cachedir-tag-specification-2019]:§Application Semantics (relevance: +1:SURE)
> System software should not, however, just periodically go through and unilaterally delete "old" files in arbitrary cache directories on a purely automatic basis. Different applications need to be able to manage their caches differently; cached data that is considered "old" to one application or to the system might not be considered "old" to another (e.g., if certain data takes a long time to regenerate).

> [A-cachedir-tag-specification-2019]:§Security Considerations (relevance: +1:SURE)
> "Blind" use of cache directory tags in automatic system backups could potentially increase the damage that intruders or malware could cause to a system. A user or system administrator might be substantially less likely to notice the malicious insertion of a CACHDIR.TAG into an important directory than the outright deletion of that directory, for example, causing the contents of that directory to be omitted from regular backups.

### Retention as a duty, and the limits of discharging it

> [A-ico-storage-limitation-principle-2026]:§How should we set retention periods? (relevance: +1:SURE)
> You should consider your stated purposes for processing the personal data. You can keep it as long as one of those purposes still applies, but you should not keep data indefinitely 'just in case', or if there is only a small possibility that you will use it.

> [A-ico-storage-limitation-principle-2026]:§What should we do with personal data that we no longer need? (relevance: +1:SURE)
> The word 'deletion' can mean different things in relation to electronic data, and we recognise it is not always possible to delete or erase all traces of the data. > [A-ico-storage-limitation-principle-2026]:§What should we do with personal data that we no longer need? (relevance: +1:SURE)

> [A-ico-storage-limitation-principle-2026]:§When should we review our retention? (relevance: -0:SUSPECT)

### Key deletion as a retention mechanism

> [A-nist-cryptographic-erase-preconditions-2025]:p.13 §3.2.2 Applicability of CE (relevance: +1:SURE)
> As a pre-condition for using CE, ISO/IEC 27040 [15] specifies that no sensitive data has previously been stored on the ISM in plaintext form (i.e., not encrypted) as CE can only sanitize keys related to encrypted data. Sanitizing sensitive data stored as plaintext requires the use of other storage sanitization techniques that are appropriate for the ISM.

> [A-nist-cryptographic-erase-preconditions-2025]:p.13 §3.2.2 (relevance: +1:SURE)
> Sanitization using CE should not be trusted on ISM that have been backed up or escrowed unless the organization has a high level of confidence regarding how and where the keys were stored and managed outside of the ISM. Such backed up or escrowed copies of data, credentials, or keys should be subject to a separate ISM sanitization policy.

> [A-nist-cryptographic-erase-preconditions-2025]:p.13 §3.2.2 (relevance: -0:SUSPECT)
> Some sensitive information can be long-lived, and confidentiality protections need to span decades. In such cases, future recovery of the data can be a concern because the data still resides in the ISM as ciphertext. If cryptographic weaknesses in the algorithms used in those ISM were found in the future or computational capabilities (e.g., quantum computing) made it feasible to recover keys, the sensitive data can become recoverable in those ISM. For such situations, CE may not be an acceptable sanitization technique.

> [A-nist-cryptographic-erase-preconditions-2025]:p.14 §3.2.3 Sanitization of Keys (relevance: +1:SURE)
> The recommended key sanitization technique is zeroization, as described in ISO/IEC 19790 [14] (e.g., overwriting with all zeros, all ones, or random data), of the target cryptographic keys. ISO/IEC 27040 [15] further specifies that all copies of the target cryptographic keys must be able to be sanitized.

> [A-nist-cryptographic-erase-preconditions-2025]:p.15 §3.2.3 (relevance: +1:SURE)
> When deciding whether to rely on CE, ISO/IEC 27040 [15] recommends considering whether the target cryptographic keys can be recovered internally or externally (e.g., injected from a key management server or from a key escrow service). If the target cryptographic keys (or any key at or below the level of key sanitized during CE) exists outside of the ISM, there is a possibility that the key can be used in the future to recover encrypted data stored on the ISM.

> [A-nist-cryptographic-erase-preconditions-2025]:p.16 §3.2.5 Traceability of CE Operations (relevance: +1:SURE)
> 9. **Error condition handling.** Identify how the ISM handles error conditions that prevent the CE operation from fully completing, such as a defect encountered where an instance of the key to be sanitized is stored. For example, if the location where the key was stored cannot be sanitized, determine whether the CE operation can report success or failure to the user.

## Answers to the seven inherited questions

1. **`ask-orphan-decision-retention`** — Incomplete is a *report* class, not a *retention* class, and orphans should be retained **longer** than complete pairs, not shorter. A decision document with no outcome is not damaged: it is the correct, expected, and highest-value artifact of a run that was killed mid-flight, and it is the only thing that will tell a firefighter which hosts were about to be touched. The earlier ruling that no unavailability cause may authorise deleting an existing document is about *unreadability* and does not reach this case, but the reconstructibility rule does: an orphan is the least reconstructible document in the store. Clearing may remove one only when the operator's own age selector matched it and it is outside the grace period — never as a distinct "tidy up incompletes" action. Salt does have that distinct action, and it is the one place in the corpus where a cleaner races its own writer.

2. **`ask-pair-deletion-atomicity`** — Neither deletion order is truthful, so ordering alone cannot answer this. Delete-outcome-first leaves "decision with no outcome", which falsely says the run was killed. Delete-decision-first leaves "outcome with no decision", which falsely says someone removed the intent record — the scarier lie. The resolution is that **a clearing operation must publish its own record before it unlinks anything**: an append-only deletion-ledger document, published by the same exclusive-create rule, naming the per-document random tokens removed, the count, and the wall-clock, and *nothing* from the opaque-value-capable set. The reader then joins against the ledger and reports "this decision's outcome was cleared on <date>" instead of manufacturing a damage claim. This is front 7's own write-ahead conclusion applied recursively to the cleaner; it converts a manufactured-damage class into a report class, it discharges the deletion-audit half of the glue mandate, and the carried-in random token is exactly the speakable handle it needs. With the ledger in place, order is secondary; prefer outcome-then-decision, matching git's loose-objects rule of deleting first the copy whose absence a concurrent reader can still resolve.

3. **`ask-doubled-store-growth`** — Re-price at two documents per invocation minimum, three where a clearing happens, and more if the engine re-decides mid-run (front 7 left that open). The absolute numbers are unthreatening — a busy operator generates low tens of thousands of files a year — but the shape matters, because deletion never gives back enumeration cost on the ext family and probably not elsewhere. **Shard from day one, by date prefix.** Date sharding is the rare choice that is better on every axis at once: it bounds any single directory read, it makes an age-based selector a directory-level operation instead of a stat per file, it keeps the human-readable-name lean intact, and it needs no hash. Go's answer (256 hash shards created eagerly at open) is the same move without the readability. The front-5 enumeration bound now applies per shard rather than per store. New small cost to name: the shard tree is a calendar of when the operator worked, though names and modification times already leaked that.

4. **`ask-unmanaged-home-abandonment`** — All four of Ansible's killers are properties of writing into the *current working directory*; none survive the move to a per-user state directory. Use `$XDG_STATE_HOME/dorc/` at 0700 (`%LOCALAPPDATA%\dorc\` on Windows; on macOS there is no state-home convention, so `~/Library/Application Support/dorc/` — noting it is backed up by default where `~/Library/Logs` is not, which is a deliberate choice rather than a detail). Never the working directory. Never the cache directory, whose specification defines its contents as non-essential and thereby licenses anyone to delete them. Never the temporary or runtime directories, both of which are actively reaped by someone else's policy. Do **not** write `CACHEDIR.TAG`: the store is not a cache, the tag would drop it out of backups, and the tag is attacker-plantable. Do document the tag as the operator's one-line lever if *they* decide the store should not be backed up — that is the correct control for the names-propagation leak, and it belongs to them, not to us. The fifth killer Ansible did not encounter, and the one that decides whether the feature survives, is being deletable by a policy the tool does not control.

5. **`ask-irreducible-identity-artifact`** — Confirmed in the shipped source, and it does **not** transfer to us as things stand. Salt creates the identity directory by exclusive-create and, with caching off, still creates it and drops a marker file inside; that is load-bearing because the job identity is spoken to minions, so two concurrent jobs must not share one. Dorc's document token today protects only the store's own namespace: if nothing is written, there is no namespace to protect, so "record nothing" *can* mean "creates nothing". It stops being able to mean that the moment the identity crosses a wire — an idempotency guard, a multi-host cache key, a saved approval — which is front 9's decision, and this is now a priced cost of that decision rather than a free reuse. Separately: under front 7's ordering, a record-nothing mode also surrenders the one guarantee write-ahead buys, so it is a safety posture rather than a verbosity knob and must be spelled as loudly as a force flag.

6. **`ask-when-a-oneshot-cleans`** — At the **end**, after the last mutation and after the outcome document is published, and only when explicitly asked. Start-of-run is ruled out: it delays the thing the operator wanted, it runs before the run's own record exists, and under front 7 it would run before the pre-mutation publication, so a cleaner that fails or consumes the disk can abort a run the operator asked for. Never detach. If an automatic mode is ever added over the top, the corpus prescribes the whole shape and every element of it is somebody's scar: a persisted stamp written *before* the work; an exclusive lock with a silent skip when it cannot be had; a grace period exceeding the worst-case timestamp slop *and* the longest plausible run, which for a multi-host Dorc invocation is tens of minutes rather than seconds; suppression whenever the tool is in a degraded mode; and judgement of age from modification time, never change time.

7. **`ask-reader-refusal-versus-retention`** — A **read** rule, not a retention rule, wired to the retention owner by the ledger from question 2. The reader renders an orphan decision as a decision, plainly labelled as having no recorded outcome, and refuses at first class to synthesize any claim about what happened — but it must **not** call it a damage report. An orphan is not damage; damage (truncation, wrong key, failed tag) already has its own vocabulary, and conflating the two would train operators to ignore the one document that says a run died mid-flight. Journald's rename-rather-than-delete is the pattern to copy; the tool that deletes its own journal because incomplete is worse than nothing is the anti-pattern, and its own author flagged it in a comment.

## The best-effort boundary

**Our responsibility ends where the effect of our deletion stops being observable to us.** Five things sit past that line, and the documentation has to name all five in plain words:

1. **Backups.** The regulator states outright that deleting from the live system does not discharge the duty while a backup holds a copy; NIST says cryptographic erase "should not be trusted" on media that have been backed up or escrowed.
2. **File-sync clients and roaming profiles.** The store will be replicated, versioned, and trashed by software that keeps its own history. This is not hypothetical for the first users.
3. **Names that have already left.** Indexers, shell completion caches, backup catalogues — front 6's finding, unchanged by anything here.
4. **The medium.** No platform obliterates on unlink (front 5). Unlink is our ceiling and we must never imply otherwise.
5. **Copies the operator made** — most obviously a whylog handed to a vendor for debugging.

On our side of the line we owe them: a store in a location nobody else reaps; a retention *vocabulary* rich enough that they never have to hand-roll a find-and-delete pipeline (duration-shaped selectors, a dry run, a refusal of both the empty and the total policy, a printed count before acting); deletion of whole pairs with a ledger entry that makes every crash-state explicable; and a report of exactly what could not be removed and why.

**Where it becomes irresponsible to continue is where the mechanism's guarantee would be weaker than the word attached to it.** That rules out three specific things, and this is the line worth welding:

- No content-overwriting-before-unlink. Copy-on-write filesystems and flash translation layers defeat it, it costs writes, and it is a lie.
- Key deletion may be offered as an opt-in retention policy but may never be described as erasure — NIST's own preconditions fail for us on two counts, and the plain-projection fallback is one of them, since it writes plaintext into the same store the key was supposed to protect.
- No secure-delete, shred, or purge flag. It cannot mean what a reader will take it to mean. The honest verb is "remove from this store".

The teaching-versus-footgun test follows from the same line: it is safe to teach the operator anything whose failure mode they can see (an exclusion rule in their own backup tool, a cache-directory tag, a scheduled clearing under their own scheduler). It is not safe to hand them a generic age-based reaper pointed at the store, because such a reaper cannot see pairs, cannot see in-flight runs, and — as the systemd case shows — deletes the file a running process depends on and is not considered wrong for doing so.
