# turn 10 — 2026-08-23

Front: `front-selection`. Which actual packages, crates and libraries to depend on, ranked
against the assembled shopping list, with seams counted. Run last by design; consumed front 1's
turn file (the shopping-posture front, fenced from every other front) plus all nine principles
fronts at once.

Method note: this front is unusual in that most of its evidence is *executed* rather than read.
Five candidate libraries were downloaded, compiled and run against hand-built byte vectors on the
target platform. Where a finding says "demonstrated", the exact bytes and the exact output are
below.

## Findings

### The largest finding, stated first

- `fnd-the-shopping-list-is-a-specification-that-already-exists`: the encryption half of the
  assembled shopping list is not a set of requirements to shop against. It is, clause for clause, an
  independent rediscovery of **C2SP `chunked-encryption`** ([A-c2sp-chunked-encryption-2026], read in
  full this turn). Derived key, base nonce and commitment from one HKDF-Expand over a per-message
  random salt; per-chunk nonce as base-nonce XOR big-endian counter; **mandatory 32-byte key
  commitment checked before any chunk is decrypted**; short-final-chunk as the end-of-message signal;
  AAD explicitly unused with context bound through the derivation info string; the info string
  encoded as fixed-length prefix, zero-terminated algorithm name, fixed-length salt, one variable
  tail. Nine fronts derived those from first principles. The spec's own Rationale section argues the
  final-chunk-flag point in the same terms front 2 used. Test vectors ship in Wycheproof
  ([B-wycheproof-chunked-encryption-vectors-2026], registered by front 2).
- `fnd-but-nobody-ships-it-in-rust`: the spec lists exactly one implementation, in Go. The only Rust
  implementation that exists is inside a Python extension module
  ([A-pyca-cobblestone-rust-implementation-2026]) — PyO3-bound, OpenSSL-backed, not a crate. There is
  no `cobblestone` or `chunked-encryption` crate on crates.io (checked). **The best-fitting package
  in the space is a specification, not a library.**
- `fnd-the-scheme-is-about-250-lines`: read in full, the pyca implementation's actual algorithm —
  `derive_keys`, `ChunkNonces`, `ChunkCipher`, `ChunkedEncryptor`, `ChunkedDecryptor` — is roughly 250
  lines of ordinary Rust over an AEAD and an HKDF. The rest is Python binding. This is the single
  most important number for the counter-thesis and it cuts the other way too: implementing a
  fully-specified scheme against published negative test vectors is a *different risk category* from
  authoring glue, because there is nothing left to decide.

### Container: verified, and the fork moves

- `fnd-evercbor-is-a-real-buildable-zero-dependency-safe-rust-crate`: the machine-checked-proof
  artefact exists, is current, and builds. `cborrs` v0.1.0 lives at `src/cbor/pulse/det/rust` in the
  EverParse tree ([A-everparse-cbordet-rust-api-2026], [A-everparse-cbor-proof-to-code-map-2026]).
  Edition 2021, **zero dependencies**, no build script, ~5900 lines. Downloaded at a pinned commit and
  built clean on Windows/rustc 1.95 this turn; **compiles under `#![forbid(unsafe_code)]`**, which is
  compiler-proof rather than grep-proof that it contains no `unsafe`.
- `fnd-evercbor-is-effect-free`: its entire `std` surface is `std::slice::from_ref`,
  `std::slice::from_mut`, `std::str::from_utf8`. No filesystem, network, environment, clock, thread or
  randomness; no build script; no proc macro. Under the effect model front 1 adopted
  ([A-zoghbi-auditing-rust-crates-2026]) it is in the third of the ecosystem that "can be accepted
  nearly automatically", and it cannot participate in a supply-chain payload that phones anywhere.
- `fnd-evercbor-is-natively-a-flat-sequence-reader`: `cbor_det_parse(input) -> Option<(item, rest)>`.
  Demonstrated: three concatenated items parsed with exact byte counts; a truncated final unit
  reported as "1 valid unit then damage, 2 bytes left". The design's core reader contract — *N valid
  units then damage at offset X* — is the library's native signature, not something assembled.
- `fnd-evercbor-enforces-the-strict-recognizer-on-decode`: demonstrated, one probe each — rejects
  non-preferred integer encodings (`0x190001` for the value 1), indefinite lengths, duplicate map
  keys, **unsorted map keys**, floats, and invalid UTF-8. Front 3's `fnd-determinism-is-opt-in-in-
  every-real-encoder` and its prescribed remedy of re-encode-and-compare **do not apply to this
  library**; it is the strictly-narrower recognizer that front 3 said we would have to build.
- `fnd-evercbor-borrows-the-exact-wire-bytes`: byte-string payloads are `&'a [u8]` pointing into the
  caller's input (verified by pointer comparison). The SD-JWT rule from front 1 — digest the exact
  serialised bytes, never a re-serialisation — is directly implementable with no copy.
- `fnd-evercbor-carries-111-proved-unreachable-panic-sites`: counted, not estimated —
  110 × `panic!("Incomplete pattern matching")` and one `panic!("Precondition of the function most
  likely violated")` across the two extracted files, plus one `.unwrap()` in the hand-written glue.
  These are Karamel extraction artifacts for F* refinement types Rust cannot express, proved
  unreachable upstream. They are nonetheless literal panic paths in a design whose reader must be
  total, and they will fire a `clippy::panic`-style lint.
- `fnd-ciborium-cannot-read-a-sequence-at-all`: demonstrated. `ciborium::from_reader` over two
  concatenated items returns `Ok(first)` and **silently discards the trailing bytes** — no error, no
  remainder. For the flat-sequence shape this is not a missing feature, it is a silent-truncation
  hazard, and it disqualifies the most-downloaded Rust CBOR crate outright.
- `fnd-ciborium-is-stale`: 0.2.2, last published 2024-01-24, against 55M recent downloads.
- `fnd-coset-inherits-all-of-it`: Google's COSE crate depends on `ciborium ^0.2.1`
  ([B-coset-builds-on-ciborium-2026]). One manifest line eliminates the standards-track structured-
  crypto option in Rust.
- `fnd-edn-is-a-specified-readable-projection-and-explicitly-not-canonical`: the readable text form of
  CBOR is now standards-track with a formal ABNF, comments that can annotate integer protocol keys
  with names, CBOR-sequence support, a media type, and — directly matching this design's omission
  markers — **a standardised elision stand-in with its own tag**
  ([A-ietf-cbor-edn-literals-draft-2025]). And it states plainly that no deterministic representation
  is defined and that round-tripping is not expected. The readable projection of a binary file is
  specified, but it is a *rendering*, and two renderers may disagree.

### Encryption: what is actually purchasable

- `fnd-age-is-the-closest-shipped-package-and-its-spec-matches-the-shopping-list`: read
  [A-c2sp-age-format-spec-2026] in full this turn. Header MAC is HMAC-SHA-256 keyed by
  `HKDF(file key, info="header")` over the whole header including the version line — which is
  simultaneously key commitment for the file key, downgrade protection, and verify-before-decrypt.
  Payload key is `HKDF(file key, salt=nonce, info="payload")`. Chunk nonce is an 11-byte counter plus a
  last-chunk byte. Five separate "MUST check the body length is exactly N bytes before attempting to
  decrypt, to mitigate partitioning oracle attacks". "MUST signal an error if the end of file is
  reached without successfully decrypting a final chunk." An scrypt stanza MUST be the only stanza —
  the at-rest form of front 9's no-weak-mode red line. Canonical base64 required.
- `fnd-age-uses-the-construction-front-2-called-the-trap-and-closes-it-differently`: age uses a final-
  chunk *flag*, which front 2 named the worse option, and closes the ambiguity by forbidding an empty
  final chunk instead. `chunked-encryption` — same author, seven years later — inverts it to a
  mandatory-short final chunk and writes out the reasons. This is a genuine conflict between the
  assembled shopping list and the best-audited *available* implementation, and it resolves in the
  shopping list's favour by the spec author's own later reasoning.
- `fnd-ages-stream-is-seekable-and-does-not-chain`: read [A-age-stream-construction-source-2026].
  `Nonce::set_counter(target_chunk_index)`, `impl Seek for StreamReader`. Nonce is position, not
  history.
- `fnd-but-ages-stream-is-not-usable-under-our-own-key`: `Stream` and `PayloadKey` are `pub(crate)`.
  `pub use primitives::stream` exports the *types* only; the sole public constructors are
  `Encryptor::with_recipients` / `with_user_passphrase` → `wrap_output`. **Taking age means taking the
  whole file format, whole-blob, or nothing.** That is by design and is why its seams are audited; it
  is also why it cannot do per-unit encryption inside a container.
- `fnd-age-costs-128-crates-measured`: `cargo tree` with default features off — **128 unique crate
  names, 138 name+version rows**. Inside them: `fluent`, `fluent-bundle`, `fluent-syntax`,
  `intl-memoizer`, `intl_pluralrules`, `i18n-embed`, `i18n-config`, `rust-embed`, `walkdir`,
  `mime_guess`, `mime`, `same-file`, `basic-toml`, `find-crate`, `parking_lot`, the whole `futures`
  family. A localisation and asset-embedding stack, and two filesystem-walking crates, non-optionally
  inside a cryptographic library ([B-age-crate-dependency-manifest-2026]). Its own manifest carries
  `maintenance = { status = "experimental" }` and its description begins `[BETA]`.
- `fnd-libsodium-secretstream-chains-on-prior-ciphertext-confirmed-from-source`: the criterion-7
  offender is libsodium's `secretstream`, and it is not visible from its documentation. Both
  `_push` and `_pull` end with `XOR_BUF(STATE_INONCE(state), mac, INONCEBYTES)` — the implicit nonce
  for message N+1 is XORed with the Poly1305 tag of message N, and a periodic `rekey` derives a new
  key from the current state ([A-libsodium-secretstream-chaining-source-2026]). Seek and resumption
  are impossible by construction; so is decrypting unit 500 without processing units 1–499. It also
  calls `randombytes_buf` internally (uninterceptable randomness) and `sodium_misuse()` (process
  abort) on a length overflow.
- `fnd-no-maintained-key-committing-aead-ships-in-rust`: the requirement the shopping list marks
  REQUIRED is the one thing nobody sells. `caead` exposes `CtxCommitment` but its repository states
  "experimental implementations ... for research purposes"; `rozbb/kc-aeads` is likewise explicitly
  experimental and last touched 2022; orion's issue asking for CTX has been open since 2023. The two
  routes that give key commitment from maintained code are both *constructions*, not crates:
  age's header HMAC, and `chunked-encryption`'s derived commitment.

### Supply chain: the audited-primitive claim, priced

- `fnd-the-audit-that-everyone-cites-was-five-person-days`: the NCC Group review of `aes-gcm` and
  `chacha20poly1305` was two consultants, five person-days, over two algorithms, in December 2019,
  scoped to an SGX timing-side-channel context ([B-ncc-rustcrypto-aead-audit-announcement-2020]).
  It is a real audit. It is not a warrant.
- `fnd-the-audited-crate-later-shipped-the-exact-failure-this-design-exists-to-avoid`: RUSTSEC-2023-
  0096 / CVE-2023-42811 — `aes-gcm`'s `decrypt_in_place_detached` **returned the plaintext in the
  caller's buffer even when tag verification failed** ([A-rustsec-aesgcm-plaintext-on-tag-failure-
  2023]). Release-before-verify, i.e. EFail's mechanism, inside the audited dependency, three years
  after the clean audit, in the API family a chunked implementation would naturally reach for. The
  advisory also notes AES-GCM-SIV in the *same repository* got it right — an inconsistency within one
  maintained crate family.
- `fnd-min-publish-age-is-now-a-real-accepted-mechanism`: front 1's highest-value control has a name,
  a specification, a default and an override — RFC 3923 `cargo_min_publish_age`, tracking issue
  cargo#17009, default `"0"`, per-registry overrides, `deny` chosen over `fallback` specifically to
  close a yank-then-force-fallback attack ([A-rfc3923-cargo-min-publish-age-2026]). Purchasable today
  as `cargo-cooldown` ([B-cargo-cooldown-shipping-quarantine-2026]).
- `fnd-quarantine-does-not-cover-vendored-code-and-that-is-fine-here`: the RFC states the check "does
  not apply to git or path dependencies" and that vendored sources typically have no publish time. A
  vendored, pinned, zero-dependency, effect-free, build-script-free crate is outside the control's
  reach *because it is outside the attack's reach* — there is no re-publication event to defend
  against once the bytes are in our tree.
- `fnd-age-has-one-advisory-and-it-is-in-a-feature-we-would-not-enable`: RUSTSEC-2024-0433, arbitrary
  binary execution via a plugin name containing a path separator, reachable only through
  `age::plugin::*` under the `plugin` feature flag ([A-rustsec-age-plugin-name-execution-2024]).

### Storage: the human's symlink lean removes the main reason to take a capability crate

- `fnd-follow-then-validate-collapses-the-capability-crate-case`: the strongest reason to depend on
  `cap-std` or `fs_at` is whole-walk no-follow. The human's firmest lean rules that out in favour of
  "follow, then validate what you landed on". Under that guarantee the required operations are
  `File::open` + `metadata()` + `MetadataExt::uid()/mode()` on Unix and an ACL policy on Windows —
  neither of which a capability crate provides. **The storage recommendation is `std` alone.**
- `fnd-capstd-windows-read-dir-panics-verified`: confirmed against current source, not inherited.
  `ReadDirInner::new` opens with `assert_eq!(follow, FollowSymlinks::Yes, "read_dir without following
  symlinks is not implemented yet")`, and `new_unchecked` reconstructs an absolute path via
  `concatenate` then calls `std::fs::read_dir` ([A-capstd-windows-readdir-follow-assert-2026]). The
  failure mode is a *panic*, in a dependency, on Windows — the totality requirement relocated out of
  our reach.
- `fnd-capstd-has-a-windows-cve-and-fsat-is-two-years-stale`: `cap-primitives` RUSTSEC-2024-0445 /
  CVE-2024-51756 (superscript-digit device names, already registered by front 5); `fs_at` 0.2.1, last
  published 2024-07, and it has no `renameat` or `linkat` at all.
- `fnd-the-windows-acl-check-is-provably-unreachable-from-safe-rust`: proved by compilation this turn.
  The official Microsoft `windows` crate declares `pub unsafe fn GetSecurityInfo(...)`; a crate with
  `#![forbid(unsafe_code)]` calling it fails with `error: usage of an 'unsafe' block`. The only safe
  wrapper is `windows-permissions` 0.2.4, published 2021, on `winapi 0.3`, 22 stars
  ([B-windows-permissions-rs-wrappers-2021], registered by front 5). **This is a hard gap with no
  maintained closure**, and it is the one that decides whether a key-file permission check exists on
  Windows at all.

### Two hazards that are properties of *schema-free* decoding, not of formats

- `fnd-duplicate-keys-are-rejected-by-typed-decoding-in-both-families`: demonstrated, correcting
  front 3's `fnd-duplicate-keys-are-a-specification-level-anti-pattern` in one respect. Against a
  `#[derive(Deserialize)]` struct, **both** ciborium and serde_json reject a duplicate key
  (`duplicate field 'ordinal'`); against `Value`, both silently take last-wins. The differential is
  typed-versus-schema-free, not text-versus-binary — the same axis DAG-CBOR's preallocation advisory
  named. This removes duplicate keys as an argument in the container fork.
- `fnd-avoid-maps-entirely-and-eyeball-readable-are-in-direct-conflict-in-text`: in a text container
  the readability *is* the field names, i.e. the maps. Applying front 3's highest-leverage restriction
  to a text format yields `["dec",3,17,"elide",[…]]`, which is not meaningfully more readable than a
  hexdump. In a binary container the restriction costs nothing, because the renderer supplies the
  names — and EDN's comment syntax exists to annotate integer keys with exactly those names.

## The recommendation

Stated plainly, because the round explicitly permits a one-package answer: **there is no one
package.** The honest shape is *two small, unusually clean dependencies and one specification we
implement against published negative vectors*, and the reason is not taste — it is that the
best-fitting artefact in the encryption space ships in Go and the best-fitting artefact in the
container space is not on crates.io.

Seam counting convention: an **authored crypto seam** is a join we write where framing, length,
ordinal, key material or associated data binds two cryptographic or format components. Other joins
are engineering seams and are counted separately, because conflating them is how a seam budget
becomes meaningless.

### Ranked candidates

**1. `cborrs` (EverCBOR deterministic CBOR), vendored at a pinned commit — for the container.**
Authored crypto seams: **0**. Authored recognizer seams: **0** — it *is* the recognizer.
What it removes from our hands: deterministic-encoding enforcement on both sides, duplicate- and
unsorted-key rejection, indefinite-length rejection, float rejection, UTF-8 validation, bounded
constant-stack validation, and the flat-sequence remainder contract. What it costs: a vendored
git-pinned dependency rather than a registry one; 111 proved-unreachable panic sites; a C-flavoured
API with no serde derive; and a `dorc why` renderer we write. What makes it safe to vendor: zero
dependencies, zero unsafe (compiler-verified), zero effects, no build script, Apache-2.0.

**2. C2SP `chunked-encryption` / Cobblestone-256, implemented over `aes-gcm` + `hkdf` + `sha2` —
for the encryption.** Authored crypto seams: **1**, and the spec tells us its shape. Everything else
in the construction is byte-specified: the info string, the salt length, the commitment length and
check order, the nonce XOR, the chunking rule, the truncation rule, the abort conditions, and the
warning not to assume the final encrypted chunk exceeds the tag length. Wycheproof supplies the
negative vectors. The one seam is encoding *our* context tuple — record identity, ordinal, schema
version — into the spec's single variable-length tail, and front 2 already named the known-good
shape (fixed-width fields, then one variable tail).
Honest risk, and it is real: this is machine-written cryptographic code, which is the exact thing the
posture ruling exists to avoid. The mitigations available are that the scheme is ~250 lines, fully
specified, has published negative vectors, has two independent implementations to differential-test
against (Go and pyca), and — critically — that RUSTSEC-2023-0096 shows the alternative is not
risk-free either.

**3. `age` 0.12 whole-blob — the zero-crypto-seam alternative, if the 128 crates are acceptable.**
Authored crypto seams: **0** for the encryption itself; **1** reappears as the digest binding between
the plaintext skeleton and the age blob (front 1's `turn01:rec-split-commit-and-blob`), so the seam
count does not actually improve — it relocates from an info string to a digest binding, which is the
easier of the two to get right. Take this if the judgement is that no amount of specification makes
machine-written cryptographic code acceptable. Its cost is the graph, the `[BETA]`/`experimental`
labels, whole-blob-only granularity, and an uninterceptable CSPRNG draw per file.

**4. `std` alone — for the storage.** Authored seams: **0** for publication. `create_new(true)`,
`File::sync_all`, `read_dir`, `metadata`, `OpenOptionsExt::custom_flags`. The human's follow-then-
validate lean removes the case for `cap-std` or `fs_at`, and both carry costs we would be paying for
a guarantee we are not buying.

**5. Supply-chain practice.** `cargo-cooldown` now, `registry.global-min-publish-age` when RFC 3923
lands; committed lockfile; `cargo-deny` in CI; diff review on upgrade; and the front-1 rule that
build scripts and proc macros are the actual attack surface — note that every crate in the
recommended set has neither.

### Rejected, with the deciding evidence

- `ciborium` — silently discards trailing bytes after the first item, so it cannot read a sequence;
  coerces byte strings and arrays into each other in both directions; accepts non-preferred integer
  encodings; stale since 2024-01.
- `coset` — depends on `ciborium ^0.2.1`.
- `cbor2` — has the right features (canonical encoder, `RawValue`, `validate`) and 8 305 lifetime
  downloads under one small organisation. Front 1's exact warning about `rops`: a mature design
  wrapped around thin maintenance is the worst of both.
- `minicbor` — genuinely good as the registry-available fallback: 1 crate, zero dependencies, current,
  no advisories, `Decoder::position` supports sequences, ships diagnostic-notation display. But
  determinism and strictness are both ours to enforce, which is exactly the work `cborrs` does for us.
  **This is the fallback if vendoring EverCBOR is refused.**
- `libsodium` / `dryoc` secretstream — chains on prior ciphertext; uninterceptable randomness;
  process-abort on misuse.
- `rusqlite` / SQLite — see below.
- `redb` — pure Rust, zero dependencies, maintained, but it is a mutable database with no stated
  posture on files of uncertain provenance, and it fights immutability exactly as SQLite does
  ([B-redb-status-and-dependency-posture-2026]).

### Total for the recommended set

**One authored cryptographic seam.** Two runtime dependencies for the artifact itself (`cborrs`
vendored; `aes-gcm`+`hkdf`+`sha2`, measured at 15 crates counting all three), plus `std`.

## The container fork, closed

**It closes toward binary — and not for the reason the principles work anticipated.**

The fork was framed as eyeball readability against exact-binary handling and proven determinism.
Having read the implementations, both sides of that framing are wrong in the same direction.

The security side is *larger* than framed. `cborrs` does not merely have a determinism proof. It is a
shipped strict recognizer that enforces, on decode, every restriction the shopping list demands —
preferred encodings, definite lengths, sorted keys, no duplicates, no floats, valid UTF-8 — with zero
dependencies, zero unsafe, zero effects, and a native `(item, remainder)` sequence contract. No text
stack offers any of that; with `serde_json` the encoder-side determinism burden and the recognizer
burden both land on us, which is the LangSec hazard relocated rather than removed.

The readability side is *smaller* than framed, for three reasons the principles work could not have
seen without the code:
1. **The skeleton's alphabet is closed.** By the design's own shape-based classification, the
   plaintext skeleton contains record names, type tags, bounded counts, enums, stable numeric
   identities, digests and omission markers — and no arbitrary text at all. A closed alphabet renders
   losslessly. There is nothing for a renderer to distort.
2. **The leaves are unreadable in either format.** Ciphertext in a text container is base64. An
   operator inspecting a text whylog before handing it to a vendor sees structure plus opaque blobs —
   which is precisely what an EDN rendering of a binary whylog shows them.
3. **The tool must be trusted either way.** The operator cannot evaluate a base64 blob by eye. The
   assurance they actually want is "show me what is in here that I would not want to send", and the
   design already has a purpose-built answer: the plain projection, which by construction *cannot
   represent* opaque-value-capable fields. `dorc why --plain <file>` is a better pre-disclosure
   inspection than `less` on a rich text file, because the thing it shows is the thing that is safe to
   show.

**Three conditions on that closure, and they are not optional.**
- A text rendering must be a first-class, single-command, always-available output. Front 3 observed
  that every binary format in its survey ended up shipping a text projection; ours must ship on day
  one, not be retrofitted.
- The rendering follows EDN rather than being invented, including its elision stand-in for omission
  markers — but our renderer is normative for *us*, because EDN deliberately defines no canonical form
  and promises no round-trip ([A-ietf-cbor-edn-literals-draft-2025] §1.3.2). A rendering is a
  rendering; it must never be presented as the document.
- RFC 9277's labeled-CBOR-sequence framing should be adopted so that a hexdump shows the ASCII
  characters "CBOR" and the first bytes are deterministic. It is nearly free and it is the only
  readability a binary file offers to someone with no tool at all.

**Where this points somewhere the principles work did not anticipate.** Front 3's highest-leverage
restriction, "avoid maps entirely", is *incompatible with a readable text container* — in text, the
readability is the field names. That restriction and the eyeball-readability requirement cannot both
be satisfied in a text format. They can both be satisfied in binary, because the names live in the
renderer and in the CDDL, and EDN's comment syntax exists to put them back. The fork was presented as
a two-way trade; it is really a place where one branch fails a requirement the other branch does not.

**What would reopen it.** A ruling that the operator must be able to inspect the file with tools they
already have, on a machine where `dorc` is not installed. That is a coherent product requirement, it
is not the one stated, and if it is adopted the answer flips to `minicbor`-shaped-but-in-text — a
JSON text sequence read through `serde_json::StreamDeserializer` with typed structs, which
demonstrably gives the same "N valid units then damage at line/col" contract, at the price of
authoring the determinism and the recognizer ourselves.

## The two verification results

### 1. The machine-checked-proof result — CONFIRMED, and stronger than reported

The paper is real, current, and maintained; the artefact exists, extracts to safe Rust, and builds.
[A-ramananandro-evercbor-evercddl-2025] maps to [A-everparse-cbor-proof-to-code-map-2026], which maps
each theorem to a named F* file. Every path it names exists in the live tree at the pinned commit.

- **Exists**: `src/cbor/pulse/det/rust`, crate `cborrs` v0.1.0, four files.
- **Maintained**: EverParse released 2026-08-21, five releases in 2026; the Rust snapshot has been
  regenerated seven times in 2026, most recently 2026-07-31; CI builds and tests it every push.
- **Builds**: verified on Windows/rustc 1.95, clean, zero dependencies, and clean under
  `#![forbid(unsafe_code)]`.
- **What it extracts**: a *deterministic-CBOR-only* validator, parser, serializer and comparator —
  RFC 8949 §4.2.1 minus floats — with constant-stack shallow parse, no heap allocation, borrowed
  payloads, and a `(item, remainder)` parse signature. Not general CBOR: the non-deterministic
  fragment is a separate crate (`cborrs-nondet`) which we would not use.
- **Could we depend on it**: yes, by vendoring the four files at a pinned commit. Not by crates.io —
  it is not published, and there is no `evercbor` crate.
- **The one thing to weigh against it**: 111 proved-unreachable panic sites, and an `.unwrap()` in the
  file the maintainer himself labels "handwritten unverified glue code".
- **Additionally**: EverCDDL generates verified parsers and serializers *per CDDL rule* and can
  mechanically prove two rules over one grammar disjoint — which is the machine-checked version of the
  rich/plain projection separation. Not evaluated further; see "not pursued".

### 2. The decoder-coercion behaviour — CONFIRMED, and broader than claimed

The claim was that one Rust decoder coerces an array where bytes are expected. Read against
[A-ciborium-deserializer-source-2026] and then executed:

The coercion is **bidirectional**. `deserialize_bytes` and `deserialize_byte_buf` both accept
`Header::Array(len)` and hand the visitor a seq; `deserialize_seq` accepts `Header::Bytes(len)` and
hands the visitor a seq via `BytesAccess`. Demonstrated with the exact bytes:

    a2 676f7264696e616c 01 626374 42 aabb          (16 bytes; ct as a byte string)
    a2 676f7264696e616c 01 626374 82 18aa 18bb      (18 bytes; ct as an array of two uints)

Both decode to the identical Rust value `(ordinal: 1, ct: aabb)`. Two distinct byte sequences, two
distinct lengths, one value — so a digest over the wire bytes differs while the decoded value does
not. **The broader claim it was cited for is upheld**: off-the-shelf decoders do not give you
deterministic encoding, and a re-encode-and-compare check is the only remedy *for that decoder*.

Two further ciborium behaviours found while verifying, both executed:
- 1000 nested unknown tags followed by `42` decodes to `Ok(42)` — 3002 bytes carrying 2 bytes of
  payload, tags silently discarded. Unknown-item retention is broken for tags, and it is a
  data-smuggling channel of exactly the RFC 7464 §3 kind.
- A non-preferred integer encoding (`19 0001`, the value 1 in two bytes) is accepted silently.

And one correction to an inherited finding: front 3's "neither ciborium nor cbor2 rejects duplicates
by default" is true for `Value` decoding and **false for typed decoding** — ciborium returns
`Semantic(None, "duplicate field 'ordinal'")` against a derived struct, as does serde_json.

## The single-package counter-candidate, evaluated

**SQLite via `rusqlite`. It loses, and the deciding evidence is its own documentation.**

It genuinely is the maximal seam reduction on offer. It absorbs atomic publication, crash
consistency, cross-process concurrency, enumeration, directory synchronisation and filename identity
into one dependency; it names our chosen shape, "pile-of-files", as the thing it improves on; it is
the most-tested software in the world with a published crash- and I/O-fault-injection methodology
[A-sqlite-how-tested-crash-io-2026]; and its VFS indirection is a thirty-year-old precedent for the
injected-seam requirement. Nine crates measured, which is fewer than `cap-std`.

Against it, in descending order of weight:

1. **It destroys the product requirement that motivated the whole design.** Whole-file encryption was
   rejected because eyeball-readability of the structure is the debugging product. SQLite's own page
   says "command-line tools such as text editors or 'grep' or 'awk' are not useful on an SQLite
   database" [A-sqlite-as-application-file-format-2026]. It fails the readability test on the
   *plaintext* skeleton, which not even whole-file encryption does.
2. **It relocates seams rather than removing them, and the relocated ones are silent.** Reading a
   file of uncertain provenance safely takes roughly fifteen configuration decisions — trusted-schema
   off, eleven limits, `integrity_check` first, `cell_size_check` on, mmap off, a heap limit
   [A-sqlite-untrusted-input-defense-2026]. That configuration is glue we author, in a domain where
   getting it wrong is silent.
3. **It does not close the Windows gaps; it hides them.** Front 5 read `winSync` and found it is
   `FlushFileBuffers` and nothing more — SQLite has no Windows directory-synchronisation step either
   [A-sqlite-os-win-vfs-2026]. Taking SQLite converts "we cannot do this on Windows" into "somebody
   else also cannot, invisibly".
4. **It fights immutability head-on, and immutability is where our atomicity comes from.**
   Create-exclusively-under-the-final-name is simultaneously the atomicity mechanism, the concurrency
   mechanism, the collision defence and the simplest code. SQLite replaces one primitive with a
   journal, a lock hierarchy and a mutable file.
5. **It converts N independent small failures into one large one.** A corrupt pile-of-files store
   loses one whylog. A corrupt database loses the archive — for an artifact whose entire purpose is
   being available after something went wrong.
6. **It re-introduces a foreign-language memory-safety surface**, with a materialised instance:
   RUSTSEC-2022-0090 / CVE-2022-35737 [A-rustsec-libsqlite3-sys-bundled-cve-2022], plus a `cc` build
   script, which front 1 identified as the actual attack surface in both live supply-chain incidents.
7. **It is the wrong shape for what the later fronts decided.** Write-ordering produced two document
   *types* published at two different moments with different failure policies; cleanup produced a
   deletion ledger under the same exclusive-create rule and date-prefix sharding that bounds
   enumeration without an index. Both are natural over files and awkward over one mutable file.

`redb` was evaluated as the pure-Rust version of the same idea — one crate, zero dependencies,
maintained, edition 2024 — and loses on (1), (4), (5) and additionally on having no stated posture at
all toward a file of uncertain provenance.

**A middle path exists and should be refused explicitly**: a SQLite sidecar *index* over immutable
files. It introduces mutable state the design otherwise has none of, and the cleanup front already
showed date-prefix sharding bounds enumeration without one.

## What the recommended set does NOT cover

The number that matters. Twelve seams remain ours.

1. **The context-string encoding** — our tuple into `chunked-encryption`'s variable tail. The only
   authored *cryptographic* seam. Front 2's fixed-width-then-one-variable-tail rule governs it.
2. **The Cobblestone implementation itself** — ~250 lines of machine-written cryptographic code,
   unless age-whole-blob is taken instead.
3. **The whylog schema in deterministic CBOR** — record types, ordinals, terminator unit, and the
   reader that compares claimed ordinal against counted. `cborrs` gives the sequence; the schema is
   ours. (EverCDDL could generate a verified parser from a CDDL model; not evaluated.)
4. **Rich/plain projection disjointness** — front 3 requires two types selected before the first byte,
   irrevocably. `cborrs` does not know about our types.
5. **The damage-model reader policy** — "N valid units then damage" reported as *partial*, never as
   complete. Front 3's own warning: a damage model is inert unless the reader checks it, and a shipped
   format with a purpose-built corruption marker had two readers that never compared it.
6. **The EDN-style renderer** for `dorc why`. Output-only, therefore not security glue, and checkable
   by re-parsing its own output.
7. **Key-file lifecycle** — creation, retain-forever rotation, the salted per-document key tag and its
   trial-match loop, and the two-valued transient/permanent unavailability.
8. **The Windows key-file ACL check** — currently *unreachable*. This is the one gap with no
   maintained closure at all.
9. **Store publication, enumeration, date-prefix sharding, and the deletion ledger** over `std`.
10. **Filename minting** — injective, case-fold- and normalisation-invariant alphabet, bound to the
    document token.
11. **The symlink follow-then-validate policy**, per the human's lean, including the Windows half
    that depends on (8).
12. **The DST seams** — one injected 24-byte salt draw per document, plus clock and filesystem.

Note what is *not* on this list and would have been under a naive assembly: nonce management,
deterministic-encoding enforcement, duplicate-key rejection, bounded decode, key commitment,
truncation detection, and the ordinal.

## Counter-thesis, at full strength

Gathered as hard as the thesis, and parts of it survive.

**"The correct dependency count is far lower than the shopping list implies."** This is largely
*right*, and the recommendation concedes it. Nine fronts produced a shopping list that reads like a
procurement document; the answer is two dependencies and one specification. Front 3's central
prescription — take somebody else's grammar and enforce a narrower recognizer — turned out to be
purchasable as a single 5900-line effect-free file. The encryption half turned out to be 250 lines
against published vectors. Anyone expecting to buy four packages should update.

**"Every package will be a poor fit because the artifact is unusual."** Half right, and the half that
is right is the half that matters. Structured skeleton with encrypted leaves *is* rare, but it is not
unprecedented — sops ships it and has for a decade, and the AWS DB-ESDK is the same idea done later
with published rationale (both from front 1). What is genuinely unshopped is the *combination*:
immutable single-shot receipts, per-user store, three first-class platforms, `forbid(unsafe)`,
deterministic replay, and a plaintext skeleton that is the product. No package targets that, and the
evidence for "no package targets that" is that the closest fit, age, cannot expose its own chunked
construction under our key, and the second closest, DB-ESDK, drags in two network SDKs and three
clock sources.

**"A small amount of our own code over very few very well-understood dependencies."** This is the
recommendation. But it needs its strongest objection stated, because the objection is real: *the
small amount of our own code is cryptographic, and it will be machine-written.* The posture ruling
exists precisely to prevent that. Three things are offered against it, and they should be weighed
rather than accepted:
- The scheme is fully specified to the byte, with published *negative* vectors, and two independent
  implementations to differential-test against. This is closer to implementing SHA-256 from FIPS 180
  than to designing a protocol.
- The alternative is not risk-free. RUSTSEC-2023-0096 shows an audited, maintained, widely-used crate
  shipping release-before-verify — the exact failure — three years after its clean audit.
- Front 1's own measured base rate says the risk lives in application misuse of libraries, not in the
  libraries. But note the honest caveat front 1 recorded: that 83% figure covers forgot-to-encrypt and
  hard-coded keys as well as framing seams, and nobody has quantified the framing share.

**The counter-thesis I could not defeat.** Taking `age` whole is a coherent, defensible answer with
zero authored cryptographic code, and the only arguments against it are a dependency count and a
granularity mismatch — neither of which is a security argument. If the ruling is "no machine-written
cryptographic code, at any cost", the answer is age-whole-blob plus a plaintext `cborrs` skeleton
carrying salted commitments, and the shopping list changes to match. That is a legitimate output of
this round and it should be put to the human as a live choice rather than buried.

## Readability versus security in the available implementations

### Genuinely in tension

- **The renderer is a trust hop.** EDN has no canonical form and no round-trip guarantee by its own
  design ([A-ietf-cbor-edn-literals-draft-2025] §1.3.2). A binary file's readable form is produced by
  software the operator must trust; a text file's readable form is the file. This is the real residual
  cost of choosing binary and it should be stated in the documentation, not argued away.
- **A pre-disclosure inspection that requires our tool is weaker than one that does not.** If the
  vendor hand-off happens from a machine without `dorc`, binary loses outright. Nothing in the
  available implementations changes that.
- **Vendoring versus quarantine.** Vendoring `cborrs` is the right supply-chain move *and* it exits
  the publication-age control's scope ([A-rfc3923-cargo-min-publish-age-2026]). The resolution is that
  a zero-dependency, effect-free, build-script-free vendored blob has no re-publication event to
  quarantine against — but the general shape of the tension is real and worth naming.
- **`cbor2` is the readability-friendliest binary option and the least maintained.** Canonical
  encoder, `RawValue`, diagnostic notation, three crates — and 8 305 lifetime downloads under one
  small organisation. The features point one way and front 1's `rops` warning points the other.

### NOT in tension — the round's easy keeps

Loudly, because the brief asks for it. Every item is good on both axes and several improve
readability.

- **`cborrs`'s strict recognizer.** Rejecting non-preferred encodings, indefinite lengths, duplicate
  keys, unsorted keys and floats makes the format *smaller and more predictable to describe*, which is
  a readability win, and it is the entire deterministic-encoding requirement, which is a security win.
  One dependency, both axes, no trade.
- **"Avoid maps entirely" in a binary container.** Free on the security axis, free on the readability
  axis, because the names live in the renderer. It is only a trade in text.
- **The plain projection as the pre-disclosure inspection.** A type that *cannot represent*
  opaque-value-capable fields is simultaneously the most readable rendering and the safest to hand
  over. Front 7 already reached the same conclusion for the last-ditch stderr dump. Using one
  mechanism for both is a pure win.
- **RFC 9277 labeled framing.** Deterministic first bytes and the ASCII characters "CBOR" visible in a
  hexdump. Costs nothing, buys file-type recognition for a human with no tool.
- **EDN's standardised elision stand-in.** The design already wants omission markers; EDN already has
  one with a registered tag. Adopting it is free and it stops us inventing a notation for "something
  was left out here", which is exactly the kind of invention that trains operators to misread files.
- **`chunked-encryption`'s mandatory commitment check before any chunk decrypts.** Security by
  construction, and it makes the failure message honest — "this key does not open this document" —
  which is the diagnostic the key-lifecycle front wanted.
- **Zero build scripts and zero proc macros across the recommended set.** Both live supply-chain
  incidents in front 1 rode in through build-time execution. Costs nothing, changes nothing a reader
  sees.
- **Typed decoding rather than schema-free.** Demonstrated to close duplicate keys in both formats,
  and it is also what bounds nesting. Free.

## Deliberately not pursued, and why

- **EverCDDL.** It generates verified parsers and serializers per CDDL rule and can mechanically prove
  two rules disjoint — which is precisely the rich/plain projection guarantee, upgraded from
  convention to proof. I confirmed it exists and extracts to Rust but did not evaluate its generated
  output, its build requirements (it needs the F*/Karamel toolchain, unlike the pre-generated CBOR
  snapshot), or whether the generated code is vendorable. **This is the highest-value unexplored
  thread on this front** and it should be a focused pass, not a footnote.
- **Retrieving the NCC Group audit PDF.** The landing page gave the scope, sponsor and effort, which
  is what the argument needed. The findings themselves would not change a decision, since the
  post-audit advisory is the load-bearing datum.
- **`filippo.io/cobblestone`, the Go reference implementation.** Could not locate its source at the
  obvious paths. It matters for differential testing later, not for selection now.
- **Tink-rust, `dryoc`, `orion`, `hpke` as encryption candidates.** Front 1 already disqualified
  Tink-rust (disclaimed as not an official Google product) and the others are primitive collections,
  not constructions — taking them is the hand-assembly the posture ruling exists to prevent.
- **`aead-stream` (RustCrypto's STREAM).** Noted as maintained and current, and it is the right
  *construction* — but it is STREAM without key derivation, key commitment, or a header, so all three
  become authored seams. Strictly dominated by implementing `chunked-encryption`, which specifies all
  three.
- **Whether `cborrs`'s panic sites are reachable in practice.** Answering properly means reading the
  F* proofs, which is a different skill and a different budget. What is recorded is the count, the
  messages, and the fact that they are extraction artifacts.
- **`etcetera` versus `dirs` versus `directories` for the configuration directory.** A one-line
  choice; front 5 already registered the resolution behaviour that matters
  ([B-dirs-sys-config-resolution-2026]) and both `dirs` and `directories` carry 2020 advisories.
- **Cross-platform CI cost of vendoring EverCBOR.** It builds on Windows; macOS and Linux were not
  tried. Zero dependencies and no build script make failure unlikely but it is unverified.
