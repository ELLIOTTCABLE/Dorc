Front: `front-verified-toolchain`. An added, final front authorised off `front-selection`'s
"highest-value unexplored thread": whether the CDDL companion tool can turn the rich/plain

## Findings

### The disjointness answer, stated first

- `fnd-the-invariant-splits-into-two-properties-and-only-one-is-proved`: the design's invariant —
  "no byte sequence valid under rich is valid under plain, *and* plain cannot represent the field
  class at all" — is two independent properties. EverCDDL proves the first and says **nothing**
  about the second. Demonstrated: a schema whose plain rule carries an *optional* ciphertext field
  is accepted as disjoint from rich, because the leading literal still separates them. Disjointness
  is not non-representability, and treating them as one thing is the trap.
- `fnd-disjointness-is-a-verified-decision-procedure-not-a-claim`: the checker's F* contract is
  `RSuccess? r ==> Spec.typ_disjoint (typ_sem ...) (typ_sem ...)`
  ([A-everparse-cddl-elaborator-soundness-contract-2026]), and `typ_disjoint` is defined as
  `forall (l: Cbor.cbor). ~ (a1 l /\ a2 l)` ([A-everparse-cddl-typ-disjoint-definition-2026]). So a
  success verdict is a machine-checked implication, one-directional: **sound, deliberately
  incomplete**, three-valued (`RSuccess` / `RFailure` / `ROutOfFuel`). It refuses rather than
  guesses.
- `fnd-disjointness-is-over-items-not-bytes`: the property quantifies over CBOR *data-model items*,
  not byte sequences. The bridge to bytes is EverCBOR's determinism theorem — deterministic CBOR is
  non-malleable, one item has exactly one encoding ([A-ramananandro-evercbor-evercddl-2025]) — plus
  the fact that EverCDDL supports *only* the deterministic encoding
  ([A-everparse-readme-platform-and-usage-2026]). The chain closes, but it is a chain, and if the
  design ever admits a non-deterministic reader the byte-level statement stops following.
- `fnd-the-checker-cannot-decide-two-maps-at-all`: demonstrated, and visible in the source as a
  literal `| TMap _, TMap _ -> RFailure "typ_disjoint: map: not supported"`
  ([A-everparse-cddl-typ-disjoint-decision-2026]). Two map-shaped projections are **rejected
  outright**. Arrays route to a real `array_group_disjoint` procedure; different tags and different
  element classes are trivially disjoint. **Front 3's "avoid maps entirely" is therefore a
  precondition for the proof being available at all** — a restriction adopted for other reasons
  turns out to be what unlocks this one.
- `fnd-the-second-half-is-a-compile-error-not-a-proof`: EverCDDL generates a Rust struct per rule.
  For a plain rule with no byte-string field the struct is
  `pub struct plain_decision { pub _x1: u64, pub _x2: u64, pub _x3: verdict }` — no lifetime
  parameter, no borrowed bytes, structurally unable to carry an opaque value. Add an optional
  ciphertext and it becomes `pub struct plain_decision <'a> { ... pub _x4: option__..ciphertext<'a> }`.
  The "cannot represent" half is delivered by `rustc`, not by F*.
- `fnd-two-one-line-guards-pin-the-second-half-and-a-third-does-not`: demonstrated by compiling both
  schemas against three candidate guards.
  - `pub type PlainMustNotBorrow = fmt::plain_decision;` → **error[E0106] missing lifetime
    specifier** on the leaky schema, compiles on the clean one. Catches borrowed bytes.
  - `let fmt::plain_decision { _x1: _, _x2: _, _x3: _ } = p;` → **error[E0027] pattern does not
    mention field `_x4`**. Catches *any* field addition, owned or borrowed, and reads as a
    declaration of exactly what plain is permitted to contain. **This is the one to ship.**
  - `static C: Option<fmt::plain_decision> = None;` → compiles in both. Does *not* fire; the
    lifetime is inferred. A plausible-looking guard that silently does nothing.
  Also note the naive form fails: `fn f<T:'static>(){}; f::<plain_decision>()` inside a function
  body compiles for the leaky schema too, because elided lifetimes in bodies are inferred.

### What the tool actually generates, measured

- `fnd-generated-output-is-checked-in-upstream-and-is-dependency-free`: `src/cose/rust/` in the
  EverParse tree holds generated EverCDDL output for the real COSE schema, committed, not
  gitignored. `coseformat.rs` is 963,527 bytes / 18,077 lines. Its entire cross-module surface is
  `crate::cbordetver` (2210 refs), `crate::cbordetveraux` (1545) and a three-line
  `crate::lowstar::ignore` shim (105) ([A-evercddl-generated-cose-rust-2026]). Zero external crates,
  zero `unsafe`, zero `std::`, zero `Vec`, zero `unwrap`. The README confirms the design intent:
  generated Rust "is standalone and does not need a separate installation of EverCBOR"
  ([A-everparse-readme-platform-and-usage-2026]).
- `fnd-generated-output-compiles-under-forbid-unsafe`: demonstrated. The generated trio
  (`coseformat.rs` + `cbordetver.rs` + `cbordetveraux.rs`) builds clean under
  `#![forbid(unsafe_code)]` on Windows / rustc 1.95, 25 warnings, all dead-code or
  function-pointer-comparison. It inherits every clean property front 10 measured for `cborrs`.
- `fnd-generated-output-is-unreviewable-by-construction`: field names are positional (`_x1`, `_x2`,
  `_x3`), enum variants are `Mkwhylog_unit0` / `Mkwhylog_unit1`, and monomorphised type names carry
  U+00B7 MIDDLE DOT characters —
  `option__·COSE_Format_cose_key_okp···Pulse_Lib_Slice_slice·uint8_t·`. Every construction site in
  our code would read `plain_decision { _x1: ordinal, _x2: site_id, _x3: verdict }`.
- `fnd-a-realistic-whylog-schema-costs-about-a-third-of-a-megabyte`: demonstrated end to end. A
  seven-line rich/plain CDDL pair plus the shipped 51-line postlude generates 177,980 bytes /
  5,083 lines / 131 panic sites. Substituting an eight-line hand-trimmed postlude drops that to
  112,473 bytes / 3,069 lines / **69 panic sites**. Add the bundled CBOR runtime (215 KB) and the
  vendored surface is roughly **327 KB of machine-generated Rust**. The postlude is a plain input
  file, so trimming it is free and worth doing; the full one drags in ~30 unused entry points

- `fnd-the-postlude-is-not-optional`: dropping it entirely fails —
  `Failure("solve_names: definition 'ordinal = uint' has not been solved")`. `uint`, `bstr` and
  friends are defined *in* the postlude, not built in.

### What adoption costs

- `fnd-generation-needs-a-proof-toolchain-but-the-build-does-not`: `cddl.exe` parses and elaborates
  in extracted OCaml, then shells out — `fstar.exe <file> --cache_dir ...` to verify, `fstar.exe
  --codegen krml` to extract, then `krml -backend rust` ([A-evercddl-gen-driver-toolchain-2026]).
  Z3 is pinned to `4.13.3`. The shipped Linux release that carries all of this is 281 MB
  compressed, **913 MB unpacked**, containing `bin/{cddl.exe,fstar.exe,krml}`. None of it is needed
  to *build* the generated code — that is one `cargo build` against `std`.
- `fnd-evercddl-does-not-exist-on-windows`: the package matrix says EverCBOR and EverCDDL are
  present on Linux and macOS and **absent on Windows**; building from source on Windows means WSL2
  and yields Linux binaries ([A-everparse-readme-platform-and-usage-2026]). For a project whose
  Windows support is first-class this is a maintainer-workstation constraint, not a user one — but
  it means regeneration cannot happen on one of our three platforms, and a Windows-only contributor
  cannot change the schema.
- `fnd-the-admit-flag-is-a-silent-proof-bypass`: `--admit` passes `--admit_smt_queries true` to F*
  ([A-evercddl-gen-driver-toolchain-2026]). Code generated with it is byte-similar and carries no
  marker. Whoever regenerates can turn the proof off by accident or by impatience, and the diff
  will not say so.
- `fnd-the-churn-cost-is-eighty-seconds-and-an-unreviewable-diff`: demonstrated — full Rust
  generation for the seven-line schema took **1m18s** wall-clock. That is cheap. The expensive part
  is that every field addition produces a six-figure-byte diff in a file no reviewer can read, which
  is precisely what Chromium's policy warns against for minified and obfuscated code
  ([A-chromium-adding-third-party-libraries-2026]).
- `fnd-the-bus-factor-is-one`: of the last 100 commits touching `src/cddl`, **98 are by one person**
  and 2 by a second. Measured, not inferred.

### Vendoring governance

- `fnd-vendoring-has-a-normative-answer-and-it-is-ownership-not-tooling`:
  [A-chromium-adding-third-party-libraries-2026] is enforced policy at the largest scale anyone
  vendors at. Named OWNERS ("two Chromium committers") who are "expected to: remove the dependency
  when/if it is no longer needed; update the dependency when a security or stability bug is fixed
  upstream". A `README.chromium` with `Security Critical` — whose predicate includes "Parses or
  interprets complex input formats", which our decoder trips — plus `Version`/`Revision`,
  `CPEPrefix`, `Shipped`, `License`.
- `fnd-the-quarantine-equivalent-for-vendored-source-is-a-declared-divergence-point`: the round
  adopted publication-age quarantine, and [A-rfc3923-cargo-min-publish-age-2026] already states it
  does not apply to git or path dependencies. Chromium's answer to the same gap is not a mechanism
  but a *disclosure discipline*: "All dependencies MUST provide sufficient metadata to enable
  vulnerability scanning: URL and (Version or Revision) match upstream identifiers; or CPEPrefix and
  Version", with an explicit named exception for `Update Mechanism: Static[.HardFork]`. And for the
  diverged case: "OWNERS should provide a revision/version/cpe which represents the closest point of
  divergence from the upstream. This may return some false positives but ensures coverage is
  optimal." **Nobody has a good answer; the best available answer is to accept false positives and
  declare the divergence point.**
- `fnd-the-day-upstream-moves-has-a-name`: `Static.HardFork` — "Origin is a Git repo or package
  manager, but our version has diverged from the upstream, and is no longer updatable" — and its
  consequence is stated flatly: "*The dependency will be treated as if it's written by Chromium
  Authors.*" That is the governance ruling the front was asked for, and it is one sentence.
- `fnd-the-six-year-datapoint-is-a-hard-fork-nobody-noticed`: the Linux kernel vendored generated
  HACL* Curve25519 in November 2019. Its banner still reads "This is a machine-generated formally
  verified implementation … Though originally machine generated, **it has been tweaked to be
  suitable for use in the kernel**" ([A-linux-vendored-hacl-curve25519-2024]). Complete commit
  history since: two touches, both unrelated tree-wide refactors (a header move in 2024, an integer
  type in 2023). Never resynced, never regenerated. The upstream URL in its own provenance banner
  now 301-redirects to a different organisation. This is `Static.HardFork` observed in the wild, and
  it is what vendoring a research artefact looks like after six years.
- `fnd-verified-code-loses-its-guarantee-when-you-touch-it`: stated by the maintainer —
  "Code that is verified may lose its guarantees when it is modified, so we run formal verification
  as part of our CI to catch and fix proof regressions. Any PR to the repository must reverify all
  the code before being merged" ([A-bhargavan-strengths-limits-verification-2026]). We cannot run
  that CI. So the discipline that has to replace it is: **never hand-edit generated code**; if a
  local change is needed, change the CDDL and regenerate, or the vendored region silently stops
  being verified while still looking verified. The kernel's "tweaked" banner is what the other
  choice looks like.

### The panic sites

- `fnd-the-panic-count-scales-with-the-schema-and-is-not-fixed`: measured on the trio —
  `cbordetver.rs` 7, `cbordetveraux.rs` 104, `coseformat.rs` 435 = **546**. Front 10's 111 was the
  CBOR core alone; the generated schema layer adds roughly one panic site per 43 lines. Two distinct
  messages only, both Karamel extraction artefacts: `"Incomplete pattern matching"` (381 in
  coseformat) and `"Precondition of the function most likely violated"` (35).
- `fnd-clippy-panic-is-unsurvivable-and-must-be-switched-off-per-region`: demonstrated —
  `#![deny(clippy::panic)]` at the crate root yields exactly **546 errors**, one per site
  ("`panic` should not be present in production code"). The only remedy is an `#![allow]` covering
  the whole vendored region, re-applied on every regeneration. The lint's protection is not
  narrowable.
- `fnd-what-proved-unreachable-actually-assumes`: the panics stand for F* refinement types Rust
  cannot express, discharged upstream. Believing they cannot fire means trusting, at minimum: the F*
  typechecker and Z3 4.13.3; the Karamel extraction to Rust; `rustc` and LLVM; and the hand-written
  glue at the boundary. [A-sel4-what-the-proofs-assume-2025] is the template for saying this
  honestly, and also supplies the argument for why it is not a defect: "Being able to clearly state
  an exhaustive list of assumptions means that the work needed to fully trust a system is massively
  reduced from looking at many thousands of lines of code to a number of small, specific, and easy
  to understand pieces." Note the one seL4 assumption we do *not* get to discharge: they removed the
  compiler from their trust base via binary verification; EverParse has no such step, so `rustc` is
  in ours.
- `fnd-panicking-on-input-is-a-cryptographic-defect-not-only-a-robustness-one`: the sharpest
  articulation found — "the IND-CCA security game requires a decryption oracle that returns ⊥ on
  invalid ciphertexts, but a panicking implementation terminates execution instead, making the
  decryption oracle unavailable after the first invalid query" ([B-symbolic-high-assurance-promises-2026]).
  This upgrades the project's no-panic policy from taste to a security property, and the design
  should say so in those terms.
- `fnd-the-precedent-exists-and-it-failed-in-the-glue`: libcrux verifies panic-freedom as an explicit
  property for its verified modules — and then shipped RUSTSEC-2026-0025, "Panic in `libcrux-psq` on
  decryption of malformed AES-GCM ciphertext", fixed by "Propagate AEADError instead of panicking"
  ([A-rustsec-libcrux-psq-panic-malformed-ciphertext-2026]). The verified primitive returned the
  error correctly; the unverified wrapper called `.unwrap()` on it, with the correct handling sitting
  commented out on the next line ([B-symbolic-high-assurance-promises-2026]).
- `fnd-kani-can-re-establish-the-claim-locally-but-only-on-linux`: Kani models `panic!` as a failing
  assertion and reports per-site `UNREACHABLE`, summarised as e.g. `0 of 786 failed (41
  unreachable)` ([A-kani-verification-result-statuses-2026]). A bounded harness over
  `cbor_det_parse` with a symbolic input slice would turn "trust the F* proof" into "our own model
  checker agrees, for inputs up to N bytes". Two caveats, both stated by the docs: `UNREACHABLE` can
  also mean an over-constrained harness (a vacuous pass), and unbounded loops need explicit
  `kani::unwind` bounds. Kani is not installed on this Windows host and does not target Windows, so
  this is a Linux-CI job.

### The verified/unverified boundary

- `fnd-the-glue-is-exactly-where-the-field-evidence-says-systems-break`: from the principal author of
  both HACL* and libcrux — "we have repeatedly seen bugs appear in unverified components - platform
  stubs, API wrappers, interface code - **while large verified components have remained bug-free**"
  ([A-bhargavan-strengths-limits-verification-2026]). Corroborated independently by the advisory
  record: RUSTSEC-2025-0133 was "an unverified fallback in `libcrux-intrinsics`" that "corrupted
  SHA-3 digests" ([A-rustsec-libcrux-intrinsics-wrong-output-2025]); RUSTSEC-2026-0025 was an
  `unwrap` in a wrapper. **20 RustSec advisories exist across libcrux crates** (measured); the ones
  read are all in unverified or specification layers, none in verified arithmetic.
- `fnd-the-reference-application-shows-the-seam-in-forty-lines`: EverParse's own COSE glue is
  `try_into().unwrap()` three times over key material and
  `mod commonabort { pub fn abort() -> ! { std::process::abort(); } }`
  ([A-evercosign-rust-handwritten-glue-2026]). The generated formatter never references `commonabort`;
  the hand-written application layer calls it on serialisation failure. So the pattern is: verified
  core returns a total result, glue converts it into a process abort. **That is the exact conversion
  Dorc must not perform**, and the upstream reference implementation performs it.
- `fnd-the-seam-here-is-small-and-nameable`: for us the boundary is four things and nothing else —
  (1) bytes in: `&[u8]` from our reader into `validate_and_parse_*`; (2) values out: generated
  structs with positional fields, which we must map into our own named types; (3) the ordinal and
  terminator checks front 3 and front 4 assigned to us, which the generated code does not know
  about; (4) the encryption seam, unchanged from front 10. Nothing crosses in the other direction —
  the generated code calls nothing of ours except a three-line `ignore` shim.

## The disjointness answer, stated for a conductor

**Yes, the invariant can become a checked property — but it takes two mechanisms, not one, and the
tool supplies only the first.**

**Property one: no byte sequence is valid under both projections.** Write the projections as one
CDDL choice, `whylog_unit = rich_decision / plain_decision`. If EverCDDL emits code at all, it has
proved `forall (l: Cbor.cbor). ~(rich l /\ plain l)` with a machine-checked decision procedure whose
soundness is itself proved in F*. If it cannot prove it, it refuses to generate and prints which
alternatives it could not separate. This is exactly the property front 3 wanted and it is genuinely
free once the schema is written that way — **one line of CDDL, checked at generation time**, not
review time.

Three conditions on it, none negotiable:

1. **The projections must be arrays or differently-tagged, never two maps.** Two maps are refused
   with `typ_disjoint: map: not supported`. This costs nothing because front 3 already ruled maps
   out; it becomes an additional, independent reason for that rule.
2. **The discriminator must be structural, not a comment.** A distinct leading literal, a distinct
   arity, or a distinct tag. Demonstrated working for all three.
3. **The guarantee is over CBOR items and reaches bytes only through determinism.** EverCDDL emits
   deterministic-only readers and writers, so it holds — but it is worth writing down as a dependency
   rather than assuming it.

**Property two: the plain type cannot represent an opaque field.** EverCDDL does **not** prove this,
and demonstrably accepts a plain rule with an optional ciphertext as disjoint. What delivers it is
the generated Rust type — `plain_decision` has three scalar fields, no lifetime, no borrowed bytes —
plus one line in our own code that fails to compile if that changes:

```rust
fn _plain_projection_shape(p: whylogformat::plain_decision) {
    // exhaustively names every field plain is permitted to carry
    let whylogformat::plain_decision { _x1: _, _x2: _, _x3: _ } = p;
}
```

Adding any field to the plain rule gives `error[E0027]: pattern does not mention field '_x4'`. Adding
a *borrowed* field additionally trips a one-line type alias with `error[E0106]`. Ship both; they cost
two lines and they are the only mechanical statement of the invariant that exists.

**What it costs to adopt.**

| | cost |
|---|---|
| build-time toolchain | none — generated Rust builds with `cargo build` against `std` |
| generation-time toolchain | 913 MB unpacked EverParse release (F\* + Karamel + Z3 4.13.3), **Linux or macOS only** |
| vendored surface | ~330 KB machine-generated Rust (~112 KB schema + ~215 KB CBOR runtime) |
| panic sites | ~69 for a trimmed realistic schema, scaling with schema size |
| per-change cost | ~80 s regeneration; a six-figure-byte diff nobody can review |
| reviewability | positional field names, non-ASCII monomorphised type names |
| bus factor | 1 |

**My reading of the trade, offered as judgement not result**: the *disjointness proof* is worth
having and is nearly free. The *code generation* is a much larger commitment than the proof, and the
two are currently sold together. There is a third option front 10 did not consider and I flag as the
most likely right answer — **use EverCDDL as a checker, not a generator**: keep front 10's vendored
`cborrs` and a hand-written schema layer, and run `cddl.exe --fstar_only` in Linux CI over a CDDL file
that models the schema, purely for the disjointness verdict. That buys the proof, keeps the code
reviewable and named, and never vendors a megabyte of extraction artefacts. Its cost is that the CDDL
model and the hand-written reader can drift, which is a real and unglamorous risk — but it is a risk
of the kind this project already manages, whereas an unreviewable vendored blob is not.

## The vendoring policy, stated concretely

Written so it can be lifted into a document. Every clause is from
[A-chromium-adding-third-party-libraries-2026] except where noted.

1. **Vendored code lives in one directory per upstream**, and that directory carries a metadata file
   recording: upstream URL; the exact upstream revision (a full hash, not a tag); the local
   divergence state; whether it is security-critical; and its licence. Our decoder is
   security-critical by Chromium's own predicate — "parses or interprets complex input formats".
2. **Two named humans own it.** Their duties are explicit: remove it when it is no longer needed, and
   update it when a security or stability bug is fixed upstream. This is a *subscription*, not a tool
   — "be mindful of security-related mailing lists for the project and relevant CVE".
3. **Declare an update mechanism from a closed set.** Autoroll / Manual / Static / Static.HardFork.
   A vendored research artefact with local edits is `Static.HardFork`, and its consequence is stated
   for us: *the dependency will be treated as if it were written by us*. Adopt that sentence
   verbatim; it settles the "day upstream stops" question with no further reasoning.
4. **The quarantine equivalent is a declared divergence point.** Publication-age quarantine cannot
   apply — there is no publication event ([A-rfc3923-cargo-min-publish-age-2026]). What replaces it
   is recording the closest upstream revision for scanning purposes and *accepting false positives*:
   "This may return some false positives but ensures coverage is optimal." There is no better answer
   in the corpus; do not go looking for one.
5. **Never hand-edit generated verified code.** Verification is lost on modification and the CI that
   would catch it is upstream's ([A-bhargavan-strengths-limits-verification-2026]). Changes go into
   the schema and come back through regeneration. The Linux kernel's "tweaked to be suitable for use
   in the kernel" banner is what the other path looks like six years on
   ([A-linux-vendored-hacl-curve25519-2024]).
6. **Regeneration must be reproducible and recorded.** Pin the generator release tag, record the
   CDDL input hash and the generator version beside the output, and never pass `--admit`. A CI job
   that regenerates and diffs is the only defence against silently-unverified output
   ([A-evercddl-gen-driver-toolchain-2026]).
7. **Treat unreviewable generated code as the exception it is.** Chromium "strongly discourages"
   checking in code "a reviewer asked to approve a change … has no way to determine the legitimacy
   of". A megabyte of positional-field Rust is in that category. If we take it, the honest framing is
   that we are trusting the generator's proof *in place of* code review, and the compensating control
   is the mechanical one — build under `forbid(unsafe_code)`, run the model checker, and diff the
   regeneration.

## The panic answer, and the honest comparison

**What "proved unreachable" covers**: the panics are Karamel's stand-ins for F* refinement types Rust
cannot express. The proof is against a model, and the model assumes the F* typechecker, Z3 4.13.3,
Karamel's extraction, `rustc`/LLVM, and the correctness of the hand-written glue at the edge. seL4's
framing is the one to copy: the assumptions are not a defect, they are the point — a small, stateable
list replaces "trust these thousands of lines"
([A-sel4-what-the-proofs-assume-2025]). The one seL4 assumption we do *not* get to discharge is the
compiler, because EverParse has no binary-verification step.

**The comparison, made honestly.** 546 proved-unreachable panics in verified code versus an unknown
number of unproved ones in a hand-written decoder is **not a close call, and the visible number is the
better position** — for four reasons:

1. The number is *knowable*. `grep -c 'panic!'` gives it exactly. The hand-written alternative's
   number is not merely larger, it is unknown, and every fuzzing campaign changes the estimate.
2. Each site is *attributable to one cause* — two distinct messages, both extraction artefacts, both
   traceable to a named upstream proof obligation. A hand-written decoder's panics are indexing,
   slicing, arithmetic and `unwrap`, spread across every code path.
3. They are *mechanically re-checkable* by us, without reading a single F* proof, via a bounded Kani
   harness reporting UNREACHABLE per site ([A-kani-verification-result-statuses-2026]).
4. The field evidence is unambiguous about where verified libraries actually break, and it is never
   the verified region ([A-bhargavan-strengths-limits-verification-2026], corroborated by
   [A-rustsec-libcrux-intrinsics-wrong-output-2025] and
   [A-rustsec-libcrux-psq-panic-malformed-ciphertext-2026]).

**What is nonetheless real and must be paid**: `#![deny(clippy::panic)]` cannot survive contact with
this code — 546 errors — so the lint has to be disabled over the whole vendored region, and re-disabled
on every regeneration. That is a genuine loss of a project-wide safety net, narrowed to a region we can
name but cannot lint. The compensating controls are the Kani harness and the fact that the region has
no `unwrap`, no `expect`, no indexing-by-user-input, and no `unsafe` at all.

**And the thing to actually worry about is not the 546.** It is the one `.unwrap()` in the file the
maintainer labels unverified glue — because that is the failure mode with a CVE attached to it in a
directly comparable project ([A-rustsec-libcrux-psq-panic-malformed-ciphertext-2026]).

## Where the verified/unverified boundary sits, and the discipline for it

The boundary is a *value boundary*, not a call boundary, and that is unusually favourable: nothing
crosses from verified code into ours except returned values, and nothing of ours is called from inside
except a three-line no-op. Four crossings, and a rule for each:

1. **Bytes in.** `&[u8]` into `validate_and_parse_*`. Rule: the slice must be bounded before it is
   passed, by us, because the generated code has no size policy of its own. This is where front 3's
   bounded-decode requirement actually lands.
2. **Values out.** Generated structs with positional fields. Rule: **convert at the boundary, once,
   into our own named types, and never let a generated type reach the rest of the codebase.** This is
   the single highest-value piece of discipline here — it contains the unreadability, it makes the
   projection guards possible, and it is the only place the `_x1`/`_x2` naming appears.
3. **Errors out.** `Option`/`option__…` returns. Rule: **the boundary converts absence into our error
   type and never into a panic, an abort, or an `unwrap`.** State this as a security property, not a
   robustness one: a terminating decryption path is not a decryption oracle
   ([B-symbolic-high-assurance-promises-2026]). Note that upstream's own reference glue does exactly
   the wrong thing here — `std::process::abort()` on serialisation failure
   ([A-evercosign-rust-handwritten-glue-2026]) — so this is not a hypothetical hazard, it is the
   pattern the example teaches.
4. **The cryptographic seam.** Unchanged from front 10: our context tuple into the derivation info
   string. The container change does not move it.

The discipline in one sentence: **the verified region is a pure function from bytes to values; every
effect, every bound, and every error decision lives on our side of it, in one file, reviewed as
security code.** That file is small — and per the round's own glue mandate, it is where all the risk
now lives.

## Readability versus security

### Genuinely in tension

- **Generated code is unreadable, and that is a security property in both directions.** It cannot be
  reviewed (bad), and it also cannot be *misread* into a false sense of having been reviewed (good, if
  we are honest about it). The tension is real and unresolvable: taking the proof means giving up code
  review over that region, and Chromium's policy says plainly that this is normally a reason to refuse
  ([A-chromium-adding-third-party-libraries-2026]).
- **Positional field names at the boundary.** `plain_decision { _x1, _x2, _x3 }` is worse to read than
  anything we would write, and the mapping from position to meaning lives only in the CDDL. Mitigated
  by the convert-once rule, not removed by it — and the mapping layer is itself a place to get a field
  order wrong, silently.
- **The disjointness proof is only as good as the schema being the real schema.** If the CDDL is used
  as a checker over a hand-written reader (my suggested third option), the proof is about a *model of*
  our format, not our format. That drift is the price of keeping the code readable.
- **`clippy::panic` must be disabled over the vendored region.** A project-wide readability-and-safety
  lint gets a hole in it, and the hole is exactly where we can least review by eye.

### NOT in tension — loudly

- **"Avoid maps entirely" is now doubly earned.** Front 3 adopted it for determinism, duplicate keys,
  stack bounds and canonical field position. It turns out to *also* be the precondition for the
  disjointness proof existing at all — two maps are refused outright. One restriction, four security
  properties, one proof, and zero readability cost in a binary container. This is the round's cleanest
  compound keep.
- **The structural discriminator is a readability win.** Requiring a distinct leading literal on every
  unit — `"dec"` versus `"dec+"` — is what makes the proof go through, and it is also exactly what
  makes a diagnostic-notation dump scannable and a hexdump navigable. The thing the prover needs is the
  thing the firefighter needs.
- **Convert-once at the boundary.** Better readability (named types everywhere but one file), better
  security (one reviewed place where untrusted values become domain values), and it is what makes the
  compile-time projection guard expressible. No trade.
- **The exhaustive-destructuring guard.** It is simultaneously the mechanical enforcement of the
  invariant and the clearest human-readable statement of it — a line of code that says "plain carries
  exactly these three things". Documentation that fails the build when it goes stale.
- **Trimming the postlude.** 40% less generated code, 47% fewer panic sites, no lost functionality,
  and a shorter file. Free on both axes.
- **Never hand-editing generated code.** Preserves the proof (security) and keeps the vendored region
  a pure function of a small readable input (readability). The kernel's six-year fork is the
  counterexample on both axes at once.

## Deliberately not pursued, and why

- **Reading the F\* proofs behind the 546 panic sites.** Same call front 10 made, same reason: it is a
  different skill and a different budget. What changed is that there is now a cheaper substitute — a
  bounded Kani harness — and that substitute is recommended instead.
- **Actually running Kani over the vendored decoder.** Kani is not installed on this host and does not
  target Windows. Doing it properly means a Linux CI job with unwind bounds chosen against real
  document sizes, which is implementation work, not research.
- **Whether `rustc` DCE actually removes the ~30 unused postlude entry points from a release binary.**
  Trimming the postlude makes the question mostly moot, and binary size is not a stated constraint.
- **The C backend.** EverCDDL's C output is more mature (`COSE_Format.c` is checked in, the paper
  benchmarks C), but we are a Rust project with `forbid(unsafe_code)`, so C is not reachable.
- **`EverCDDL` on macOS.** The package matrix says it is present; I verified only Linux. Low risk,
  and it does not change the Windows finding.
- **The three later posts in the Symbolic Software series**, including one specifically about
  structural gaps in the extraction pipeline, which is the most on-point of them. The URL pattern I
  guessed 404s and I did not spend further budget locating them; the first post plus the advisory
  database already carried the argument. **A conductor with five minutes should find that post** —
  "The Verification Facade: Structural Gaps in Cryspen's Hax Pipeline", 2026-04-07 — because an
  extraction-pipeline critique transfers directly to Karamel.
- **Debian/Fedora anti-bundling policy** as the institutional counter-position on vendoring. It would
  have added a distributor's perspective, but we ship a binary and not a distro package, and Chromium's
  policy already carries the ownership argument in an enforceable form.
- **Differential-testing the generated reader against another CBOR implementation.** Front 10 left this
  for later and it stays there; the `#[ignore]`d upstream interop test
  ([B-evercosign-interop-test-ignored-2026]) suggests it would be informative, but it is a testing task.

## Closing note for the conductor inheriting the round

Three things, and only three.

**1. The round produced two kinds of output and they should not be handled the same way.** Most of it
is *principles* — derived independently, corroborated against specifications and attack literature,
and stable. A small part is *product selection* — the two dependencies, the specification, the vendoring
call — and that part has a shelf life measured in months. When you write the design, put the principles
in the durable documents in their own voice and put the selections in one place, dated, with the
measurement that justified each one, so that the next person can re-run the measurement instead of
re-reading eleven fronts. The seam counts, the crate counts, the panic counts and the advisory censuses
are all reproducible in an afternoon; the reasoning that made them matter is not.

**2. The single most transferable result of this front is not about CBOR.** It is that a design
invariant which currently reads "reviewers must ensure X" can, surprisingly often, be converted into
"the build fails if not X" — and that the conversion is usually *two* mechanisms, not one, because the
invariant is usually two properties wearing one sentence. Here it was a proof for "the two types cannot
both accept a byte string" and a two-line compile error for "one of them cannot hold the field". Go
through the design's other stated invariants — irrevocable mode selection, the decision document being
a different top-level type, the plain projection as the stderr dump, "no value-derived output for an
opaque field" — and ask each one the same question. Some of them will have the same shape and the same
cheap answer. That is a better use of the next session than any further shopping.

**3. Be suspicious of the round's own coherence.** Eleven fronts derived a specification that turned
out to already exist, a container that turned out to be a shipped strict recognizer, and a proof that
turned out to be one line of schema. That is a genuinely good outcome and it is *also* exactly the
shape a set of correlated blind spots produces — each front briefed from the last, each inheriting the
previous framing. The independent corroborations are real (C2SP matching front 2 clause for clause was
not something a researcher could have engineered) but they are not evenly distributed: the storage
front, the write-ordering front and the cleanup front had no external specification to collide with,
and their conclusions rest on the round's own reasoning. Before implementation, those three are the
ones worth an outside pass. And the one finding I would most want a hostile reader to attack is the one
this front produced: that the projection invariant is now "checked", when what is checked is a model of
it, by a tool with a bus factor of one, on two of our three platforms.
