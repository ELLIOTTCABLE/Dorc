# turn 13 — 2026-08-24 04:53:11 CDT


Scope: one immutable local debugging receipt; readable structural skeleton plus
opaque values; inline per-value encryption (A) vs one grouped compartment (B).

## Findings

- The A-vs-B choice is second-order. Every shipped failure I could find in this shape failed for a reason orthogonal to it: the skeleton was unbound ([A-mueller-pdfex-partial-encryption-2019]), the reader interpreted before verifying ([A-getsops-tree-walk-source-2026]), or the reader rendered partially-valid documents best-effort ([A-poddebniak-efail-exfiltration-2018]).
- Grouping does materially reduce authored cryptographic seams, but by one specific mechanism worth naming: binding the skeleton into the single compartment's associated data *subsumes* the separate document-level authenticator that inline needs and cannot do without.
- Grouping does NOT reduce parser surface. It trades N ciphertext parsers for one, and adds a reference/manifest namespace that inline has no analogue of. That new surface is exactly the precondition PDFex's direct exfiltration requires (cross-object references from unencrypted parts into encrypted ones).
- The metadata case for grouping is the strongest evidenced one: inline leaks each value's exact plaintext length, and in the shipped exemplar also leaks per-value equality via deterministic IV reuse. Both are maintainer-acknowledged and unfixed after five years ([B-getsops-length-leak-issue-2021], [B-getsops-format-wishlist-issue-2025]).
- Almost nothing user-visible is lost by dislocation. An inline ciphertext blob has near-zero readable utility already; the readable utility lives in the field name and the presence marker, both of which survive grouping. What is genuinely lost: one-line grep adjacency, and per-field diff localisation — and the latter is the same fact as the privacy win, seen from the other side.
- Grouping strictly *improves* the "quote into an issue" workflow: any contiguous run of the skeleton can be copied with certainty that no ciphertext went with it.
- Binding is a solved problem with four standardized answers; the discriminator between them is ordering, not strength. Associated data and KDF context make correct context a *precondition* of decryption; a digest inside the plaintext makes it a *postcondition*. Same detection, weaker discipline.
- The party who can re-author each construction is the same in all four: whoever holds the content key. age's header MAC is the cautionary case — its MAC key derives from the file key, so every decryptor can rewrite the skeleton and recompute the MAC ([A-filippo-age-authentication-2022]).
- Key-commitment machinery is probably NOT owed here. Both known attack families need preconditions this threat model excludes (an adaptive decryption oracle; a sender who chooses the keys). This is a reasoned exclusion with a named flip condition, not an oversight.
- One attack survives every construction and is topology-independent: strip the compartment from a rich receipt, rewrite references as omission markers, present it as a plain projection. The plain projection carries no cryptographic material by design, so nothing can detect it. That is a product decision, not a cryptographic one.
- A maintained package can be taken substantially as-is, but only if it exposes caller-controlled associated data bound to the whole message. Tink's streaming AEAD folds it into HKDF info; libsodium secretstream takes per-message ad; COSE_Encrypt0 has external_aad. age has none — verified in both the format specification and the public API.
- Base64 inside the compartment should be rejected: +33% storage, no leakage change, a second canonicality surface, and it destroys readability of the one view where readability was still possible (the decrypted view).
- Grouping wins Q12 structurally: one authenticated byte-range pair the reader can hold as slices. The shipped inline exemplar MACs a re-serialisation of the *parsed model*, not the file's bytes — precisely the anti-pattern [A-dsse-protocol-pae-2024] forbids.
- Recommendation: grouped, one compartment, associated data or KDF context over the literal bytes preceding it, via a maintained package. Confidence ~SUSPECT that it is the better default, -GUESS that the margin is large.

## Report

### 1. Conclusion (one screen)

Choose B, one compartment, with the skeleton bound into it as associated data or
KDF context over the literal bytes — but understand that this is a modest win on
a second-order axis, and that the decisions which actually determine whether this
receipt is safe are three others: bind the skeleton at all, verify before you
interpret, and never render unauthenticated bytes as though they were authentic.

The case for grouping rests on three things, in descending order of evidential
strength. First, metadata: inline publishes each opaque value's exact plaintext
length, and the only shipped exemplar of inline also publishes per-value equality;
both are maintainer-acknowledged and unfixed. Second, seams: one compartment
collapses N nonces to one (or to zero authored, if a package owns them), turns
padding from a per-field policy into a single decision, and — the substantive
point — *subsumes* the document-level authenticator, because a single AEAD whose
associated data is the whole skeleton already fails on record addition, removal,
reordering and reference edits. Third, excerpting: any contiguous run of a grouped
skeleton can be pasted into an issue with certainty that no ciphertext travelled
with it.

The case against grouping is real and should not be waved away. Grouping introduces
a reference-and-manifest indirection that inline does not have, and that indirection
is the precondition PDFex's exfiltration attack requires. It concentrates corruption
blast radius unless the compartment is chunked. And it forfeits per-field diff
localisation, which is a genuine firefighting affordance.

What almost nothing rests on is readability. An inline ciphertext blob is not
readable; the readable content is the field name and the fact that a value was
captured, and grouping keeps both. The intuition that inline "keeps the file useful
under `less` and `grep`" does not survive contact with what an inline blob actually
looks like.

### 2. Topology comparison

| Axis | A — inline per value | B — one grouped compartment |
|---|---|---|
| Readable skeleton survives less/grep/diff | yes | yes, identically |
| Adjacency of value to its field | yes (blob unreadable anyway) | reference id only |
| Safe to quote a contiguous excerpt | no — may carry ciphertext | yes |
| Per-field diff localisation | yes | no (whole compartment churns) |
| Per-field plaintext length leaked | yes, exactly | no (aggregate only) |
| Per-field equality leaked | yes if nonces deterministic; SOPS's are | no |
| Per-field presence / type leaked | yes | only what the skeleton chooses to say |
| Authored nonce management | N per receipt + a nonce-budget argument | 1, or 0 if a package owns it |
| Padding policy | per field, N decisions | one decision |
| Separate document-level MAC needed | yes, unavoidably | no — subsumed by the AAD |
| Reference / manifest confusion surface | none | new: dangling, orphan, aliased, cross-compartment |
| One damaged byte destroys | that value only | all values if one-shot; one chunk if chunked with counter nonces; all subsequent if state-chained |
| Decrypt exactly one member | O(1) | O(chunk) with an index, O(all) without |
| Bounded allocation | N attacker-influenced lengths | one known length |
| Authenticated bytes == interpreted bytes | achievable, but drifts toward MACing the parsed model | one byte-range pair, natural to hold as slices |
| Plain-projection enforcement | per-field check at N sites | one crypto site + the same N type discriminations |

The rows that actually moved my view: per-field length and equality leakage
(evidenced, shipped, unfixed), the subsumed document MAC (structural, for), and
the new reference surface (structural, against).

### 3. Authored cryptographic-seam inventory

*Topology A, done properly — not as SOPS ships it:*

1. Content-key derivation and management. (shared with B)
2. Per-value nonce generation, plus an argument that nonce uniqueness holds across
   N values × M receipts under one key. Random 96-bit GCM nonces put a real ceiling
   here; the shipped exemplar sidesteps it with a non-standard 32-byte nonce, which
   is analysis debt rather than a fix.
3. An injective encoding of the per-value associated data — field path, ordering,
   length prefixes, context string — applied N times. The rules are normative and
   easy to get wrong ([A-rfc9052-cose-structures-2022] §4.3).
4. A per-value wire framing and its parser.
5. A per-value type/shape tag that must live *inside* the associated data or the
   plaintext, or it is malleable. The shipped exemplar puts it in neither.
6. A document-level authenticator, because per-value associated data provably
   cannot catch addition, removal, reordering or rollback — only movement between
   fields.
7. A per-value padding policy, if length matters. This is the seam nobody has closed.
8. A deterministic-versus-random nonce decision, trading equality leakage against
   ciphertext churn across re-emissions.

Eight seams, three of them subtle (2, 3, 7).

*Topology B, one compartment:*

1. Content-key derivation and management. (shared)
2. Nonce: one, or zero authored if the package owns it.
3. One skeleton-binding construction, in one place — liftable verbatim from COSE's
   Enc_structure or DSSE's PAE rather than invented.
4. One compartment framing and one parser.
5. A member manifest inside the authenticated plaintext (length-prefixed id→value
   list). Its integrity is free; only its *encoding* is authored.
6. Reference and omission markers in the skeleton, plus a bidirectional
   reference↔manifest equality check. **New; A has no analogue.**
7. Padding: one decision.
8. Document-level authenticator: none. Subsumed by (3).

Five to six seams, and the two subtle ones from A either vanish (2) or reduce to a
single choice (7). The reduction is real but not dramatic, and item 6 is a genuine
new liability.

### 4. Strongest first-party evidence, both directions

*For grouping.*

The shipped inline exemplar's own maintainers list, as things they would change
given a new format: include keys in the MAC, stop ignoring null values, pad so
plaintext length is not fully revealed, and use a real serialisation format instead
of a hand-rolled one ([B-getsops-format-wishlist-issue-2025]). Three of those four
are seams grouping either eliminates or reduces to one decision. The length leak has
an independent, reproducible report from a security consultant citing real client
engagements, still open after five years, with the maintainer's own reply explaining
why per-field padding is hard to retrofit ([B-getsops-length-leak-issue-2021]). That
report's pasted output incidentally demonstrates per-value equality leakage: repeated
boolean values produce byte-identical ciphertext *and* byte-identical IV, which the
cipher source explains — an IV stash keyed on (plaintext, associated data)
([A-getsops-aes-cipher-source-2026]).

Reading the tree walker settles two more things ([A-getsops-tree-walk-source-2026]).
The document MAC is a bare concatenation hash over leaf values with no key names, no
separators and no length prefixes — so it is not injective, and the only thing
actually preventing structural forgery is the per-value path binding in the
associated data. And the decrypt path materialises every plaintext value into the
tree *before* the document MAC is compared, with a supported flag to skip the
comparison entirely.

The strongest general statement comes from the format that gave up: PDF's analysts
concluded that mixed content should be dropped altogether and that an encryption
scheme covering the whole document including its structure should be preferred,
"to leave no room for injection or wrapping attacks"
([A-mueller-pdfex-partial-encryption-2019] §7).

*Against grouping.*

PDFex's direct-exfiltration attack has exactly three requirements, and the second is
"it must be possible to reference and access encrypted string or stream objects from
unencrypted attacker-controlled parts of the PDF document"
([A-mueller-pdfex-partial-encryption-2019] §5.1.1). That indirection is precisely
what topology B introduces and topology A does not have. On this one axis B is
structurally *closer* to the format that got broken.

The same paper documents eighteen distinct standard-compliant routes to partial
encryption in one format — the concrete cost of any classification taxonomy over
what is and is not sealed. That is the warning behind Q10, and it applies the moment
a second compartment exists.

The standards response to the per-element attacks is instructive by omission: XML
Encryption 1.1 hardened the ciphers, mandated rejection of the broken ones, and left
the per-element mixed structure exactly as it was ([A-w3c-xmlenc-core1-2013] §6.1).
A standards body with a decade to think about it did not conclude that the topology
was the problem.

Finally, the reader-side incidents in the inline exemplar have nothing to do with
topology at all: an unauthenticated structural index in the readable region drove an
unbounded allocation ([A-getsops-memory-exhaustion-advisory-2026]), and
unauthenticated fields in the readable region steered the reader into an outbound
network call carrying the operator's credential
([A-getsops-vault-token-exfil-advisory-2026]). Grouping fixes neither.

### 5. Attacks against the recommended construction

Recommended construction, for the walkthroughs: readable skeleton; one encrypted
compartment appended after it; the compartment sealed with associated data (or KDF
context) equal to an injective encoding of a context string, a projection-mode
label, a run identity, and the literal bytes of the entire file preceding the
compartment; a member manifest inside the authenticated plaintext; the compartment
chunked with counter nonces and an explicit final-chunk marker; nothing written
after the compartment.

**A1 — compartment transplant (substitution).** The attacker holds two receipts from
the same fleet and key epoch and splices receipt 1's skeleton onto receipt 2's
compartment. Under the recommendation the associated data presented at decryption is
receipt 1's skeleton bytes while the compartment was sealed under receipt 2's; tag
verification fails and no plaintext is ever released. Blocked, and blocked *before*
release. Under the digest-in-plaintext variant decryption succeeds and the mismatch
is caught only at the subsequent comparison — detected, but the reader has held
attacker-contextualised plaintext in the interim. Under no binding at all the reader
shows receipt 2's values under receipt 1's narrative and the firefighter concludes
the wrong host was touched. This is the attack that matters most for a debugging
artefact: it does not leak, it lies.

**A2 — projection downgrade (confusion).** The attacker deletes the compartment and
rewrites the reference markers as omission markers, presenting the result as a
genuine plain projection. Nothing detects this, because the plain projection carries
no cryptographic material by design. The firefighter concludes the values were never
captured rather than that they were captured and removed. This is the same shape as
EFAIL's packet-type downgrade, where flipping an integrity-protected packet type to
its unprotected sibling silently removes the guarantee
([A-poddebniak-efail-exfiltration-2018] §5.2), and it was raised unprompted against
the inline exemplar too ([B-getsops-mac-scope-thread-2024]). It survives every
construction in Q4 and is independent of topology. The only mitigations are product
decisions: give the plain projection its own authenticator (at which point "plain"
is no longer crypto-free), or have the reader never assert that a plain receipt is
authentic.

**A3 — truncation to a valid prefix.** The attacker truncates the file mid-compartment.
Chunks before the cut authenticate cleanly; the final-chunk marker never arrives. A
reader that decrypts what it can and prints it produces something that reads like a
complete receipt with the last few commands simply absent — which is how you hide the
command that broke production. The mitigation is normative and cheap: signal an error
when end-of-input is reached without a valid final chunk
([A-c2sp-age-format-spec-2026], payload section), and treat end-of-file and
decryption failure as distinguishable outcomes rather than conflating them
([A-tink-aes-gcm-hkdf-streaming-2025], decryption section). Under inline the analogue
is truncating whole records, caught by the document MAC — but in the shipped exemplar
only after everything preceding has already been decrypted.

**A4 — reference aliasing (grouping-specific).** Two skeleton records reference the
same member id; or a record references an id absent from the manifest; or the manifest
holds a member no record references. All three change what the receipt means without
touching a byte of ciphertext. The binding catches them only if the *entire* skeleton
including every reference id is inside the bound region — an implementation that binds
"the structural records" but not the reference table reopens the whole class. The
manifest→skeleton direction needs an explicit check of its own: an unreferenced member
is an omission attack against a reader that reports only referenced values. This is the
price grouping pays that inline does not, and it is the same shape as PDFex's
cross-object-reference requirement.

**A5 — document-context swap.** The receipt is renamed, or presented as belonging to a
different run. Nothing prevents it unless the run identity sits inside the bound region.
Cheap to fix, easy to forget, and it is the residue of the general principle that the
inner layer must name the outer context ([A-davis-defective-sign-encrypt-2001]).

**A6 — hostile skeleton before any crypto runs.** The reader must locate the skeleton
and compartment byte ranges before it can verify anything, and that location step parses
untrusted input. Both shipped incidents in the inline exemplar live here, not in the
cryptography. The requirement is lexical, bounded and total region-finding, with no
semantic interpretation and no I/O, before a single byte is authenticated.

### 6. Candidate packages (only now that the construction is fixed)

The construction demands caller-controlled associated data bound to the *whole*
message. That single requirement does most of the filtering.

- **libsodium `crypto_secretstream_xchacha20poly1305`** — claims exactly this problem's
  property list: messages cannot be truncated, removed, reordered, duplicated or
  modified undetected; owns nonce generation and rekeying entirely; accepts per-message
  associated data; has an explicit final tag; and encrypts its own sequence tags so
  boundaries do not leak ([A-libsodium-secretstream-design-2026]). Caveat: its state chains
  (the nonce is XORed with each MAC), so a damaged chunk poisons everything after it —
  which changes the Q7 answer materially.
- **Tink AES-GCM-HKDF-Streaming** — folds the caller's associated data into HKDF `info`,
  so the derived key for the whole stream depends on it: a single whole-message binding,
  exactly the KDF-context option, with a peer-reviewed analysis of the implementation
  cited by its own specification. Supports random access without decrypting the whole
  compartment ([A-tink-aes-gcm-hkdf-streaming-2025]). Per-language support varies; verify
  before committing.
- **COSE_Encrypt0** — the only *standardized envelope that already owns the join*.
  Enc_structure binds a context string, the literal protected-header bytes and
  application `external_aad` into one deterministically encoded associated-data value
  ([A-rfc9052-cose-structures-2022] §5.3). Costs a CBOR dependency and makes the
  compartment CBOR.
- **JWE** — qualifies (protected header as associated data, plus an optional second
  component joined with a delimiter that cannot occur in base64url) but is base64 all the
  way down ([A-rfc7516-jwe-2015] §5.1 step 14), which collides with the Q11 finding.
- **age** — does **not** qualify as-is. The format fixes `aad = ""` for every recipient
  type ([A-c2sp-age-format-spec-2026]) and the public API exposes no associated-data
  parameter at all ([A-filippo-age-go-api-2026]). It remains usable via the
  digest-in-plaintext variant, at the cost of post-decryption checking.
- **Raw AEAD** (AES-GCM / ChaCha20-Poly1305, one-shot) — qualifies on associated data;
  you then author framing, chunking and truncation semantics yourself, which is most of
  what a package was supposed to buy.

### 7. Recommendation and confidence

Grouped; one compartment; bound by associated data or KDF context over an injective
encoding of (context string, projection mode, run identity, literal bytes of everything
preceding the compartment); member manifest inside the authenticated plaintext; chunked
with an explicit final marker; nothing written after the compartment, so no region needs
excluding from the binding.

- ~SUSPECT that grouping is the better default. The seam inventory, the metadata table
  and the excerpt-safety property all point the same way, and two of the three rest on
  first-party evidence rather than reasoning.
- -GUESS that the margin is large. It is not. Nothing I found shows inline-done-right
  failing. What the evidence shows is inline-as-shipped leaking, and every topology
  failing when the skeleton is unbound or the reader interprets first.
- +SURE that binding by associated data or KDF context dominates digest-in-plaintext on
  ordering, since the former makes correct context a precondition of decryption and the
  latter a postcondition — with the same set of parties able to re-author either
  ([A-rfc5116-aead-interface-2008], [A-rfc9771-aead-properties-2025]).
- +SURE that key-commitment machinery is not owed under the stated threat model, because
  both known attack families need preconditions this model excludes: an adaptive
  decryption oracle ([A-len-partitioning-oracle-attacks-2021]) or a sender who chooses
  the keys ([A-dodis-invisible-salamanders-2019]).
- ~SUSPECT that one compartment is right and a taxonomy is not. No concrete benefit for
  multiple compartments survives the stated constraints: there is one operator, the
  receipt is immutable so redaction is moot, and independent corruption domains are
  better bought with chunking.

### 8. Kill criteria

1. **Partial disclosure becomes a requirement.** If one field's value must ever be
   released without the rest, inline wins immediately; grouping forces all-or-nothing on
   the compartment key.
2. **Per-member decryption becomes hot.** A consumer that reads one field out of very
   large receipts at rate inverts the Q8 answer.
3. **The compartment cannot be chunked and corruption is observed.** If the chosen
   package forces one-shot sealing *and* single-bit damage happens in practice, the
   all-values-lost blast radius may outweigh the metadata win.
4. **No maintained package exposes associated data in the implementation language.**
   Falling back to digest-in-plaintext costs grouping its ordering advantage and moves
   the balance back toward parity.
5. **Receipts acquire multiple decryptors with distinct keys.** Then the age
   re-authorship hazard applies — any decryptor can rewrite the skeleton and recompute a
   key-derived authenticator ([A-filippo-age-authentication-2022]) — and key commitment
   re-enters scope.
6. **A machine consumer of receipts appears.** "Receipts never authorize" stops being
   documentation and becomes something that must be enforced; the Vault-token advisory is
   what that failure looks like.

### 9. Open questions requiring product judgment

1. Does the plain projection need its own authenticator? A2 is unmitigated otherwise, and
   the answer turns on whether "this is a plain receipt" is a *claim* the tool makes or
   merely a *rendering* it offers.
2. What padding size-class policy? Even TLS declines to specify one, calling the choice a
   complex topic explicitly out of scope ([A-rfc8446-tls13-2018] §5.4). Someone must pick.
3. Must run and host identity live inside the bound region, or is a receipt always
   interpreted relative to where it was found?
4. Is per-field equality across receipts an acceptable leak? It is the one leak inline
   cannot avoid without random nonces, and random nonces cause ciphertext churn across
   re-emissions — the exact trade the shipped exemplar resolved in favour of stability.
5. How is a TRUNCATED verdict surfaced so a firefighter cannot mistake it for a complete
   receipt? A rendering question with a security consequence.
6. What does the reader promise about the readable region? The XML Encryption
   Recommendation states the obligation directly: communicate clearly which information
   is authenticated and which is merely present.

### 10. Answers to the numbered questions, in order

**Q1.** Adjacency for single-line greps, and per-field diff localisation. Nothing else —
an inline blob carries no readable content, and the field name plus presence marker
survive grouping. Grouping *adds* excerpt safety.

**Q2.** Yes, but narrowly: it collapses N nonces to one or zero authored, makes padding a
single decision, and subsumes the separate document-level authenticator. It does not
reduce parser surface; it adds referential surface. Dependency complexity is roughly a
wash, or better for B if one package owns the compartment.

**Q3.** Yes, if and only if the package exposes caller-controlled associated data bound to
the whole message. Tink, libsodium secretstream, COSE_Encrypt0 and JWE do. age does not.

**Q4.** Four constructions; all re-authorable by exactly the content-key holders; they
differ in *when* the check happens. Associated data and KDF context verify inside tag
checking, so nothing is released on mismatch. An outer authenticator verifies before
decryption (also good) but adds a primitive and a key, and if that key derives from the
content key then every decryptor can re-author. A digest inside the plaintext verifies
after release. A standardized envelope is the associated-data option with the encoding
already specified — use COSE's Enc_structure or DSSE's PAE rather than inventing a join;
the injectivity rules are normative and the classic failure is concatenating without
length prefixes.

**Q5.** Adequate under this threat model, but strictly worse on ordering for no
compensating benefit unless the package forces it. Parse order must be lexical and
bounded before any cryptography runs; document identity must be inside the bound region
or rollback and renaming are unbound; projection mode must be inside both the bound
region and the context string; the member manifest is covered for free once it is inside
the plaintext, but the reader must still check set equality in both directions;
second-preimage resistance suffices with a trusted writer, and that assumption is exactly
what would change if writers ever became untrusted; on mismatch the reader must render
nothing as authentic.

**Q6.** Inline reveals per-field presence, type (if a type tag is carried), exact length,
equality (with deterministic nonces), ordering, aggregate length, and per-field change
patterns across receipts. Grouped reveals presence and whatever the skeleton chooses to
say about type, the ordering of references, and aggregate ciphertext length only. The
largest practical difference is change patterns: inline lets an observer holding two
receipts localise exactly which secrets changed.

**Q7.** Readable structure survives identically in both — this is the intuitive objection
and it is simply wrong. Opaque values: inline loses one; grouped one-shot loses all;
grouped chunked with counter nonces loses one chunk; grouped chunked with chained state
loses everything after the damage. A valid authenticated prefix can be reported, but only
behind a distinct truncation verdict that is never elided; the governing precedent is that
best-effort rendering of partially-valid documents is itself a vulnerability class.

**Q8.** Decrypting one member: O(1) inline, O(chunk) grouped-with-index, O(all)
grouped-one-shot — and largely irrelevant, since a debugging receipt is read whole.
Streaming: both stream; putting the compartment last lets the skeleton stream first.
Bounded allocation: grouping is better, one known length instead of N attacker-influenced
ones. Unknown future record species: both work provided the compartment is a flat
id→value map, so unknown members pass through untouched.

**Q9.** It reduces the *cryptographic* enforcement to one site but does not eliminate the
per-field runtime check — that check merely changes from "is this an encrypted blob?" to
"is this a reference or an omission?". The projection mode itself should be bound into the
AEAD context, following the domain-separation pattern the inline exemplar had to retrofit
for exactly this reason.

**Q10.** One. No concrete benefit for a taxonomy survives the stated constraints, and a
taxonomy costs a classification policy, a per-compartment key and context, and a new
confusion axis (members moved between compartments).

**Q11.** No. Plus 33% storage on the bulk of the file, no change to length leakage
(base64 is a deterministic length function, so pad before encoding, never after), a second
canonicality surface inside the plaintext where non-canonical encodings are a malleability
channel, and — decisively — it destroys readability of the decrypted view, the only view
where readability was still available. Use raw bytes with explicit length framing inside;
base64 only at the outer boundary if the file must stay 7-bit text.

**Q12.** Grouped, structurally. One authenticated byte-range pair that a reader can hold as
slices and never re-serialise. Inline can achieve the same by MACing the literal skeleton
bytes, but the natural implementation drifts into authenticating a re-serialisation of the
parsed model, because the parsed values are what is in hand — which is what the shipped
exemplar does.
