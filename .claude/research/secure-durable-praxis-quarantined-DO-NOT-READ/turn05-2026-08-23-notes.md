# turn 05 — 2026-08-23

Front: `front-storage-primitives`. Question 4 as a platform-semantics and safe-Rust-reachability
question. Product selection is deferred to `front-selection`; crates appear here only as evidence
about whether a primitive is *reachable*.

## Findings

- **The decisive split is not platform capability, it is safe-Rust reachability, and the two do not
  line up.** Windows has handle-relative atomic no-replace rename at the platform level
  ([A-ms-file-rename-info-noreplace-2026]) and nothing in safe Rust exposes it.
- **Windows genuinely has a real `openat`,** via `NtCreateFile` with `OBJECT_ATTRIBUTES.RootDirectory`
  set from a directory handle, and two maintained crates reach it from safe Rust
  ([A-capstd-windows-open-unchecked-2026], [A-fsat-at-syscalls-windows-2026]). Ownership-bearing
  directory handles are therefore reachable on all three platforms today.
- **But the leading capability crate is handle-relative on Windows only for `open`.** Its Windows
  `rename`, `hard_link`, `remove_file` and `read_dir` reconstruct an absolute path from the handle
  and re-enter the path namespace ([A-capstd-windows-get-path-2026]). The competing crate says so
  in its README and I confirmed it against the code ([A-fsat-at-syscalls-windows-2026]). Publication,
  enumeration and deletion — three of our required properties — are the exact operations affected.
- **`cap-std::fs::Dir` also cannot enumerate without following symlinks on Windows at all**: the
  Windows `ReadDirInner::new` asserts `follow == FollowSymlinks::Yes` and panics otherwise.
- **`std::fs::Dir` exists but is unstable** behind `#![feature(dirfd)]`, tracking issue 120426, so it
  is off-limits at MSRV 1.96; and its `rename` replaces the destination
  ([A-rust-std-fs-toctou-dirfd-2026]).
- **Whole-walk no-follow is a kernel primitive on Linux *and* macOS, not Linux alone.** Darwin has
  `O_NOFOLLOW_ANY` and `O_RESOLVE_BENEATH` ([A-darwin-xnu-fcntl-flags-2026]); Linux has
  `RESOLVE_NO_SYMLINKS` ([A-linux-openat2-resolve-flags-2026]). Both are reachable from safe Rust —
  macOS through `std`'s own `custom_flags`, Linux through `rustix::fs::openat2`
  ([A-rustix-openat2-safe-wrapper-2026]). **Windows has no equivalent**; there it is emulated
  component-by-component with a post-open metadata check ([A-capstd-windows-open-unchecked-2026]).
- **`O_NOFOLLOW` is not the flag people think it is**: it governs only the final component. The
  distinction is stated normatively in the openat2 page and is the reason the design's "whole
  directory walk" requirement is a different requirement from "no-follow on open".
- **macOS `fsync` does not reach the platters.** Apple says so in its own man page
  ([A-apple-fsync-fullfsync-manpage-2014]). Rust's `File::sync_all`/`sync_data` already issue
  `fcntl(F_FULLFSYNC)` on Apple targets — but **with no fallback to `fsync` when it fails**, where
  SQLite explicitly falls back because `F_FULLFSYNC` is unsupported on some filesystems
  ([A-sqlite-os-unix-vfs-2026]). On a network volume our sync can therefore fail where a careful
  C program's would not.
- **There is no directory synchronisation on Windows and the design should stop asking for one.**
  SQLite's Unix VFS opens the containing directory and syncs it; its Windows VFS has no counterpart
  at all — `winSync` is `FlushFileBuffers` on the file handle and nothing more
  ([A-sqlite-os-win-vfs-2026]).
- **What a correct program does when sync reports failure: treat it as unrecoverable, do not retry,
  do not trust the page cache.** All three studied Linux filesystems mark the page *clean* after a
  failed `fsync`, so a retry can falsely succeed ([A-rebello-fsync-failures-2020]); PostgreSQL's
  shipped resolution is to PANIC ([A-postgres-fsync-errors-wiki-2023]).
- **An `fsync` on a file does not persist its directory entry** — the "safe file flush" property —
  and appends are not content-atomic on several filesystems, so a crashed writer can leave a file
  whose tail is *garbage rather than short* ([A-pillai-alice-persistence-2014]). Length alone cannot
  distinguish a clean document from an interrupted one.
- **The journald state-field precedent is real but is the wrong pattern for us.** It is a *mutable*
  header field with an `fdatasync` before and after each transition
  ([A-systemd-journal-file-format-2026]), which contradicts immutability. Exclusive-create-then-publish
  plus front-4's terminator unit achieve the same discriminator without mutating anything.
- **Filenames are not a reliable identity channel.** Windows is case-insensitive by default, macOS is
  case-insensitive by default and normalisation-preserving
  ([B-apple-apfs-faq-normalization-2018]), and a user-space program *cannot learn* the case-folding
  rules of the target directory ([A-basu-name-collisions-case-2023]). **Concrete rule: any
  digest-in-filename scheme must use a case-fold-and-normalisation-invariant alphabet — lowercase
  hex or lowercase base32. Base64 and mixed-case base32 silently halve or collide on two of our
  three platforms.**
- **Exclusive create is the recommended defence against exactly this**, named in that paper:
  `O_CREAT|O_EXCL` "prevents a name collision from overwriting an existing file". It is in `std` on
  all three platforms as `create_new(true)`.
- **Bounded honest enumeration has a hard ceiling: you cannot detect that the directory changed under
  you.** POSIX leaves it unspecified whether an entry added or removed after `opendir` is returned,
  and the RATIONALE records that an error or signal for "directory changed while open" was
  *considered and rejected* ([A-posix-readdir-spec-issue8-2024]).
- **The Windows equivalent of "permissions 0600 or I refuse" is roughly 200 lines of ACE walking**,
  including a SID-history reverse lookup to avoid rejecting a file the user legitimately owns under a
  second SID ([A-win32-openssh-fileperm-acl-2026]). The Unix side is three lines against `fstat` on
  an already-open descriptor ([A-openssh-authfile-perm-ok-2026]). That asymmetry is the front's
  largest single seam.
- **The Unix precedent checks the handle, not the path** — `sshkey_perm_ok(fd, …)` does `fstat(fd)`
  and is called after `open` and before any key bytes are read. That is exactly the ordering the
  key-lifecycle front asked for, and it is free in `std`.
- **The same project's ancestor-directory walk is itself path-based and TOCTOU-vulnerable**:
  `safe_path` calls `realpath` then `stat`s each ancestor by string manipulation
  ([A-openssh-misc-safe-path-2026]). The canonical precedent does not meet the bar the design is
  setting.
- **You cannot fix a TOCTOU by adding a check at the call site.** The Rust security advisory says it
  outright ([A-rust-remove-dir-all-toctou-advisory-2022]). This is the single strongest argument
  against "just be careful" and for taking somebody's safe primitive.
- **Windows deletion is not `unlink` by default**: the entry survives until the last handle closes.
  POSIX-style deletion exists as `FILE_DISPOSITION_POSIX_SEMANTICS`
  ([A-ms-file-disposition-posix-semantics-2024]) and one safe-Rust crate uses it with a Win7 fallback
  ([A-fsat-at-syscalls-windows-2026]).
- **Windows share modes buy something Unix has no analogue for**: withholding `FILE_SHARE_DELETE` on a
  directory handle pins the directory against rename and deletion for the handle's lifetime. The cost
  is that you then cannot delete your own directory while holding the handle
  ([A-capstd-windows-get-path-2026] region; see citation).
- **Windows rename-replace is observably non-atomic** — a Microsoft-STL bug with a full repro shows
  concurrent readers getting `ERROR_FILE_NOT_FOUND` ([A-msvc-stl-rename-deletes-target-2025]). Our
  design does *no-replace* publication, which is the easier case, so this constrains us less than it
  first appears — but it forecloses any later "replace the latest pointer" convenience.
- **The per-user configuration directory can genuinely fail to resolve on Windows and effectively
  cannot on Unix.** `SHGetKnownFolderPath` reads `HKEY_CURRENT_USER` and needs the user's hive
  mounted ([B-chen-knownfolderpath-impersonation-2016]); the common Rust resolver returns nothing when
  it fails, while on Unix it falls back from `$HOME` to `getpwuid_r`
  ([B-dirs-sys-config-resolution-2026]). "Not configured" is a Windows-service-and-CI state, not a
  Unix one.
- **The testable-seam answer is a virtual filesystem, and it is thirty years old.** SQLite routes its
  whole syscall surface through an overridable function-pointer table *explicitly* for fault
  injection ([A-sqlite-os-unix-vfs-2026]) and its crash tests insert an alternative VFS that
  snapshots and then reorders and corrupts unsynchronised writes, looping the failure point forward
  ([A-sqlite-how-tested-crash-io-2026]). Compound-failure tests inject an I/O error *while recovering
  from a prior crash*.
- **Counter-thesis, strongest form: take SQLite whole and delete the entire front.** It absorbs atomic
  publication, crash consistency, cross-process concurrency, enumeration, directory sync and filename
  identity into one dependency, and it names our chosen shape ("pile-of-files") as the thing it
  improves on ([A-sqlite-as-application-file-format-2026]).
- **Counter-thesis, honest cost: it relocates the seams rather than removing them.** Reading a file of
  uncertain provenance safely requires roughly fifteen configuration decisions — trusted-schema off,
  eleven limit values, `integrity_check` first, `cell_size_check` on, mmap off, a hard heap limit
  ([A-sqlite-untrusted-input-defense-2026]). That configuration *is* glue we would author.
- **Counter-thesis, three-honest-implementations form: a Google-authored atomic-write library exports
  nothing at all on Windows**, on the grounds that a correct implementation is not possible there
  ([B-renameio-no-windows-support-2026]).
- **Counter-thesis, opposing practitioner form: a security-tool team that shipped native Windows
  support concluded "write abstractions early"** rather than maintaining three implementations
  ([B-semgrep-cross-platform-windows-2025]).
- **Counter-thesis, usability form, and it is the sharpest: the no-symlink-anywhere rule breaks
  dotfile-manager users, and has done so twice in a shipped tool.** A 387k-star project's config-path
  hardening rejects a symlinked `~/.openclaw`, which is the ordinary GNU Stow layout; two successive
  fixes still did not cover it ([B-openclaw-symlink-config-rejection-2026]). The kernel maintainers
  say the same thing more mildly: setting `RESOLVE_NO_SYMLINKS` indiscriminately "may result in
  spurious errors on previously functional systems" ([A-linux-openat2-resolve-flags-2026]).
- **Portable path abstractions do get Windows wrong in the specific way the counter-thesis predicts**:
  the capability crate blocked `COM1` but not `COM¹` ([A-capstd-windows-device-name-advisory-2024]).
  Low severity, but it is the failure mode, not a hypothetical.

### Reachability matrix (safe Rust, today, MSRV 1.96, `unsafe_code = "forbid"` in our crates)

Legend: **SAFE** = reachable from safe Rust through a maintained dependency or `std`;
**RAW** = the platform has it but only a raw call reaches it, so for us it does not exist;
**NONE** = the platform does not offer it.

| Required property | Linux/Unix | macOS | Windows |
|---|---|---|---|
| Ownership-bearing directory handle | SAFE (`std`+`rustix`, `cap-std`, `fs_at`) | SAFE (same) | SAFE — `NtCreateFile` w/ `RootDirectory`, via `cap-std` or `fs_at`; also a plain `File` on the dir via `FILE_FLAG_BACKUP_SEMANTICS` |
| Subsequent work *through* that handle, not by path | SAFE (`*at` throughout) | SAFE | **SPLIT** — open/create SAFE; **rename, hard-link, delete, enumerate are path-mediated in `cap-std`**; `fs_at` covers delete + enumerate handle-relative but has **no** `renameat`/`linkat` |
| Private temporary/unnamed object in the dir | SAFE (`O_TMPFILE` via `rustix`; else exclusive-create temp name) | SAFE (exclusive-create temp name; no `O_TMPFILE`) | SAFE (exclusive-create; `FILE_ATTRIBUTE_TEMPORARY` via `custom_flags`) |
| Stream + flush + synchronise the object | SAFE (`File::sync_all`) | SAFE (`sync_all` = `F_FULLFSYNC`) — **but no fallback if `F_FULLFSYNC` returns `ENOTSUP`** | SAFE (`sync_all` = `FlushFileBuffers`) |
| Atomic publication under a final name, **no replace** | SAFE — `create_new(true)` at the final name, or `linkat`/`hard_link` from a temp name | SAFE (same) | SAFE **only via `create_new(true)`**; handle-relative no-replace *rename* is **RAW** (`FileRenameInfo`, `ReplaceIfExists=FALSE`) |
| Atomic publication **replacing** an existing name | SAFE (`rename`) | SAFE (`rename`) | **NONE in practice** — observably non-atomic; readers see the target absent |
| Directory synchronisation | SAFE (open dir + `sync_all`) | SAFE (same) | **NONE** — no such operation in the durability contract; NTFS journals metadata |
| Partial/uncommitted files invisible to "most recent" | SAFE (property of the publication step, not a primitive) | SAFE | SAFE |
| Bounded, complete, honest enumeration | SAFE (`Dir::entries().take(n+1)`) — **completeness under a concurrent writer is unspecified everywhere** | SAFE (same caveat) | SAFE via `fs_at` (`FileIdBothDirectoryInfo` on the handle); `cap-std` enumerates by path |
| Never follow a link — **final component only** | SAFE (`O_NOFOLLOW` via `custom_flags`) | SAFE | SAFE (`FILE_FLAG_OPEN_REPARSE_POINT` + post-open metadata check — an *emulation*, not a kernel refusal) |
| Never follow a link — **whole walk** | SAFE (`rustix::fs::openat2` + `RESOLVE_NO_SYMLINKS`; Linux ≥5.6 only, needs a fallback) | SAFE (`O_NOFOLLOW_ANY` via `custom_flags`, macOS ≥11) | **NONE at kernel level** — only component-by-component emulation with a TOCTOU window each step |
| Delete only an object whose identity we established | SAFE (`unlinkat` from the handle; `d_ino` from the same walk) | SAFE | **PARTIAL** — `fs_at` deletes handle-relative with POSIX semantics; identity via `FILE_ID_INFO` is **RAW** |
| Report write/sync/enumerate/cleanup failures | SAFE everywhere (`io::Result`) | SAFE | SAFE |
| Verify key-file ownership+permissions *before* reading | SAFE — `File::open` then `metadata()`; `MetadataExt::uid()/mode()` in `std` | SAFE (same) | **SAFE-BUT-ROTTEN** — `windows-permissions` 0.2.4 (2021, winapi 0.3) covers every needed call; the ~200-line policy is ours to author |
| Filesystem/clock/randomness behind an injected seam | SAFE (our own trait over the above) | SAFE | SAFE |

Honest gaps, stated plainly: **whole-walk no-follow on Windows**, **directory sync on Windows**,
**atomic replace on Windows**, **handle-relative rename/link anywhere on Windows from safe Rust**,
**detecting a disturbed enumeration on any platform**, and **a maintained safe route to Windows ACLs**.
