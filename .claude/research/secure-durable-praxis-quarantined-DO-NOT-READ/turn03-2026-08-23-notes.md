# turn 3 — 2026-08-23 17:40:47 CDT

Front: `front-wire-container`. Which format supports bounded streaming decode, exact binary
fields, deterministic readable structure, unknown-field retention, and explicit partial-damage
status without custom-parser fragility. Library selection deliberately out of scope; decoder
source read as evidence about format hazards, not as package ranking.

## Findings

- `fnd-ordinal-is-a-shape-not-a-format`: the canonical gap-free per-unit ordinal is a property of
  the document SHAPE, not of the format family. Every format used as a flat top-level sequence of
  self-delimiting units gives it for one-pass positional counting; every format used as one big
  nested document with optional fields and maps makes it glue. CBOR sequences, JSON text
  sequences, length-prefixed message streams and the current line-framed format all qualify;
  a single CBOR map document, a COSE structure, a JWE object and a single protobuf message do not.
- `fnd-positional-ordinal-breaks-on-schema-blind-readers`: a positional ordinal is only agreed by
  writer and reader if BOTH count the same units. A reader that does not recognise a unit must
  still count it, which requires encrypted units to be syntactically recognisable without schema
  knowledge. This is the precise reason unknown-field retention and ordinal derivation interact:
  a reader that silently drops an unknown unit desynchronises every nonce after it.
- `fnd-claimed-ordinal-is-self-validating-but-not-position-validating`: the shipped answer
  (AWS Encryption SDK) stores the ordinal explicitly per frame AND requires it to increment by
  exactly one, erroring otherwise. Under derived nonces a lied-about ordinal simply fails to
  authenticate, so storing it is safe; what storing it does NOT do is prove the unit is where the
  writer put it. Reader must compare claimed against counted and report a gap as damage.
- `fnd-damage-model-exists-in-four-places-only`: of everything examined, only four artefacts write
  down a damage model rather than leaving it to the decoder author — JSON text sequences (two ABNF
  grammars, one for parsers permitting recovery and one for encoders), the systemd journal
  (normative rules for both writer and reader on encountering corruption), the age test suite
  (six distinct outcome classes, and a requirement that plaintext released before the error still
  be accounted for), and the AWS ESDK frame sequence rule. CBOR, protobuf, MessagePack, COSE and
  JWE have no damage model at all.
- `fnd-damage-mechanism-is-inert-without-a-checking-decoder`: Avro puts a 16-byte sync marker after
  every block expressly so corrupt blocks are detectable; two mainstream Rust readers parsed the
  marker and never compared it, so production corruption decoded silently into wrong values. The
  same decode path had needed two earlier fixes for block count/size bounds and varint bounds.
- `fnd-truncation-at-a-unit-boundary-is-invisible-to-the-container`: CBOR sequences can reliably
  detect truncation of the LAST item's bytes but cannot detect entirely missing items at the end.
  JSON text sequences say the same more bluntly — nth-element references are unreliable under
  truncation. No structural container closes end-truncation; only a cryptographic final marker
  does, which is why the encryption layer and not the container owns that requirement.
- `fnd-recovery-and-ordinal-are-in-tension`: the recovery behaviour that makes text sequences good
  at damage (skip to the next separator and keep going) is also, by the spec's own security
  considerations, a data-smuggling channel, and it destroys the positional ordinal for everything
  after the damage. Resynchronisation past damage and a positional nonce ordinal cannot both be
  had; a stored-and-checked ordinal is the only construction that gets both.
- `fnd-unknown-retention-needs-self-description-sufficient-to-skip`: a format supports unknown-field
  retention if and only if its wire encoding carries enough type information to copy or skip an
  unknown item without the schema. Cap'n Proto put struct/list/size bits in its pointers
  deliberately for this; protobuf's is INSUFFICIENT (bytes and sub-message share a wire type),
  which is simultaneously why protobuf retains unknown fields badly and why it cannot be
  canonicalised. CBOR and JSON are fully self-describing; FlatBuffers and SBE cannot do it at all.
- `fnd-unknown-retention-is-the-attack-path`: the unknown-field path is not a neutral feature. In
  protobuf-java it WAS the unbounded-recursion vector; in DAG-CBOR, schema-free or `Any`-typed
  fields are precisely what reopens unbounded nesting after the schema otherwise bounds it. Any
  design that retains unknown material must bound that material separately from the known schema.
- `fnd-authenticated-but-unrecognised-beats-unauthenticated-and-merged`: age puts unknown recipient
  stanzas INSIDE the header HMAC and requires implementations to ignore them — authenticated,
  retained, uninterpreted. JWE's shared and per-recipient unprotected headers are outside the
  authentication, and a live 2026 issue shows a mainstream library merging them into the same
  post-decryption header object as the authenticated ones, so attacker-chosen `kid`/`jwk`/`x5c`
  surface as trusted identity. Having the split in the format is not enough; the reader's TYPE
  must keep them apart.
- `fnd-rawvalue-is-the-rust-shape-for-advisory-material`: the "unknown, retained, cannot be
  accidentally promoted" primitive exists off the shelf as a validated-pass-through raw-value type
  that holds one item's exact bytes and requires an explicit second call to interpret them. Two of
  five surveyed Rust CBOR crates have it; plain serde discards unknown fields by default.
- `fnd-deterministic-cbor-is-proved-non-malleable`: the deterministic fragment of CBOR has a
  machine-checked proof of unique binary representation — the first such proof — together with a
  verified validator, parser and serializer extracted to BOTH C and safe Rust. This is the only
  candidate whose determinism claim is settled by proof rather than by specification assertion.
- `fnd-definite-length-cbor-validates-in-constant-stack`: proved, with the general theorem stated:
  a format whose object is a header followed by a contiguous sequence of payload entries, where
  the header alone determines the child count, validates in constant stack and memory. The
  implementation is a counter loop with no recursion. Indefinite-length encodings break this and
  are excluded from the deterministic subset anyway.
- `fnd-determinism-is-opt-in-in-every-real-encoder`: CBOR's own editor states deterministic
  encoding must be switched on explicitly in most implementations, and that the reader-side check
  is re-encode-and-compare. Across five Rust CBOR crates exactly one ships a canonical encoder,
  and that one still accepts indefinite lengths, segmented strings and unknown tags on decode
  "following the robustness principle". Determinism survives real implementations only if you
  enforce it yourself on both sides.
- `fnd-avoid-maps-entirely`: the format editor's own advice — where the structure permits,
  expressing the data item without maps avoids all deterministic-encoding effort beyond preferred
  serialisation. Doing so simultaneously removes map-key ordering, duplicate-key parser
  differentials, the map-inside-map-key stack-consumption case, and makes field position the
  canonical ordinal. This is the single highest-leverage restriction available.
- `fnd-duplicate-keys-are-a-specification-level-anti-pattern`: JSON permits duplicate object keys
  (SHOULD be unique, not MUST), specifies no precedence, and real parsers differ on first-wins
  versus last-wins; the survey names the specification itself as the root cause. CBOR inherits it:
  duplicate map key checking is optional in generic decoders, and neither ciborium nor cbor2
  rejects duplicates by default.
- `fnd-postels-law-is-live-in-the-decoders`: ciborium states it "follows the Robustness Principle …
  liberal in what we accept", and its source silently skips an unbounded run of unknown tags before
  any value, accepts an array where bytes were expected, and never checks duplicate map keys. This
  is the exact inverse of the Most Restrictive Input Definition pattern, in the most widely used
  Rust CBOR crate.
- `fnd-ciborium-is-nonetheless-allocation-safe`: read line by line, ciborium never preallocates from
  a declared length — byte and text bodies grow by `extend_from_slice` from a caller-supplied
  scratch buffer, and fixed-size reads are guarded by `len <= self.scratch.len()`. Recursion is
  bounded at 256 by default with a distinct `RecursionLimitExceeded` error. The residual count-driven
  hole lives in serde's `size_hint`, not in the codec.
- `fnd-decoder-errors-already-carry-offsets`: the low-level CBOR decoder's error type is
  `Syntax(usize)` carrying the byte offset where well-formedness failed. "Valid prefix of N units,
  then damage at offset X" is assemblable from off-the-shelf parts; it is not a bespoke capability.
- `fnd-langsec-endorses-the-flat-record-shape-explicitly`: the LangSec design-pattern paper answers
  "how do we know reading a file of a hundred records is safe" with exactly this design's shape —
  each record judged apart from the others, objects following each other rather than nesting, a
  pattern that may repeat without limit but whose structure is rigid and cannot contain itself.
- `fnd-rolling-your-own-parser-is-worse-than-rolling-your-own-crypto`: stated flatly by the same
  authors, with the reason: faulty input handling comes BEFORE crypto in the attack path and leads
  to full compromise. This is the strongest available answer to "keep the hand-rolled format".
- `fnd-but-the-prescribed-fix-is-subsetting-not-adoption`: the same paper's Most Restrictive Input
  Definition pattern says the grammar should have the minimum complexity needed, which "means
  purposeful, thoughtful subsetting of many protocols, formats, encodings … eliminating unneeded
  variability and introducing determinism and static values". The resolution of this front's
  central question is therefore neither pole: take somebody else's format and decoder, and enforce
  your own strictly narrower recognizer over it.
- `fnd-restricting-the-encoding-measurably-reduces-bugs`: within ASN.1, the permissive BER has 45
  CVEs against DER's 26 out of 95 total; XML has an order of magnitude more CVEs than JSON
  (850, of which 216 XXE-related, versus 96). Both comparisons point the same way: fewer accepted
  forms, fewer bugs.
- `fnd-nested-length-fields-are-the-named-hazard`: nested objects each carrying a length require
  all the lengths to agree with each other and with the whole, "a quadratic number of checks on
  these fields alone", and Heartbleed arose from exactly that construct. Relevant because TLV,
  protobuf and CBOR byte strings all nest lengths; the mitigation is depth, not format choice.
- `fnd-zero-copy-family-is-disqualified`: FlatBuffers' bounds checking is an OPTIONAL upfront
  verifier — "you must explicitly call the verifier, otherwise no bounds checking is performed" —
  and it is "primarily designed for use as a format for static, trusted data files, not network
  messages"; one Cap'n Proto codegen backend states outright that its output must not be used with
  untrusted input. Neither retains unknown fields. Both leave padding on the wire.
- `fnd-leading-length-forbids-single-pass-emission-of-one-big-item`: because a minimal length prefix
  precedes content whose length it encodes, a large length-prefixed item cannot be emitted without
  first knowing its whole length. Moving the length to the trailer restores single-pass emission but
  destroys reliable partial parsing of a truncated serialization, with a worked ambiguous-prefix
  example. A sequence of small individually-buffered units escapes the dilemma entirely — which is
  another reason the flat-sequence shape is the right one.
- `fnd-self-delimiting-means-no-framing-glue-at-the-payload-seam`: a shipped encrypted container
  concatenates a CBOR envelope directly with a detached raw ciphertext — "the envelope is
  self-delimiting CBOR; everything after it is the STREAM ciphertext" — with no length field, no
  separator and no framing code between them. Self-delimitation removes a seam that would otherwise
  have to be authored.
- `fnd-the-chunk-count-ambiguity-is-real-and-was-solved-by-typing-it-advisory`: the same container
  documents that a plaintext of exactly k×chunkSize is a valid stream of either k or k+1 chunks,
  and therefore that a declared count must never be checked against a count re-derived from the
  plaintext length. Their fix is to type the declared count as advisory metadata not required to
  decrypt. This corroborates the earlier front's short-final-chunk finding and shows the shape of
  the residual ambiguity.
- `fnd-cose-and-jose-derive-the-same-named-algorithm-incompatibly`: ECDH-ES key derivation differs
  between COSE (RFC 9053 §6.3.1 with a COSE_KDF_Context) and JOSE (RFC 7518 §4.6, NIST SP 800-56A
  single-step), so "a KEK derived that way will not unwrap"; the same project shipped v0.1.0 with
  the wrong one and had to break compatibility. Taking a standard whole does not eliminate the KDF
  seam, it relocates it into a choice you can still get wrong.
- `fnd-composing-encryption-with-signing-cannot-be-done-cleanly`: encrypt-then-sign lets an attacker
  strip and replace the signature; sign-then-encrypt lets a recipient re-encrypt to a third party.
  The maintainer of the format concerned declines to document a recommended way to combine them.
  The seam-count criterion is not a heuristic here; it is the state of the art.
- `fnd-optional-integrity-is-no-integrity`: OpenPGP's Modification Detection Code was optional for
  years, so attackers stripped it and the resulting warning was ignored by every user and
  application — that is how EFail happened. Bears directly on the partial-damage requirement: a
  partial-status signal that is advisory will be ignored, so it must be a hard failure of the
  "complete" claim, not a warning beside it.
- `fnd-eyeball-readability-is-a-vulnerability-class-not-only-a-feature`: the parser-differential
  survey has an entire category for differentials involving human interaction — the human reads the
  document differently from the machine. Named instances include Unicode Trojan Source bidi
  reordering, a PDF signed-then-updated ambiguity the viewer cannot distinguish, and a crafted
  filename that reads as prose in a dialog. A readable container carrying attacker-influenced text
  inline inherits this class.
- `fnd-encrypting-the-opaque-fields-removes-the-human-differential`: the corollary is a genuine
  both-axes win. Every byte a semi-trusted host can influence is exactly the set of bytes the rich
  projection encrypts, so the readable skeleton contains no attacker-controlled text at all, and
  the plain projection cannot represent those fields by construction. Readability and the
  human-parser-differential defence point the same way here.
- `fnd-exact-binary-and-readability-barely-conflict-here`: the same corollary settles the
  exact-binary requirement. Under the rich projection the exact bytes are ciphertext, which is
  opaque regardless of container; under the plain projection they are absent. The transcoding
  question therefore reduces to whether the container round-trips ciphertext exactly, which every
  candidate does.
- `fnd-binary-formats-end-up-shipping-a-text-projection`: three independent instances. systemd's
  own maintainers tell you not to parse the journal binary format and to use the Journal Export
  Format instead. Cap'n Proto's author names JSON conversion via reflection as a debugging use of
  reflection "because it is human-readable". CBOR ships diagnostic notation, a CLI and
  round-trippable text. Choosing binary does not avoid the text format; it adds one.
- `fnd-cbor-readability-is-tool-mediated-not-eyeball`: honest answer. CBOR is not readable by eye;
  it is readable with one small ubiquitous tool that renders diagnostic notation and parses it
  back, including a mode that annotates integer protocol keys with their string names as comments.
  The stored-file specification even chose its magic bytes so that a human in a hex dump sees the
  ASCII characters "CBOR" prominently. That is a real but strictly weaker property than text.
- `fnd-quoting-a-fragment-is-the-operational-readability-test`: the sharpest statement of why
  readability is operational rather than aesthetic — with text you can copy-paste the relevant
  section into a message when reporting an issue, and "things are much harder with a binary
  format". Directly the whylog-handed-to-a-vendor case.
- `fnd-sops-is-the-shipped-precedent-and-its-mac-violates-prefix-determinism`: sops keeps keys in
  cleartext explicitly "for better diff and overall readability" and encrypts only leaf values —
  the design's exact shape, shipped. But its integrity story is a MAC over ALL the values,
  computed at the end, precisely to detect added or removed values; and it uses the value's key
  path as AEAD associated data, which YAML anchors break. Detecting element removal is what pushes
  a design toward a whole-document authenticator, and a prefix-only design must buy it another way.
- `fnd-sops-mac-only-encrypted-is-the-tension-made-configurable`: sops exposes a flag that MACs only
  the encrypted values rather than all of them, so the plaintext skeleton can be edited without
  invalidating the document. That is readability-versus-integrity shipped as a knob, and it is
  worth knowing that a mature tool did not find a way to have both.
- `fnd-journal-recovers-but-does-not-report-partial`: the systemd journal's normative reader rule is
  to skip corrupted data, expose as much as possible, and "interleave rotated and corrupted files
  as good as possible and present them as single stream to the user". Maximum recovery, no partial
  status. Its explicit completeness signal is elsewhere: a header state field distinguishing
  offline, online and archived, so a file that was never cleanly closed is identifiable.
- `fnd-journal-two-tier-unknown-policy`: compatible flags mean keep reading, incompatible flags mean
  refuse and ask for a software update; unknown object types are skipped; reserved fields must be
  written zero and ignored on read. A shipped three-way taxonomy of unknown material.
- `fnd-padding-has-no-native-element-in-the-binary-candidates`: OpenPGP has a Padding packet
  (registered by the earlier front, not re-read here); TLS 1.3 has record padding. CBOR, protobuf
  and COSE have none. Retrofitting into CBOR is nonetheless cheap and canonical: in an
  array-shaped record a trailing byte-string field is positionally deterministic and ignorable, and
  unknown tags are skipped by generic decoders. Fixed-size framing is itself coarse padding —
  a 64 KiB-chunked payload leaks length only at chunk granularity.
- `fnd-two-projections-can-be-mechanically-proved-disjoint`: CDDL alone does not guarantee it —
  alternatives are not required to be disjoint and map groups can be ambiguous, and the shipped
  CDDL of COSE and DPE had to be AMENDED to become unambiguous. But an elaboration algorithm exists
  that proves well-formedness, rejects ambiguous schemas, and then generates verified parsers and
  serializers per rule. Two rules over one grammar can therefore be a checked guarantee rather than
  a convention — which no other candidate's schema story offers.
- `fnd-protobuf-two-types-is-actively-unsafe`: protobuf messages are not self-identifying on the
  wire, so a rich message decoded as the plain type does not fail — under a retaining
  implementation its encrypted fields land in the unknown-field set and round-trip back out. The
  narrow projection would carry exactly what it is supposed to be unable to represent.
- `fnd-counter-the-format-is-not-where-most-of-the-risk-is`: worth stating plainly against my own
  findings. Every damage model examined was implemented wrongly or partially by at least one real
  decoder; determinism is opt-in everywhere; padding is absent everywhere. The differences between
  the plausible candidates are smaller than the difference between a checked and an unchecked
  reader of any of them.

## Not pursued, and why

- MessagePack, BSON, UBJSON, Amazon Ion: strictly dominated. Each is a less-specified CBOR with no
  deterministic profile, no proof work, and a comparable decoder-CVE profile; nothing they offer is
  absent from the shortlist. One MessagePack advisory (EXT32 unbounded allocation) was noted in
  passing and adds nothing the DAG-CBOR one does not already say better.
- ASN.1 DER: eliminated on the CVE record above and on readability, without further reading.
- YAML: eliminated without further reading. Anchors alone break structural authentication (shown
  concretely by sops), and alias expansion is a resource-amplification vector.
- Cap'n Proto and FlatBuffers were read only far enough to eliminate them; their RPC and mutation
  stories are irrelevant here.
- KDBX, Cryptomator, Tink and the OpenPGP packet grammar were left to the earlier front, which
  registered them; I did not re-read them and have cited none of them verbatim.
- Which crate to depend on. Decoder source was read strictly as evidence about what decoders do to
  a format. Nothing here is a package recommendation, and the two Rust crates read are evidence of
  VARIANCE between decoders, not candidates.
- Compression interactions were not re-examined; the earlier front closed that question.
