# turn 4 — 2026-08-23 18:04:39 CDT

Front: `front-key-lifecycle`. Where the per-user key comes from, how it is recovered or
rotated against immutable files, and what precisely constitutes "encryption unavailable".

## Findings

Mode selection and "unavailable"

- **A shipped tool already implements the irrevocable-mode ruling exactly.** Borg fixes the
  encryption mode at repository creation, refuses to vary it per archive, and refuses to
  change it afterwards; the un-encrypted options are separate named modes, not a degraded
  encrypted mode. That is the plain projection ruling, in production, with a decade of users.
- **Chromium is the counter-example the ruling forbids**, and it is the default behaviour of
  the single most-deployed local-encryption implementation: detect a store, and *silently fall
  back* to a plaintext store when the detected one is not available.
- **The most useful shipped contrast is Git Credential Manager**: it enumerates stores, marks
  each with the platform and session type it needs, ships *no default at all* on Linux, and
  makes both the plaintext store and the no-store mode explicit named selections rather than
  fallbacks. Refusing to choose is a defensible product decision.
- **VS Code's shape is the warned-degraded-mode anti-pattern**: an opt-in "basic text
  encryption" the docs themselves label "not recommended", reached by editing a config file
  after a modal error. In the field it did not even work for the reporter.
- **Unavailability is at least two-valued, and conflating the two destroys data.** Chromium's
  key-provider interface distinguishes `kPermanentlyUnavailable` from
  `kTemporarilyUnavailable` and its own comment warns that returning "permanent" may cause
  callers to conclude previously encrypted data is lost and *drop it*. Default to temporary.
- **A third axis exists and is separately shipped**: "may this key encrypt new data" is a
  different predicate from "may this key decrypt old data" (`UseForEncryption()` in Chromium;
  originator-usage versus recipient-usage period in NIST). This is the axis a rotation story
  lives on.
- **The randomness seam has a precisely enumerable failure set on Linux**: block until the
  pool is initialised, `EAGAIN` if told not to block, `ENOSYS` on a kernel without the call,
  `EINTR`, and short reads above 256 bytes. Small reads from an initialised pool are the only
  case with a no-short-read guarantee.

Key sources, per platform

- **Windows DPAPI's contract is user-logon-credential-bound and usually machine-bound**, with
  a roaming-profile exception; the machine-wide flag dissolves the per-user boundary entirely
  (any user on the box can decrypt). The `CRYPTPROTECT_UI_FORBIDDEN` flag is the documented
  no-interaction path and its failure is `ERROR_PASSWORD_RESTRICTION`.
- **Windows Credential Manager cannot be written over an SSH session at all** — first-party
  statement in GCM's docs, attributed to a Windows limitation; RDP does not suffer it. This is
  a hard "unavailable" case on a first-class platform, not an edge case.
- **macOS: Apple's own platform-security guide does not document the behaviour everyone hits.**
  It covers iOS accessibility classes and the securityd/access-group model; the locked
  login keychain in a non-GUI session is absent. The honest record is entirely in issue
  trackers, which is itself a finding about how much vendor documentation can be relied on.
- **Linux has no single answer and the failure is routine.** Chromium detects GNOME libsecret,
  three KWallet generations, or plaintext. A fully installed, running gnome-keyring still fails
  when `DBUS_SESSION_BUS_ADDRESS` is unset — a maintainer confirmed correct configuration and
  the reporter's root cause was the missing bus address.
- **The platform key store's boundary is the user principal, not the process** — stated by the
  GNOME Keyring team themselves ("Any application that executes with the same user's
  privileges can get access to any of the user's keyrings"). Chromium's owner says the same for
  Windows DPAPI, and notes macOS is only partially better because malware can drive the real
  application as a sock-puppet.
- **systemd is the one place a no-ceremony key source is fully specified**: TPM2-derived key,
  or a host key file under `/var`, or both, chosen automatically with no user setup, and with
  the unavailability cases (no TPM2, `/var` not yet mounted in early boot) named and given a
  different mode flag.
- **The honest baseline is a key file in the per-platform user config directory**, and SOPS
  specifies it precisely: `$XDG_CONFIG_HOME/sops/age/keys.txt`, `~/Library/Application
  Support/...` on macOS, `%AppData%\sops\age\...` on Windows, with three environment overrides
  including a key-*producing command*, plus reuse of the user's existing SSH private key.

Rotation and recovery against immutable files

- **NIST supplies the vocabulary and rules the question.** Originator-usage period ends when the
  key may no longer *apply* protection; recipient-usage period extends past it so stored data
  can still be read. Retention for a symmetric data-encryption key is "until no longer needed
  to decrypt data encrypted by this key". Cryptoperiods for *stored* data are deliberately
  longer precisely because re-encryption is burdensome.
- **NIST forbids deriving a replacement key from its predecessor** ("Federal applications shall
  not use key update"), which rules out the tempting cheap chain.
- **The shipped rotation pattern is a wrapped master key, and its limit is stated bluntly by
  both projects that use it.** Borg: changing the passphrase "only changes the passphrase, but
  not any secret protected by it … does not protect future (nor past) backups". Restic: "since
  the local encryption key gives access to the master key, a password change will not prevent
  this", and "it is impossible to securely revoke a leaked key without re-encrypting the whole
  repository".
- **The maintainer's reason for refusing multi-key retention is exactly the key-identity
  problem**: "each blob/pack would need an additional header that specifies which key should be
  used to decrypt/verify it. This means a lot of additional complexity and another layer of
  indirection." Retention and cleartext key identifiers are the same decision.
- **Restic's accepted answer to rotation was not rotation**: copy into a fresh repository under
  a new master key. Against immutable files that is "start a new store", not "re-key".
- **Retention-as-key-deletion has a named, unsolved cost**: the journald analysis states that
  secure erasure of the old key "is not easy to guarantee and is a research topic on its own",
  and NIST's own footnote says simple deletion may not obliterate.
- **Tink's rotation discipline is an ordering constraint, not a re-encryption**: add the key,
  distribute, only then make it primary. Decryption tries every key in the set.

Key identity in the header

- **Trial decryption is the shipped default in three independent designs** and a key identifier
  is a stated *optimisation*: Tink's five-byte prefix exists "to avoid trying all keys" and is
  per-key opt-in; SOPS tries every identity in `keys.txt` in sequence; OpenPGP's wildcard
  key-id forces the recipient to try every candidate subkey.
- **age's `p256tag` recipient types are the cleanest statement of the trade**, and they exist
  only because hardware keys make trial decryption expensive in *user presence*: "With
  knowledge of the public key, it is possible to check if a stanza was addressed to a specific
  recipient before attempting decryption. (This offers less privacy than the default recipient
  types.)" The tag is four bytes and is a salted HKDF over the ephemeral key plus a truncated
  hash of the recipient — so it is per-file unlinkable to an observer without the public key,
  and recognisable to a holder who has it. **That is the construction the front's question asks
  for, already specified.**
- **The linkability leak is the enumeration leak**: OpenPGP's own developer handbook says an
  observer "can easily enumerate recipients of a message by comparing the PKESKs with
  certificates of potential recipients" — the identifier is only harmful because it is
  *stable and matchable against a candidate*, which a per-document salted tag is not.

Fail before crypto

- **The cheap wrong-key pre-check is a named decryption oracle.** OpenPGP's SEIPDv1 "quick
  check" (two repeated plaintext bytes) is warned against by the standard for exactly this
  reason; the recommended replacement is to let the AEAD's first-chunk tag be the answer.
- **The shipped fail-before-crypto boundary is a strict grammar plus fixed-width field
  validation, and the length checks are explicitly anti-partitioning-oracle.** age requires the
  version line to match exactly, rejects non-canonical base64, rejects stanzas with the wrong
  argument count, and states "MUST check that the body length is exactly 32 bytes before
  attempting to decrypt it, to mitigate partitioning oracle attacks."
- **The file must not choose which key backend runs.** age's plugin dispatch keys off the
  *reader's own identity encoding*, not off anything in the file, and Filippo records this as a
  deliberate decision to avoid "giving potentially untrusted files control over what plugins
  are executed."

Unit count and element removal

- **Yes, binding sequence completeness is sound, it is shipped, and not doing it earned CVEs.**
  AWS's message-body specification requires the final frame's sequence number to equal the total
  number of frames, inside that frame's own authentication tag. journald did not check epoch
  continuity and got CVE-2023-31438 (truncation by removing a seal) and CVE-2023-31439
  (back-dating with a newer key); both fixes are completeness checks.
- **But the count is bound where it is known, not where the key is committed.** AWS binds it in
  the terminator; journald's fix seals every epoch, including empty ones, so absence is
  detectable. Neither binds a total into the header. This is compatible with the
  prefix-determined constraint if the terminator is itself an ordinary unit.
- **journald's fix does use an authenticated `isfinal` flag** — which reads against front 2's
  "not a final-chunk flag" — but only because the sealing key is *destroyed* the moment a final
  block is produced, so a second one cannot be forged. Without forward-secure erasure the
  objection stands.

Password derivation

- **Partitioning oracles do not threaten random keys but do threaten key anonymity.** The paper
  is explicit: the attack "will not work to recover much information about, e.g., random
  128-bit keys where d = 2^128, but we show that it suffices to be damaging in settings where
  keys are derived from user-selected passwords *or where key anonymity is important*."
- **The attack needs an adaptive oracle**, i.e. an interface the attacker can feed chosen
  ciphertexts to and observe success/failure. A reader run by the key owner on their own file
  is not one; a reader pointed at a directory another local principal can write into is closer
  to one.
- **age's mitigation is a shipped pattern to copy**: exact-length checks before any decryption,
  plus a rule that a password stanza may be the *only* stanza in a file, rejecting mixed
  headers outright.
- NIST requires SP 800-132 KDFs for keys derived from passwords for storage applications, and
  notes such keys are "likely to be less secure than randomly generated keys".

First run and the counter-thesis

- **clig.dev's rules constrain the first run**: only prompt if stdin is a TTY; if `--no-input`
  is passed, fail and say which flag to pass instead. A once-per-invocation batch tool
  therefore cannot rely on a setup prompt.
- **The no-key position has standards backing**: OWASP's logging guidance lists access tokens,
  authentication passwords, database connection strings and "encryption keys and other primary
  secrets" among data that should not be recorded directly in logs at all — removed, masked,
  hashed or encrypted at capture.
- **And ecosystem backing**: clig.dev says do not read secrets from flags *or* from environment
  variables; Dribin's demonstration is that a `--password` flag has already leaked to shell
  history and to `ps` before the tool ever ran. If the argv field carries a token, it is not the
  only copy.
- **The strongest counter is from the person who shipped it**: "keeping secrets from yourself is
  a fool's errand, so it's a waste of time and effort to encrypt data if you have to store the
  decryption key in a place that's accessible to the attacker" — with the honest residual value
  named (a misconfigured web server exposing a profile directory; a laptop without full-disk
  encryption) and a catalogue of field failures: silent DPAPI loss, a Windows scheduled-task
  bug that corrupted DPAPI credentials and took months to root-cause, and an Edge/macOS
  keychain error whose UI *offered to wipe the user's data*.
- **Where readability and security are NOT in tension**: mode-before-first-byte, the two-valued
  unavailability distinction, the separation of encrypt-new from decrypt-old, the strict
  fail-before-crypto grammar, and binding sequence completeness. Every one of these makes the
  reader's diagnostics *better* — "this document was written in plain mode", "this key is
  temporarily unlocked-elsewhere, not gone", "unit 7 of 12 is missing" — while also being the
  secure choice.

### Key identity in the clear: an optimisation, with a stated privacy price

### Partitioning oracles and password derivation

> [A-len-partitioning-oracle-attacks-2021]:p.1 §1 (relevance: +1:SURE)
> Given access to an oracle that reveals whether decryption succeeds, our key multi-collisions
> for AES-GCM enable a partitioning oracle attack that recovers the secret key in roughly
> m + log k queries in situations where possible keys fall in a set of size d = m · k. This will
> not work to recover much information about, e.g., random 128-bit keys where d = 2^128, but we
> show that it suffices to be damaging in settings where keys are derived from user-selected
> passwords or where key anonymity is important.

> [A-len-partitioning-oracle-attacks-2021]:p.2 §2 "Attack abstraction" (relevance: +1:SURE)

> possible values D. The attacker has access to an interface that takes as input a bit string V,
> and uses it plus pw to output the result of some boolean function f_pw […] Given oracle access
> to adaptively query f_pw on chosen values, the question is: Can an attacker efficiently recover
> pw?

### The counter-thesis

> [A-lawrence-chromium-local-data-encryption-2020]:¶2 (relevance: +1:SURE)
> Generally speaking, "keeping secrets from yourself" is a fool's errand, so it's a waste of time
> and effort to encrypt data if you have to store the decryption key in a place that's accessible
> to the attacker. That's one reason why physically local attacks and machines infected with
> malware are generally outside the browser's threat model.

> [A-lawrence-chromium-local-data-encryption-2020]:§"Okay, so Local Data Encryption might be useful" (relevance: +1:SURE)
> However, that's not to say that Local Data Encryption is entirely without value– for instance,
> I recently came across a misconfigured web server that allowed any visitor to explore the server
> owner's profile (e.g. c:\users\sally), including their Chrome profile folder. Because the
> browser key in the profile is encrypted using a key stored outside of the Chrome profile, their
> most sensitive data remained encrypted. Similarly, if a laptop isn't protected with Full Disk
> Encryption, Local Data Encryption will make a thief's life harder.

> [A-lawrence-chromium-local-data-encryption-2020]:§"Tradeoffs?" (relevance: +1:SURE)
> The bigger risk is complexity: If something goes wrong with either of the keys […] then the
> user's cookie and credential data will be unrecoverable. […] On Mac, Edge recently had a problem
> where the browser would fail to get the browser key from the OS keychain. The browser would offer
> to wipe the keychain (losing all of your data) […] On Windows, DPAPI failures are typically
> silent– your data disappears with nary a message box.

> [B-owasp-logging-cheat-sheet-2026]:§"Data to exclude" (relevance: -0:SUSPECT)
> The following should usually not be recorded directly in the logs, but instead should be
> removed, masked, sanitized, hashed, or encrypted: Application source code / Session
> identification values […] / Access tokens / […] Authentication passwords / Database connection
> strings / Encryption keys and other primary secrets / Bank account or payment card holder data /
> Data of a higher security classification than the logging system is allowed to store

> [B-owasp-logging-cheat-sheet-2026]:§"Event collection" (relevance: -0:SUSPECT)

> running or allow information leakage

> [B-clig-command-line-guidelines-2026]:§Arguments and flags (relevance: +1:SURE)
> Do not read secrets directly from flags. When a command accepts a secret, e.g. via a --password
> flag, the flag value will leak the secret into ps output and potentially shell history. And,
> this sort of flag encourages the use of insecure environment variables for secrets.
> […] Consider accepting sensitive data only via files, e.g. with a --password-file flag, or via
> stdin.

> [B-clig-command-line-guidelines-2026]:§Environment variables (relevance: +1:SURE)
> Do not read secrets from environment variables. While environment variables may be convenient
> for storing secrets, they have proven too prone to leakage […] Secrets should only be accepted

> [B-clig-command-line-guidelines-2026]:§Interactivity (relevance: +1:SURE)

> --no-input is passed, don't prompt or do anything interactive. […] If the command requires
