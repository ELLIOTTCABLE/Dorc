## Findings

- `fnd-ad-must-be-injective`: the AEAD interface takes ONE associated-data string. Binding a
  tuple (field name, scope, ordinal, schema version, length) is a vector-to-string problem, and
  the definitional requirement is that the encoding be *injective* — stated by the author of the
  AEAD-with-AD definition in the document that introduced the associated-data problem.
  Naive `a || b || c` over variable-length parts is not injective and is the trap.
- `fnd-two-designs-put-context-in-the-kdf-not-the-aad`: the two most current serious chunked-AEAD
  designs both leave the AEAD's own AAD EMPTY and bind context through the key-derivation info
  string instead. The stated reason is that context is already bound there; the stated cost is
  that context must be known before encryption starts. This converts an authoring problem
  (invent an AD encoding) into a use of somebody else's KDF contract.
- `fnd-nonce-never-from-the-rng`: four independent authorities converge — derive the nonce
  deterministically from context plus an index, and put the randomness in the KEY (a per-document
  salt feeding a KDF), never in the nonce. NIST's deterministic IV construction, TLS 1.3 /
  ChaCha20-Poly1305 / OCB record nonces, Tink's streaming design, and Cobblestone all do this.
  This is the answer to the deterministic-replay collision: a replay harness that reproduces a
  seed cannot reproduce a nonce, because the nonce was never drawn from the seed.
- `fnd-nist-forbids-reuse-only-on-distinct-inputs`: the normative uniqueness requirement is
  against invoking encryption with the same IV and key "on two (or more) DISTINCT sets of input
  data". A byte-for-byte replay that produces an identical message is not a violation. The
  hazard is precisely the DST case where the seed is held and the CONTENT is varied.
- `fnd-counter-reset-is-the-published-failure`: the exact structural hazard a replay harness
  reproduces is already in the literature under a different name — "routers are booted frequently
  and their counters will therefore be reset often" — and the shipped answer (Tink) was to move
  randomness into a per-message derived subkey so that repeating short nonces live under
  different keys. The same paper then shows that answer is NOT robust to randomness failure.
- `fnd-hedging-is-the-general-fix`: the general, proved construction for "randomness may repeat"
  is hedging: replace `Op(inputs; R)` with `Op(inputs; Hedge(R, OpID, inputs))` where Hedge is
  HMAC and the inputs are folded in under an unambiguous encoding, with a domain-separating
  operation id. Hedged symmetric encryption then leaks nothing but plaintext equality even under
  adversarially chosen randomness.
- `fnd-wrong-key-is-not-an-error-by-default`: standard AEADs do not commit to the key. A reader
  arriving with a wrong or rotated key can get a DIFFERENT VALID plaintext rather than a failure,
  and there is a cheap fix (CTX: replace the tag with `H(K, N, A, T)`) that commits to key, nonce,
  associated data AND message, at cost independent of message length and no ciphertext growth.
- `fnd-one-known-key-suffices`: the sharpest commitment attack is weaker-adversary than usually
  quoted — knowing just ONE key, an attacker can compute an associated-data value that makes an
  honestly produced GCM or OCB ciphertext decrypt validly under that key. Since this design's
  associated data would be derived from a PLAINTEXT skeleton that anyone holding the file can
  edit, the attacker-controls-AD precondition is satisfied by construction.
- `fnd-final-chunk-flag-is-the-trap`: authenticating each chunk but not the sequence is the known
  trap, and the two closures are (a) a short-final-chunk rule and (b) a final tag over the total
  plaintext length. A final-chunk FLAG is the worse option and the rationale is written down:
  in-band signalling, trial decryption or look-ahead on the streaming reader, extra buffering, an
  empty-chunk exception, and — decisively — with full final chunks one valid ciphertext length can
  be both a valid truncation and a valid message.
- `fnd-eof-vs-error-confusion`: the first-party warning on the deployed streaming construction is
  that an API which returns "an error" for both end-of-file and decryption failure lets an
  adversary truncate files. The reader must distinguish clean termination from damage and must
  keep reporting the error on subsequent reads rather than presenting a clean end.
- `fnd-lengths-identify-objects`: measured, not argued — 45% of 848k real hard-drive user files
  are uniquely identifiable by size alone, and 83% of 56k Ubuntu packages; padding to a fixed
  block size barely helps. Per-field AEAD is length-preserving plus a fixed tag, so per-field
  ciphertext lengths are per-field plaintext lengths.
- `fnd-standards-treat-length-leak-as-real`: OpenPGP carries a Padding packet whose stated purpose
  is defeating traffic analysis, with the canonical example that a yes (3 octets) / no (2 octets)
  plaintext is revealed by its encrypted length.
- `fnd-openpgp-ad-is-all-fixed-width`: the shipped standards-track answer to the AD-encoding
  problem is to make every component fixed width — packet type, version, cipher id, AEAD id, chunk
  size, each one octet — so concatenation is injective for free, and to bind the SAME tuple again
  through the HKDF info string.
- `fnd-relocation-has-a-standard-name`: moving an authenticated object into another context is
  "surreptitious forwarding" in the standard, and the standard remedy is binding the intended
  recipient into the signed material — the format-level statement of "must not be movable".
- `fnd-unauthenticated-material-must-be-typed-advisory`: OpenPGP's hashed/unhashed subpacket split
  is a shipped model for retaining unauthenticated material inside an authenticated container:
  it is typed as advisory only, never promoted.
- `fnd-confused-deputy-is-copy-paste`: the practical attack on per-field encryption is not
  cryptographic — copy one encrypted field over another and let the reader decrypt it in the wrong
  context. A maintainer needed three attempts to close it: per-field key derivation, then key
  commitment (because non-committing AEAD defeats per-field keys), then row identity in the AD.
- `fnd-ad-binding-has-an-ordering-cost`: binding record identity into AD means the identity must
  be known BEFORE the field is encrypted. Directly constrains a streaming writer: nothing computed
  at the end of the document (a whole-file digest, a final count) can be bound into an earlier
  field's AD.
- `fnd-glue-is-the-named-cause`: the two strongest recent break-a-real-system papers both name the
  seams. Threema: "using modern, secure libraries for cryptographic primitives does not on its own
  lead to a secure protocol design", with its bespoke metadata construction traced directly to a
  library that lacked associated-data support. Matrix: protocol confusion, checking properties at
  display time rather than receive time, and missing domain separation between two identifier
  namespaces so one value could be reinterpreted as the other.
- `fnd-compression-is-algorithmic-not-implementational`: the compression side channel is a property
  of the algorithm, not the implementation, so no implementation escapes it — and a real messenger
  lost long-term private keys through the length of compressed-then-encrypted backups because an
  attacker could inject chosen plaintext into the same file.
- `fnd-memory-safety-is-not-resource-safety`: a current Rust CVE is exactly the bounded-reader
  failure — decoding a length-prefixed field into an owned allocation before checking the prefix
  against a local bound — with a count-driven variant where element fanout, not byte length, is
  the multiplier, and a compression stage amplifying 652 bytes into 600 KB before the parser runs.
- `fnd-vectors-are-negative-tests`: the test-vector practice is not round-tripping. The corpus is
  organised around known attacks; the "invalid" and "acceptable" vectors are the point, and for a
  chunked construction the vector flags are exactly the failure modes above — partial-plaintext
  prefix, valid-final-chunk, header failure, invalid key size.
- `fnd-salt-injection-is-the-testable-seam`: a randomised scheme is made deterministically testable
  by exposing a salt-injection entry point (or a raw deterministic mode), NOT by making the random
  generator injectable in the crypto path. The vector guide specifies this as the supported way to
  test encryption. This reconciles replayable testing with nonce discipline without weakening
  production.
- `fnd-counter-storage-encryption`: the counter-thesis in its strongest form — storage encryption
  addresses offline theft and disk disposal, and against a live attacker with application-level
  access "it might as well be plaintext"; symmetrically, local file encryption under a key the
  local account can derive buys nothing against that account.
- `fnd-counter-the-system-remembers`: the sharper counter-thesis — the leakage that defeats
  application-level encryption comes from the surrounding system retaining the same values
  (logs, caches, in-memory residue), not from the cipher. Encrypting one artefact while the same
  bytes sit in shell history, the process table, and the source files on disk is the same shape.
- `fnd-counter-no-cleartext-markers`: the strongest published position against a readable skeleton
  is that encrypted formats should carry NO cleartext markers at all, because plaintext headers
  leak format version, scheme, recipient count and identities, and the software that produced them.
- `fnd-partitioning-oracle-needs-low-entropy-keys`: multi-key-collision attacks are not damaging
  against random 128-bit keys, but are damaging when keys derive from user-selected passwords or
  when key anonymity matters, and they need an oracle revealing whether decryption succeeded.
  A read-back subcommand that reports "wrong key" IS such an oracle. Hands a constraint to the
  key-lifecycle front.
- `fnd-streaming-and-misuse-resistance-are-exclusive`: nonce-misuse-resistant AE cannot be online —
  every ciphertext bit must depend on every plaintext bit — so a streaming document cannot be
  misuse-resistant as a whole. The choices are per-segment nAE (STREAM) or per-segment MRAE
  (CHAIN), and no online definition "can meaningfully tolerate nonce-reuse".
- `fnd-online-ae-leaks-common-prefixes`: any online AE scheme leaks longest-common-prefix
  structure, which supports a chosen-prefix/secret-suffix recovery attack; this is why nonce reuse
  cannot be tolerated even under the stronger of the two streaming definitions.
- `fnd-authenticate-every-segment`: the argued position is that EVERY segment should carry its own
  expansion rather than only the last, because a reader acting on a prefix deserves assurance for
  that prefix; the bandwidth argument against it is under 2% at 1 KiB segments with 128-bit tags.
- `fnd-right-answers-were-silent-on-commitment`: the best-known practitioner "right answers"
  document recommends exactly the construction a library maintainer later had to reverse for lack
  of key commitment, and never mentions commitment. Evidence for why so many systems shipped
  without it — and a caution about the shelf life of practitioner guidance in this area.

### Granularity and what a plaintext skeleton leaks

> [A-nikitin-purbs-padme-2019]:Abstract p.6 (relevance: +1:SURE)
> Most encrypted data formats leak metadata via their plaintext headers, such as format version,
> encryption schemes used, number of recipients who can decrypt the data, and even the recipients'
> identities. This leakage can pose security and privacy risks to users, e.g., by revealing the
> full membership of a group of collaborators from a single encrypted e-mail, or by enabling an
> eavesdropper to fingerprint the precise encryption software version and configuration the sender
> used.

> [A-nikitin-purbs-padme-2019]:§1 p.7 (relevance: +1:SURE)
> Analysis of real-world data sets show that many objects are trivially identifiable by their
> unique sizes without padding, or even after padding to a fixed block size (e.g., that of a block
> cipher or a Tor cell). We show that Padmé can significantly reduce the number of objects uniquely
> identifiable by their sizes: from 83% to 3% for 56k Ubuntu packages, from 87% to 3% for 191k
> Youtube videos, from 45% to 8% for 848k hard-drive user files, and from 68% to 6% for 2.8k
> websites from the Alexa top 1M list. This much stronger leakage protection incurs an average
> space overhead of only 3%.

> [A-nikitin-purbs-padme-2019]:§4.3 p.16 (relevance: +1:SURE)
> In practice, when plaintext sizes differ by orders of magnitude, there is no good value for b
> that serves all plaintexts well. […] To reduce information leakage asymptotically over a vast
> range of cleartext sizes, therefore, padding must depend on plaintext size.

> [A-rfc9580-openpgp-2024]:§13.11 (relevance: +1:SURE)
> For example, if possible cleartext messages for a given protocol are known to be either yes
> (3 octets) or no (2 octets) and the messages are sent within a Symmetrically Encrypted and
> Integrity Protected Data packet, the length of the encrypted message will reveal the contents of
> the cleartext.

### The glue mandate: composition failures

> [A-paterson-threema-lessons-2023]:§5 p.1301 (relevance: +1:SURE)
> First, using modern, secure libraries for cryptographic primitives does not on its own lead to a
> secure protocol design: It is possible to misuse libraries such as NaCl and libsignal when
> building a more complex protocol and developers must be wary not to be lulled into a false sense
> of security. […] In some cases, it is the API of the libraries themselves that encourages bad
> cryptographic practice. For instance, NaCl's authenticated encryption routines do not allow for
> associated data. This was the reason for the Threema's bespoke metadata box construction. To
> their credit, Threema's developers did (largely) avoid "rolling their own crypto" but this advice
> should be extended to "don't roll your own cryptographic protocol".

> [A-paterson-threema-lessons-2023]:§4 p.1301 (relevance: +1:SURE)
> The attacks […] exploit the fact that the same "X25519-then-Encrypt" paradigm is used multiple
> times for different purposes but with the same keys. By using payloads created in one protocol in
> another, the adversary gains capabilities that they would not have when viewing the protocols
> separately. A secure application should cryptographically compartmentalise its protocols, taking
> a very conservative approach when using the same cryptographic material in different protocols.

### Terminology to specify in

> [A-rfc9771-aead-properties-2025]:§4.3.2 (relevance: +1:SURE)
> An AEAD algorithm guarantees that it is hard to find two or more different tuples of the key,
> nonce, associated data, and plaintext such that they encrypt to the same ciphertext. In other
> words, an AEAD scheme guarantees that a ciphertext is a commitment to all inputs of an
> authenticated encryption operation. Security notions: CMT-4.

> [A-rfc9771-aead-properties-2025]:§4.3.7 (relevance: +1:SURE)
> Nonce misuse resilience: Security is provided for messages encrypted with non-repeated (fresh)
> nonces (correctly encrypted messages). […] Nonce misuse resistance: Security is provided for all
> messages that were not encrypted with the same nonce value more than once. […] Nonce misuse
> resilience follows from nonce misuse resistance. Nonce misuse resistance does not follow from
> nonce misuse resilience.

> [A-rfc9771-aead-properties-2025]:§4.3.10 (relevance: -0:SUSPECT)
> An AEAD algorithm provides data integrity even if plaintext is released for every ciphertext,
> including those with failed integrity verification. Security notions: INT-RUP. […] In the
> provided definition, we only consider integrity in the RUP setting, since confidentiality, in
> the usual sense, is unachievable under RUP.

> [A-rfc9771-aead-properties-2025]:§5 (relevance: -0:SUSPECT)
> When specifying security requirements for an AEAD algorithm in an application, it SHOULD be
> indicated, for every required security property, whether only integrity or confidentiality is
> necessary. […] In an application, the requirements for additional AEAD properties SHOULD be
> highly motivated and justified, and all trade-offs should be carefully considered.

## Not pursued, and why

- Library and crate selection, per the front's scope. Implementations noted only where a spec
  named one: a Go implementation of the chunked-encryption scheme, and Tink's own streaming AEAD.
- The commercial field-level-encryption literature. Every general search for per-field versus
  per-record tradeoffs returned vendor marketing; the one apparently serious journal treatment
  (a 2026 *Journal of Information Security and Applications* paper on selective encryption of
  sensitive fields in structured logs) is paywalled and only its abstract was reachable, so it was
  not registered — an abstract is not a source. It is the single most on-point title found and is
  worth acquiring out-of-band.
- Searchable/property-preserving encryption beyond what was needed to establish the digest
  hazard. The design does not need to query ciphertexts, so order-revealing and deterministic
  schemes are out of scope except as a warning about deterministic artefacts.
- Formal verification of the composed construction (Tamarin/ProVerif-style symbolic analysis).
  Surfaced repeatedly as the recommended remedy for exactly this class of failure but is a
  research programme, not a design input for this round.
- Post-quantum considerations. Symmetric AEADs are Q1-secure; nothing here changes.
