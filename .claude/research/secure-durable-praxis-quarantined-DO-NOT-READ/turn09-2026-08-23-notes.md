# turn 9 — 2026-08-23 20:31:41 CDT

Front: `front-transport-red-lines`. Which of this round's at-rest conclusions may be shared with a
live transport, and — more valuably — which must never be, however convenient the reuse looks.

## Findings

- `fin-prefix-contract-inverts-hard` — The at-rest reader contract (valid prefix of N units, then
  damage) is not merely wrong on a wire, it is the *definition* of the truncation attack class, and
  a shipped protocol was broken by exactly this shape as recently as 2023. Suffix truncation cannot
  be prevented at all in an interactive protocol; it can only be *detected* by an explicit
  end-of-communication unit. Prefix truncation is a wholly new class with no at-rest analogue.
- `fin-error-predictability-is-the-law` — There is a formal name for the failure-reporting red line:
  ERR-PRE, error predictability. The classical composition theorem (IND-CPA ∧ INT-CTXT ⟹ IND-CCA)
  provably *fails* for a channel with multiple distinguishable decryption errors; it is rescued only
  by requiring that every error be efficiently computable from data the adversary already holds. A
  reader that says "no key for this document" versus "wrong key" is by construction not predictable
  from public data, because the distinction depends on the secret.
- `fin-ordinal-origin-is-attackable` — Nonce-from-ordinal transfers, but only with three additions
  the file does not need: the ordinal must be *reset to zero* at every key change, the reset point
  must be inside the authenticated transcript, and — if delivery is lossy — the ordinal must be
  transmitted and paired with a replay set. Terrapin is precisely the failure of the second: SSH
  derived nonces from a counter whose origin an attacker could move.
- `fin-two-directions-two-keyspaces` — A file has one writer. A session has two, and every mature
  design derives a *separate* key and nonce space per direction, with the wrong-direction use
  called out as catastrophic. The at-rest construction has no notion of a reverse direction, so
  reuse silently gives both peers one keystream.
- `fin-plain-projection-is-a-downgrade` — A negotiated fallback-to-plaintext on a wire is the
  STARTTLS shape, whose whole vulnerability class is defined as "issues which would not exist if
  implicit TLS had been used exclusively", and whose sharpest result is that *offering* the weak
  mode endangers peers who chose the strong one when the two share identity or key material.
- `fin-compression-is-notoriously-worse` — Same three-part precondition as at rest, but the wire
  adds adaptivity: the attacker drives thousands of chosen requests and averages away length-hiding
  noise at one-over-root-N. The BREACH authors state they know of no clean practical fix.
- `fin-decision-identity-not-prohibited` — The inherited "must never cross a wire" is wrong as
  stated, and so is sending the public re-derivable digest. Two independent shipped answers agree:
  the wire identity is a *client-minted random token*, and the content-derived part stays with the
  side that already holds the content.
- `fin-rederivability-unlinkability-truly-exclusive` — The structural claim survives: no
  deterministic function of the same inputs can be both re-derivable and unlinkable. But
  *verifiability* and unlinkability can coexist — Privacy Pass does it — at the price of an
  interactive blinded issuance and a separated context. That is the honest option list.
- `fin-glue-is-the-named-root-cause` — Two peer-reviewed papers state the glue mandate in their own
  words: Terrapin says "the fault is not with ChaCha20-Poly1305 as an AEAD scheme but with its
  integration"; ALPACA says the violation "is an emergent property due to the attacker's ability to
  recombine the components in an unintended way", measured at 114,197 exploitable servers.
- `fin-whole-package-still-leaves-seams` — RFC 9180 enumerates six properties it deliberately does
  not provide and hands back: message order, message loss, downgrade prevention, replay protection,
  forward secrecy, plaintext-length hiding — and declines to specify a wire encoding at all. That
  is the seam count for the most complete single package available.
- `fin-retention-couples-to-the-wire` — Two shipped protocols retain local material whose deletion
  permanently destroys a wire guarantee (Signal's skipped message keys; Privacy Pass's redeemed-token
  set). Both bound retention in *both* directions and both make the bound a published, deterministic
  property rather than a secret.
- `fin-key-reuse-across-modalities-unproven` — The most permissive first-party statement available
  (HPKE, on one key pair across all four modes) says security follows from domain separation *and*
  in the same paragraph that there is no formal proof for parallel use. Noise flatly says reusing a
  static key outside Noise "would require extremely careful analysis".
- `fin-plaintext-skeleton-worse-in-transit` — The readable skeleton is the at-rest product. On a
  wire, every mature design does the opposite: Signal encrypts the header so an observer cannot
  order or group messages; libsodium encrypts the tags so sequence boundaries do not show; Noise
  recommends padding for length hiding and requires ciphertexts indistinguishable from random.
- `fin-truncated-tags-stop-being-free` — At rest, truncating an integrity digest is free. On a wire
  the adversary "can receive rapid feedback on whether guesses for authentication data are correct",
  which is why Noise fixes tags at 128 bits and Signal caps truncation at 64 bits with analysis.

## The red lines

Written so a future builder can be handed them directly. Each names what would be reused, why it
looks safe, and what breaks.

### `red-never-reuse-the-prefix-reader`

**Reuse candidate:** the total, bounded reader that reports "N valid units, then damage at unit
N+1" and returns the prefix as report material.

**Why it looks safe:** it is correct, it is total, it is already fuzzed, and returning what you
could parse is obviously more useful than returning nothing.

**What breaks:** on a wire, "N valid units then damage" is what a truncation attack looks like from
the inside. The adversary chooses N. Two consequences, both bad: the peer acts on a prefix the
sender never meant to end there, and — because the at-rest reader is designed to *keep going* past
damage where it can resynchronise — the peer keeps accepting units after an adversary-chosen cut.
Terrapin is the shipped instance: an attacker deleted chosen units from the *start* of an SSH
channel and neither peer noticed, disabling a keystroke-timing countermeasure. Note also that
suffix truncation is unpreventable in any interactive protocol; the only defence is an explicit
end-of-communication unit that both sides require. The at-rest terminator unit is the right
mechanism and it must become *mandatory and checked in both directions* (libsodium's file example
errors both on "stream ended before the file" and "file ended before the stream").

**Instruction:** the transport reader is a different reader. On the first authentication failure it
stops permanently, discards the message, discards the partial state, and does not resynchronise. It
never surfaces a prefix as a result. It requires a terminator before treating a sequence as
complete. Share the *grammar* with the at-rest reader if you like; do not share the recovery
policy, and do not let one code path serve both with a flag.

### `red-never-reuse-the-key-diagnostics`

**Reuse candidate:** the reader's key-failure vocabulary — "no key for this document", "wrong key",
"unknown key version" — which front 4 correctly designed as facts about keys rather than about
corruption.

**Why it looks safe:** it is already careful. It deliberately refuses to say *why* derivation failed
at any granularity finer than "this key does not open this document", and it exists to stop an
operator concluding their archive is corrupt.

**What breaks:** at rest, the reader answers once, to its owner, about bytes fixed before the
question was asked. A peer answers repeatedly, to a party choosing the inputs. That is the
adaptive-oracle setting, and the formal consequence is exact: the composition theorem that gets you
chosen-ciphertext security *does not hold* when a channel can emit multiple distinguishable errors,
and is rescued only by error predictability — every error must be computable from the ciphertext
stream and public data alone. "This key does not open this document" is not computable from public
data. Neither is timing. HPKE names the mechanism without hedging: the oracle is "any other
recipient behavior that is observably different when using a wrong PSK", and it is what makes a
partitioning-oracle attack recover a low-entropy secret in roughly m + log k queries.

**Instruction:** a transport peer has exactly one externally visible failure behaviour, and the
preferred one is silence. WireGuard's rule is the model: an unauthenticated peer gets no response
at all, the responder is "silent and invisible". Diagnostics go to the *local* operator's log, never
into a response. Do not carry the at-rest error enum onto the wire even as an internal type that
someone might later serialise.

### `red-never-share-one-keyspace-across-directions`

**Reuse candidate:** the document key plus base nonce plus per-unit ordinal, applied to a session.

**Why it looks safe:** it is one derivation, one salt, one seam. Adding a second looks like
duplication.

**What breaks:** a file has one writer and a canonical order. A session has two writers who both
increment. If both directions share a CipherState the two peers will encrypt different plaintexts
under the same key and nonce, which Noise calls "a catastrophic security failure" — and it says so
about a mode that *is* safe when the protocol strictly alternates, which is exactly the kind of
precondition a later engineer deletes. Every mature design splits: Noise's Split() returns two
CipherStates; WireGuard derives sending_key and receiving_key separately with independent counters;
HPKE says the sender's context MUST NOT be used for decryption and tells you to Export separately
labelled keys per direction.

**Instruction:** two keys, two counters, two contexts, derived with distinct labels, from the
moment the session exists. Never a shared context with a direction bit.

### `red-never-let-the-ordinal-origin-be-negotiated`

**Reuse candidate:** nonce = base_nonce XOR ordinal, with the ordinal counted left-to-right.

**Why it looks safe:** it is the same construction TLS 1.3, HPKE, and WireGuard all use. It genuinely
does transfer — see the green lines.

**What breaks:** in a file the ordinal starts at zero by construction and nothing before it exists.
In a session the ordinal has a *history*, and if any part of that history is unauthenticated the
attacker moves the origin. That is Terrapin exactly: SSH never reset sequence numbers when
encryption keys were activated, and the handshake did not authenticate every message, so injecting
ignorable messages shifted the counter and let the attacker delete a matching number of protected
units without detection. 71.6% of scanned servers supported an affected mode. The fix adopted
upstream was to reset the counter to zero on key activation and to refuse unexpected messages
during key exchange.

**Instruction:** the counter resets to zero at every key installation, the reset point is inside the
authenticated transcript, and counter exhaustion terminates the session rather than wrapping. If
the underlay can lose or reorder, the counter must additionally be transmitted per message and
paired with a replay window checked *after* tag verification — at which point the inherited rule
"a gap in the ordinal is damage" inverts to "a gap is normal and a repeat is an attack".

### `red-never-put-a-plain-projection-on-the-wire-as-a-mode`

**Reuse candidate:** the plain projection — a narrower type that cannot represent
opaque-value-capable fields — offered as a wire mode for peers that cannot do the rich one.

**Why it looks safe:** front 3 already got the hard part right. It is a different type, selected
before the first byte, irrevocable for the run. That is precisely the discipline STARTTLS lacks.

**What breaks:** at rest, "selected before the first byte" is a local decision by a process that
knows its own configuration. On a wire the selection is a *negotiation*, and a negotiation an
attacker can see is a negotiation an attacker can edit. The measured toll of exactly this shape:
only 3 of 28 clients and 7 of 23 servers were clean. Worse, the second-order result — offering the
weak mode endangers peers who chose the strong one, because implementations share certificates and
state between the two paths. And the mechanism generalises beyond negotiation: buffered bytes from
the unprotected phase cross into the protected phase and become indistinguishable from protected
data.

**Instruction:** if two postures must exist on a wire they are two *endpoints*, not two modes of one
endpoint, and they share no key material, no identity, and no buffer. If a downgrade path is
genuinely unavoidable, the pre-decision code is a separate routine holding a stack-local buffer and
the socket and nothing else, everything after behaves as if the strong mode had been used from byte
zero, and every byte of the negotiation is hashed into the transcript (Noise's prologue) so an edit
fails the handshake. Prefer indistinguishability over negotiation: Noise's answer to "which of
three handshakes is this" is to pad all of them to a constant size and use trial decryption.

### `red-never-compress-anything-on-the-wire-either`

**Reuse candidate:** none, if the at-rest prohibition is carried across. This red line exists to
stop someone re-deriving the precondition and concluding the transport case is milder because the
bytes are ephemeral.

**Why it looks safe:** transport payloads are transient, a network appliance wants throughput, and
the at-rest reasoning was about a file sitting on disk.

**What breaks:** it is worse, not milder, and by a measurable factor. The three ingredients are the
same, but the wire supplies adaptivity: the attack is active and online, proceeds byte-by-byte, and
coerces thousands of chosen requests. Length-hiding padding — the obvious mitigation — fails
because repeating a guess and averaging shrinks the noise as one-over-root-N. The BREACH authors
say plainly they know of no clean, effective, practical fix, and that nothing about the channel is
special: any injectable payload sharing a compression context with a secret suffices. TLS removed
compression from the protocol entirely in response to this family.

**Instruction:** no compression anywhere in the transport path, including at any layer above or
below the encryption. If a separate content-addressed store ever compresses, its compression
context must contain only controller-side material and must never be shared with a context holding
host-influenced bytes.

### `red-never-cross-a-scope-with-a-scope-local-value`

**Reuse candidate:** the per-document salt, the per-document random tag used for within-document
equality classes, the per-document field tags, and the per-document salted key identity.

**Why it looks safe:** each derives its entire guarantee from never leaving its scope, and the
scopes look analogous — a document, a session. Both are bounded, both have a header, both have one
salt.

**What breaks:** crossing a transport *is* crossing a document boundary, so the guarantee is void by
definition, and the transport adds two failure modes the file does not have. First, a value that is
merely *not transmitted* still leaks: Noise's identity-hiding property 3 records that an attacker
can replay a recorded message to a new responder and learn whether two responders share a static
key, purely from whether the message is accepted. The per-document salted key tag, which is exactly
right at rest, becomes a same-peer oracle the moment a peer trial-decrypts. Second, a value that
does reach the peer becomes a forging capability: age's own author documents that a recipient who
can derive the file key can rewrite the file for the *other* recipients and recompute the header.

**Instruction:** every value crossing the wire is minted fresh for the wire, in wire scope, and is
never a value that also exists inside a durable document. Context binding for the wire must include
the dimensions a file does not have — both peer identities, the direction, the protocol name and
version, and the session — bound into the key-derivation label the way HPKE binds "HPKE-v1" plus a
prefix-free suite identifier, or the way Noise hashes a full protocol name as the first act.

### `red-never-reuse-key-material-across-the-two-modalities`

**Reuse candidate:** the per-user key file. It exists, it is already generated, rotated, and
trial-matched.

**Why it looks safe:** it is one key lifecycle to explain, one file to back up, one rotation story.

**What breaks:** nobody will prove it safe for you. Noise: a static key pair "should not be used
outside of Noise... would require extremely careful analysis to ensure the uses don't compromise
each other, and security proofs are preserved". HPKE is the most permissive first-party statement
available — one key pair across all four of its modes, safe *by construction* through domain
separation — and it says in the same paragraph that there is no formal proof for parallel use,
only for isolated modes. The 1998 chosen-protocol result that ALPACA cites foresaw exactly this for
reused key material. And the practical failure mode is not subtle: at rest the key protects a copy
that leaves the machine and cannot defend against same-user code; on a wire it is the sole
authentication of a remote party. Those are different security levels for the same bytes.

**Instruction:** separate root key material. If a single root secret is genuinely wanted, it is a
*derivation root*, and both uses derive through labelled expansion with prefix-free labels, neither
ever touching the root directly. Rotation policies are separate: retaining every key forever is
correct for reading old documents and is wrong for a wire, where old keys are a standing
impersonation risk.

## The green lines

Things that genuinely transfer, with the reason the reasoning survives.

- `green-flat-sequence-of-self-delimiting-units` — Survives. Every transport record layer examined
  is exactly this shape: a flat sequence of independently authenticated, self-delimiting units. It
  is what makes bounded decode provable and damage locatable in both modalities, and the reason is
  the same in both — no unit's parse depends on a later unit.
- `green-chunk-then-authenticate-before-release` — Survives, and is the *same* rule for the same
  reason. Never release plaintext from a unit before verifying its tag. At rest the motivating
  failure is EFail; on a wire it is every padding-oracle. The at-rest chunked construction was
  selected for a bounded streaming writer, and a bounded streaming writer is exactly what a
  transport needs.
- `green-derived-nonces-never-drawn` — Survives with the parameters in `red-never-let-the-ordinal-origin-be-negotiated`.
  HPKE, TLS 1.3, and WireGuard all compute the nonce as base XOR counter. The randomness seam stays
  touched once per key rather than once per message, which is the property that made it attractive
  at rest and is worth more on a wire where the seam is hotter.
- `green-key-commitment-is-required` — Survives and hardens. Standard AEADs do not commit to the
  key; at rest that yields a wrong plaintext instead of an error, which is bad. On a wire the same
  gap is what makes a partitioning oracle *efficient* — HPKE says so explicitly, citing the same
  partitioning-oracle result the earlier front used. Whatever key-committing construction is chosen
  at rest should be chosen for the wire, for a strictly stronger reason.
- `green-injective-context-encoding` — Survives verbatim. The requirement that the bound context be
  an unambiguously parseable encoding is stated identically in both modalities: HPKE hashes
  variable-length inputs to fixed width before concatenating; Signal says a length must be prepended
  "to ensure that the output is parseable as a unique pair". The fixed-width-plus-one-variable-tail
  shape front 2 chose is the shape the wire already uses.
- `green-domain-separation-through-labels` — Survives and is the single most transferable piece.
  Noise hashes a full protocol name (`Noise_XX_25519_AESGCM_SHA256`) as the first act; HPKE prefixes
  every derivation with a version literal and a prefix-free suite identifier. Both say the label
  must uniquely identify the whole construction *for every key it is used with*. This is the
  mechanism that would make shared root key material defensible if it is ever wanted.
- `green-terminator-unit-closes-truncation` — Survives as *the* mechanism, upgraded from good idea
  to mandatory. Noise: "Applications should include explicit length fields or termination signals
  inside of transport payloads to signal the end of an interactive session." libsodium ships it as
  TAG_FINAL and checks it against end-of-file in both directions. The at-rest terminator-unit design
  is directly the right shape.
- `green-never-choose-a-backend-from-untrusted-input` — Survives and widens. Front 4's rule that the
  document must never choose which key backend runs extends to: nothing a remote peer sends may
  select an algorithm, a key, a key backend, or a retention policy. Unit 42's fourth technique is
  this exact failure in production — an attacker who can change which key encrypts the record makes
  the record unreadable.
- `green-never-derive-a-nonce-from-document-end` — Survives. Only prefix-determined context may be
  bound. A wire has no "end" at all until it has one, so the rule is unchanged and, if anything,
  more obviously necessary.

## The amber cases

Same component, different parameters or mode on each side. Stated so a later reader cannot collapse
them. Each of these is a place where "we use the same library" is true and "we use the same
construction" is false.

| Component | At-rest parameterisation | In-transit parameterisation | What collapsing them costs |
|---|---|---|---|
| `amber-chunked-stream-construction` | One writer, one pass, canonical order, no loss tolerance needed, seekability optional | Two writers with separate states, ordinal reset per key, explicit ordinal if lossy, replay window, hard message cap, mandatory terminator | Terrapin (channel integrity gone) or nonce reuse |
| `amber-nonce-derivation` | base XOR ordinal, ordinal from position in file, exhaustion impossible in practice | base XOR counter, counter zeroed per key, exhaustion is a session-kill error, counter authenticated | Silent nonce reuse across a rekey |
| `amber-rekey-trigger` | Not needed; one document, one key era | Time-driven and count-driven, decoupled from message content so loss cannot desynchronise, and the trigger must be identically implemented on both sides | libsodium's untagged rekey requires "the exact same stream location" — a desync bug that is silent until it is a decryption failure |
| `amber-error-surface` | Rich, distinguishable, human-facing — the debugging product | Exactly one behaviour, preferably silence; errors must be predictable from public data | Decryption oracle |
| `amber-integrity-tag-length` | Truncate freely; the adversary gets one offline attempt | 128 bits fixed; 64 bits is the floor and only with analysis, because the adversary gets "rapid feedback on whether guesses for authentication data are correct" | Online forgery |
| `amber-associated-data-channel` | Empty; context lives in the KDF info string | The standard stream-channel construction puts the ordinal in the AD, and HPKE recommends per-message varying context go in `aad` while per-context information goes in `info` | Either an unauthenticated ordinal, or redundant per-message KDF work |
| `amber-structural-visibility` | Plaintext skeleton is the product: record names, counts, enums, ordinals | Encrypt the header and the tags; pad for length hiding; ciphertexts indistinguishable from random | The skeleton names hosts and orders operations to a population observer |
| `amber-identity-value` | Public collision-resistant digest over an injective tuple, deliberately re-derivable | Client-minted random token, single-use where possible, expiry owned by the minter | See below |
| `amber-key-rotation-policy` | Retain every key forever; the reader trial-matches | Retire aggressively; every live configuration partitions the anonymity set and every retained key is a standing impersonation risk | Privacy Pass states this as an explicit trade-off between privacy and security |

## The decision-identity resolution

The inherited red line was: *a public collision-resistant digest, deliberately re-derivable with no
secret, must never cross a wire.* Resolution below.

`res-prohibition-is-wrong-digest-also-wrong` — Both halves are wrong. The prohibition is wrong
because the peer already holds most of the preimage; the reasoning in the brief is sound, and
nothing found here contradicts it. But sending the public digest is *also* wrong, for a reason the
prohibition did not name: a deliberately re-derivable digest over largely-known inputs is a
**low-entropy, guessable identifier**, and the IETF idempotency-key draft names exactly that as its
security failure mode — "when an idempotency implementation allows low entropy keys, attackers MAY
determine other keys and use them to fetch existing idempotent cache entries, belonging to other
clients." An adversary who can guess a decision's inputs can query any host's guard for somebody
else's result.

`res-second-identity-minted-for-the-wire` — The answer is a second identity, and two independent
shipped systems agree on its shape:

1. **It is client-minted and random, not derived.** The idempotency standard recommends a UUID or
   similar random identifier and never a digest of the request.
2. **The content-derived part stays with the side that already has the content.** The same document
   separates the *key* (client, random) from the *fingerprint* (resource-computed, from the payload
   it already holds) — so a host confirms "same decision" without the controller having to publish
   a matchable value.
3. **The host composes it with something only the host knows.** Recommended verbatim: "a composite
   key MAY be implemented by combining the idempotency key sent by the client with other client
   specific attributes known only to the resource."
4. **Single-use beats stable.** TLS 1.3's answer to exactly this problem was to replace one stable
   resumption identifier with a batch of PSK identities so that each contact uses a different one,
   and the measurement paper is explicit that this "protect[s] against a correlation of single user
   sessions by a passive network-based observer".
5. **The minter owns the expiry, not the peer.** The prolongation attack works because a server can
   renew an identifier and extend the linkage window; the countermeasure is that the client sticks
   to the expiry of the identifier it first minted.

`res-linkability-price-is-measured` — The cost of getting this wrong is quantified rather than
theoretical: a seven-day identity lifetime made 65% of users permanently linkable; twenty-four
hours dropped it to 1.3%. Whatever lifetime a wire identity gets, that is the correlation window,
and it should be chosen against that curve rather than against convenience.

`res-structural-tension-holds-with-an-escape` — The brief's structural point stands: any
deterministic function of the same inputs yields the same output, and that sameness *is* the
linkability, so re-derivability and unlinkability cannot coexist in one value. What the corpus adds
is that a *weaker and sufficient* pair can coexist: **verifiability** and unlinkability. Privacy
Pass tokens "can be validated by anyone with the per-Issuer key but cannot be linked to the content
of the token request or token response". The price is an interactive blinded issuance protocol and
a separated context — real cost, but it means the option list is three items, not two: public
digest (rejected), random per-peer token (recommended), blinded verifiable token (available if the
host must verify provenance without the controller being linkable). A fourth, cheaper point exists
if the requirement is per-peer unlinkability rather than global: a *pairwise* derived identity —
deterministic per peer, unlinkable across peers — which is what OpenID Connect's pairwise subject
identifiers do. That was not read in full and is flagged as unpursued below.

`res-price-the-retention-coupling` — Confirmed and shipped. Privacy Pass: "Origins that send token
challenges that are compatible with cached tokens need to take precautions to ensure that tokens
are not replayed. This is typically done via keeping track of tokens that are redeemed for the
period of time in which cached tokens would be accepted." So yes — once an identity crosses a wire,
somebody must retain a set keyed by it, and the retention window is *derived from* the published
acceptance window. The good news is that this makes the rule mechanical rather than a judgement:
retain exactly as long as you will accept, publish the acceptance window, and the store's new
retention rule follows from a number you already had to publish.

## The previous front's four retention-and-wire questions

`ret-deletion-ledger-may-not-travel-to-a-target` — The ledger may cross a wire *to a trusted audit
sink*; it may not cross to a semi-trusted managed host. The distinction is direction and trust, and
both halves are in the corpus. Forwarding is the canonical mitigation for local record tampering —
"automatically forward events to a log server or data repository to prevent conditions in which the
adversary can locate and manipulate data on the local system... minimize time delay on event
reporting to avoid prolonged storage on the local system". But the mirror-image attack is equally
documented: an adversary who can change the log destination gets a real-time feed of the victim's
environment. Dorc's remote hosts are the *targets*, not an audit sink; sending them a map of what
the operator stopped keeping gives them the second thing and none of the first. If the ledger ever
does travel, MITRE's other mitigation applies without exception: "obfuscate/encrypt event files
locally **and in transit** to avoid giving feedback to an adversary" — which also means the
plaintext-skeleton design does not survive the trip.

`ret-policy-must-not-be-remotely-reachable` — No. Retention policy must not cross a wire and must
not be influenced by a remote host or a shared configuration, and the evidence is a demonstrated
attack family rather than a hypothetical: five of the seven Unit 42 techniques change *policy or
routing* rather than records — stop logging, delete the destination, delete the router, swap the
encryption key and revoke access, redirect the feed. Note the fourth in particular, because it is
front 4's rule violated at the policy layer: an attacker who can change which key encrypts the
record destroys it without touching it. The defensive pattern both major clouds converged on is
worth copying: the baseline retention is a *locked, immutable* channel the ordinary control plane
cannot reach, and only the optional, exported copy is configurable. If Dorc ever gains remote
configuration, retention belongs on the locked side. This also closes the decoy-injection concern
directly: count-shaped policies were already ruled out, and remote reachability would have made
them remotely attackable.

`ret-wire-must-not-assume-local-durability` — There is a plausible wire protocol that assumes it,
and there is a shipped precedent for how to bound it. The remote idempotency guard is the case: if
a host answers "I already applied decision D" by reference to a local controller-side record, and
retention removed that record, the two ends disagree silently. The precedent is Signal's skipped
message keys — a wire protocol whose correctness depends on locally retained material, where
retention is bounded in *both* directions at once: unbounded retention is a denial-of-service
vector a malicious peer can drive by inducing storage, and long retention is a compromise hazard
because "the lost messages may have been seen (and recorded) by an attacker... The attacker can
compromise the intended recipient at a later time to retrieve the skipped message keys." The rule
that falls out: any state a wire protocol depends on must have an explicit, published, bounded
lifetime that both ends can compute, and the protocol must have a defined behaviour for "past the
bound" that is not silent disagreement. This is free to design now and expensive later.

`ret-grace-should-be-public-uniform-and-deterministic` — Publish it, and make it identical across
deployments. The instinct that publishing tells an adversary how long to wait is right in isolation
and wrong in aggregate, because a *non-uniform* retention policy is worse: Signal's fingerprinting
section instructs implementations to "use identical limits for the number of skipped message keys
stored, and identical deletion policies... Deletion policies should be based on deterministic events
(e.g. messages received), rather than time" — precisely so the policy does not identify the
deployment. Privacy Pass makes the same point in the general form: every distinguishing bit
partitions the anonymity set. So: one grace value, documented, deterministic, the same everywhere.
The adversary learns a constant they could have read in the manual; a per-operator value would have
told them which operator they were looking at. The front-8 constraint — grace must exceed the
longest plausible run — is unaffected and remains the binding one.

## The counter-thesis at full strength

Stated as strongly as the corpus supports, not strawmanned.

`ctr-two-stacks-doubles-the-review-surface` — Two independently-designed cryptographic stacks means
two key schedules, two nonce disciplines, two damage models, two conformance-vector suites, and two
sets of reviewers who each understand half. The project's own posture ruling is that
not-invented-here security glue is the dominant failure source; a second stack is, definitionally, a
second full set of seams. There is no evidence in this corpus that two half-reviewed stacks beat one
well-reviewed one.

`ctr-mature-designs-do-parameterise-one-construction` — This is not a hypothetical preference. It is
what the best-regarded designs actually do:
  - **libsodium** ships one construction whose own documentation offers it for both modalities in
    consecutive sentences: "securely send an ordered sequence of messages to a peer" and "encrypt
    files regardless of their size".
  - **Noise** is one framework instantiated into both one-way patterns (offered explicitly for
    "files, database records, or other non-interactive data streams") and interactive patterns, with
    the difference expressed as *machine-checkable validity rules* rather than developer discipline.
  - **HPKE** runs one key schedule across four modes, defines the single-shot API literally in terms
    of the multi-shot one, and permits one key pair across all four modes on domain-separation
    grounds.
  This is the strongest form of the argument: the discipline of a single well-parameterised
  construction used correctly in two modes is what mature systems demonstrably do, and the
  parameterisation is made *checkable* rather than left to judgement.

`ctr-the-counter-thesis-has-two-real-limits` — Both are on record and both come from the same
sources, which is why they are credible rather than convenient:
  1. **The permission is unproven.** HPKE's own text, in the same paragraph that permits key reuse
     across modes: "there is no formal proof of security at the time of writing for using multiple
     modes in parallel; [the analyses] only analyze isolated modes." Noise is blunter about reuse
     outside its own scope.
  2. **Accretion is itself the documented failure mode.** Terrapin's conclusion is that SSH's
     complexity "has increased over its 25 years of development to a point where the addition of new
     algorithms and features has introduced new vulnerabilities", and that the potential was present
     in the original specification. A single stack that grows a second modality is the shape that
     produced Terrapin. The STARTTLS result is the same lesson at a different layer: maintaining a
     second path alongside the strong one was the bug farm, and the second path contaminated the
     first.

`ctr-the-synthesis-that-survives-both` — One *library* and one *primitive set*; two *constructions*,
each named, each with its own conformance vectors, sharing no key material and no code path that
branches on modality. That satisfies the counter-thesis's real content (do not hand-roll a second
set of primitives; do not maintain two half-understood implementations) without satisfying the thing
that actually kills people (one code path with a mode flag that a later engineer collapses).
Noise's own structure is the existence proof that this is achievable: the shared part is the
framework, and the modality difference is a *name* — `Noise_N_...` versus `Noise_XX_...` — which
means a reviewer can see which one is in use without reading the call site.

## Readability versus security

`tension-real-structural-skeleton` — Genuinely in tension, and this is the sharpest instance the
round has produced. The plaintext skeleton is the at-rest debugging product and the round's central
justification for not encrypting whole files. Every mature transport design does the exact opposite:
Signal's header-encryption variant exists "so that an eavesdropper can't tell which messages belong
to which sessions, or the ordering of messages within a session"; libsodium encrypts its tags so
"encrypted streams do not reveal any information about sequence boundaries"; Noise recommends a
padding-capable payload format and requires ciphertexts indistinguishable from random. The
firefighter reading a whylog on their own disk and the observer watching a controller talk to twelve
hosts want the same bytes, and only one of them should get them.

`tension-real-error-detail` — Genuinely in tension, and it is the same tension the round already
knows, sharpened. Rich, distinguishable failure reporting is what makes a whylog worth having.
Predictable-or-silent failure is what keeps a peer from being an oracle. There is no construction
that gives both to the same audience over the same channel.

`no-tension-terminator-unit` — Loudly good on both axes. The mandatory terminator closes
truncation, gives the reader an unambiguous "this is the whole thing", and makes "I have a partial
record" a first-class, honest report rather than a guess. Keep it, make it mandatory in both
modalities, and check it in both directions.

`no-tension-flat-sequence-shape` — Loudly good on both axes and in both modalities. Readable,
scannable, bounded-decode-provable, damage-locatable, and it is the shape every transport record
layer already has. No cost was found anywhere.

`no-tension-injective-labels` — Loudly good. Labelled, prefix-free, injective context encoding costs
nothing, is trivially reviewable (you can read the label and know what it binds), and is the
mechanism that would let a shared key root be defensible. Readable *and* secure.

`no-tension-splitting-directions` — Loudly good. Two keys per session is more code but strictly
clearer code: a reviewer can see which direction a call site belongs to. The alternative — one
context with a direction bit — is both less readable and catastrophic when wrong.

`no-tension-error-goes-to-the-operator-not-the-peer` — Loudly good, and it resolves what looks like
a tension. The operator still gets the full diagnostic; it goes to the local log rather than into a
response. Nothing readable is lost; the only thing lost is the adversary's feedback channel.

## What I deliberately did not pursue

- `skip-datagram-versus-stream-modality` — I did not read DTLS 1.3 or QUIC in full. The
  datagram/stream distinction is covered adequately by WireGuard (replay window, loss tolerance),
  Noise §11.4 (out-of-order transport messages), and HPKE §9.7.1 (loss intolerance). If Dorc's
  transport is ever anything other than a reliable ordered stream over SSH, this needs its own pass;
  the anti-replay-window design in particular has parameters I have not priced.
- `skip-pairwise-derived-identifiers` — OpenID Connect's pairwise subject identifiers are almost
  certainly the cheapest correct answer for a *per-peer* wire identity (deterministic per peer,
  unlinkable across peers). I surfaced the mechanism but did not read the specification, so the
  recommendation above rests on the two sources I did read. One focused read would settle it.
- `skip-tls13-specification-in-full` — I did not read RFC 8446 end to end. Its 0-RTT anti-replay
  guidance is the one thing I would have wanted from it, and the replay conclusion is already
  supported independently by HPKE §9.7.3, the idempotency draft, and WireGuard's monotone timestamp.
- `skip-transport-package-selection` — Deliberately out of scope by the round's own standing rule:
  product-flavoured research runs last. I named constructions and specifications, never candidate
  crates.
- `skip-formal-channel-notion-zoo` — I read the definitions that matter (INT-PST, INT-CST, IND-CCFA,
  ERR-PRE) but did not chase the surrounding literature on buffered or fragmented decryption. The
  conclusions here do not depend on the finer distinctions.

## What the final front should carry

- **Count the seams against the six HPKE names them.** Any candidate package should be scored on how
  many of message ordering, loss detection, downgrade prevention, replay protection, forward
  secrecy, and length hiding it leaves in our hands — because the most complete package available
  leaves all six, plus the wire encoding.
- **Never choose a package *because* it also serves transport.** This front's whole point is that
  the transport parameterisation differs on nine axes. A package that makes both easy is fine; a
  package chosen for dual use, with one code path, is the failure this front exists to prevent.
- **Prefer a package whose modality difference is visible in a name.** Noise's protocol-name
  discipline and HPKE's suite identifier both make the construction legible at the call site. That
  is a real, checkable review property and it should be a ranking criterion, not a nicety.
- **Prefer key-committing constructions, now for two reasons.** The at-rest reason (a rotated key
  yielding a different valid plaintext) and the transport reason (partitioning oracles get
  efficient without it) both point the same way.
- **Check whether the candidate's streaming construction chains state on prior ciphertext.**
  libsodium's does (`n <- n ^ mac[0..8]`), which forbids seeking and resumption. That is acceptable
  at rest if the reader always starts at the beginning and is a hard constraint for anything
  resumable. It is not visible from a feature list.
- **Ask what the candidate does on a decryption failure, and whether it is configurable.** The
  correct at-rest answer and the correct transport answer are different, and a package that offers
  only one is a package that will be misused in the other modality.
