# Loom harness alternatives — survey

Scope: should an in-house Rust CLI acceptance-test harness (txtar-style case files,
bless flows, PATH-shim mock stubs, POSIX-sh floor, Windows+*nix, `cargo test`
integration) adopt/wrap an existing tool instead of continuing to grow its own.
No decision made here — spectrum only, human decides.

## The mock-stub half, specifically

No surveyed tool is simultaneously: (a) Rust-native/`cargo-test`-embeddable, (b) POSIX-sh-shimmed (not a language-specific IPC layer), and (c) argv-recording-with-plan-verification. The three partial answers:

1. **bats-mock** [A-batsmock-readme-2026] — closest *mechanism* match (PATH symlink to a binstub, per-invocation run-file log, plan verified at `unstub`) but is bash-locked, disqualified by the brief's own POSIX-sh-floor concern.
2. **ShellSpec `Mock`** [A-shellspec-site-2026] — closest *ergonomics* match (declarative, scope-released, POSIX-sh-portable including Windows via busybox-w32) but is a canned-output stub, not an argv-assertion spy, and it's a whole-DSL replacement rather than a library your Rust harness calls.
3. **cmd-mox** [A-cmdmox-readme-2026] — closest *cross-platform-claim* match (explicitly Linux/macOS/Windows via named pipes) and closest to full mock/stub/spy vocabulary, but it's Python, outside `cargo test`, and its Windows claim is single-source/unverified here.

None of these are "vendor the crate and stop hand-writing stubs." The realistic move, if any, is porting the *design* (PATH-shim binstub + JSON/text argv log + plan-verification, à la bats-mock, done in POSIX sh or generated by the Rust harness) rather than depending on any of these three.

## Forward-features analysis: what mature frameworks ship that this harness will predictably want

Cross-referencing trycmd/snapbox, insta/cargo-insta, ShellSpec, and testscript, the recurring feature set beyond MVP golden-testing:

- **Interactive review UI for bless updates** — cargo-insta's `cargo insta review` (accept/reject/skip per-snapshot, diff toggle) [B-cargo-insta-review-2026] is materially better UX than a blind `overwrite` env-var. The brief already wants "case-by-case review" — this is the one place an existing tool is *ahead* of a typical in-house bless flow, not just parallel to it.
- **Declarative fake-command registration** — Go testscript's `Cmds` map [A-goInternal-readme-2026] is the cleanest prior-art for "case file declares a fake `dpkg`, harness wires it up" without per-case boilerplate.
- **Sandbox/scrubbed-PATH mode as a first-class toggle** — ShellSpec's "Sandbox mode" (empty `PATH` except mocks, forces every external call through a mock or explicit escape-hatch) [A-shellspec-site-2026] is a sharper version of "scrubbed deterministic env" than a manually-cleared `PATH` string.
- **Tiering: skip/xfail/pending** — ShellSpec's pending/quick-mode red-green-refactor loop, sharness's `test_expect_failure`, bats' `skip` — near-universal in mature harnesses, notably *absent* from the trycmd/snapbox/insta family (they're closer to pure golden-diffing, no first-class xfail concept surfaced in the docs read this pass).
- **Timeouts per-case** — shelltestrunner and crok (`%TIMEOUT`) both have this; not seen in trycmd/insta.
- **Retry/flake-tolerance blocks** — crok's `retry{}` is notable; nothing else surveyed has it as a primitive (most mature CI-adjacent tools push this to the CI layer instead).
- **Env-matrix / parameterized runs** — ShellSpec's `Parameters`/`Parameters:matrix` is the most developed version of this; testscript supports env vars per-script but not matrix expansion natively.
- **Interactive-TTY coverage** — solved only by rexpect (Windows-weak) among Rust options, or ShellSpec/bats indirectly via subshell tricks; **this is a real gap for a Rust-only stack** and the brief should treat "someone eventually wants to test a TTY-prompting command" as a live future-need, not hypothetical.
- **Tagging/filtering** — libtest-mimic (already in use per the brief) already gives filtering; tagging is more of a ShellSpec/bats-core feature (`--tag`), less critical since `cargo test`'s own filter substring often suffices for a workspace this size.

**Is rolling-your-own a feature treadmill?** Yes, roughly the six items above (review UI, declarative fakes, sandbox-PATH toggle, skip/xfail, timeouts, retry) are the concrete next asks, in rough order of "how soon a real case will need it": skip/xfail and timeouts are typically the first pain (a case that's flaky under CI load, or a known-broken oracle), review UI is the next quality-of-life want once case count grows past ~30-50, retry/env-matrix are further out. None of the three cargo-test-embeddable candidates (trycmd, snapbox, insta) caps more than 1-2 of these six — they're golden-diffing engines, not full acceptance-test frameworks. The two tools that *do* cap most of the list (ShellSpec, testscript) are respectively a foreign-DSL non-Rust framework and a Go-only reference — neither is adoptable as a dependency, only as a design source.

## Recommendation spectrum

No decision — options ordered roughly weakest-to-strongest intervention:

1. **Keep rolling, mine designs.** Continue the in-house harness; borrow testscript's `Cmds`-map shape and bats-mock's plan/run-file mechanism for the stub half, and ShellSpec's sandbox-PATH-toggle idea for the env half, all reimplemented natively in Rust/POSIX-sh. Zero new dependencies, full control, but the six forward-features above are still owed as future work.
2. **Wrap-or-vendor snapbox for the diffing/bless engine only**, keep the case-file format, PATH-stub mechanism, and env-scrubbing fully in-house. Snapbox is MIT/Apache, well-maintained, 10M+ downloads, and is explicitly designed to be a building block ("flexible enough to build your own test harness like trycmd") — this is the lowest-risk adoption, displacing only the byte-diffing/golden-rewrite plumbing, not the case-file or mock-stub design that's the actual differentiator here.
3. **Adopt trycmd wholesale for the pure-snapshot subset of cases** (those with no PATH-stub involvement), and keep the in-house harness only for stub-heavy cases. Splits the test suite into two harnesses/two `cargo test` targets — real maintenance cost, but offloads a chunk of golden-file boilerplate to a maintained, widely-used tool.
4. **Adopt cargo-insta's review-UI pattern (not the crate) for the bless flow**, independent of any other decision — this is a UX upgrade orthogonal to the case-file/mock-stub questions and could be lifted regardless of what else happens.
5. **Do not adopt bats-core/bats-mock/sharness/cram/shelltestrunner directly** — bash dependency (bats/bats-mock), GPL licensing (cram, sharness likely, shelltestrunner confirmed), or external-tool-outside-cargo-test friction (sharness, shelltestrunner) rule each out as a wholesale dependency; useful only as further design reference for the stub mechanism.
6. **Track cmd-mox and ShellSpec's Mock as the field matures**, without depending on either now — cmd-mox is the only tool found that claims to have already solved cross-platform (including Windows) argv-recording PATH-shim stubs, but it's Python, young, and its Windows claim wasn't independently corroborated this pass; worth a follow-up check if the hand-rolled stub boilerplate keeps growing, not worth a dependency today.

None of the surveyed tools is a "replace the whole harness" answer — the case-file-plus-PATH-stub-plus-bless combination the project has built doesn't exist prepackaged in the Rust ecosystem; the closest single-tool matches (ShellSpec for POSIX-mock ergonomics, testscript for the case-file/declarative-fake design, bats-mock for the stub-plan mechanism) are all non-Rust or bash-locked, so any adoption is necessarily partial (snapbox for diffing) or design-borrowing rather than dependency-taking.
